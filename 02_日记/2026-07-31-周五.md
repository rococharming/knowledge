# 跟踪日志

1、Windows 前置兼容修复

问题：

- `appmgr`无条件使用 Unix 专属的`DirBuilderExt::mode`
- `skia-safe`无条件使用 Unix 专属的 `RawFd`

修复：

- 使用`#[cfg(feature = "drm")]`限制 `RawFd`导入

2、Windows 分层 DLL 运行时

问题：

- 原`system_framework.dll`聚合整个 UI 运行时
- Rust 导出及 MSVC 导入库成员超出 65535 限制，触发`LINK1189`

修复：

- Windows 将运行时拆成 12 个指责明确的 DLL，最后通过轻量 `system_framework.dll`保持原有 API


## 为什么需要分层 DLL

原来的 `system_framework.dll`把UI、Skia、sgui、frontend、Rivo、系统服务等全部静态聚合到一个 Rust `dylib`。

Rust `dylib` 会导出大量 Rust 符号，并为 MSVC 生成对应的导入库成员。全部聚合后超出 PE/COFF/MSVC 单库 65535 个成员的限制，触发：

```
LINK1189: 超出 65535 对象的库限制
```


### 完整分层架构

分层串联 DLL，让每个上层 DLL 动态依赖下层 DLL。应用最终只引用最后的`system_framework.dll`，Windows 递归加载整条依赖链。





# 总结

Windows 的 rust-ui 跑不起来的原因是原来的 `system_framework.dll`太大了。它作为单体 Rust dylib 聚合并重新导出了整个 UI 运行时依赖树，导出符号约 175189 个。

但 Windows DLL 导入/导出机制无法正常承载。

为什么 MSVC 不行：

MSVC 在生成 `system_framework.dll` 的 import library 时失败：

```
LINK1189: 超出 65535 对象的库限制
```

链路：约 17.5 万个导出 -> 生成 .lib import library -> 库成员数量超过 65535 -> LINK1189

也就是说，MSVC 甚至还没成功生成最终的 DLL，就已经在 DLL import library 阶段终止。即使尝试绕过 `.dll.lib`，大量导出面还是会撞 Windows PE 导出/ordinal 相关限制。

为什么 GNU 也不行：

GNU 只是把失败后移了，同样不能解决问题。

当前 GNU 路线还有几个问题：

- QuickJS MinGW 兼容问题
- Skia MSVC ABI 和 GNU ABI 不兼容（当前仓库 Skia native lib 是 MSVC ABI）
- 即便重新构建 MinGW ABI 的 Skia
- system_framework 仍然有 17.5 万的导出
- GNU ld 在 65536 个导出会失败，export ordinal too large
