# 跟踪日志

**一、统一 --app 路径**

直接运行 `uipreviewer --app <目录>`时，JS 和 Rust 都会创建软链接。

直接启动（没有`--session-data-root`）时：

```shell
uipreviewer --app /path/to/app
```

两类应用共用下面流程：

```
--app 目录
  ↓ 读取 manifest.json，得到 package
  ↓
<资源根目录>/data/app/<package>  ──软链接──>  /path/to/app
  ↓
PMS 注册 package，AMS 以 package 启动
```

BDB 时路径不同，BDB 会为每一个 UI 预览窗口分配一个 session_root 目录

**二、热更新实现**

Rust Native 应用的`restart-app`热更新策略：Previewer 窗口不重启，只把里面运行的 Rust App Generation 换成新的一代。

1. 同一条 BDB `launch`发现已有同一 Session 后，转为 `preview.update`，不新建进程、窗口或 session。
2. Runtime 校验 Native app、package 未变、产物确实更新；把新一代应用暂存到`session_root/generations/<N>/<package>`，然后更新 Preview 注册，并把新 dylib 拷贝成唯一文件名，例如 `libapp-generation-2.dylib`，再 `dlopen` 预加载。
3. UI 线程串行执行重启式切换：
    `旧 App on_stop` → 销毁旧路由/根节点与运行时状态 → `旧 App on_destroy` → 保留旧 dylib handle（不 `dlclose`）→ 安装新 App → `新 App on_create` → 从 manifest 入口重新挂载页面 → `新 App on_resume`。
4. 成功不是收到 RPC 就算完成，而是新 Generation 实际绘制出目标帧后才确认；这是防止“接口成功、界面仍是旧内容”的关键屏障。


```shell
session_root/generations/
  slots/a/<package>/
  slots/b/<package>/
  current   -> slots/a
  candidate -> slots/b

data/app/<package> -> ../../generations/current/<package>
```

| 层面    | Rust Native                           | JS                                           |
| ----- | ------------------------------------- | -------------------------------------------- |
| 更新内容  | 新 cdylib                              | 新 RPK / JS / manifest / 资源                   |
| 加载    | 唯一 dylib 名 + `dlopen`                 | 重新读取 RPK，重新创建 JS Application                 |
| 旧状态回收 | Native lifecycle、路由根、保留旧 dylib handle | JS 页面、DOM、路由、定时器、Promise/回调、服务与 QuickJS 应用状态 |
| 最大风险  | dyld 复用旧镜像                            | 旧 JS 异步任务或旧对象在新 App 创建后继续执行                  |
| 成功判定  | 新 Generation 目标帧                      | 同样应是新 Generation 目标帧                         |
