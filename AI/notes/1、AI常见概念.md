# 一、LLM

LLM（Large Language Model，大语言模型）是一类能够理解和生成自然语言的人工智能模型。它通过大量文本数据训练，形成对语言规律、知识和表达方式的学习能力。

从工作方式看，LLM 可以理解为一种“语言预测模型”：它会根据已有上下文，预测接下来最可能出现的内容。LLM 通常基于 Transformer 神经网络架构。

## 2、训练过程

LLM 能够根据上下文生成回答，关键在于训练过程。这个过程大致可以分为三个阶段：预训练、指令微调和人类反馈强化学习。

![[assets/Pasted image 20260811224631.png|600]]

- **预训练（Pre-training）**：提供海量文本数据，例如网页、书籍、代码和文章，让模型学习语言规律和世界知识。
- **指令微调（Instruction Tuning / SFT）**：将训练数据变成“用户问题 + 标准答案”，让模型学会理解人类需求，并按要求完成任务。
- **人类反馈强化学习（RLHF）**：即使模型已经能够理解指令，也可能回答啰嗦、不安全或不符合用户期待。因此加入人类反馈：模型生成多个答案，由人类评价答案质量，再根据评价结果优化模型。


# 二、Token

Token 是模型处理文本时使用的基本单位。LLM 不会直接把人类输入的整段文字送进 Transformer，而是先把文本转换成 Token 序列，再转换成模型可以计算的数字表示。

## 1、Tokenizer

`Tokenizer` 是负责处理文本切分的组件。它按照一套与模型配套的规则，把输入文本拆成若干个 Token；Tokenizer 的主要职责是完成“文本 → Token 序列”，并不负责生成回答。

例如，人看到的是：

```text
解释一下什么是 Rust 所有权？
```

经过 Tokenizer 处理后，可能得到这样的 Token 序列：

```text
解释 | 一下 | 什么 | 是 | Rust | 所有权 | ?
```

这里的竖线只是为了展示切分边界，并不是输入文本中的内容。切分完成后，Token 还要经过后续的数字化和向量化，才能交给 Transformer 进行计算。

## 2、Token 不等于一个字或一个单词

Token 的大小不是固定的。它可能是一个汉字、一个词、一个英文单词的一部分，也可能是标点或其他文本片段，具体取决于模型使用的 Tokenizer。

例如，英文单词可能被拆成多个 Token：

```text
unbelievable

    ↓

un | believable
```

中文也可能按词语或其他片段切分：

```text
解释一下什么是 Rust 所有权？

    ↓

解释 | 一下 | 什么 | 是 | Rust | 所有权 | ?
```

同一段文本交给不同模型时，使用的 Tokenizer 可能不同，因此切分结果和 Token 数量也可能不同。

## 3、Token 如何进入模型

Token 只是文本处理过程中的中间结果，还不能直接作为 Transformer 的计算输入。模型只认识数字，需要把 Token 转换为为向量，这称为向量化。

向量可以理解为一组数字，例如 `[0.21, …]`。这些数字不是给人直接阅读的答案，而是模型进行后续计算时使用的表示。

## 4、LLM 如何逐个生成 Token

LLM 通常不是一次性生成完整回答，而是循环预测下一个 Token。每一轮都会把新生成的 Token 加回原来的序列，再用完整的新序列预测下一步。

![[assets/Pasted image 20260811231810.png|800]]

整个过程可以拆成以下步骤：

1. **输入文本**：用户输入问题，例如“解释一下什么是 Rust 所有权？”。
2. **切分 Token**：Tokenizer 将文本拆成 Token 序列。
3. **转换为向量**：每个 Token 被转换为模型可以计算的数字向量。
4. **模型处理**：Transformer 根据当前上下文进行计算。
5. **预测概率**：模型输出下一个 Token 的概率分布。例如，“所有权”可能比“概念”具有更高的概率。
6. **解码**：从概率分布中选出一个 Token，作为当前这一步的输出。
7. **追加序列**：把新 Token 加到已有 Token 序列末尾。
8. **循环预测**：将更新后的完整序列再次交给模型，继续预测下一个 Token。
9. **生成回答**：经过多轮循环后，多个 Token 被组合起来，形成最终的文字回答。

例如，第一轮预测出“所有权”后，下一轮的输入就会包含这个新 Token；模型可能据此继续预测“是”或“是一种”等后续 Token。回答就是这样逐步生成的。

# 三、Context Window

Context Window（上下文窗口）是一次请求中，LLM 能够接收和处理的最大 Token 容量。

简单理解，Context Window 决定了模型当前能够“看到多少内容”。它不是永久记忆，模型每次生成回答时，主要依据当前请求中携带的上下文进行计算。

## 1、Context Window 包含什么

Context Window 不只是聊天记录。在 Claude Code、ChatGPT 这类 AI Agent 中，一次请求的上下文通常还包括系统指令、工具信息、工具结果和文件内容等。

| 内容 | 示例 |
| --- | --- |
| System Prompt | 模型行为规则、系统指令 |
| User Prompt | 用户输入的问题 |
| Conversation History | 历史聊天内容 |
| Tool Result | 工具执行结果 |
| File Content | 读取的代码文件 |
| Project Context | 项目信息、配置文件 |
| Generated Output | 当前生成过程中的内容 |

## 2、接近上限时如何处理

当上下文接近限制时，需要减少一次请求携带的 Token；如果超过限制，模型就无法完整处理全部内容。常见处理方式有以下三种。

### （1）截断旧内容

删除较早的消息，只保留最近的内容：

```text
旧对话 → 删除较早内容 → 保留最近内容
```

这种方式简单直接，但可能丢失早期的重要信息。

### （2）压缩上下文（Compaction）

将较长的历史对话总结成较短的摘要，用摘要替代原始内容：

```text
完整历史对话 → 总结关键信息 → 生成摘要 → 替代旧内容
```

摘要通常保留已完成工作、重要决定和当前任务状态，从而减少上下文占用。

### （3）外部检索（RAG）

对于大量文档，不把全部内容一次性放进上下文，而是先搜索与当前问题相关的内容，再将相关结果交给 LLM：

```text
大量文档 → 检索相关内容 → 放入必要信息 → LLM 回答
```

RAG（Retrieval-Augmented Generation，检索增强生成）的核心，就是按需提供信息，减少无关内容对 Context Window 的占用。

## 3、Context Window 越大越好吗

不一定。更大的 Context Window 可以读取更多代码、处理更长文档、保留更多历史，但也可能带来额外成本、延迟和注意力分散问题。

| 方面 | 可能的好处 | 可能的代价 |
| --- | --- | --- |
| 内容容量 | 可以放入更多代码、文档和历史 | 信息过多时，关键内容可能被无关内容淹没 |
| 成本 | 可以在一次请求中处理更多内容 | 输入 Token 增加，费用可能上升 |
| 速度 | 可以减少拆分任务的次数 | 输入越长，计算量和响应延迟可能增加 |

> [!note] 实际使用原则
> 目标不是把所有信息都塞进 Context Window，而是让当前任务需要的关键信息进入窗口。上下文过长时，可以结合截断、压缩和外部检索进行处理。
