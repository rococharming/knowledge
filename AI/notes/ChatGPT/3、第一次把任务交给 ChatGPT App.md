# 一、任务目标

第一次使用 ChatGPT App 完成任务时，重点不是一次性掌握所有功能，而是建立一条完整的工作链路：选择合适的工作区，提供任务上下文，确认执行计划，等待实现结果，再用可见结果和验证信息判断任务是否完成。

这里以 **在 Codex 中创建一个待办事项网页** 为例。这个例子足够小，适合观察 Codex 如何理解需求、创建文件、运行检查和打开预览；同时它又包含真实任务常见的几个环节：需求澄清、方案确认、代码生成、浏览器验收和继续迭代。

如果任务不是代码或网页实现，而是整理资料、撰写文档或制作表格，应优先使用 Chat 或 Work。三种工作模式的区别参考 [[1、认识 ChatGPT App|认识 ChatGPT App]]。

# 二、准备

## 1、权限模式

Codex 在执行任务时可能需要读取文件、修改文件、运行命令或访问网络。权限模式决定哪些操作可以直接执行，哪些操作需要用户确认。

在输入框左下角的权限入口中，可以将审批方式设置为 **替我审批**。这个模式对应 Auto-review：Codex 会自动审查一部分额外权限请求，减少频繁确认；但它并不等于完全访问权限，也不代表所有高风险操作都会被无条件批准。

![[assets/Pasted image 20260731023042.png|600]]

大部分情况下使用替我审批都没什么问题，能够观察 Codex 的完整执行过程，同时避免每一步都被权限确认打断。

## 2、上下文窗口

上下文窗口是模型在一次任务中能够参考的信息范围，包括用户输入、历史对话、文件内容、图片、工具结果和 Codex 自己的中间总结。上下文窗口不是永久记忆；当任务变长时，较早的信息可能被压缩成摘要，或者需要通过文件、链接和明确指令重新提供。

可以在 **Settings > General** 中开启 **显示上下文窗口使用情况**：

![[assets/Pasted image 20260731023223.png|600]]

开启后，输入框附近会显示上下文使用量。它的作用不是要求用户频繁管理 token，而是帮助判断任务是否已经过长：

- 如果上下文使用量很低，可以继续在同一任务里推进。
- 如果上下文使用量接近较多，可手动压缩上下文释放空间，而不必等 Codex 临近上限自动压缩。
- 如果任务经历了多轮实现和修改，可以先让 Codex 总结当前状态生成交接文档，再新建对话继续推进。

# 三、创建本地 Project

## 1、创建 Project

Codex 需要知道要在哪个文件夹中工作。点击侧边栏 **项目** 区域旁边的 `+`，可以创建新的本地 Project，或选择已有 Project 继续工作。

![[assets/Pasted image 20260731021457.png]]

Project 是 ChatGPT App 组织本地文件夹和任务上下文的方式。创建 Project 时，需要填写项目名称，并添加 ChatGPT 可以读取和编辑的源文件夹。

![[assets/Pasted image 20260731021342.png|400]]

源文件夹决定 Codex 能看到哪些文件，也决定本次任务生成的文件会写到哪里。

## 2、进入任务

选择 Project 后，Codex 会以该目录作为当前工作范围。输入框上方通常会显示当前 Project 名称和本地执行位置，表示后续任务会围绕这个目录展开。

本例使用名为 `todo` 的本地 Project。它是一个练习目录，目标是在其中生成一个可以本地运行的待办事项网页。

# 四、任务描述

## 1、计划模式

在真正执行前，可以通过输入框左下角的 `+` 菜单开启 **计划模式**：

![[assets/Pasted image 20260731022100.png]]

计划模式适合第一次交付任务、需求还不够清楚，或需要先确认实现边界的场景。开启后，Codex 会优先阅读上下文、提出问题和生成方案，而不是立即修改文件。

计划模式的价值在于把“动手实现”推迟到“目标和边界清楚之后”。这样更容易提前发现歧义，例如数据如何保存、页面是否需要部署、视觉风格要偏工具化还是偏展示化。

## 2、提示词

因为任务比较简单，所以这里提示词也比较简单：

![[assets/Pasted image 20260731021833.png]]


# 五、确认方案

## 1、澄清问题

计划模式下，Codex 会先检查当前目录，再根据任务缺口提出问题：

![[assets/Pasted image 20260731022355.png]]

选择 **本地保存** 表示待办事项保存在浏览器本地存储中，不需要账号、后端服务或数据库。对于第一次练习，这是最合适的选择，因为它减少了部署和后端设计的复杂度。

接着，Codex 会确认交付方式：

![[assets/Pasted image 20260731022520.png]]

选择 **本地可运行** 表示先在当前电脑上启动开发服务器并预览网页。它适合学习和验证；如果目标是公开访问或长期分享，则需要进一步考虑部署方式。

最后，Codex 会确认页面体验风格：

![[assets/Pasted image 20260731022539.png]]

这些问题不是闲聊，而是在把模糊需求转成可执行约束。用户的选择会影响数据结构、技术栈、页面样式和验收方式。

## 2、实施计划

澄清完成后，Codex 会生成实施计划，并询问是否开始执行：

![[assets/Pasted image 20260731022700.png|600]]

这一步应重点检查三件事：

- **范围是否正确**：是否只在练习目录中创建待办网页。
- **方案是否过度**：第一次练习不需要账号系统、后端数据库或复杂部署。
- **验收是否明确**：是否会运行构建、测试、静态检查，或至少提供可打开的预览地址。

如果计划不合适，应继续补充要求；如果计划已经清楚，再选择执行。

# 六、执行预览

## 1、开始执行

确认计划后，Codex 才会进入实际执行阶段。它会读取目录、生成或修改文件、安装或使用依赖，并在过程中报告关键步骤。

![[assets/Pasted image 20260731023441.png]]

执行阶段不需要用户盯着每一行输出，但需要关注三类信息：

- Codex 是否仍在目标目录内工作。
- 是否出现需要确认的权限请求。
- 是否有测试、构建或运行错误。

## 2、完成结果

任务完成后，Codex 会总结实际改动、验证方式和预览入口。本例中，Codex 生成了一个本地运行的待办事项应用，并通过构建、测试、静态检查和本地页面响应检查。

![[assets/Pasted image 20260731023802.png|600]]

如果生成的是网页，结果卡片中通常会提供 **网页预览** 或打开方式。点击后，可以在 ChatGPT App 的内置 Browser 中查看页面：

![[assets/Pasted image 20260731023901.png|600]]

也可以从打开方式中选择外部浏览器，例如 Google Chrome：

![[assets/Pasted image 20260731023938.png|600]]

外部浏览器打开后，页面会以本地地址运行：

![[assets/Pasted image 20260731024001.png|600]]

## 3、功能验收

代码任务不能只看“已生成文件”。网页类任务至少应做一次可见功能验证，例如输入一条待办事项，点击 **添加**，确认页面状态发生变化。

![[assets/Pasted image 20260731024122.png|600]]

对于这个示例，最小验收标准可以是：

- 页面能够正常打开。
- 能新增待办事项。
- 能切换完成状态。
- 能编辑和删除事项。
- 刷新页面后数据仍然保留。
- 筛选和统计数量符合当前列表状态。

# 七、继续迭代

## 1、补充需求

第一版结果通常只是可用版本。对结果不满意时，可以直接在同一任务中继续描述修改需求，Codex 会基于已有文件继续调整。

例如，想增加浅色和深色主题切换，可以继续输入：

![[assets/Pasted image 20260731024406.png|600]]

这种方式适合需求能用文字说清楚的情况，例如“把按钮改到右上角”“增加编辑功能”“把本地保存改成后端接口”。

## 2、页面注释

当修改要求和页面位置强相关时，可以使用内置 Browser 的注释功能。点击右上角的注释按钮后，页面会进入注释状态：

![[assets/Pasted image 20260731024516.png|600]]

进入注释状态后，可以点选页面中的具体位置，并写下修改意见：

![[assets/Pasted image 20260731024739.png|600]]

提交注释后，输入框会带上该注释及其位置上下文：

![[assets/Pasted image 20260731024907.png|600]]

发送后，Codex 会结合文字需求和页面位置继续修改：

![[assets/Pasted image 20260731025006.png|600]]

页面注释适合表达“这里增加一个按钮”“这个区域太挤”“这个控件应该靠右”这类视觉需求。它比单纯文字描述更精确，但仍需要在完成后检查最终结果是否符合预期。

## 3、检查结果

迭代完成后，应重新打开页面并检查目标功能。本例中，页面已经出现浅色和深色切换控件，并保留了待办事项输入、统计和本地保存能力：

![[assets/Pasted image 20260731025353.png|600]]

如果注释点选的位置并不是最终适合放置控件的位置，Codex 可能会选择更合理的布局位置。验收时应以最终页面行为和视觉结果为准，而不是只看它是否严格放在注释坐标上。

# 八、上下文管理

## 1、查看使用量

开启上下文窗口使用情况后，输入框附近会出现一个小圆圈，用来显示当前任务的上下文使用状态：

![[assets/Pasted image 20260731025116.png|600]]

上下文使用量升高并不表示任务出错，只表示当前对话、文件内容、工具结果和图片说明已经积累较多。长任务中可以观察这个指标，判断是否需要整理上下文。

## 2、手动压缩

Codex 在上下文接近上限时通常会自动压缩上下文。用户也可以主动输入 `/压缩`，让 Codex 总结当前任务状态，减少后续对话负担：

![[assets/Pasted image 20260731025641.png|600]]

压缩前最好确认当前阶段已经有清楚结果，例如“第一版已完成并通过测试”或“主题切换已实现但还没验收”。这样压缩摘要更容易保留关键状态。
