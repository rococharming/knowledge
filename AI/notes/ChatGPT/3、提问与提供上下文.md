# 一、提示词

提示词（Prompt）是你告诉 ChatGPT 想知道什么、创建什么或修改什么的输入。它可以是一句话、一个问题，也可以是一份完整的任务说明。

ChatGPT 不要求使用固定语法或复杂模板。简单任务可以直接用自然语言描述；任务越复杂、结果越重要，越需要补充目标、上下文、输出要求和边界。

官方的 [Prompting](https://learn.chatgpt.com/docs/prompting) 指南把有效提示概括为四类信息：

| 信息 | 要回答的问题 |
|---|---|
| 目标 | ChatGPT 最终要做成什么？ |
| 上下文 | 哪些资料和背景会改变结果？ |
| 输出 | 结果需要什么格式、篇幅和深度？ |
| 边界 | 哪些内容不能改、不能做或必须先确认？ |

这些不是必须逐项填写的表格。只提供真正影响结果的信息即可。

# 二、目标

## 1、描述结果

优先描述想得到的结果，而不是替 ChatGPT 写死每一步。

较弱的写法：

```text
先读取这些会议记录，然后提取内容，然后分类，最后写一份文档。
```

更清楚的写法：

```text
把这些会议记录整理成一份发给项目组的简短进展。
先列决定，再列下一步，并标出负责人和截止时间。
```

第二种写法说明了交付物、读者和输出重点，同时给 ChatGPT 留出了选择处理步骤的空间。

## 2、给出验收标准

任务需要交付可使用的成果时，说明怎样才算完成。

示例：

```text
根据附件中的调研资料生成一份 8 页演示文稿。
必须包含问题背景、三个方案的对比、推荐方案和下一步。
所有数字都要能追溯到附件，并在生成后检查每一页是否存在文字溢出。
```

这里不仅说明要“制作 PPT”，还明确了内容结构、事实来源和检查条件。

# 三、上下文

## 1、提供必要资料

上下文是 ChatGPT 完成任务时需要参考的信息。常见来源包括：

- 当前消息中的文字
- 上传的文件
- 图片或截图
- Web Search
- Project 中的 Files、Sources 和 Instructions
- Plugin 连接的外部服务
- 本地 Project 中的文件夹

不要一次性附加所有可能相关的材料。应选择能够改变结论、格式或执行方式的资料，并说明每份资料的用途。

示例：

```text
使用 Project 中最新版本的产品计划确认范围，
使用附件中的访谈记录提取用户问题。
旧版需求文档只用于了解背景，不要把其中已删除的功能写入结论。
```

## 2、说明图片重点

添加图片时，不要只说“看一下这张图”。需要指出图片是什么、应该检查哪里，以及想得到什么结果。

示例：

```text
这是一张支付页面的错误截图。
重点检查右下角被遮挡的按钮，判断是布局问题还是窗口尺寸问题。
先解释原因，不要修改代码。
```

图片输入、文件和网页资料的具体用法参考 [[5、资料、搜索与多模态输入|资料、搜索与多模态输入]]。

## 3、指定外部来源

任务依赖当前信息时，应明确要求使用 Web Search，并说明是否需要引用来源。

任务依赖已连接服务时，应说清楚去哪里寻找什么，而不必逐条规定搜索动作。

示例：

```text
从项目的 Google Drive 中查找最新发布计划，
再结合 Slack 的项目频道整理本周状态。
只使用最近七天的信息。
```

# 四、输出

输出要求用于约束结果的呈现方式。它可以包括：

- 目标读者
- 文件类型
- 篇幅
- 标题结构
- 表格字段
- 语气
- 是否需要图表
- 是否需要保留源文件
- 保存路径

示例：

```text
为没有 Rust 经验的前端工程师写一篇中文入门说明。
先解释所有权解决什么问题，再给一个最小示例。
使用 Markdown，控制在 1200 字以内。
```

当 ChatGPT 需要创建文档、演示文稿或表格时，应进一步说明页面、Sheet、列、图表和视觉检查要求，详见 [[6、使用 Work 完成交付物|使用 Work 完成交付物]]。

# 五、边界

边界用于避免真实风险，而不是限制 ChatGPT 的每一个小步骤。常见边界包括：

- 不修改指定文件
- 不删除数据
- 不提交或推送 Git
- 不向外部服务发送消息
- 不访问包含敏感信息的目录
- 遇到某类操作必须先确认
- 保持现有接口或输出兼容

示例：

```text
先诊断构建失败的根因，不要修改文件。
可以运行只读命令和测试；如果需要下载依赖或更改工具链，先说明原因并等我确认。
```

边界应描述真正不能发生的结果。不要把实现方案误写成边界，否则可能阻止 ChatGPT 找到更简单的解决方法。

# 六、迭代

## 1、检查结果

第一版结果应该被视为可检查的草稿。需要核对：

- 名称、日期、数字和引用是否准确
- 是否使用了指定资料
- 是否遗漏关键内容
- 文件能否正常打开
- 页面、幻灯片和表格是否完整
- 代码是否通过构建或测试

高风险领域仍需要相应专业人员复核，不能把 ChatGPT 的输出当作最终专业判断。

## 2、继续修正

后续消息可以很短，只要指向明确：

```text
把第二部分缩短一半，保留结论和数据。
```

```text
只修改第 4 张幻灯片的图表标签，其他页面保持不变。
```

```text
先列出你做出的假设，不要继续执行。
```

较长任务运行时，新的消息可以立即调整当前方向，也可以排队成为下一步。具体行为由 **Settings > General > Follow-up behavior** 控制。

# 七、模式差异

## 1、Chat

Chat 的提示适合从一个问题或草稿开始，通过对话逐步形成结果。

示例：

```text
我准备给团队介绍 AI Coding Agent。
先问我三个问题，确认受众、时长和他们已有的知识，再帮我设计提纲。
```

## 2、Work

Work 的提示应突出交付物、来源、约束和审阅标准。

示例：

```text
使用 Project 中的调研材料生成一份方案比较报告。
比较成本、落地难度和维护风险，给出推荐方案。
报告完成后检查引用、表格和 PDF 页面布局。
```

## 3、Codex

Codex 的提示应说明项目范围、预期行为、允许的修改和验证方式。

示例：

```text
检查当前项目登录页偶发跳回首页的问题。
先复现并解释根因，再做最小修改。
保持现有路由接口不变，完成后运行相关测试并总结实际改动。
```

第一次开始复杂任务时，可以先要求 ChatGPT 检查理解和提出问题：

```text
请先不要执行。复述你对目标、上下文、输出和边界的理解，
指出仍存在的歧义，并给出执行计划。
```
