# 一、长期任务

长期任务是需要多个步骤、较长时间和持续判断才能完成的工作。它与普通 Chat 的主要区别是：开始前需要明确完成标准，运行中需要查看进度、处理阻塞并调整方向。

适合的例子：

- 跨多个文件完成代码迁移
- 持续搜索和整理一个研究主题
- 制作并反复检查一组交付物
- 监控一项外部变化
- 定期生成状态报告

一次性的长任务使用 Goal；需要按时间重复运行的工作使用 Scheduled Task。

# 二、Goal

## 1、定义目标

在 ChatGPT 桌面 App 中输入 `/goal` 可以启动 Goal Mode。Goal 内容同时是第一条任务说明和完成标准。

一个可执行的 Goal 通常包含：

| 要素 | 内容 |
|---|---|
| Outcome | 最终结果，而不是笼统活动 |
| Constraints | 文件范围、兼容要求、禁止事项和工具限制 |
| Verification | 能证明完成的测试、测量或审阅条件 |

示例：

```text
/goal
把这个 JavaScript 项目迁移到 TypeScript。
保持现有运行行为，在 strict mode 下编译通过，
不使用显式 any，并让完整测试套件通过。
```

如果目标还不清楚，先使用 `/plan`，让 ChatGPT 通过提问确认范围和验收条件，再把结果转换成 Goal。

## 2、控制进度

Goal 运行时，输入区上方会显示进度条，可以：

- Pause
- Resume
- Edit goal
- Clear goal

运行期间仍可发送后续消息，补充上下文或调整约束。只想了解进度而不打断主任务时，可以使用 Side Chat。

## 3、并行任务

彼此独立的任务可以放入不同 Chat 并行运行；依赖同一上下文的连续工作保留在同一 Chat。

多个任务会修改相同文件或外部记录时，不应直接并行。Codex 代码任务可以使用不同 Worktree 隔离 Git 修改，但仍需检查共享服务、数据库和生成文件是否会冲突。

# 三、Scheduled Tasks

## 1、用途

Scheduled Task 按计划在后台重复运行。可以从左侧 **Scheduled** 查看：

- Active
- Paused
- Completed
- 最近运行记录

它可以结合 Files、Plugins、Skills 和 Project 上下文完成更复杂的工作。

适合的例子：

- 每周生成项目进展报告
- 定期检查依赖发布说明
- 每天整理未读邮件
- 监控网站状态
- 周期性运行代码检查

## 2、独立任务与 Chat 内任务

| 类型 | 上下文 |
|---|---|
| 独立 Scheduled Task | 每次从保存的 Prompt 开始 |
| Chat 内 Scheduled Task | 返回同一 Chat，继续使用已有上下文 |

需要稳定、可复现的任务时，把必要背景写入 Prompt、Skill 或可访问的 Project Source，不要依赖一次对话中未明确保存的临时信息。

## 3、本地与 Web

桌面 App 的 Scheduled Task 可以在本地 Project 中运行。任务需要本地文件时：

- 电脑必须保持开机
- ChatGPT App 必须运行
- Project 目录仍需存在
- 本地权限和网络权限必须允许任务执行

Web 端 Scheduled Task 可以使用上传文件、Connected Tools、Skills 和 Plugins，但不能直接访问电脑中的文件夹。

需要脱离本机持续运行时，优先选择云端可访问的来源和工具。

## 4、Worktree

Git Project 的 Scheduled Task 可以在当前本地目录或新 Worktree 中运行。

- **当前目录**：直接修改正在使用的工作区，简单但容易与人工改动冲突。
- **Worktree**：把自动任务的修改隔离到独立目录，更适合代码类后台工作。

非 Git Project 没有 Worktree 隔离，Scheduled Task 会直接在 Project 目录中运行。

# 四、创建任务

## 1、先测试

正式调度前，先在普通 Chat 中执行一次 Prompt，确认：

- 输入来源可以访问
- 输出范围正确
- 工具选择合理
- 结果可以验证
- 不会自动执行危险外部动作

确认后，再让 ChatGPT 创建 Scheduled Task。

## 2、描述计划

创建任务时要说明：

- 做什么
- 何时运行
- 使用哪个 Project 或来源
- 输出到哪里
- 哪些动作需要确认
- 失败时如何报告

示例：

```text
每周一上午 9 点检查这个 Project 中最近一周的代码变更，
生成一份 Markdown 周报，包含主要功能、修复和仍未解决的问题。
只创建报告，不提交、不推送，也不要发送到外部服务。
如果项目目录不可用，报告阻塞原因，不要创建新目录。
```

# 五、权限

Scheduled Task 会在无人持续盯着界面时运行，因此权限应比交互任务更谨慎。

建议：

- 使用能够完成任务的最小 Sandbox
- 只开放必要目录
- 只允许必要网络范围
- 发送、发布、删除和付款等动作保留人工确认
- 优先使用 Worktree 隔离代码修改
- 检查前几次运行记录，再逐步调整 Prompt

定时任务不会因为“自动运行”而绕过 Permission Mode。权限和 Sandbox 的具体含义参考 [[12、权限、设置与故障排查|权限、设置与故障排查]]。

# 六、Notifications

Notifications 用于提醒任务已经完成、需要权限或需要回答问题。

桌面 App 可以在 Settings 中选择：

- 从不显示完成通知
- 只在 App 位于后台时显示
- 始终显示
- 是否显示权限和问题提醒

Web 端的可用通知方式可能包括 Push、Email 或 SMS，取决于账号和任务类型。

通知只是状态提醒，不代表任务结果已经通过验证。收到完成通知后，仍要打开 Chat 检查实际输出、工具活动和未解决问题。

# 七、实践

可以先创建一个低风险的每周官方文档监控：

1. 在普通 Chat 中测试搜索 Prompt。
2. 限定只使用指定官方域名。
3. 要求比较上次报告，列出新增、修改和删除内容。
4. 输出为 Project 中的 Markdown 文件。
5. 不发送消息、不发布、不提交 Git。
6. 设置每周运行一次。
7. 检查前三次运行记录，再决定是否扩大范围。

长期任务依赖外部服务时，先完成 [[9、Plugins 与外部服务|Plugin]] 的授权检查；依赖本地文件或代码时，先确认 Project 和 Worktree 边界。
