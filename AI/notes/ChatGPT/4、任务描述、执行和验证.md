# 一、任务描述

任务描述就是告诉 ChatGPT 想知道什么、创建什么或修改什么。它可以是一句话、一个问题、一段背景说明，也可以是一份完整的任务要求。

写任务描述的重点不是套模板，而是让 ChatGPT 理解 **要完成什么、可以参考什么、结果要长什么样、哪些事情不能做，以及什么才算完成**。简单任务可以直接说；任务越复杂、结果越重要，越应该补充目标、上下文、输出和边界。

## 1、四个要素

一个稳定的任务描述通常包含四类信息：

| 要素 | 要回答的问题 | 作用 |
|---|---|---|
| 目标 | 要做成什么？ | 定义最终结果 |
| 上下文 | 哪些信息会影响结果？ | 减少猜测和误解 |
| 输出 | 结果要怎样呈现？ | 控制格式、篇幅和详细程度 |
| 边界 | 什么不能改、不能做或必须先确认？ | 避免真实风险 |

这四项不是固定格式，也不是每次都必须写全。小任务只写一句话即可；大型任务则要把真正影响结果的信息补齐。

对于编程任务，还可以额外写清 **完成标准**。例如：测试要通过、页面行为要改变、Bug 不能再复现，或者最终需要提供哪些命令结果。

## 2、目标

目标应优先描述想得到的最终结果，而不是替 ChatGPT 规定每一个执行步骤。

较弱的写法：

```text
先看这些会议记录，然后总结，再分类，最后写一段话。
```

更清楚的写法：

```text
把这些会议记录整理成发给项目组的简短进展。
先列已经确定的决定，再列下一步行动，并标出负责人和截止时间。
```

第二种写法更好，因为它说明了交付物、读者和结果结构。ChatGPT 可以自行决定如何阅读、归纳和排序，而不是被迫按一串未必必要的步骤执行。

同一个主题面对不同读者，输出会完全不同。目标读者会影响术语解释、细节深度和表达方式。

示例：

```text
为没有编程经验的产品经理解释什么是 API。
用“点餐和厨房”的例子说明，不要使用代码。
```

```text
为刚加入项目的前端工程师解释这个 API。
说明请求路径、字段含义、错误码和一个最小调用示例。
```

前者需要类比和背景，后者需要接口细节。读者越明确，ChatGPT 越容易选择合适的解释层次。

## 3、上下文

上下文是 ChatGPT 完成任务时需要参考的信息。它可以来自当前消息、附件、图片、Project、本地文件夹、网页搜索或已连接的外部服务。

提供上下文时，要说明资料的角色，而不是只把资料丢给 ChatGPT。

示例：

```text
附件 A 是当前有效的产品需求，附件 B 是旧版方案，只用于理解背景。
请比较两者，列出仍然有效的需求变化，不要把 B 中已删除的功能写入结论。
```

处理文件时，可以这样写：

```text
使用附件中的访谈记录提取用户问题。
使用表格中的客户类型做分类依据。
不要修改原始文件。
```

处理截图时，应指出图片是什么、重点看哪里、希望得到什么：

```text
这是一张支付页面错误截图。
重点检查右下角按钮被遮挡的问题，判断是布局问题还是窗口尺寸问题。
先解释原因，不要修改代码。
```

不要只写“看一下这个文件”或“分析这张图”。这类提示没有告诉 ChatGPT 应该从资料中提取什么，容易得到泛泛总结。

如果任务依赖新闻、版本、价格、政策、文档更新或产品当前能力，应明确要求使用搜索，并说明是否需要来源。

示例：

```text
搜索 OpenAI 官方文档，确认 ChatGPT App 当前支持哪些桌面操作能力。
只使用官方来源，并在关键结论旁附链接。
```

使用 Plugins 这类已连接来源时，也要说明去哪里找、找什么、结果怎么用，而不必规定每一次搜索动作。

示例：

```text
使用 Google Drive 中最新的发布计划，
结合 Slack 项目频道最近七天的决定和进展，
整理一份项目状态更新。
只生成草稿，不要发送到任何外部服务。
```

## 4、输出

输出要求用于告诉 ChatGPT 结果会被怎样使用。它会影响内容结构、篇幅、语气和细节。

常见输出要求包括：

- 读者是谁。
- 使用场景是什么。
- 文件类型是什么。
- 需要多长或多详细。
- 是否用表格、清单、邮件、报告或代码块。
- 是否需要引用来源。
- 是否需要保存到指定路径。

示例：

```text
把这些会议记录整理成一封后续邮件。
邮件要包含决定事项、负责人和截止日期。
语气礼貌、简洁，不超过 300 字。
```

如果只说“整理一下”，ChatGPT 可能不知道应该写成邮件、纪要、表格还是汇报材料。

代码任务的输出要求不能只写“修好”。应说明要交付什么行为，以及如何证明它已经正确：

- 说明根因。
- 列出改动文件。
- 给出验证结果。
- 标出剩余风险。

## 5、边界

边界不是用来控制每一个小步骤，而是用来防止真实问题。它应该描述哪些结果不能发生，或者哪些动作必须先确认。

需要写边界的常见情况包括：

- 改错内容会让结果无法使用。
- 某些数字、日期、接口或文件必须保持不变。
- 任务可能触及外部服务、发送消息、发布内容或删除数据。
- 你只想先诊断，不希望立即修改。
- 结果要给其他人看，发送前必须审阅。

示例：

```text
先诊断构建失败原因，不要修改文件。
如果需要安装依赖或访问网络，先说明原因并等我确认。
```

边界应少而关键。写太多无关限制，反而会让任务变僵硬。

| 场景 | 更合适的边界 |
|---|---|
| 项目汇报 | 保持已批准的日期和预算不变 |
| 邮件草稿 | 只生成草稿，不要发送 |
| 资料总结 | 只使用指定资料，缺失处明确标注 |
| 代码修复 | 保持公开接口不变，不提交、不推送 Git |
| 数据处理 | 保留原始文件，输出到新文件 |

边界最好围绕后果来写。例如“不要提交 Git”比“不要运行任何 Git 命令”更准确，因为检查 `git status` 往往是安全且必要的。

# 二、执行控制

任务描述决定“要做什么”，执行控制决定“怎么推进”。对 ChatGPT 和 Codex 来说，最可靠的方式不是一次性把所有事情交出去不管，而是让任务保持可观察、可打断、可修正。

## 1、先计划

遇到复杂、模糊或风险较高的任务，应先让 Codex 只读分析，暂时不要修改文件。

可以这样写：

```text
先不要改文件。
请先阅读相关代码，说明当前结构、关键文件、风险点和建议步骤。
如果有需要我确认的决策，先列出来。
```

这种做法适合下面几类情况：

- 不确定相关文件在哪里。
- 任务涉及多个目录或多个模块。
- 需要重构较大的代码。
- 担心 Codex 改动范围过大。
- 希望先比较方案，再决定是否执行。

在 ChatGPT App 或 Codex 里，也可以使用计划相关入口，让 Codex 先收集上下文、提出澄清问题并形成方案。计划不是形式主义，它的作用是把“马上动手”推迟到“目标和边界清楚之后”。

## 2、小步推进

执行阶段最好拆成小步。每一步只处理一个明确阶段，并在阶段结束后说明做了什么、还剩什么、下一步准备做什么。

小步推进的好处是：

- 更容易看出 Codex 是否还在正确方向上。
- 更容易发现是否改到了不相关文件。
- 发生问题时更容易定位是哪一步引入的。
- 用户可以在中途补充信息或改变优先级。

当 Codex 正在执行任务时，可以继续发送后续消息。桌面 App 会根据 Follow-up behavior 采用两种行为：

| 行为 | 含义 | 适合场景 |
|---|---|---|
| Steer（引导） | 把新消息加入当前正在执行的任务 | 补充遗漏信息、改变当前方向 |
| Queue（排队） | 把新消息排到下一轮执行 | 等当前任务结束后再处理下一件事 |

Queued 消息会显示在输入框上方，可编辑、重排、发送或删除。在 Codex CLI 中，Codex 工作时按 <kbd>Enter</kbd> 会引导当前轮次，按 <kbd>Tab</kbd> 会把消息排到下一轮。

## 3、语音补充

语音听写适合把口头想法快速转成输入框里的文字。它不是实时语音对话，而是“先转录，再发送”。

在桌面 App 中，当输入框可见时，可以使用麦克风按钮或对应快捷键开始语音听写。终止后，ChatGPT 会把语音转录到输入框中，发送前仍然可以编辑。

# 三、验证闭环

验证是判断任务是否完成的依据。对代码任务来说，验证不能只看 Codex 的总结；对写作和资料任务来说，也不能只看语言是否流畅。验证要回到任务目标，检查结果是否真的满足使用场景。

## 1、完成标准

一个稳定的 Codex 任务通常包含六步：

1. 说明目标。
2. 建立任务地图。
3. 小步执行。
4. 检查 diff。
5. 运行验证。
6. 记录结果。

其中最容易被忽略的是“完成标准”。完成标准应该写在任务一开始，而不是等 Codex 说“完成了”之后才临时判断。

示例：

```text
修复登录页按钮在窄屏下被遮挡的问题。
完成后请运行最小相关测试，并用浏览器截图验证 375px 和 1440px 宽度下按钮都可见。
最后说明改动文件、验证命令和剩余风险。
```

这条任务同时定义了目标、验证方式和最终汇报内容。

## 2、检查 diff

Codex 改完后，不要只看总结。要检查 diff。

重点看：

- 有没有改到不相关文件。
- 有没有删掉仍然有价值的内容。
- 公开接口、数据格式、文件路径是否被意外改变。
- 链接是否指向正确的新路径。
- 配置文件是否只做了必要改动。
- 新增代码是否和项目现有风格一致。

检查 diff 的目的不是手工重做 Codex 的工作，而是确认改动范围和任务目标一致。尤其是本地代码任务，最终责任仍然在使用者身上。

## 3、运行验证

验证方式取决于任务类型。

| 任务类型 | 常见验证 |
|---|---|
| 前端页面 | 运行构建、打开页面、检查截图和交互 |
| 代码修改 | 跑单元测试、类型检查、lint |
| 配置修改 | 查询当前状态、启动一次最小任务 |
| 文档笔记 | 检查链接、图片、标题层级和渲染 |
| 发布任务 | 检查访问地址、日志、状态码 |

如果验证失败，不要马上扩大修改范围。先判断失败属于哪类：

- 本次改动造成的错误。
- 环境依赖问题。
- 项目已有问题。
- 外部服务或网络问题。

只有第一类才应该继续修本轮改动。其他类型要先记录原因，再决定是否另开任务处理。

## 4、记录结果

任务结束时，应让 Codex 汇报四类信息：

- 做了什么。
- 改了哪些文件。
- 怎么验证。
- 还有什么风险。

当验证失败时，可以这样处理：

1. 保留当前错误输出。
2. 让 Codex 解释错误来源，并区分“本地改动导致”和“环境已有问题”。
3. 只修与本次目标直接相关的问题。
4. 修完后重新跑最小验证。

# 四、可复用模板

模板不是为了把每次输入都写得很长，而是为了在重要任务里少漏关键信息。实际使用时，只保留真正影响结果的部分即可。

## 1、普通任务

```text
目标：
把 [材料] 整理成 [交付物]，供 [读者/场景] 使用。

上下文：
- [资料 A] 是当前有效版本。
- [资料 B] 只作为背景，不要把已删除内容写进结论。

输出：
- 使用 [表格/清单/邮件/报告]。
- 控制在 [长度/详细程度]。
- 需要标出 [来源/不确定点/下一步]。

边界：
- 不要 [发送/发布/修改原文件/改动某些字段]。
- 缺失信息直接标注，不要猜。
```

## 2、代码任务

```text
目标：
修复 [具体行为]，期望结果是 [可观察行为]。

上下文：
- 相关路径可能在 [文件/目录]。
- 复现步骤是 [步骤]。
- 需要保持 [接口/数据结构/样式/兼容性] 不变。

执行：
先阅读并说明根因，再提出修改方案。
确认方向后再改文件。

验证：
运行 [测试/lint/构建/浏览器检查]。
如果验证失败，先区分是本次改动、环境问题还是历史问题。

交付：
最后说明改动文件、验证结果和剩余风险。
不要提交、推送或部署。
```

## 3、继续修正

第一条任务描述不需要完美。先看第一版结果，再用后续消息精确调整。

示例：

```text
把开头改得更直接。
保留现有证据，把建议部分移动到背景说明之前。
```

```text
刚才的方向对，但不要继续扩展功能。
只修复当前 bug，并保留现有接口。
完成后重新跑同一组验证。
```

后续消息可以补充资料、纠正方向、要求另一个版本，或调整详细程度。只要仍在同一个任务上下文中，就不必从头新建对话。
