# 二、Token

**Token 即词元，是模型处理文本时使用的基本单位**。文本在进入模型计算前，会先切分成 Token，再转换成 Token ID，最后转换成向量表示。

## 1、Tokenizer：文本 → Token

Tokenizer 是负责处理文本切分的组件。它按照一套与模型配套的规则，把输入文本拆成若干个 Token。

Tokenizer 的主要职责是完成“文本 → Token 序列”，并不负责生成回答。

例如，当向模型提问：

```Plain Text
解释一下什么是 Rust 所有权？
```

经过 Tokenizer 处理后，可能得到这样的 Token 序列：

```Plain Text
解释 | 一下 | 什么 | 是 | Rust | 所有权 | ?
```

这里的竖线只是为了展示切分边界，并不是输入文本中的内容。切分完成后，Token 还要经过后续的数字化和向量化，才能交给 Transformer 进行计算。

再例如，英文单词 `unbelievable` 在某种 Tokenizer 中可能被拆成：

```text
un | believable
```

## 2、Token 不等于一个字或一个单词

切分的 Token 的大小不是固定的。它可能是一个汉字、一个词、一个英文单词的一部分，也可能是标点或其他文本片段，具体取决于模型使用的 Tokenizer。

同一段文本使用不同的 Tokenizer，得到的切分结果和 Token 数量也可能不同。需要准确计数时，应使用目标模型配套的计数工具。

## 3、Token → Token ID

Token 只是文本处理过程中的中间结果，还不能直接作为 Transformer 的计算输入。模型只认识数字，需要把 Token 数字化和向量化，才能交给 Transformer 进行计算。

模型内部不会直接处理 `"解释"`、`"Rust"` 这些字符串。

**Tokenizer 会查自己的词表 Vocabulary，把每个 Token 映射成一个整数 ID**。

比如假设：

| Token | Token ID |
|-|-|
| 解释 | 18234 |
| 一下 | 7361 |
| 什么 | 4210 |
| 是 | 318 |
| Rust | 45231 |
| 所有权 | 29184 |
| ? | 30 |

于是：

```Plain Text
解释 | 一下 | 什么 | 是 | Rust | 所有权 | ?
```

变成：

```Plain Text
18234, 7361, 4210, 318, 45231, 29184, 30
```

记住，真正送进模型计算的不是文字，而是数字。



## 4、Token ID → Embedding 向量

整数 ID 仍然不能直接拿来做语言理解。

例如：

```Plain Text
Rust = 45231
所有权 = 29184
```

这里的 `45231` 并不意味着 `"Rust"` 比 `"所有权"` 大，也没有任何语义。

它只是一个**编号**。

模型会通过一个很大的 **Embedding Table（嵌入矩阵）**，根据 ID 查出对应的向量。

例如，为了方便理解，假设每个 Token 只用 4 维向量表示：

```Plain Text
解释   → [ 0.21, -0.73,  0.14,  0.51 ]
一下   → [ 0.08, -0.22,  0.81, -0.13 ]
什么   → [-0.41,  0.64,  0.18,  0.37 ]
是     → [ 0.13,  0.27, -0.49,  0.72 ]
Rust   → [ 0.78, -0.11,  0.46,  0.32 ]
所有权 → [ 0.62,  0.44, -0.28,  0.57 ]
?      → [-0.19,  0.33,  0.07, -0.52 ]
```

> 实际上现代 LLM 的向量可能有几千维，而不是 4 维。

输入就变成了一个矩阵。

但此时还不够，模型必须知道谁在前，谁在后。因为：

```Plain Text
Rust 所有权
```

和：

```Plain Text
所有权 Rust
```

顺序不同，含义也不同。

所以模型还需要加入**位置信息（Position Information）。**概念上可以理解成：

```Plain Text
解释   + 第1个位置
一下   + 第2个位置
什么   + 第3个位置
是     + 第4个位置
Rust   + 第5个位置
所有权 + 第6个位置
?      + 第7个位置
```

现代模型通常不会简单地给每个 Token 加一个「位置编号向量」，很多模型会采用 **RoPE（Rotary Position Embedding）** 等机制，把位置信息融入 Attention 计算。

## 5、进入 Transformer 计算

此时真正进入 Transformer 的，已经不是文字，也不是 Token ID，而是一组数字向量。

Transformer 会结合前面所有 Token 的信息，对这些数字进行大量计算。

最终得到的仍然是一组数字，也就是说模型内部不会突然变回中文或英文。



## 6、模型预测的是下一个 Token ID

假设模型词表一共有 100,000 个 Token。

那么 Transformer 计算完成后，会给这 100,000 个 Token 分别产生一个分数。

概念上可能是：

```Plain Text
Token ID 10     → 1.2
Token ID 20     → 3.8
Token ID 30     → 0.7
Token ID 31     → 2.4
...
Token ID 99999  → 0.3
```

然后把这些分数转换成概率。

例如：

```Plain Text
Token ID 10 → 5%
Token ID 20 → 20%
Token ID 30 → 2%
...
```



Transformer 会结合前面所有 Token 的信息，判断“接下来最可能出现什么”。

例如当前输入是：

```Plain Text
解释 | 一下 | 什么 | 是 | Rust | 所有权 | ?
```

模型经过计算后，不会一次性直接生成完整答案，而是先预测**下一个 Token**。

模型根据这些概率选择下一个 Token ID。

假设最终选择：

```Plain Text
Token ID 20
```

模型内部此时得到的仍然只是 20，而不是 `"在"`。



## 7、Token ID 解码成文字

Tokenizer 的词表里有 Token 和 Token ID 的对应关系。

例如：

```Plain Text
20 → "在"
```

因此系统可以把模型生成的：

```Plain Text
Token ID 20
```

解码成人类看到的：

```Plain Text
在
```

所以：

```Plain Text
模型真正生成：20
人类最终看到：在
```



## 8、生成的 Token ID 加入上下文

这一步是理解 LLM 逐个生成的关键。

最开始的问题对应的 Token ID 是：

```Plain Text
18234, 7361, 4210, 318, 45231, 29184, 30
```

模型第一次预测得到：

```Plain Text
20
```

那么下一轮的上下文就变成：

```Plain Text
18234, 7361, 4210, 318, 45231, 29184, 30, 20
```

模型再基于这整个序列预测下一个 Token ID。

例如下一次预测：

```Plain Text
45231
```

那么序列继续变成：

```Plain Text
18234, 7361, 4210, 318, 45231, 29184, 30, 20, 45231
```

再预测下一个。

如此反复。

## 9、模型怎么知道什么时候停止

在生成完整内容之后，模型继续预测出了一个特殊的结束 Token，系统收到这个 Token 后才停止生成。

最后，模型就可能生成这样的回答：

```Plain Text
在 Rust 中，所有权是一种内存管理机制。
```

# 三、Context Window

Context Window 即上下文窗口，指模型一次计算时最多能够处理的 Token 范围。

它首先是模型本身的一项能力限制。至于这个窗口里具体装什么内容，则通常由 ChatGPT、Claude Code 等 Agent 来组织。

简单理解，Context Window 决定了模型当前能够“看到多少内容”。它不是永久记忆，模型每次生成回答时，主要依据当前请求中携带的上下文进行计算。

## 1、模型本身：Context Window 是容量上限

对于 LLM 来说，Context Window 可以简单理解成：

> 模型一次最多能同时处理多少 Token

例如假设某个模型支持：

```Plain Text
Context Window = 256K Tokens
```

表示这一次模型计算能够使用的上下文总量存在一个上限，即 256K。



## 2、Agent/应用：负责往 Context Window 中放内容

像 ChatGPT、Claude Code 这样的 Agent，会先收集当前任务需要的信息，再组织成上下文交给模型。

Agent 可能放入以下内容：

| Context 来源 | 例子 | 作用 |
|-|-|-|
| System / Developer 指令 | System Prompt、Agent 工作规则 | 规定模型如何工作、遵守什么规则 |
| 项目级指令 | CLAUDE.md、AGENTS.md | 提供当前项目的规范和要求 |
| 历史对话 | 前面的 User / Assistant 消息 | 保持多轮对话的连续性 |
| 当前 User Prompt | 用户当前提出的问题 | 告诉模型当前要完成什么 |
| 任务相关资料 | 代码、README、文档、图片内容 | 给模型提供完成任务所需的信息 |
| Tool 返回结果 | 搜索结果、终端输出、文件检索结果、数据库结果 | 补充模型原本不知道的外部信息 |

## 3、接近上限时怎么处理

当上下文接近限制时，需要减少一次请求携带的 Token；如果超过限制，模型就无法完整处理全部内容。常见处理方式有以下三种。

### （1）截断旧内容

删除较早的消息，只保留最近的内容。

这种方式简单直接，但可能丢失早期的重要信息。

### （2）压缩上下文

将较长的历史对话总结成较短的摘要，用摘要替代原始内容。

摘要通常保留已完成工作、重要决定和当前任务状态，从而减少上下文占用，相对来说不会丢失太多的重要信息。

### （3）按需检索

大量资料保留在外部，需要时只取相关片段。

> 如果请求超过允许的容量，系统可能拒绝请求，或由应用先截断、压缩内容。不能假设模型会自动、完整地处理所有超限资料。

## 4、上下文窗口越大越好吗？

Context Window 不是越大越好，更大的 Context Window 可以读取更多代码、处理更长文档、保留更多历史，但也可能带来额外成本、延迟和注意力分散问题。

| 方面 | 可能的好处 | 可能的代价 |
|-|-|-|
| 内容容量 | 可以放入更多代码、文档和历史 | 信息过多时，关键内容可能被无关内容淹没 |
| 成本 | 可以在一次请求中处理更多内容 | 输入 Token 增加，费用可能上升 |
| 速度 | 可以减少拆分任务的次数 | 输入越长，计算量和响应延迟可能增加 |
