# 一、概述

`Ponytail` 是一套面向 Coding Agent 的插件与 Skill 集合，目标是让 Agent 在编写代码前先理解需求，阅读相关代码并追踪真实运行路径，然后选择能够满足需求的最简单方案。

它不是代码生成框架，也不会替代测试、代码审查或架构设计。它更像一位讨厌无效复杂度的资深工程师，会在 Agent 准备增加代码时不断追问：

> 这段代码真的需要存在吗？

Ponytail 主要用于减少以下问题：

- 项目中已经存在相同能力，Agent 却重新实现一遍
- 标准库或平台本身可以完成，Agent 却引入第三方依赖
- 当前只有一个使用场景，却提前设计通用接口和扩展层
- 需求只要求一项改动，Agent 却顺手增加配置、缓存和抽象
- 修复 Bug 时只给单个调用点打补丁，没有定位共同根因

它的核心原则不是“代码越少越好”，而是：

> 只编写当前任务真正需要的代码，同时不压缩安全、校验、错误处理、可访问性和防止数据丢失的必要逻辑。

Ponytail 会按照一条固定顺序选择实现方案，并在找到第一个可靠方案后停止继续增加复杂度。开始选择方案之前，它仍要求 Agent 阅读相关代码并追踪真实流程。

例如，需要增加日期输入时，Agent 不应该直接安装日期组件库，而应先判断：

1. 项目是否已经存在日期组件。
2. 浏览器原生 `<input type="date">` 是否满足需求。
3. 已安装依赖中是否已有可用能力。
4. 只有前面的方案都不满足明确需求时，才编写最小自定义实现。

# 二、安装

Ponytail 的 Claude Code 和 Codex 插件会运行 Node.js 生命周期钩子，因此需要保证 `node` 位于非交互 Shell 的 `PATH` 中。

可以先检查：

```
node --version
```

如果 Node.js 不在该环境的 `PATH` 中，Skill 本身仍可能可用，但自动模式激活和持续规则注入不会正常工作。

## 1、在 Claude Code 中安装

在 Claude Code 中分别发送下面两条命令：

```
/plugin marketplace add DietrichGebert/ponytail
```

```
/plugin install ponytail@ponytail
```

两条命令必须分开发送。

安装完成后，新建一个会话，使 Ponytail 的 Skill 和 Hook 进入新的上下文。

Ponytail 使用 Hook 完成以下工作：

- 保存当前 Ponytail 模式。
- 向 Agent 注入对应规则。
- 用户切换模式时更新状态。
- 创建子代理时传递相同规则。

# 三、工作原理

## 1、规则不是只在点命令时才生效

Ponytail 具有 6 个 Skill 和一份钩子配置。其运行链如下：

```text
新任务开始
  → SessionStart 钩子读取默认模式
  → 写入当前模式状态
  → 注入与该模式对应的 Ponytail 规则
  → Agent 按最小实现阶梯工作

用户切换模式
  → UserPromptSubmit 钩子更新状态

Agent 创建子代理
  → SubagentStart 钩子读取状态
  → 把同一规则注入子代理
```

因此，它既有显式调用方式，也有“当前会话一直有效”的行为。Codex 中可用 `@` 调用对应 Skill：

| 调用 | 用途 |
|---|---|
| `@ponytail lite` / `full` / `ultra` / `off` | 切换强度或关闭。 |
| `@ponytail-review` | 只审查当前改动中的过度设计，给出可删除/可替换项，不自动修改。 |
| `@ponytail-audit` | 扫描整个仓库，按优先级找冗余抽象、重复实现和不必要依赖。 |
| `@ponytail-debt` | 汇总用 `ponytail:` 标记的、已知但暂不解决的简化边界。 |
| `@ponytail-gain` | 查看项目附带的基准结果。 |
| `@ponytail-help` | 查看命令速查。 |

## 2、三种工作强度

| 强度 | 行为 | 适合场景 |
|---|---|---|
| `lite` | 正常实现需求，同时指出更轻的替代方案，由用户决定。 | 需求已明确且团队偏保守。 |
| `full` | 强制执行实现阶梯，优先原生能力和最短正确改动。 | 日常功能、修复和重构；默认推荐。 |
| `ultra` | 极端强调 YAGNI，先删再加，并直接质疑复杂需求。 | 原型、明显膨胀的需求或代码清理。 |

强度控制的是“允许多少实现复杂度”，不是质量标准。无论哪个强度，Ponytail 都要求：先跟踪真实流程；修 Bug 时修共同根因而不是只补一个调用点；不要删掉安全、可访问性、输入校验或防数据丢失的错误处理。

## 3、何谓“最小正确”

最小不等于最少字符。一个没有路径遍历校验的六行文件服务函数，比带校验的十行版本短，却不正确。Ponytail 的规则把这些不可删内容列为底线：

- **信任边界**：外部输入进入系统时必须验证。
- **安全与数据完整性**：不能为了少写代码跳过权限、转义、事务或防丢数据的处理。
- **可访问性基础**：不能用自定义 UI 替代已具备键盘和语义支持的原生控件后却不补齐能力。
- **最小验证**：分支、循环、解析、金额或安全路径等非平凡逻辑，至少留下一个可运行的断言或小测试；真正的一行简单改动不必强行搭测试框架。

若当前简单方案确实有已知上限，应明确留下可搜索的注释，例如：

```python
# ponytail: 当前为全局锁；吞吐成为瓶颈后改为按账户加锁。
with global_lock:
    update_balance(account_id)
```

这不是“偷偷欠债”，而是记录为什么现在够用，以及何时该升级。

# 四、实践指南：把它应用到自己的项目

## 1、先选对任务

Ponytail 最适合以下场景：

- Agent 容易顺手新增依赖、组件层、配置项或“以后可能用到”的扩展点。
- 旧项目有大量包装层、单实现接口、手写工具函数，想先得到一份删除清单。
- 想用原生 HTML、CSS、数据库约束或标准库替代自建实现。
- 修复 Bug 时，希望 Agent 先查所有调用点并定位共享根因。

不应把它当成“所有项目都要极简”的命令。以下情况先把需求明确写进任务或项目规则：

- 设计系统、兼容性、审计、性能或领域规范明确要求自定义实现。
- 正在建设会被多处复用的公共能力，且已有真实的第二个使用者。
- 团队需要完整设计说明、迁移方案或回滚预案；这些是交付要求，不是应删的“废话”。

## 2、推荐的落地流程

1. **先小范围试用**：选一个有过度实现风险、但影响可控的任务，启动 `full` 模式。
2. **把不可妥协条件写明**：例如“必须兼容 Safari 版本 X”“保留现有 API”“补集成测试”。Ponytail 会把明确要求视为不能省略的约束。
3. **让 Agent 先读再选阶梯**：可直接说：“先追踪这个功能的真实调用流程，再给出能满足需求的最高层方案；不要新增依赖。”
4. **实现后单独执行 `@ponytail-review`**：它只找复杂度，正常代码审查仍要继续覆盖正确性、安全与性能。
5. **保留最小验证并量化收益**：运行原有测试、构建或 smoke test（冒烟测试：验证主路径能启动和工作的一次轻量检查）；比较改动行数、依赖数与维护成本，而不是只看代码短不短。

## 3、一个完整示例：给筛选页增加日期条件

需求是“用户能按日期筛选记录”。不要一开始就要求 Agent 造日期组件，先这样下达任务：

```text
@ponytail full
先追踪筛选参数从页面到接口的路径。日期输入优先复用项目已有能力；
如果没有，优先原生能力。保留 URL 参数同步和现有校验，不新增依赖。
```

Agent 应按以下顺序判断：

1. 项目是否已有筛选栏或日期字段组件？有则复用。
2. 浏览器原生日期输入是否满足设计和目标浏览器？满足时使用它。
3. 后端是否已能处理 ISO 日期参数？能则只接入现有参数解析。
4. 只有原生控件无法满足明确体验要求时，才评估已安装日期库或最小新实现。

可能得到的最小前端改动是：

```html
<label>
  日期
  <input type="date" name="date" />
</label>
```

然后用已有的筛选提交逻辑把 `date` 写入 URL。若这个方案无法满足时区、范围选择或既定设计系统，应把原因和替代方案说清，而不是为了“极简”硬上。

## 4、验收清单

- 是否先理解了真实调用流程，还是只在表层文件做了最短改动？
- 是否优先复用了项目、标准库、平台和已安装依赖？
- 是否新增了没有第二个真实使用者的抽象、配置或依赖？
- 是否保留了安全、错误处理、可访问性和用户明确指定的行为？
- 非平凡逻辑是否有一个能失败的最小检查？
- 已知简化是否用 `ponytail:` 写清边界和升级时机？

# 五、如何看待它的基准结果

项目提供了可复现的 Agent 基准：在固定的 FastAPI + React 开源仓库中，让同一 Claude Code Agent 分别以无 Skill、Ponytail、只压缩表达的对照 Skill、以及简短 YAGNI 提示完成任务，并按 `git diff` 的新增行数计量。项目报告 Ponytail 在 12 个“容易过度实现”的功能任务上平均少 54% 代码，且在其 20 次安全测试中均通过。

这些数字适合作为“值得试用”的证据，不是对任何团队的保证：实验只使用 Haiku 4.5、每种任务运行 4 次，安全测试是有限的确定性用例，且部分前端任务波动很大。更可靠的做法是把它当作一条团队假设，在自己的仓库用相同验收标准做小规模对照。

项目的完整测试依赖 Python 的 `pandas` 来校验 CSV 场景；复现测试前应安装该依赖。仓库也提供了规则副本校验与多平台代理/钩子测试，说明其重点不仅是提示词文本，也包括跨 Agent 的一致注入。

# 六、小结

把 Ponytail 用好，不是要求 Agent “少写一点”，而是给它一套稳定的取舍顺序：**先理解，再复用；能不做就不做；必须做时只做最小正确版本；底线能力绝不压缩。**

若你的主要痛点是流程混乱，先结合 [[AI/notes/常用Skill和插件汇总/3、Superpowers|Superpowers]] 或 [[5、Matt Pocock Skills|Matt Pocock Skills]] 建立需求和验证纪律；若主要痛点是“每个小需求都被 Agent 做成一个小框架”，就从 Ponytail 的 `full` 模式和一次 `@ponytail-review` 开始。
