# 一、概述

`Superpowers` 是一套面向 Coding Agent 的工程工作流 Skill 集合。它不替代 `Claude Code`、`Codex`、`Cursor` 这类 Agent，也不会让模型本身变聪明；它的作用是把开发过程管起来：

- 写代码前先澄清需求
- 实现前先写计划
- 改代码时优先用测试约束行为
- 完成前必须验证
- 重要改动要审查
- 分支收尾时让用户决定合并、推送、保留还是丢弃

可以把它理解成：给 Coding Agent 加上一套“软件工程纪律”。

> [!summary] 核心判断
> Superpowers 解决的不是“模型不会写代码”，而是“模型太容易跳过需求、计划、测试和验收”。

它主要避免四类问题：

- **过早编码**：需求还没说清，Agent 已经开始搭架构。
- **上下文漂移**：长会话里越做越偏，后面忘了最初目标。
- **验证不足**：代码看起来对，但没有跑过测试或构建。
- **交付混乱**：最后才讨论提交、推送、合并和清理。

# 三、它是怎么生效的

Superpowers 的 Skill 不是“菜单里点一下才执行的命令”。正常情况下，Agent 在回答、澄清、写计划或改代码前，会先检查当前任务有没有适用技能；如果有，就读取对应 Skill 的当前说明，再按里面的步骤执行。

也就是说，用户可以显式点名某个 Skill，但日常使用更像这样：

```text
用户提出任务
→ Agent 判断任务类型
→ 匹配适用 Skill
→ 读取 Skill 说明
→ 按流程澄清、计划、实现、验证或审查
```

例如你说“给项目加一个登录功能”，它不应该立刻写代码，而应先进入需求澄清；如果你说“这个测试为什么失败”，它应该先进入系统化调试。

# 四、标准功能开发流程

完整功能开发大致可以理解成这条线：

```text
需求澄清 → 编写施工计划 → 确认是否需要隔离工作区
→ 执行计划 → 测试优先开发 → 代码审查 → 验证与分支收尾
```

![[assets/Superpowers-端到端工程工作流.png|600]]

这条线不是死板的七个按钮。小任务可以轻一点；复杂任务才需要完整流程。

## 1、需求澄清：`brainstorming`

新增功能、组件、行为修改等创造性工作，会先触发 `brainstorming`。

它的关键规则是：**设计没得到用户确认前，不写实现代码。**

通常会做这些事：

1. 先读项目文件、文档和最近提交。
2. 每次只问一个关键问题。
3. 给出 2～3 个方案和取舍。
4. 把设计保存成文档。
5. 请用户确认保存后的设计文档。

这里有两次确认：

- 聊天中确认方向：目标、范围、方案是否对。
- 文档保存后再确认：写下来的内容有没有漏掉、改偏或新增未确认内容。

如果方案画出来更清楚，Agent 可能询问是否打开可视化辅助窗口。它只是辅助澄清复杂流程或界面关系，不是每次都必须打开。

## 2、隔离工作区：`using-git-worktrees`

隔离工作区可以理解为“给这次任务单独开一张工作台”。Agent 在这张工作台上改代码、跑测试、提交本地记录，不容易和你当前手头改动混在一起。

它不是安装 Superpowers 时创建，也不是一进入聊天就创建。常见触发时机是：需求已经澄清，准备把计划落到代码之前。

通常不需要创建隔离工作区的情况：

- 只读调查
- 解释问题
- 单纯讨论方案
- 很小的文档或配置修改

可能需要创建隔离工作区的情况：

- 会改多个文件
- 要执行较长计划
- 当前工作区已有用户改动
- 后续可能需要提交、审查、推送或丢弃整组改动

如果真的创建了 Git worktree，通常可以通过下面命令看到额外工作区和分支：

```shell
git worktree list --porcelain
```

但如果平台本身提供隔离环境，就不一定表现为项目目录下的 `.worktrees/`。

## 3、施工计划：`writing-plans`

设计确认后，`writing-plans` 会把方案变成可执行计划。计划不是普通待办列表，而是写给“另一个 Agent 或工程师也能照着做”的施工说明。

一个好计划应该说明：

- 每个任务要改哪些文件或模块
- 每个任务的输入和输出是什么
- 哪些约束必须全程遵守
- 每个任务如何验证
- 哪些任务必须按顺序做

计划太大时，要拆；计划太碎时，也要合并。一个任务最好能用一句话验收，例如“接口返回新增字段且兼容旧调用”。

## 4、执行计划：分任务或顺序执行

执行计划通常有两种方式：

| 方式 | 含义 | 适合场景 |
|---|---|---|
| 子 Agent 分任务开发 | 每个任务交给新的 Agent，主会话负责统筹和审查 | 任务边界清楚、改动较大 |
| 同一会话顺序执行 | 当前会话按计划一步步做 | 任务较小、上下文强相关 |

子 Agent 分任务开发的重点不是并行，而是隔离上下文。上一个任务完成后，主会话会把提交、报告、审查结论和进度记录下来，再把下一个任务交给新的 Agent。

![[assets/Superpowers-子Agent分任务审查闭环.png|600]]

## 5、测试优先开发：`test-driven-development`

实现功能或修 Bug 时，Superpowers 会倾向使用测试优先开发：

1. 先写一个会失败的最小测试。
2. 再写最少代码让测试通过。
3. 最后在测试继续通过的前提下整理结构。

核心不是形式主义，而是防止“先写代码、后补测试”带来的假安全感。后补且立即通过的测试，不一定证明它能抓住原始问题。

## 6、审查与收尾

任务完成后，可以触发代码审查。审查重点不是“多派几个 Agent”，而是让审查者拿到准确材料：

- 设计或计划要求
- 当前代码差异
- 测试结果
- 实现报告

收到审查反馈后，`receiving-code-review` 会要求先验证反馈是否成立，再决定接受、修改或反驳。它适用于：

- PR 评论
- 同事审查意见
- 审查 Agent 返回的问题列表
- 用户粘贴的外部反馈

最后进入分支收尾。常见选项是：

| 选项 | 含义 |
|---|---|
| 本地合并 | 合并回基线并再次测试 |
| 推送并创建合并请求 | 保留分支，继续处理远端反馈 |
| 保留现状 | 用户稍后处理 |
| 丢弃 | 删除本次工作，需要明确确认 |

# 五、不同任务怎么走

## 1、从零开发功能

从零项目通常不会一开始就有 Git worktree。一般先创建项目、初始化 Git、形成初始提交。后续功能迭代才更适合使用隔离工作区。

从零项目最容易出的问题是 Agent 过早抽象。因此一开始要明确：

- 最小可用范围
- 暂时不做什么
- 如何验收

## 2、在已有项目中增加功能

已有项目更需要先读上下文：

- 项目规则
- 现有模块
- 测试方式
- 最近提交
- 相关接口

不要让一次流程吞下一个“大杂烩任务”。开始前先判断：这是 **一个目标的多个阶段**，还是 **多个目标混在一起**。

- 一个目标的多个阶段：可以写一份设计文档，在计划里拆任务。
- 多个目标混在一起：应拆成多次需求澄清，分别推进。

例如“给用户资料增加手机号字段”，可以一份设计文档拆成后端接口、前端表单、导入流程。  
但“重做登录、改账单、加权限系统、做历史数据迁移”更像多个目标，不适合塞进一次流程。

## 3、定位和修复 Bug

Bug 修复不应直接跳到补丁。更稳妥的路径是：

1. 复现问题。
2. 找正常样例和异常样例。
3. 一次验证一个假设。
4. 找到根因后写回归测试。
5. 做最小修复。
6. 重跑原始症状和相关测试。

如果修复只是根因定位和小补丁，通常不需要完整需求澄清；如果修复涉及新的交互、行为取舍或较大设计，再进入需求澄清。

## 4、多个独立故障的并行调查

`dispatching-parallel-agents` 用在并行调查，不是普通分任务开发。

适合并行的情况：

- 多个测试文件分别失败
- 初步判断根因互不相关
- 每个调查范围清楚
- 不会修改同一状态

不适合并行的情况：

- 第二项依赖第一项结果
- 多个 Agent 会改同一文件
- 共用同一个数据库、端口或测试夹具
- 还不知道多个症状是否来自同一根因

# 七、实战心得

## 1、先告诉 Agent 任务希望多重

Superpowers 会自动触发适用技能，但用户仍然可以表达流程偏好：

```text
请先判断这个任务适合轻流程、中流程还是完整流程。
如果只是机械修改，不要生成长计划；如果涉及多个模块，再说明为什么需要拆任务。
```

这不是绕开 Superpowers，而是告诉 Agent：这个任务值得付出多少流程成本。

## 2、把需求写成可验收的句子

起始请求最好包含五块信息：

```text
目标：给现有导入流程增加断点续传。
现状：导入失败后只能从头开始。
非目标：不改存储格式，不新增第三方服务。
约束：保持现有 API 兼容；失败后可安全重试。
验收：中断后重新启动，应从最后成功处理的位置继续；现有测试必须全过。
```

如果 Agent 询问仓库里已有答案的问题，直接提醒它先读项目规则、相关模块和最近提交。

## 3、确认计划时看有没有过载

计划写完后，不需要逐行审稿，但要重点看三件事：

- 是否把多个目标混进同一份设计。
- 是否有任务小到不值得单独审查。
- 是否有任务大到无法独立验收。

## 4、把 Git 权限说清楚

如果不希望 Agent 自动推送、创建合并请求、合并或删除分支，应在任务开始前说清楚。长期偏好可以写进项目规则文件。

```markdown
# Git 权限

- Agent 可以在隔离工作区的任务分支中创建本地提交。
- 未经明确确认，不得推送、创建合并请求、合并或删除分支。
- 每次外部写操作前报告目标分支和变更范围。
```

## 5、长任务要约定停靠点

不要只说“你自己一直做完”。可以提前约定：

```text
如果进入子 Agent 分任务开发：
- 每完成 2～3 个任务，在任务边界汇报一次。
- 到达约定时间或调用成本阈值时停下。
- 汇报时说明：完成了什么、测试结果、剩余风险、下一步建议。
```

# 八、推荐使用模板

```text
请使用 Superpowers 完成这个任务。

目标：<希望实现的用户价值>
现状：<相关模块、已有行为、已知问题>
约束：<兼容性、依赖、性能、安全、Git 权限>
非目标：<这次明确不做什么>
验收：<可观察、可执行的成功标准>

先读取项目规则和现有实现；不要重复询问仓库里已有答案。
在任何推送、合并请求、合并、部署或删除操作前获得我的明确确认。
```

如果只是 Bug，可以这样写：

```text
请先使用 systematic-debugging 复现并定位根因，不要先猜修复。
找到根因后，用失败的回归测试证明问题，再实现最小修复并运行完整验证。
```

# 九、总结

Superpowers 最有价值的地方，是把 Coding Agent 从“生成代码的对话框”拉回可审计的软件工程过程。

它适合复杂、有风险、需要验证的开发任务；不适合把所有小事都变成长流程。最好的使用方式，是让流程强度和任务风险匹配。
