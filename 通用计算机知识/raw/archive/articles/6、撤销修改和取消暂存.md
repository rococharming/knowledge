# 一、概述

在实际写代码时，经常会遇到这些情况：

- 文件写错了，想恢复到修改前
- 执行了`git add`，但发现暂时不想提交这个文件
- 暂存区放错了内容，想先拿出来
- 工作区和暂存区都有修改，需要分清楚撤销哪一部分

因此，在进行撤销操作前，需要先判断两个问题：

| 问题       | 说明                 |
| -------- | ------------------ |
| 撤销哪里     | 工作区，还是暂存区          |
| 是否保留文件内容 | 保留已经写的内容，还是直接丢弃修改 |

常用命令有两个：

| 命令                         | 作用             |
| -------------------------- | -------------- |
| `git restore --staged <file>` | 取消暂存，但保留工作区内容 |
| `git restore <file>`          | 丢弃工作区中的未暂存修改  |

# 二、git restore --staged

修改好某个文件`d.txt`，并执行了：

```shell
git add d.txt
```

此时`d.txt`的修改已经进入暂存区。

但现在发现修改有问题，或者说暂时不想提交该文件，但不想丢掉文件内容，可以执行：

```shell
git restore --staged d.txt
```

它的作用是：

| 区域  | 结果       |
| --- | -------- |
| 暂存区 | 取消暂存     |
| 工作区 | 文件内容继续保留 |

可以理解为：

> 我暂时不提交`d.txt`，但我写过的内容还要保留。

实际上，暂存之后执行`git status`，Git 也会贴心地给出一些我们可能想要的操作：

![[assets/Pasted image 20260611234623.png|400]]

因此，`git restore --staged`前期也不用强行记忆。

在取消暂存前，执行`git status -s`，可能看到：

```text
A  d.txt
```

表示暂存区相对最近一次提交有新增文件`d.txt`。

但此时执行：

```shell
git restore --staged d.txt
```

取消暂存之后，再执行`git status -s`得到：

```text
?? d.txt
```

表示此时`d.txt`已经变成未跟踪状态，说明它现在只在工作区保留。

> `git restore --staged`不会删除文件内容，它只是把修改从暂存区拿出来。

# 三、git restore

像前面这种新增的`d.txt`文件，它还没被纳入 Git 的版本控制：

![[assets/Pasted image 20260611235316.png|400]]

因此，如果想要废弃该文件，本质上就是要删除这个文件。

直接执行：

```shell
rm d.txt
```

那么当前工作区就变成了干净状态。

但如果`d.txt`已经纳入 Git 版本控制（暂存了或者之前提交过），现在继续修改`d.txt`，执行`git status`可以看到：

![[assets/Pasted image 20260611235622.png|500]]

此时暂存区和工作区同时有`d.txt`的修改，但对于工作区的修改，可以看到 Git 给出了两条提示：

- 要么`git add`暂存
- 要么`git restore`废弃修改

执行：

```shell
git restore d.txt
```

它的作用是把工作区中的`d.txt`恢复到暂存区或最近一次提交中的状态。

或者理解为：

> 丢弃`d.txt`当前还没有暂存的修改。

`git restore`操作需要谨慎，执行前建议先查看修改内容：

```shell
git diff d.txt
```

确认这些修改确实不需要，再执行`git restore d.txt`。

# 四、同时有已暂存和未暂存修改

假设对`d.txt`做了第一次修改，然后执行：

```shell
git add d.txt
```

此时第一次修改进入暂存区。

接着又继续修改`d.txt`，但没有再次执行`git add`。

这时执行：

```shell
git status -s
```

会看到：

```shell
MM d.txt
```

这表示同一个文件同时有两部分修改：

| 区域  | 内容        |
| --- | --------- |
| 暂存区 | 第一次修改     |
| 工作区 | 第二次未暂存修改  |

此时执行：

```shell
git restore d.txt
```

会丢弃工作区后续修改，但暂存区中的修改还保留。

也就是说，`MM d.txt`可能变成：

```shell
M  d.txt
```

如果执行：

```shell
git restore --staged d.txt
```

会取消暂存区中的修改，但工作区内容会保留。

也就是说，修改还在文件里，只是不再处于“准备提交”的状态。

# 五、常用场景对比

| 场景             | 命令                         | 是否保留文件内容 |
| -------------- | -------------------------- | -------- |
| 已经暂存，但暂时不想提交  | `git restore --staged d.txt` | 保留       |
| 修改错了，想丢弃未暂存修改 | `git restore d.txt`          | 不保留      |
| 一个文件显示`MM`，只想丢弃第二次修改 | `git restore d.txt`          | 保留暂存区修改  |
| 一个文件显示`MM`，只想取消暂存 | `git restore --staged d.txt` | 保留工作区内容  |
