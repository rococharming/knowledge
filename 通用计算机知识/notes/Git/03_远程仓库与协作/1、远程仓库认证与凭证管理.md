# 一、认证的作用

远程仓库认证用于证明“谁正在访问仓库”。克隆公共仓库通常不需要认证；但推送代码、读取私有仓库或执行受保护操作时，托管平台需要确认身份和权限。

Git 只负责发起网络连接，账号认证由 GitHub、GitLab、Gitee 等托管平台完成。常用方式有 HTTPS 搭配 Personal Access Token（PAT），以及 SSH 密钥。

| 方式 | 身份凭证 | 适合场景 |
|---|---|---|
| HTTPS + PAT | 访问令牌 | 临时环境、企业统一使用 HTTPS、需要细粒度令牌权限 |
| SSH | 本地私钥与平台公钥 | 个人开发机长期使用，日常拉取和推送方便 |

> [!warning] 不要把密码、PAT 或私钥提交到 Git 仓库，也不要把 PAT 直接写进远程 URL、脚本或笔记。泄露后应立即在平台撤销令牌或删除密钥。

# 二、HTTPS 与 PAT

HTTPS 远程地址兼容性好，常见形式如下：

```text
https://github.com/user/repo.git
```

## 1、使用令牌

多数托管平台不再允许通过 HTTPS Git 操作使用账户密码。Git 提示输入用户名和密码时，用户名仍填写平台用户名，密码位置填写 PAT。

PAT 是可单独设置权限和有效期的访问令牌。创建令牌时遵循最小权限原则：只授予当前仓库和当前操作所需的权限，并设置合理的过期时间。

## 2、管理凭证

macOS 常见的凭证助手是 `osxkeychain`。先检查当前配置：

```shell
git config --global credential.helper
```

若已配置为 `osxkeychain`，成功认证后的 HTTPS 凭证会由 macOS 钥匙串管理。不要使用 `credential.helper store` 保存长期凭证；它会将凭证以明文写入本地文件。

当令牌失效、账号切换或远程地址变更时，应从“钥匙串访问”中删除对应平台的 Internet Password，再在下一次 Git 操作时重新认证。

# 三、SSH 密钥

SSH 使用“私钥留在本机、公钥上传到平台”的方式认证。配置完成后，日常 `pull` 与 `push` 通常不需要重复输入 PAT。

## 1、生成密钥

查看已有公钥：

```shell
ls ~/.ssh/*.pub
```

没有可用密钥时，生成一对 Ed25519 密钥：

```shell
ssh-keygen -t ed25519 -C "zhangsan@example.com"
```

命令会询问保存位置和口令。默认保存位置通常是 `~/.ssh/id_ed25519`；为私钥设置口令可以降低设备遗失时的风险。

> [!warning] 只能将 `.pub` 结尾的公钥内容上传到 Git 托管平台。私钥（如 `id_ed25519`）不得复制、发送或上传。

## 2、上传并验证

复制公钥内容：

```shell
pbcopy < ~/.ssh/id_ed25519.pub
```

将其添加到托管平台账号的 SSH Keys 设置中。以 GitHub 为例，可以验证连接：

```shell
ssh -T git@github.com
```

首次连接时，SSH 会要求确认主机指纹。应核对托管平台官方公布的指纹后再接受，避免在不可信网络中盲目确认。

## 3、使用 SSH 地址

SSH 远程地址通常形如：

```text
git@github.com:user/repo.git
```

克隆时直接使用 SSH 地址：

```shell
git clone git@github.com:user/repo.git
```

已有仓库可查看并替换远程地址：

```shell
git remote -v
git remote set-url origin git@github.com:user/repo.git
```

# 四、选择与排错

## 1、如何选择

- **个人长期开发机**：优先 SSH，操作顺畅且不必频繁输入令牌。
- **临时设备或自动化环境**：按平台和组织规则选择 HTTPS + 短期 PAT，或使用专用的部署密钥、应用令牌。
- **公司项目**：优先遵守组织的 SSO、密钥轮换和访问控制要求，不要共用个人令牌。

同一仓库只需为 `origin` 选择一种地址；HTTPS 与 SSH 都能访问同一份仓库内容，区别只在认证与连接方式。

## 2、常见问题

| 现象 | 优先检查 |
|---|---|
| HTTPS 推送被拒绝 | PAT 是否过期、权限是否覆盖目标仓库、钥匙串是否缓存旧凭证 |
| SSH 显示 `Permission denied (publickey)` | 公钥是否已上传、私钥是否存在、SSH 是否选择了正确的密钥 |
| 仓库地址不符合预期 | `git remote -v` 查看 `origin` 的 fetch 与 push 地址 |
| 能读取但不能推送 | 当前账号是否拥有写权限，或目标分支是否受保护 |

排查 SSH 时可以增加详细日志：

```shell
ssh -vT git@github.com
```

日志中可能包含用户名和本地路径，但不应包含私钥内容；分享日志前仍应检查敏感信息。

# 五、小结

HTTPS 与 SSH 都是访问远程仓库的正常方式：HTTPS 适合令牌和组织策略驱动的场景，SSH 适合个人开发机的长期日常使用。无论选择哪种方式，都应最小化权限、保护私钥与令牌，并在异常时先检查远程地址和认证来源。
