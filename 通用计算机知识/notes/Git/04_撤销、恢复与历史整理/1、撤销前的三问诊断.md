# 一、诊断优先

Git 里的“撤销”不是一个命令能覆盖所有情况。真正危险的动作不是选错某个参数，而是在没看清改动位置和共享范围时就开始恢复。

每次恢复前先问三个问题：

```text
1. 改动在哪里？
2. 改动提交了吗？
3. 改动共享了吗？
```

同一句“我想撤销”，可能对应 working tree、index、commit、远程 PR、主线历史等完全不同的位置。先诊断，再选择 `restore`、`reset`、`revert` 或其他恢复路径。

# 二、改动位置

## 1、status

`git status -sb` 用来快速判断当前分支、工作区是否干净，以及改动位于 working tree 还是 index。

示例：

```shell
git status -sb
```

可能看到：

```text
## main...origin/main
 M README.md
```

这里的 ` M README.md` 表示：`README.md` 在 working tree 有未暂存修改。

常见短状态：

| 输出 | 含义 |
|---|---|
| ` M file.txt` | working tree 有未暂存修改 |
| `M  file.txt` | index 里有已暂存修改 |
| `MM file.txt` | index 和 working tree 都有修改 |
| `?? file.txt` | untracked，新文件还没被 Git 跟踪 |
| clean | working tree 和 index 都没有待处理变化 |

## 2、diff

`status` 告诉你哪里变了，`diff` 告诉你具体变了什么。

```shell
git diff
git diff --staged
```

| 命令 | 看什么 | 不改什么 |
|---|---|---|
| `git diff` | working tree 相对 index 的修改 | 不改文件、不改暂存区 |
| `git diff --staged` | index 相对 HEAD commit 的修改 | 不提交、不取消暂存 |

如果 `git diff` 有输出，而 `git diff --staged` 没输出，通常说明改动还只在 working tree，没有进入暂存区。

# 三、提交状态

## 1、最近历史

如果 `git status -sb` 显示 clean，但仍然想撤销刚才做过的事，改动可能已经进入提交历史。

查看最近提交：

```shell
git log --oneline --decorate --max-count=5
```

命令拆解：

| 部分 | 作用 |
|---|---|
| `git log` | 查看提交历史 |
| `--oneline` | 每个提交压成一行 |
| `--decorate` | 显示分支名、远程跟踪分支名等指针 |
| `--max-count=5` | 只显示最近 5 条，不删除历史 |

这个命令只观察历史，不修改文件、不移动分支。

## 2、提交内容

如果想看最近一次提交具体改了什么：

```shell
git show --stat --oneline HEAD
```

`git show` 也是观察命令。撤销前先看目标提交包含哪些文件和哪些改动，能避免把不相关内容一起撤掉。

# 四、共享风险

## 1、共享迹象

“共享”指别人或远程可能已经看见这个提交。常见迹象：

| 已共享迹象 | 含义 |
|---|---|
| 提交已经 push 到 GitHub | 远程分支上能看到 |
| 提交已经进入 PR | reviewer 可能基于它评论 |
| 提交已经合入 `main` | 主线历史已经包含 |

越接近“别人已经看见”，越不要优先使用会改写历史的命令。

## 2、ahead 与 behind

查看本地分支和 upstream 的关系：

```shell
git status -sb
```

常见输出：

| 输出 | 含义 |
|---|---|
| `[ahead 1]` | 本地有 1 个远程还没有的提交，通常还没共享到这个 upstream |
| 没有 ahead/behind | 本地分支和 upstream 对齐 |
| `[behind 1]` | 远程有本地还没拿到的提交 |

需要注意：`ahead 1` 只能说明当前 upstream 还没有这个提交，不等于“世界上绝对没人见过”。在练习仓库里，它可以作为判断共享风险的主要信号；真实团队里还要考虑是否已经发过 patch、截图、PR 或其他副本。

# 五、选择方向

三问之后，再决定恢复方向：

| 三问结果 | 风险 | 后续方向 |
|---|---|---|
| 未提交、未暂存 | 较低 | restore working tree |
| 未提交、已暂存 | 较低 | unstage 或 restore staged |
| 已提交、未 push | 中等 | amend 或 reset 可能适合 |
| 已 push、PR 中 | 较高 | 优先追加提交或 revert |
| 已合入 `main` | 高 | 优先 revert，避免改写共享历史 |

这张表不是让人马上背命令，而是帮助判断风险边界：改动越本地、越未提交，恢复选择越多；改动越共享，越应使用保留历史的方式。

# 六、练习流程

## 1、制造未暂存修改

在本地仓库确认当前状态：

```shell
cd path/to/practice-repo
git status -sb
```

期待当前在 `main`，工作区 clean。

然后打开 `README.md`，追加一行：

```text
Recovery diagnosis practice line.
```

## 2、观察状态

运行：

```shell
git status -sb
git diff
git diff --staged
git log --oneline --decorate --max-count=5
```

逐项判断：

| 问题 | 期待判断 |
|---|---|
| 改动在哪里 | working tree |
| 是否 staged | 没有 |
| 是否 committed | 没有 |
| 是否 shared | 没有 |
| 下一步可能使用的恢复方向 | restore working tree |

练习结束时保留这行未暂存修改，不提交、不 push。这个状态可以继续用于后续练习 `git restore`。

# 七、常见误区

## 1、先猜命令

`restore`、`reset`、`revert` 都和“撤销”有关，但作用对象完全不同。先用 `status`、`diff`、`log` 判断位置，再选命令。

## 2、clean 就以为没有风险

`status clean` 只说明 working tree 和 index 没有待处理变化。它不说明最近提交一定正确；如果要撤销的是已提交内容，应继续看 `git log` 和 `git show`。

## 3、忽略共享边界

已 push、已进入 PR、已合入 `main` 的提交不应随便用 `reset` 改写历史。共享历史里的撤销更适合用 `revert` 或追加修复提交。

撤销前的三问是整个恢复主题的入口。后续无论选择 `restore`、`reset`、`revert`、`commit --amend` 还是 `reflog`，都应先用这三个问题区分“本地可重写”和“协作应保留历史”的边界。
