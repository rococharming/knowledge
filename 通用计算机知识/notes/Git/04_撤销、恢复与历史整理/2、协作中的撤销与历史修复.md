# 一、共享历史的边界

提交一旦已经推送、被他人拉取，或进入受保护分支，就不再只是个人的本地历史。此时直接用 `git reset` 改写分支指针，会让其他人的提交基线与远程历史不一致，增加同步和恢复成本。

| 历史状态 | 优先选择 | 原因 |
|---|---|---|
| 仅自己本地可见 | `git reset` | 可按需要保留或丢弃改动 |
| 已推送或可能被他人使用 | `git revert` | 追加反向提交，不改写已有历史 |

本地 `reset` 和 `reflog` 的机制见 [[1、撤销提交与恢复历史|重置本地提交与恢复历史]]。

# 二、使用 `git revert`

## 1、工作方式

`git revert` 不删除旧提交，而是新建一次反向提交来抵消目标提交的影响。

```text
A → B → C
          ↓ revert B
A → B → C → D
```

`B` 仍保留在历史中，`D` 记录了“反做 B”的明确意图，因此团队成员可以正常拉取、审查和追踪这次修复。

## 2、基本流程

先确认工作区干净并检查目标提交：

```shell
git status
git show <commit>
git revert <commit>
```

如果接受 Git 自动生成的提交信息：

```shell
git revert --no-edit <commit>
```

完成后检查结果：

```shell
git show HEAD
git log --oneline -5
```

# 三、冲突与限制

## 1、处理冲突

后续提交若已修改同一位置，反做旧提交可能产生冲突。解决冲突后继续：

```shell
git status
git add <file>
git revert --continue
```

放弃这次撤销：

```shell
git revert --abort
```

## 2、理解结果

> [!important] `revert` 不等于回到旧提交之前
> `git revert B` 只尝试反做 `B` 引入的改动；后续提交 `C` 中与 `B` 无关的内容仍会保留。

因此，执行前应先用 `git show <commit>` 了解目标提交的范围。对于已经合并的分支或复杂依赖关系，应先与团队确认撤销范围，再提交反向修改。

# 四、操作选择

## 1、快速判断

| 场景 | 优先操作 |
|---|---|
| 最近一次本地提交要补内容 | `git commit --amend` |
| 本地提交想撤回并重新整理 | `git reset --soft` 或 `--mixed` |
| 本地误操作后寻找旧位置 | `git reflog` |
| 已共享提交要撤销影响 | `git revert <commit>` |

## 2、协作原则

共享分支优先保持历史可追溯：用新提交表达修复，而不是让已发布的提交“消失”。如果确实必须重写远程历史，应遵守团队约定、确认没有其他人基于旧历史工作，并使用受控的强制推送流程；这属于例外，不应作为日常撤销手段。
