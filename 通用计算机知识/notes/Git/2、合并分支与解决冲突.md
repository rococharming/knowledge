# 一、合并解决什么问题

分支开发完成后，需要把任务分支上的提交整合回目标分支。`git merge` 的作用就是把另一个分支的历史带入当前分支。

典型流程是：

```shell
git switch main
git merge feature-login
```

这表示：当前站在 `main` 上，把 `feature-login` 的成果合进来。

> [!important] 先确认当前位置
> `git merge <branch>` 合并的是“别的分支”到“当前分支”。执行前先用 `git branch --show-current` 或 `git status` 确认自己站在哪个分支上。

# 二、两类常见合并结果

## 1、Fast-forward 合并

如果目标分支没有新的分叉提交，Git 可以直接把目标分支指针向前移动：

```text
A --- B        main
       \
        C --- D feature-login
```

站在 `main` 执行：

```shell
git merge feature-login
```

结果是：

```text
A --- B --- C --- D
                  ^
                 main
                 feature-login
```

这种情况没有额外合并提交，历史保持一条直线。

## 2、三方合并

如果两个分支都各自有新提交，Git 会以共同祖先、当前分支、被合并分支为基础进行三方合并：

```text
      C --- D feature-login
     /
A --- B --- E main
```

站在 `main` 执行合并后，若没有冲突，Git 会创建一个 merge commit：

```text
      C --- D
     /       \
A --- B --- E --- M main
```

`M` 有两个父提交，表示两条历史在这里汇合。

# 三、什么时候会冲突

冲突通常发生在两个分支修改了同一文件的同一区域，而 Git 无法自动判断应该保留哪一边。

示例：

```text
main:          title = "Git 学习路线"
feature-login: title = "Git 分支学习路线"
```

Git 可能在文件里写入冲突标记：

```text
<<<<<<< HEAD
title = "Git 学习路线"
=======
title = "Git 分支学习路线"
>>>>>>> feature-login
```

其中：

- `HEAD` 一侧表示当前分支的内容。
- 分隔线下面表示被合并分支的内容。
- 最终文件不能保留这些冲突标记，必须人工改成想要的结果。

# 四、解决冲突的基本流程

## 1、开始合并

```shell
git switch main
git merge feature-login
```

如果出现冲突，先看 Git 告诉你哪些文件需要处理：

```shell
git status
```

## 2、编辑冲突文件

打开冲突文件，删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记，并把内容改成最终想保留的版本。

处理时不要机械选择“上面”或“下面”。正确问题是：合并后的主线应该表达什么业务结果？

## 3、标记冲突已解决

```shell
git add <file>
```

这里的 `git add` 不是单纯“添加文件”，而是告诉 Git：这个文件的冲突已经解决，最终版本已经放入暂存区。

## 4、完成合并

```shell
git commit
```

大多数情况下，Git 会准备好默认合并提交信息。确认信息清楚后保存即可。

如果所有冲突文件都已 `git add`，也可以：

```shell
git merge --continue
```

# 五、放弃本次合并

如果发现合并方向错了、冲突太复杂，或需要先补测试，可以中止当前合并：

```shell
git merge --abort
```

它会尝试把仓库恢复到合并开始前的状态。中止前若又做了额外手工修改，应先确认这些修改是否需要另外保存。

# 六、合并前的好习惯

```shell
git status
git log --oneline --graph --decorate --all -10
```

- `git status` 确认工作区是否干净。
- `git log --graph` 先看两个分支是否已经分叉。
- 合并到共享分支前，先确认测试和代码审查要求。

# 七、命令速查

| 场景 | 命令 |
|---|---|
| 合并分支到当前分支 | `git merge <branch>` |
| 查看冲突文件 | `git status` |
| 标记冲突已解决 | `git add <file>` |
| 完成合并 | `git merge --continue` |
| 放弃本次合并 | `git merge --abort` |
| 看分支图 | `git log --oneline --graph --decorate --all` |

# 八、小结

合并前先确认“我站在哪个分支上”。冲突不是错误，而是 Git 要你对同一段内容的最终结果做判断。解决冲突的闭环是：查看冲突、编辑成最终版本、`git add` 标记已解决、继续合并。

后续如果希望合并历史更线性，可以继续学习变基与整理提交历史。
