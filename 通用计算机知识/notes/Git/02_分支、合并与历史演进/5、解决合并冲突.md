# 一、合并冲突

合并冲突不是 Git 崩了，而是 Git 不敢替你决定同一块内容最终应该长什么样。它会暂停合并，把需要人工判断的文件标出来，等你编辑出最终结果。

![[assets/merge-conflict-markers-generated.png|600]]

前面的 [[4、三方合并与 merge commit|三方合并]] 示例是自动完成的，因为两边改的是不同文件。冲突练习要单独制造：让两个分支都修改同一个文件的同一块内容。

# 二、冲突场景

Git 能自动处理很多合并，但遇到同一块内容被两边同时改写时，它无法判断最终应该选哪边。

## 1、常见类型

| 场景 | 说明 |
|---|---|
| 两边改同一行 | Git 不知道选当前分支还是目标分支 |
| 一边删除一边修改 | Git 不知道保留还是删除 |
| 同一块文本被两边重写 | Git 不知道最终顺序和内容 |

冲突的本质是“需要人做产品判断或语义判断”，不是“仓库坏了”。

## 2、练习起点

冲突练习的起点状态是：当前分支为 `main`，最新提交是合并 `feature/note-title` 的 merge commit，工作区 clean。

接下来先在 `main` 上创建 `conflict-note.txt`，再从上一个提交开出 `feature/conflict-title`，在 feature 分支上创建同名文件。这样两边都会新增同一个路径，但内容不同，合并时会触发冲突。

# 三、冲突标记

冲突文件里会出现 Git 写入的标记。标记用于展示两边内容，不应该保留到最终提交里。

## 1、标记结构

```text
<<<<<<< HEAD
Title from main
=======
Title from feature/conflict-title
>>>>>>> feature/conflict-title
```

| 标记 | 含义 |
|---|---|
| `<<<<<<< HEAD` | 当前分支，也叫 `ours` |
| `=======` | 两边内容的分隔线 |
| `>>>>>>> feature/conflict-title` | 被合进来的分支，也叫 `theirs` |

如果站在 `main` 上运行：

```shell
git merge feature/conflict-title
```

那么 `HEAD` / `ours` 是 `main`，`theirs` 是 `feature/conflict-title`。这和 [[4、三方合并与 merge commit|三方合并]] 里的 `ours` / `theirs` 站位规则一致。

## 2、最终内容

解决冲突不是一定选一边。可以保留当前分支内容，可以保留目标分支内容，也可以把两边重写成第三种更好的内容。

冲突内容可能是：

```text
<<<<<<< HEAD
Branch practice title: calm main version.
=======
Branch practice title: lively feature version.
>>>>>>> feature/conflict-title
```

可以解决成：

```text
Branch practice title: resolved version from both branches.
```

最终文件里不能再有：

```text
<<<<<<<
=======
>>>>>>>
```

# 四、状态阅读

冲突发生后，先看状态，再打开文件。不要急着反复运行 merge。

## 1、冲突输出

```shell
git merge feature/conflict-title
```

可能输出：

```text
Auto-merging conflict-note.txt
CONFLICT (add/add): Merge conflict in conflict-note.txt
Automatic merge failed; fix conflicts and then commit the result.
```

这表示 Git 已经进入合并过程，但 `conflict-note.txt` 需要人工解决。

## 2、简洁状态

```shell
git status -sb
```

可能看到：

```text
## main
AA conflict-note.txt
```

在这个练习里，两边都新增同名文件，所以状态可能是 `AA`。如果是两边都修改已有文件，常见状态会是 `UU`。

| 标记 | 说明 |
|---|---|
| `AA` | 两边都新增了同一路径，内容冲突 |
| `UU` | 两边都修改了同一路径，内容冲突 |
| 文件里有冲突标记 | 需要手动编辑 |
| 合并未完成 | 解决后还需要暂存并提交 |

# 五、解决流程

解决冲突有一条固定顺序：看状态，编辑文件，暂存解决结果，完成合并提交。

## 1、固定步骤

| 步骤 | 命令或动作 | 目的 |
|---|---|---|
| 1 | `git status -sb` | 确认哪些文件冲突 |
| 2 | 打开冲突文件 | 读懂 ours 和 theirs |
| 3 | 编辑成最终内容 | 删除所有冲突标记 |
| 4 | `git add conflict-note.txt` | 告诉 Git：这个文件解决好了 |
| 5 | `git commit` | 完成 merge commit |

这里的 `git add` 不只是“加入新文件”。在冲突解决阶段，它表示“这个冲突文件的最终结果已经确定”。

## 2、检查标记

提交前可以搜索冲突标记：

```shell
git diff --check
```

也可以直接在编辑器里搜索：

```text
<<<<<<<
```

如果冲突标记还在文件中，先继续编辑，不要提交。

# 六、放弃合并

如果还没有完成合并提交，可以撤回正在进行的 merge：

```shell
git merge --abort
```

它会尽量把仓库恢复到合并前状态。这个命令很适合练习冲突时作为安全出口；一旦已经完成合并提交，就要用其他历史修复方式处理。

# 七、本地练习

起点：继续使用 `practice-repo/`。完成自动三方合并示例后，应在 `main`，最新提交是合并 `feature/note-title` 的 merge commit，工作区 clean。

## 1、准备 main

```shell
cd /Users/songpengfei/Learn/Git/practice-repo
git status -sb
git log --oneline --decorate --graph --all --max-count=10
```

在 `main` 上新建 `conflict-note.txt`，内容写成：

```text
Branch practice title: calm main version.
```

提交：

```shell
git add conflict-note.txt
git commit -m "Add main conflict practice title"
```

## 2、准备 feature

从上一个提交开出冲突练习分支：

```shell
git switch -c feature/conflict-title HEAD~1
```

在 feature 分支上创建同名文件 `conflict-note.txt`，内容写成：

```text
Branch practice title: lively feature version.
```

提交：

```shell
git add conflict-note.txt
git commit -m "Add feature conflict practice title"
```

## 3、解决冲突

回到 `main` 并合并：

```shell
git switch main
git merge feature/conflict-title
```

看到冲突后，打开 `conflict-note.txt`，解决成：

```text
Branch practice title: resolved version from both branches.
```

完成合并：

```shell
git add conflict-note.txt
git commit
git log --oneline --decorate --graph --all --max-count=10
git status -sb
```

目标状态：

| 检查项 | 期待结果 |
|---|---|
| 当前分支 | `main` |
| 最新提交 | 解决冲突后的 merge commit |
| `conflict-note.txt` | 只有最终内容，没有冲突标记 |
| 工作区 | clean |

# 八、常见误区

## 1、提交冲突标记

不要把 `<<<<<<<`、`=======`、`>>>>>>>` 原样提交。它们只是 Git 暂时写给人的提示，不是业务内容。

## 2、误解 `git add`

冲突解决阶段的 `git add conflict-note.txt` 表示“这个文件已经解决”。它既更新暂存区，也让 Git 知道这个路径不再处于未解决状态。

## 3、只能选一边

最终内容不必等于 ours 或 theirs。真正要提交的是语义上正确、能让项目继续工作的版本。

# 九、小结

本篇最重要的一句话：

```text
冲突解决不是选命令，而是编辑出最终正确文件；git add 表示“这个冲突我已经解决好了”。
```
