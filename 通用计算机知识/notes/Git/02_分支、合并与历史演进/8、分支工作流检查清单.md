# 一、工作流

分支工作流不是固定背一串命令，而是在每次操作前先确认当前位置、工作区状态和历史图形，再选择 [[3、Fast-forward 合并|fast-forward]]、[[4、三方合并与 merge commit|三方合并]]、[[5、解决合并冲突|解决冲突]] 或 [[6、Rebase：把提交重放到新起点|rebase]]。

简单来说，分支操作的主线是：

```text
看状态 -> 看历史图 -> 判断关系 -> 选择动作 -> 再检查状态
```

![[assets/branch-workflow-loop-generated.png|600]]

## 1、观察优先

任何会移动分支指针或改写历史的操作，都先从两个问题开始：

- 当前在哪个分支？
- 工作区和暂存区是否干净？

示例：

```shell
git status -sb
git log --oneline --decorate --graph --all --max-count=12
```

`git status -sb` 用来确认站位和工作区状态；`git log --graph --all` 用来观察各个分支之间是同线、分叉，还是已经合回。

## 2、动作选择

观察之后再决定动作，能避免在错误分支上 merge、在脏工作区里切换分支，或者对已经共享的历史做 rebase。

| 场景 | 常见动作 | 判断重点 |
|---|---|---|
| 开始一个独立任务 | `git switch -c feature/name` | 当前起点是否正确 |
| `main` 只是落后于 feature | `git merge feature/name` | 是否能直接 fast-forward |
| 两条分支都前进过 | `git merge feature/name` 或 `git rebase main` | 历史是否已经共享 |
| 状态显示 `UU` | 编辑文件，`git add`，继续 | 最终文件内容是否正确 |

> 关键：`git merge x` 更新的是当前分支；`git rebase main` 重放的是当前分支上的提交。两个命令都不能脱离“我当前站在哪个分支”来理解。

# 二、图形判断

Git 历史图里最值得看的不是线条好不好看，而是分支指针、共同祖先和当前 `HEAD` 的位置。它们决定下一步该整合、整理，还是停下来处理冲突。

## 1、常见关系

| 图形关系 | 含义 | 常见动作 |
|---|---|---|
| 两个分支指向同一个 commit | 内容已经对齐 | 通常不需要合并 |
| `main` 落后于 feature，且没有额外提交 | 可以 fast-forward | 站在 `main` 上 merge feature |
| 双方都从共同祖先后前进 | 需要三方合并或 rebase | 共享历史选 merge，本地私有线可 rebase |
| 状态显示 `UU` | 文件仍有未解决冲突 | 编辑最终内容，删除冲突标记，`git add` |

这里的共同祖先，就是两条历史线分叉前最后一个共同 commit。[[4、三方合并与 merge commit|三方合并]] 会同时参考共同祖先、当前分支和待合入分支；[[6、Rebase：把提交重放到新起点|rebase]] 则把当前分支上的提交复制到新的起点之后。

## 2、示例历史

完成本地 rebase 分支收回后，练习仓库的关键历史可能类似：

```text
* df306c3 (HEAD -> main, feature/rebase-practice) Add second rebase practice line
* 758bd87 Add first rebase practice line
*   e1aaa33 Merge branch 'feature/conflict-title'
|\
| * bba5c8f (feature/conflict-title) Add feature conflict practice title
* | 295dae3 Add main conflict practice title
|/
*   148f5fb Merge branch 'feature/note-title'
```

这张图可以这样读：

| 片段 | 读法 |
|---|---|
| `HEAD -> main` | 当前站在 `main` |
| `main, feature/rebase-practice` | `feature/rebase-practice` 已经被收回到 `main` 上 |
| `Merge branch 'feature/conflict-title'` | 冲突解决后留下了一个 merge commit |
| `Merge branch 'feature/note-title'` | 分叉后的自动三方合并留下了一个 merge commit |

如果某个分支名和 `main` 出现在同一个提交旁边，说明这两个分支指针当前指向同一个 commit。这个状态常见于 feature 已经被 fast-forward 收回之后。

# 三、命令清单

命令清单的用法不是机械照抄，而是先判断自己处在哪类场景，再取相应命令。观察命令应该最常用，整合命令反而应该更谨慎。

## 1、观察

```shell
git status -sb
git branch
git log --oneline --decorate --graph --all
```

`git branch` 用来看本地分支列表和当前分支；`git log --decorate` 会把分支名、`HEAD` 等引用显示在提交旁边，方便理解 [[1、分支、refs 与 HEAD|refs 与 HEAD]] 的位置。

## 2、分支

```shell
git branch feature/name
git switch feature/name
git switch -c feature/name
```

`git branch feature/name` 只创建分支，不切换；`git switch feature/name` 切换到已有分支；`git switch -c feature/name` 创建并切换。分支创建后，提交移动的是当前分支指针，这一点与 [[2、创建与切换分支|创建与切换分支]] 的模型一致。

## 3、整合

```shell
git merge feature/name
git rebase main
git merge --abort
git rebase --abort
```

`merge` 更适合保留共享历史的真实分叉与合流；`rebase` 更适合整理尚未共享的本地私有线。两者的选择可以参考 [[7、选择 merge 还是 rebase|merge / rebase 选择]]：先问历史是否已经共享，再决定是否改写提交身份。

# 四、诊断顺序

遇到分支问题时，优先按固定顺序诊断。这样做的价值是把“我感觉应该执行某个命令”改成“我知道当前图形关系，所以选择这个动作”。

## 1、先看现状

示例：

```shell
git status -sb
git log --oneline --decorate --graph --all --max-count=12
```

然后依次确认：

| 问题 | 为什么重要 |
|---|---|
| 当前分支是谁 | merge 和 rebase 都受当前分支影响 |
| 工作区是否 clean | 脏工作区会让切换和整合更难判断 |
| 哪个分支是接收方 | merge 更新当前分支 |
| 这段历史是否已经共享 | 决定是否避免 rebase |
| 如果冲突，最终文件应该是什么 | 冲突解决靠编辑最终内容 |

## 2、再做收尾

动作完成后，再运行一次：

```shell
git status -sb
git log --oneline --decorate --graph --all --max-count=12
```

理想的收尾状态通常是：当前分支符合预期，工作区 clean，历史图能解释清楚。如果其中任何一项不清楚，先停下来读图，不要继续叠加新的操作。

# 五、常见误区

## 1、只记命令

分支问题通常不是缺命令，而是不知道当前图形关系。先看 `status` 和 `log --graph`，比直接试一个 merge 或 rebase 更可靠。

## 2、忘记站位

`git merge x` 是把 `x` 合进当前分支；`git rebase main` 是把当前分支重放到 `main` 后面。当前分支判断错了，命令语法正确也会得到错误结果。

## 3、默认 rebase

rebase 会生成新提交，提交号会变化。只要这段历史已经推送给别人、被别人基于它继续开发，默认就应该保留共享历史，优先考虑 merge。

# 六、本地检查

完成本地分支、合并、冲突和 rebase 的练习闭环后，可以用下面这组命令确认仓库状态：

```shell
cd /Users/songpengfei/Learn/Git/practice-repo
git status -sb
git branch
git log --oneline --decorate --graph --all --max-count=14
git show --no-patch --pretty=raw HEAD
git status -sb
```
