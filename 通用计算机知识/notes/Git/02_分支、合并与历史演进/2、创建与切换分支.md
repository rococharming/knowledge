# 一、任务分支

做一个新任务时，通常不直接在 `main` 上继续改，而是从合适的起点开出一条任务分支。这样可以把不同任务的提交分开，让后续合并、回滚和 review 都更清楚。

![[assets/create-switch-branch-generated.png|600]]

最小流程是：

```text
看状态 -> 回到合适起点 -> 确认 clean -> 创建并切换新分支 -> 提交
```

这套流程建立在 [[1、分支、refs 与 HEAD|分支、refs 与 HEAD]] 的模型上：新分支从当前 commit 长出来；之后提交会推动当前分支向前移动。

# 二、开分支前

开新分支前先确认两个问题：当前站在哪里，工作区是否干净。起点不清楚，后面的分支历史就容易乱。

## 1、看当前位置

```shell
git status -sb
```

输出示例：

```text
## main
```

这表示当前在 `main`，并且没有额外改动。`-sb` 可以理解为 short branch：用简洁格式同时显示当前分支和工作区状态。

## 2、回到起点

新任务通常从 `main` 或团队指定的基础分支开出：

```shell
git switch main
git status -sb
```

如果目标是从 `main` 开新任务，切回 `main` 后再确认一次状态。这个动作看起来啰嗦，但能避免“站错分支还继续往下做”的问题。

# 三、创建切换

`git switch -c` 是“创建并切换”的组合动作。日常开新任务分支时，它比先 `git branch` 再 `git switch` 更顺手。

## 1、组合命令

```shell
git switch -c feature/daily-summary
```

示例输出：

```text
Switched to a new branch 'feature/daily-summary'
```

拆开看：

| 部分 | 含义 |
|---|---|
| `git switch` | 切换分支 |
| `-c` | create，创建新分支 |
| `feature/daily-summary` | 新分支名 |

这条命令会从当前 commit 创建 `feature/daily-summary`，然后立刻把 `HEAD` 切过去。

## 2、等价写法

`git switch -c feature/daily-summary` 等价于下面两步：

```shell
git branch feature/daily-summary
git switch feature/daily-summary
```

区别在于：两步写法可以把“创建”和“切换”拆开观察；组合写法适合日常工作。

| 写法 | 适合场景 |
|---|---|
| `git branch name` + `git switch name` | 学习指针变化、调试起点 |
| `git switch -c name` | 已确认起点后快速开任务分支 |

# 四、clean 起点

Git 允许带着未提交改动切换分支，只要这些改动不会和目标分支冲突。但学习和日常协作中，先从 clean 状态开分支更稳。

## 1、clean 状态

clean 状态示例：

```text
## main
```

它表示当前在 `main`，并且 working tree 没有未提交改动。相关状态模型可回看 [[通用计算机知识/notes/Git/01_本地仓库与提交基础/3、工作区域与文件状态|工作区域与文件状态]]。

## 2、残留改动

如果看到：

```text
## main
 M daily-note.txt
```

说明 working tree 里还有未提交改动。此时不要急着开新分支，先判断这份改动属于哪里。

| 处理方式 | 适合情况 |
|---|---|
| 提交 | 改动已经完整，且属于当前任务 |
| 丢弃 | 改动是误操作或实验残留 |
| 暂存起来 | 想先切换任务，但暂时不提交 |
| 带进新分支 | 改动本来就属于即将创建的新任务 |

> [!warning] 起点会影响历史
> `git switch -c name` 从当前 commit 开分支。如果当前站错位置，新分支也会从错误位置长出来。

# 五、分支命名

分支名不需要复杂，但要表达任务目的。好的分支名让未来的自己一眼知道这条线在做什么。

## 1、常见前缀

| 类型 | 例子 | 适合场景 |
|---|---|---|
| `feature/...` | `feature/daily-summary` | 新功能或新内容 |
| `fix/...` | `fix/status-typo` | 修 bug 或修错误 |
| `docs/...` | `docs/branch-notes` | 文档改动 |
| `practice/...` | `practice/switch-c` | 本地练习和实验 |

团队项目里应优先遵循团队约定；个人学习仓库里，前缀只要稳定、清楚即可。

## 2、命名判断

| 分支名 | 问题 |
|---|---|
| `tmp` | 看不出目的 |
| `test2` | 看不出内容，也容易越用越乱 |
| `main-copy-final` | 暗示分支是副本，容易加深错误心智模型 |

更好的名字通常包含任务类型和目标对象，例如 `feature/daily-summary`、`fix/status-typo`、`docs/branch-notes`。

# 六、分支改名

本地分支名写错时，优先判断“提交位置是否正确”。如果分支指向的提交是对的，只是名字拼错，通常不需要删除再重建，直接重命名即可。

![[assets/branch-rename-local-generated.png|600]]

## 1、基本命令

把本地分支从旧名字改成新名字：

```shell
git branch -m recover/revert-partice recover/revert-practice
```

命令结构是：

```shell
git branch -m <旧分支名> <新分支名>
```

拆开看：

| 部分 | 含义 |
|---|---|
| `git branch` | 管理分支引用 |
| `-m` | move / rename，移动或重命名分支名 |
| `recover/revert-partice` | 旧分支名 |
| `recover/revert-practice` | 新分支名 |

`git branch -m` 改的是分支引用名，不是提交内容。它不会创建新提交，也不会把当前分支自动切到新名字上。

## 2、结果检查

改名前先看状态和候选分支：

```shell
git status -sb
git branch --list "recover/*"
```

可能看到：

```text
## main...origin/main
  recover/revert-partice
```

改名后再检查：

```shell
git branch --list "recover/*"
git status -sb
git log --oneline --decorate --all --max-count=4
```

重点不是记住提交哈希，而是确认三件事：

| 观察点 | 结论 |
|---|---|
| 新分支名出现在原提交旁边 | 分支仍指向原来的提交 |
| `HEAD -> main` 仍在原来的位置 | 当前 `main` 没有移动 |
| `git status -sb` 仍 clean | working tree 和 index 没有被改动 |

如果这个分支只是本地恢复分支，例如 [[通用计算机知识/notes/Git/04_撤销、恢复与历史整理/9、用 git reflog 找回 reset 前的位置|reflog 恢复分支]]，改名不会自动修改 GitHub。已经 push 到远程的分支改名，还会涉及远程分支删除/推送和 upstream 更新，属于远程协作问题。

> [!tip] 写错名字先改名
> 分支名拼错通常是命名问题，不是历史问题。只要分支指向的提交是对的，`git branch -m old new` 比删除再重建更直接，也更不容易忘记旧分支原来指向哪里。

# 七、本地练习

起点：继续使用 `practice-repo/`。已有 `feature/note-title` 分支提交后，通常当前仍在该分支，并且工作区 clean。

## 1、准备起点

```shell
cd path/to/practice-repo
git status -sb
git log --oneline --decorate --graph --all --max-count=8
```

回到 `main`：

```shell
git switch main
git status -sb
```

检查点：

| 检查项 | 期待结果 |
|---|---|
| 当前分支 | `main` |
| 工作区 | clean |
| 已有分支 | `feature/note-title` 仍然存在 |

## 2、开新分支

```shell
git switch -c feature/daily-summary
git status -sb
```

在 `daily-note.txt` 末尾新增：

```text
Started a daily summary branch.
```

提交：

```shell
git status -s
git diff
git add daily-note.txt
git commit -m "Start daily summary branch"
git log --oneline --decorate --graph --all --max-count=8
git status -sb
```

目标状态：

| 检查项 | 期待结果 |
|---|---|
| 当前分支 | `feature/daily-summary` |
| 最新提交 | `Start daily summary branch` |
| `feature/daily-summary` | 比 `main` 多一个提交 |
| `feature/note-title` | 保留 `Add branch practice note` 提交 |
| 工作区 | clean |

# 八、小结

本篇最重要的一句话：

```text
开新任务分支前先确认状态和起点；git switch -c 负责创建并切换，git branch -m 负责只改分支名。
```

掌握创建与切换分支后，就可以继续理解 fast-forward：有些合并看起来像“合并”，本质上只是把分支名向前移动。
