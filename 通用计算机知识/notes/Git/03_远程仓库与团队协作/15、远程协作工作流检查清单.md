# 一、协作模型

远程协作不是背一串命令，而是先回答一组固定问题：我在哪个分支、工作区是否干净、远程是谁、本地是否已经看见远程最新状态、接下来是 pull、push、开 PR、同步 PR、合并还是清理。

核心模型是：

```text
先确认我在哪
再确认远程是谁
先 fetch 观察
再选择 pull / push / PR / sync / merge / cleanup
```

这个模型的重点是“先观察，再操作”。`fetch`、`status`、`remote -v` 负责建立判断依据；`pull`、`push`、PR、merge、cleanup 才是改变状态的动作。

# 二、最小循环

## 1、阶段顺序

一次完整的远程协作通常可以压成六个阶段：

| 阶段 | 动作 | 目的 |
|---|---|---|
| 同步视野 | `git fetch origin` | 让本地知道 GitHub 最新状态 |
| 确认站位 | `git status -sb` | 知道当前分支、工作区和 ahead/behind |
| 开任务分支 | `git switch -c feature/name` | 不直接在 `main` 上做协作改动 |
| 提交并推送 | `git add`、`git commit`、`git push -u origin feature/name` | 把 feature 分支发布到 GitHub |
| 维护 PR | review、更新提交、同步 base、处理冲突 | 让改动可讨论、可检查、可合并 |
| 合并和清理 | Merge PR、同步本地 `main`、清理分支 | 让主线前进并收拾分支入口 |

这不是必须机械执行的仪式，而是一条可靠的判断路线。任何远程协作问题，都可以先回到“我在哪、远程在哪、谁领先、要改变谁”这几个问题。

## 2、观察问题

| 问题 | 常用观察 |
|---|---|
| 我在哪个分支 | `git status -sb` |
| 工作区干净吗 | `git status -sb` |
| 远程地址是谁 | `git remote -v` |
| 本地知道 GitHub 最新状态吗 | `git fetch origin` |
| 本地和远程谁领先 | `git status -sb`、`git rev-list --left-right --count ...` |
| 这次改动应直接 push，还是开 PR | 看当前分支、团队规则、是否需要 review |
| PR 是否落后 main | 比较 `origin/main...origin/feature/...` |
| PR 能不能合并 | 看 base/compare、Files changed、Checks、Conversation |

# 三、命令清单

## 1、远程地址

查看远程仓库配置：

```shell
git remote -v
```

常见输出：

```text
origin  git@github.com:YOUR-USER/git-practice-remote.git (fetch)
origin  git@github.com:YOUR-USER/git-practice-remote.git (push)
```

读法：

| 部分 | 含义 |
|---|---|
| `origin` | 本地给远程仓库起的名字 |
| `(fetch)` | 从哪里拿回远程状态 |
| `(push)` | 往哪里推送本地提交 |

`git remote -v` 只查看配置，不会修改文件、分支或远程仓库。

## 2、远程视野

只想拿回远程最新状态，先用：

```shell
git fetch origin
```

它更新本地的 `origin/main`、`origin/feature/...` 这类远程跟踪分支，不会自动改当前分支文件。

判断原则：

```text
先 fetch，再比较；不要拿旧地图判断新远程。
```

## 3、快进更新

本地 `main` 只是落后远程 `main` 时，用：

```shell
git pull --ff-only
```

它会先 fetch，再尝试让当前分支快进到 upstream。`--ff-only` 的边界是：只有能 fast-forward 才继续；如果历史分叉，就停下来。

学习阶段用它同步本地 `main`，因为它不会悄悄制造 merge commit。

## 4、推送分支

第一次推送 feature 分支：

```shell
git push -u origin feature/pr-practice
```

`push` 把本地分支提交发送到远程。`-u` 是 `--set-upstream`，会建立本地分支和远程分支的默认对应关系。

第一次推送后，后续通常可以直接：

```shell
git push
```

边界：`push` 会改变 GitHub 上的远程分支。运行前先确认当前分支和要发送的提交内容。

## 5、PR 落后判断

判断 PR 分支是否落后 `main`：

```shell
git rev-list --left-right --count origin/main...origin/feature/pr-practice
```

读法：

| 位置 | 含义 |
|---|---|
| 左边数字 | `origin/main` 独有提交数 |
| 右边数字 | `origin/feature/pr-practice` 独有提交数 |

合并 PR 前通常希望左边是 `0`。如果左边大于 `0`，先同步 PR 分支。

## 6、清理远程跟踪记录

远程分支删除后，清理本地过期的 `origin/*` 记录：

```shell
git fetch --prune origin
git branch -r
```

`--prune` 清理本地过期的远程跟踪分支记录；`git branch -r` 用来查看本地保存的远程跟踪分支。

边界：它不会删除 GitHub 上的真实分支，也不会删除本地普通分支。

# 四、状态判断

## 1、终端状态

常见状态可以这样读：

| 看到的状态 | 含义 | 下一步 |
|---|---|---|
| `## main...origin/main` | 本地 `main` 和远程 `main` 对齐 | 可以从 `main` 开新分支 |
| `## main...origin/main [behind 1]` | 本地 `main` 落后远程 | `git pull --ff-only` |
| `## feature/x...origin/feature/x [ahead 1]` | 本地 feature 有远程还没有的提交 | 检查后 `git push` |
| `non-fast-forward` push 被拒绝 | 远程已有本地没有的提交 | `git fetch origin`，看图，再整合 |
| PR 左边数字大于 0 | PR 分支缺少 `main` 的新提交 | Update branch、本地 merge，或处理冲突 |
| PR 有 failing Checks | 自动检查失败 | 先读失败信息，不要 merge |
| PR merged 后本地 `main` behind | GitHub 主线已前进，本地还没跟上 | 切到 `main` 后 `git pull --ff-only` |
| 删除远程分支后仍看到 `origin/feature/x` | 本地远程跟踪记录没刷新 | `git fetch --prune origin` |

这些状态不是错误本身，它们是在告诉你下一步该观察什么、改变谁。

## 2、PR 页面

合并前至少看这些区域：

| 页面区域 | 检查什么 |
|---|---|
| base / compare | base 是 `main`，compare 是 feature 分支 |
| Conversation | 描述、评论、review 是否处理完 |
| Commits | 提交是否属于这次任务 |
| Files changed | 最终 diff 是否正确 |
| Checks | 通过、失败、等待，还是没有配置 |
| merge box | 是否有 conflicts、out-of-date 或其他阻塞 |

看到 `This branch can be merged` 只代表技术上可合并，不代表应该合并。真正的判断还要看 diff、讨论、Checks 和同步状态。

# 五、练习流程

## 1、本地盘点

完成一次 PR 合并和分支清理后，在本地运行：

```shell
cd path/to/practice-repo
git status -sb
git remote -v
git branch
git branch -r
git log --oneline --decorate --graph --all --max-count=16
```

逐项确认：

1. 当前分支是谁。
2. 工作区是否 clean。
3. `origin` 的 fetch 和 push URL 是否都指向 GitHub 练习仓库。
4. 本地还剩哪些分支。
5. 远程跟踪分支还剩哪些。
6. 最近历史里能否看到 PR 合并进入 `main`。

## 2、场景复盘

用自己的话回答这些问题：

1. 什么时候应该用 `git fetch origin`？
2. 什么时候应该用 `git pull --ff-only`？
3. 什么时候应该用 `git push`？
4. 什么时候应该开 Pull Request？
5. PR 合并前至少要看哪些页面区域？
6. PR 是否落后 `main` 要看哪个命令、哪个数字？
7. PR merged 后，本地 `main` 如何跟上？
8. 远程 feature 分支删除后，本地 `origin/feature/...` 如何刷新？

目标状态是：不看单篇笔记，也能按场景说出下一步该观察什么、运行什么、为什么。

# 六、常见误区

## 1、pull 万能化

`pull` 会改变当前分支。只想拿回远程状态时，先用 `fetch`。

## 2、忽略 push 风险

`push` 会改变 GitHub 上的分支。运行前确认当前分支、提交内容和远程目标。

## 3、只看 PR 按钮

按钮只是最后入口。合并前要看方向、diff、讨论和 Checks。

## 4、未合并就清理

只清理已 merged 的 PR 分支。未合并分支可能还有未进入主线的工作。

## 5、不拆新命令

后续遇到新命令，也按这个方式拆开：它改什么、不改什么、输出怎么看、风险在哪里。

远程协作的主线是：先 `fetch` 建立新视野，再根据分支状态选择 `pull`、`push`、PR、同步、合并或清理。这个清单可以和 [[14、清理已合并的 PR 分支|分支清理]]、[[12、PR 合并前检查清单|合并前检查]]、[[2、Fetch 与远程跟踪分支|fetch]] 一起复习。
