# 一、同步冲突

PR 分支同步冲突，是指在本地 PR 分支上执行 `git merge origin/main` 时，Git 发现 `origin/main` 和当前 PR 分支改到了同一块内容，无法自动决定最终文件应该长什么样。

核心顺序是：

```text
PR 分支和 origin/main 改到同一块内容
merge origin/main 时 Git 暂停
编辑最终内容
git add 标记已解决
git commit 完成合并
git push 更新 PR
```

冲突不是远程仓库损坏，也不是 PR 无法继续。它只表示 Git 把内容选择权交给了人：最终文件可以采用 PR 分支版本、`origin/main` 版本，也可以整理成第三种更清楚的版本。

# 二、冲突标记

## 1、ours 与 theirs

当站在 `feature/pr-practice` 上运行：

```shell
git merge origin/main
```

冲突文件里可能出现：

```text
<<<<<<< HEAD
Feature version from the PR branch.
=======
Main version from origin/main.
>>>>>>> origin/main
```

读法如下：

| 标记 | 含义 |
|---|---|
| `<<<<<<< HEAD` | 当前分支，也就是 `feature/pr-practice`，通常叫 ours |
| `=======` | 两边内容的分隔线 |
| `>>>>>>> origin/main` | 被合进来的远程 base，也就是 `origin/main`，通常叫 theirs |

ours/theirs 不是“谁对谁错”，只表示合并方向。在这个场景里，当前分支是 PR 分支，被合进来的是远程 base。

## 2、最终文件

冲突标记只是 Git 留下的临时提示，最终提交进去的文件不能保留这些标记。

![[assets/merge-conflict-markers-generated.png|700]]

最终文件可以选一边，也可以保留两边，或者重新写成更准确的内容。关键是最终文件里不能再出现：

```text
<<<<<<<
=======
>>>>>>>
```

# 三、状态读取

## 1、冲突输出

执行 [[10、本地 merge 同步 PR 分支|本地 merge 同步 PR 分支]] 时，可能看到：

```shell
git merge origin/main
```

```text
Auto-merging main-sync-note.md
CONFLICT (content): Merge conflict in main-sync-note.md
Automatic merge failed; fix conflicts and then commit the result.
```

这表示 Git 已经开始合并，但在 `main-sync-note.md` 里遇到了内容冲突。

## 2、状态缩写

继续查看状态：

```shell
git status -sb
```

可能看到：

```text
## feature/pr-practice...origin/feature/pr-practice
UU main-sync-note.md
```

`UU` 表示这个文件处在 unmerged 状态：两边都改了，Git 等你处理。此时不要 `push`，也不要把冲突标记原样提交。

# 四、解决顺序

## 1、固定步骤

PR 同步冲突的解决顺序和普通本地合并冲突一致，只是最后还要把结果推回远程 PR 分支：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | `git status -sb` | 找到冲突文件 |
| 2 | 打开冲突文件 | 读懂 PR 分支版本和 `origin/main` 版本 |
| 3 | 编辑成最终内容 | 删除所有冲突标记 |
| 4 | `git add main-sync-note.md` | 告诉 Git：这个文件已经解决 |
| 5 | `git commit` | 完成本地 merge commit |
| 6 | `git push` | 更新 GitHub 上的 PR 分支 |

`git add` 在这里不只是“加入暂存区”，还表示“这个冲突文件已经处理完，可以继续完成合并”。

## 2、放弃合并

如果还没有完成 merge commit，可以撤回正在进行的 merge：

```shell
git merge --abort
```

这通常会回到执行 `git merge origin/main` 之前的状态。发现自己处理乱了，先用这个安全出口，不要把未完成的冲突状态继续往后推。

# 五、练习流程

## 1、确认共享文件

练习同步冲突时，需要选择一个 `origin/main` 和 PR 分支都已经包含的文件。`main-sync-note.md` 适合作为示例，因为它已经进入过 PR 分支。

先在本地确认当前分支和文件内容：

```shell
cd path/to/practice-repo
git status -sb
cat main-sync-note.md
```

期待当前分支是：

```text
## feature/pr-practice...origin/feature/pr-practice
```

文件内容可能类似：

```text
Main moved forward for PR sync practice.
```

如果 `main-sync-note.md` 不存在，说明当前仓库状态和这个练习前提不一致，应先回到 PR 分支同步状态确认流程，不要继续制造冲突。

## 2、修改 main

在 GitHub 页面操作：

1. 打开仓库主页。
2. 切换到 `main` 分支。
3. 打开 `main-sync-note.md`。
4. 把同一行改成：

```text
Main sync note edited on GitHub main.
```

5. 提交到 `main`。

这一步模拟 base 分支上出现了新的主线改动。

## 3、修改 PR 分支

回到本地，确认仍在 `feature/pr-practice`：

```shell
git status -sb
```

把 `main-sync-note.md` 的同一行改成：

```text
Main sync note edited on local PR branch.
```

提交到本地 PR 分支：

```shell
git add main-sync-note.md
git commit -m "Update main sync note locally"
```

先不要 push。此时本地 PR 分支和远程 `main` 分别改了同一行，已经具备冲突条件。

## 4、触发冲突

先刷新远程跟踪分支，再把 `origin/main` 合进当前 PR 分支：

```shell
git fetch origin
git rev-list --left-right --count origin/main...origin/feature/pr-practice
git merge origin/main
```

期待看到类似：

```text
CONFLICT (content): Merge conflict in main-sync-note.md
Automatic merge failed; fix conflicts and then commit the result.
```

查看状态：

```shell
git status -sb
```

期待看到：

```text
UU main-sync-note.md
```

## 5、解决冲突

打开 `main-sync-note.md`，把最终内容改成：

```text
Main sync note resolved with both main and PR context.
```

确认文件里没有 `<<<<<<<`、`=======`、`>>>>>>>` 后，标记冲突已解决并完成 merge commit：

```shell
git add main-sync-note.md
git commit
```

如果编辑器打开默认 merge message，保存退出即可。默认信息通常已经能表达“把 `origin/main` 合进当前分支”的事实。

## 6、推送确认

冲突解决提交只在本地存在，还需要推送到远程 PR 分支：

```shell
git push
```

最后刷新并确认：

```shell
git fetch origin
git rev-list --left-right --count origin/main...origin/feature/pr-practice
git status -sb
```

期待状态是：

| 检查项 | 期待结果 |
|---|---|
| 当前分支 | `feature/pr-practice` |
| 工作区 | clean |
| 冲突标记 | 文件里没有 `<<<<<<<`、`=======`、`>>>>>>>` |
| 左边数字 | 回到 `0` |
| 远程 PR 分支 | 包含解决冲突后的 merge commit |
| PR 状态 | 仍然 open，尚未 merge |

# 六、常见误区

## 1、冲突中 push

冲突还没解决时，`push` 不能替你解决问题。需要先编辑最终文件、`git add`、`git commit`，完成本地 merge commit 后再推送。

## 2、只删标记

删除冲突标记只是格式要求。真正重要的是最终文件内容是否正确、是否保留了该保留的信息、是否删除了不该保留的信息。

## 3、认错分支

`origin/main` 是本地保存的远程跟踪分支，不是当前工作分支。这个场景通常是站在 `feature/pr-practice` 上，把 `origin/main` 合进来。

## 4、忘记推送

冲突在本地解决后，GitHub PR 页面还不知道。只有 `git push` 成功后，远程 PR 分支和 PR 页面才会更新。

PR 同步冲突的核心不是找一个跳过冲突的命令，而是写出最终正确文件。处理完成后，再结合 [[6、PR Review 与检查状态|PR 检查状态]] 确认 Files changed、Checks 和合并提示。
