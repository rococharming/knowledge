# 一、合并判断

点击 `Merge pull request` 前，需要确认的不只是绿色按钮是否可点。绿色按钮通常只表示 GitHub 当前允许某种合并动作，不等于这次改动一定正确、风险一定可接受。

合并前判断可以压缩成六件事：

```text
确认方向
确认差异
确认提交
确认讨论
确认检查状态
确认 PR 分支已同步
```

只有这些信息都说得通，才进入真正合并。否则应该先同步、修正、回应评论或重新检查差异。

# 二、页面检查

## 1、基础方向

PR 的方向决定“谁合进谁”。合并前先看 base 和 compare：

```text
base: main
compare: feature/pr-practice
```

`base` 是目标分支，通常是 `main`；`compare` 是来源分支，也就是 PR 分支。方向反了时，不要继续合并。

## 2、页面标签

GitHub PR 页面可以按这个顺序检查：

| 页面位置 | 要看什么 | 如果不满足 |
|---|---|---|
| 标题和描述 | PR 声称要解决什么问题 | 先补充说明或重新确认目标 |
| base / compare | `base: main`，`compare: feature/pr-practice` | 停下确认方向 |
| Commits | 提交都属于同一个任务 | 先解释或整理无关提交 |
| Files changed | 最终会进入 `main` 的差异 | 先处理无关文件或错误改动 |
| Conversation | 没有未处理评论或 review 问题 | 先回应或更新 PR |
| Checks / merge box | 检查、冲突、同步状态都明确 | 根据提示修复或等待 |

这个顺序能避免“看到按钮能点就直接合并”的误操作。

# 三、本地诊断

## 1、同步状态

合并前先刷新远程状态：

```shell
git fetch origin
```

确认当前分支和工作区：

```shell
git status -sb
```

理想状态是站在 PR 分支上，而且工作区干净：

```text
## feature/pr-practice...origin/feature/pr-practice
```

再判断 PR 分支是否还落后于 `main`：

```shell
git rev-list --left-right --count origin/main...origin/feature/pr-practice
```

常见结果如下：

| 输出 | 含义 | 合并前判断 |
|---|---|---|
| `0 3` | `origin/main` 没有 PR 分支缺少的提交；PR 分支有自己的提交 | 同步状态通常可以 |
| `1 3` | `origin/main` 有 1 个 PR 分支还没包含的提交 | 先同步 PR 分支 |
| `0 0` | 两边没有差异 | 这个 PR 可能已经没有可合并内容 |

如果左边大于 0，先不要合并 PR。可以回到 [[9、同步 PR 分支|GitHub Update branch]]、[[10、本地 merge 同步 PR 分支|本地 merge 同步]] 或 [[11、解决 PR 分支同步冲突|同步冲突处理]]。

## 2、提交列表

数字能快速判断同步状态，提交列表能帮你确认没有混入奇怪内容：

```shell
git log --oneline --left-right origin/main...origin/feature/pr-practice
```

读法如下：

| 符号 | 含义 | 合并前判断 |
|---|---|---|
| `<` | `origin/main` 独有提交 | 如果出现，说明 PR 可能还没同步 base |
| `>` | `origin/feature/pr-practice` 独有提交 | 应该都能解释为 PR 改动、同步或冲突解决 |

示例：

```text
> a1b2c3d Resolve PR sync conflict
> e4f5g6h Update main sync note locally
> h7i8j9k Merge remote-tracking branch 'origin/main'
```

这些 `>` 开头的提交都属于 PR 分支侧。它们可以是功能改动、review 更新、同步 base 的 merge commit，或冲突解决 commit。若出现完全无关的提交，应先停下读历史。

# 四、检查状态

## 1、Checks

Checks 表示仓库配置的自动检查结果，可能来自 CI、测试、lint、代码扫描或分支保护规则。

| 页面状态 | 含义 | 动作 |
|---|---|---|
| Passing | 自动检查通过 | 继续做人工判断 |
| Failing | 自动检查失败 | 先读失败信息，不要合并 |
| Pending | 检查还在跑 | 等它完成 |
| 没有检查 | 仓库没有配置 CI 或规则 | 记录这个事实，用人工检查补上 |

练习仓库没有 CI 很正常。没有 Checks 不等于失败，但也不等于通过；它只表示缺少机器验证。

## 2、Merge box

GitHub 页面底部的 merge box 可能出现这些提示：

| 提示 | 常见含义 |
|---|---|
| `This branch has conflicts` | 有冲突，需要先解决 |
| `This branch is out-of-date` | PR 分支落后于 base |
| `All checks have passed` | 自动检查通过 |
| `Some checks were not successful` | 有检查失败 |
| `This branch can be merged` | 当前没有技术阻塞 |

> `This branch can be merged` 不是“应该 merge”，只是“技术上可以 merge”。最终仍要看差异是否正确、讨论是否处理、检查是否可信。

# 五、练习流程

## 1、本地检查

在本地仓库运行：

```shell
cd path/to/practice-repo
git fetch origin
git status -sb
git rev-list --left-right --count origin/main...origin/feature/pr-practice
git log --oneline --left-right origin/main...origin/feature/pr-practice
```

期待结果：

| 检查项 | 期待结果 |
|---|---|
| 工作区 | clean |
| 当前分支 | `feature/pr-practice` |
| 左边数字 | `0` |
| `<` 开头提交 | 没有，或能解释为什么存在 |
| `>` 开头提交 | 都属于 PR 改动、同步或冲突解决 |

如果左边数字大于 0，先同步 PR 分支；如果出现无法解释的 `>` 提交，先查看提交内容，不要继续合并。

## 2、页面检查

打开 GitHub PR 页面，逐项确认：

1. base 是 `main`。
2. compare 是 `feature/pr-practice`。
3. Commits 里没有无法解释的提交。
4. Files changed 里的文件都属于当前改动目标。
5. Conversation 没有未处理评论。
6. Checks 是通过、失败、等待，还是没有配置。
7. merge box 没有 conflicts 或 out-of-date 提示。

确认完成后，应该能清楚说出：

```text
这个 PR 当前是否已经准备好合并，以及理由是什么。
```

如果仍有不确定项，先处理不确定项。合并前检查的价值就在于把“看起来能点”变成“知道为什么能合并”。

# 六、常见误区

## 1、只看按钮

按钮可点不代表改动正确。合并前必须看 Files changed，因为那里展示的是最终会进入 base 的差异。

## 2、误读 Checks

Checks 没有结果只是缺少自动验证，不是失败，也不是通过。真实项目里，应根据团队规则决定是否必须补充自动检查或人工验证。

## 3、忽略落后状态

`git rev-list --left-right --count origin/main...origin/feature/pr-practice` 左边大于 0，表示 PR 分支缺少 `origin/main` 的提交。先同步，再判断。

## 4、误判同步提交

如果前面用 merge 方式同步过 PR 分支，出现同步 merge commit 是正常的。关键是能解释它为什么存在，以及它是否只服务于同步 base。

合并前检查的目标不是追求页面上所有东西都“看起来绿色”，而是确认方向、差异、提交、讨论、Checks 和同步状态都能被解释。这个判断衔接 [[6、PR Review 与检查状态|PR Review]]，也为真正合并 PR 做最后准备。
