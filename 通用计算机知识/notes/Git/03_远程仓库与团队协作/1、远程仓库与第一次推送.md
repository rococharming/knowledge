# 一、远程仓库

远程仓库是托管在网络服务（代码托管平台）上的 Git 仓库，用来让多台电脑、多个开发者围绕同一份提交历史协作。以 GitHub 为例，一个 GitHub repository 就是一份远程 Git 仓库。

本地仓库和远程仓库不是两个互相覆盖的文件夹，而是两份可以交换提交的 Git 历史。本地通过 remote URL 知道“远程在哪里”，再通过 `push` 把本地提交发送过去。

![[assets/github-origin-push-generated.png|600]]

## 1、最小模型

远程协作的第一层模型只需要分清四个名字：

| 名字 | 含义 | 例子 |
|---|---|---|
| GitHub repository | GitHub 上的远程仓库 | `git-practice-remote` |
| remote URL | 本地连接远程仓库的地址 | `git@github.com:user/repo.git` |
| `origin` | 本地给某个远程地址起的名字 | 默认常用名 |
| `origin/main` | 本地记录的远程 `main` 状态 | remote-tracking branch |

`origin` 不是分支，也不是 GitHub 服务器本身。它只是本地仓库 `.git/config` 里保存的一个 remote 名字，通常指向克隆来源或第一个手动添加的远程仓库。

## 2、交互方向

本地与远程之间常见的交互可以先简化成三类：

| 动作 | 方向 | 作用 |
|---|---|---|
| `push` | 本地到远程 | 把本地提交发送到 GitHub |
| `fetch` | 远程到本地记录 | 更新 `origin/main` 等远程跟踪分支 |
| `pull` | 远程到当前分支 | 取回远程更新并整合到本地分支 |

第一次连接远程仓库时，重点是先建立 `origin`，再用 `git push -u origin main` 发布本地 `main`。

# 二、认证凭证

认证用于证明“谁正在访问仓库”。克隆公开仓库通常不需要认证；推送提交、读取私有仓库或执行受保护操作时，GitHub 需要确认账号身份和权限。

Git 只负责发起连接，真正的账号认证由 GitHub、GitLab、Gitee 等托管平台完成。常用方式有 HTTPS + Personal Access Token（PAT）和 SSH key。

## 1、HTTPS 与 PAT

HTTPS 远程地址兼容性好，常见形式如下：

```text
https://github.com/YOUR-USER/git-practice-remote.git
```

通过 HTTPS 执行需要身份权限的操作时，Git 可能会弹出用户名和密码提示。常见触发场景包括：向私有仓库 `push`、从私有仓库 `clone` 或 `fetch`、向需要权限的远程分支推送提交。

这里的“密码”通常不是账号登录密码，而是 PAT。多数托管平台不再允许把账号密码直接用于 Git 命令行认证，原因是账号密码权限过大、难以限定仓库范围，也不方便单独吊销或设置有效期。

PAT 是可以单独设置权限和有效期的访问令牌。它的优势是权限更细、可随时撤销、可按用途创建多枚令牌，也更适合命令行、临时环境和自动化场景。创建令牌时遵循最小权限原则：只授予当前仓库和当前操作所需权限，并设置合理过期时间。

凭证助手的作用是替 Git 保存和取用 HTTPS 凭证：第一次认证成功后，后续 `push`、`fetch`、`pull` 可以由系统安全存储自动提供凭证，不必每次手动输入 PAT。macOS 常见的凭证助手是 `osxkeychain`，它会把凭证交给 macOS 钥匙串管理，而不是让 Git 自己保存明文密码。

可以先检查当前配置：

```shell
git config credential.helper
```

如果已经配置为 `osxkeychain`，成功认证后的 HTTPS 凭证会进入钥匙串，并受系统登录、访问控制和钥匙串管理工具保护。不要使用 `credential.helper store` 保存长期凭证，因为它会把凭证以明文写入本地文件。

## 2、SSH key

SSH 使用“私钥留在本机、公钥上传到平台”的方式认证。配置完成后，使用 SSH 远程地址进行 `pull` 与 `push` 时，会通过 SSH key 完成身份验证，不走 HTTPS + PAT 的认证流程。

查看已有公钥：

```shell
ls ~/.ssh/*.pub
```

一般情况下，系统不会自带可用于 Git 托管平台认证的个人 SSH 公钥。`ls ~/.ssh/*.pub` 是用来检查自己是否曾经生成过 SSH key；如果没有输出，通常就需要新生成一对密钥。

常见 SSH key 类型里，有 RSA 和 Ed25519 两种：

| 类型 | 特点 | 适用判断 |
|---|---|---|
| Ed25519 | 密钥更短，性能好，现代 OpenSSH 和 Git 托管平台普遍支持 | 新生成个人 SSH key 时优先选择 |
| RSA | 兼容老系统更广，但需要足够长度才合适 | 只有旧环境不支持 Ed25519 时再选，通常用 4096 位 |

现在更常用、也更推荐新生成 Ed25519 密钥：

```shell
ssh-keygen -t ed25519 -C "zhangsan@example.com"
```

如果遇到旧系统不支持 Ed25519，再退回到 4096 位 RSA：

```shell
ssh-keygen -t rsa -b 4096 -C "zhangsan@example.com"
```

`-C` 用来写入公钥末尾的注释标签，方便识别这把密钥，不参与认证。

只能把 `.pub` 结尾的公钥内容上传到 GitHub。私钥文件，例如 `id_ed25519`，必须留在本机，不能复制给别人、上传到平台或提交进仓库。

以 GitHub 为例，先复制`.pub`公钥文件内容。

然后在 GitHub 右上角头像菜单进入 Settings，打开 SSH and GPG keys，选择 New SSH key，把公钥粘贴到 Key 输入框，Title 写成便于识别的设备名或用途，最后保存。

上传公钥后，可以验证连接：

```shell
ssh -T git@github.com
```

首次连接时，SSH 会要求确认主机指纹。应核对托管平台官方公布的指纹后再接受，避免在不可信网络中盲目确认。

## 3、安全边界

| 风险                                  | 正确处理                            |
| ----------------------------------- | ------------------------------- |
| 把 PAT 写进远程 URL                      | 通过本地环境变量指定，不把令牌写入仓库             |
| 私钥泄露                                | 立即删除平台上的对应公钥，重新生成密钥             |
| HTTPS 反复认证失败                        | 检查 PAT 是否过期、权限是否覆盖仓库、钥匙串是否缓存旧凭证 |
| SSH `Permission denied (publickey)` | 检查公钥是否上传、私钥是否存在、SSH 是否选中正确密钥    |
| 能读取但不能推送                            | 检查账号写权限和目标分支保护规则                |


# 三、创建远程

把已有本地仓库第一次推到 GitHub 时，推荐先在 GitHub 创建一个空仓库。空仓库没有额外提交，本地历史可以直接成为远程的初始历史。

## 1、仓库设置

在 GitHub 新建 repository 时，可以按下面的方式设置：

| 设置               | 建议                    | 原因                   |
| ---------------- | --------------------- | -------------------- |
| Repository name  | `git-practice-remote` | 名字清楚，便于识别练习用途        |
| Visibility       | Private               | 练习仓库不需要公开            |
| Add README       | 不勾选                   | 避免远程先多一个本地没有的 commit |
| Add `.gitignore` | 不勾选                   | 保持远程为空               |
| Choose a license | 不勾选                   | 保持远程为空               |

如果创建时勾选了 README，远程会先产生一个提交。本地已有历史再直接推送时，Git 会发现本地和远程不是同一条起点，需要额外处理同步关系。入门练习里先保持远程为空，能更清楚地观察 `push -u` 的效果。

## 2、URL 选择

GitHub 创建完成后会提供 HTTPS 或 SSH 远程地址。这里优先使用 SSH 地址，因为 SSH 认证已经验证通过：

```text
git@github.com:YOUR-USER/git-practice-remote.git
https://github.com/YOUR-USER/git-practice-remote.git
```

两种地址访问的是同一份远程仓库，区别在认证方式：

| 方式 | 适合场景 | 注意点 |
|---|---|---|
| SSH | 个人长期开发机、日常频繁拉取和推送 | 私钥只留在本机，公钥上传平台 |
| HTTPS + PAT | 临时环境、组织统一使用 HTTPS、需要细粒度令牌权限 | 不要把 PAT 写进 URL |

同一仓库只需要为 `origin` 选择一种地址。后续如果要从 HTTPS 改成 SSH，可以用 `git remote set-url` 修改。

# 四、连接 origin

本地仓库通过 `git remote add` 记录远程地址。常见做法是把 GitHub 仓库命名为 `origin`，这样后续命令可以写得更短、更符合社区习惯。

## 1、添加地址

示例：

```shell
cd path/to/practice-repo
git remote add origin git@github.com:YOUR-USER/git-practice-remote.git
git remote -v
```

可能看到：

```text
origin  git@github.com:YOUR-USER/git-practice-remote.git (fetch)
origin  git@github.com:YOUR-USER/git-practice-remote.git (push)
```

`fetch` 地址用于从远程取回更新，`push` 地址用于把本地提交发送到远程。Git 把二者分开，是因为“读远程”和“写远程”可能需要不同地址或不同权限。

大多数个人仓库里二者相同；在团队或开源协作里可能不同。例如：从上游仓库只读 `fetch`，但把自己的提交 `push` 到 fork；或者从一个镜像仓库读取，却把写入发送到另一个有权限的仓库。

## 2、修改地址

如果一开始填错 URL，或者想切换 HTTPS 与 SSH，不需要重建仓库，直接改 remote URL：

```shell
git remote set-url origin git@github.com:YOUR-USER/git-practice-remote.git
git remote -v
```

这只改变本地如何连接远程，不会改动提交历史，也不会删除 GitHub 上的仓库。

# 五、第一次推送

`push` 的作用是把本地已有提交发送到远程仓库。第一次推送本地 `main` 时，常用 `-u` 同时建立 upstream 关系，让 Git 记住本地 `main` 默认对应远程的 `origin/main`。

## 1、推送命令

示例：

```shell
git push -u origin main
```

可能看到：

```text
To github.com:YOUR-USER/git-practice-remote.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`-u` 是 `--set-upstream` 的短写。它让后续在 `main` 上执行 `git push` 或 `git pull` 时，不必每次都写完整的 `origin main`。

## 2、状态读取

推送后查看简短状态：

```shell
git status -sb
```

可能看到：

```text
## main...origin/main
```

这表示本地 `main` 已经和 `origin/main` 建立跟踪关系。再查看更详细的分支信息：

```shell
git branch -vv
```

可能看到：

```text
* main df306c3 [origin/main] Add second rebase practice line
```

方括号里的 `[origin/main]` 表示本地 `main` 的 upstream 是远程跟踪分支 `origin/main`。`origin/main` 不是用来直接工作的本地分支，而是本地保存的一份“远程 main 上次被观察到的位置”。

# 六、命令对照

## 1、核心命令

| 命令 | 作用 | 读法 |
|---|---|---|
| `git remote add origin URL` | 添加远程仓库地址 | 给 URL 起名为 `origin` |
| `git remote -v` | 查看远程地址 | 检查 fetch 和 push 指向哪里 |
| `git remote set-url origin URL` | 修改远程地址 | 切换 HTTPS、SSH 或修正仓库地址 |
| `git push -u origin main` | 推送并设置 upstream | 让本地 `main` 跟踪 `origin/main` |
| `git branch -vv` | 查看分支跟踪关系 | 观察 `[origin/main]` |

## 2、关系区分

| 对象 | 类型 | 是否直接工作 |
|---|---|---|
| `main` | 本地分支 | 是 |
| `origin` | remote 名字 | 否 |
| `origin/main` | 远程跟踪分支 | 通常否 |
| GitHub repository | 远程仓库 | 通过 push/fetch/pull 交互 |

如果已经理解 [[通用计算机知识/notes/Git/02_分支、合并与历史演进/8、分支工作流检查清单|分支工作流检查清单]] 里的分支指针模型，可以把 `origin/main` 看成一个特殊的本地指针：它不是你提交时推进的当前分支，而是 Git 记录远程分支状态的引用。

# 七、本地检查

完成第一次远程连接后，用下面的顺序确认状态：

```shell
cd path/to/practice-repo
git remote -v
git status -sb
git branch -vv
git log --oneline --decorate --graph --all --max-count=10
```

重点观察：

- `git remote -v` 是否出现 `origin`，且 fetch/push 地址符合预期。
- `git status -sb` 是否显示 `main...origin/main`。
- `git branch -vv` 是否在 `main` 后显示 `[origin/main]`。
- `git log --decorate --all` 是否能看到 `origin/main` 的位置。

第一次远程连接的核心结论是：GitHub repository 是远程仓库，`origin` 是本地给它起的名字，HTTPS/PAT 或 SSH key 负责证明访问身份，`git push -u origin main` 会把本地 `main` 发到 GitHub，并建立本地 `main` 与 `origin/main` 的默认对应关系。
