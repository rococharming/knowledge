# 一、可读提交

最小可读提交不是“越小越好”，而是让一次提交只承载一个清楚的理由。一个好提交应该像历史里的一个完整句子，而不是把几件不相关的事打包成杂乱备份。

![[assets/minimal-readable-commit-generated.png|600]]

核心判断可以压缩成一句话：

```text
一个 commit，一个理由。
```

能被一句清楚 message 概括的改动，通常可以放进同一个 commit；写不出清楚 message 时，往往说明这次提交混进了多个意图。

# 二、判断标准

## 1、四个特征

| 特征 | 含义 |
|---|---|
| 小 | 只包含一个清楚意图 |
| 完整 | 这个意图所需内容都在 |
| 可读 | message 能说明为什么改 |
| 可撤销 | 必要时能单独 revert |

这里的“小”不是按行数或文件数判断，而是按意图判断。一个功能如果需要代码、配置和文档一起才完整，它们可以属于同一个 commit。

## 2、三个问题

提交前可以快速问三件事：

| 问题 | 如果答案不清楚 |
|---|---|
| 这次改动能不能用一句话说明 | 可能混了多个理由 |
| 如果撤销这次提交，会不会连带撤销无关目标 | 需要拆开 |
| 评审者能不能快速看懂这次提交为什么存在 | message 或改动范围需要整理 |

这套判断和 [[11、提交前检查清单|提交前检查清单]] 连在一起：先看清楚改动范围和内容，再决定它们该不该放进同一个 commit。

# 三、拆分时机

## 1、适合拆开

| 情况 | 建议 | 理由 |
|---|---|---|
| 修改学习笔记，同时整理 README | 拆成两个 commit | 一个是记录学习，一个是说明仓库 |
| 修 bug，同时顺手改格式 | 通常拆开 | 评审和回滚目标不同 |
| 改配置，同时重命名无关文件 | 拆开 | 两个变化没有共同意图 |
| 一个文件里有两个不相关改动 | 考虑 `git add -p` | 需要按 hunk 选择 |

拆分的目的不是制造更多提交，而是让每个提交能独立解释、独立检查、必要时独立撤销。

## 2、可以放一起

| 情况 | 建议 | 理由 |
|---|---|---|
| 修拼写并补相关说明 | 可以一个 commit | 同一个文档意图 |
| 一个功能需要代码、配置、文档一起 | 可以一个 commit | 它们共同完成同一目标 |
| 调整命令示例并同步说明文字 | 可以一个 commit | 示例和解释需要保持一致 |

关键不是“一个文件一个提交”，而是“一个意图一个提交”。

# 四、路径拆分

## 1、选择路径

当两个意图落在不同文件里，可以按路径选择性暂存。不要在混合改动里习惯性执行 `git add .`，先把范围和内容看清楚。

先提交学习笔记：

```shell
git status -s
git diff
git add daily-note.txt
git diff --staged
git commit -m "Record commit hygiene note"
```

再提交 README 说明：

```shell
git status -s
git add README.md
git diff --staged
git commit -m "Clarify practice repository purpose"
```

这样历史里会出现两个理由清楚的提交，而不是一个含混的 `Update files`。

## 2、读取状态

两个文件都改过时，简洁状态可能是：

```text
 M README.md
 M daily-note.txt
```

只暂存 `daily-note.txt` 后：

```shell
git add daily-note.txt
git status -s
```

可能看到：

```text
 M README.md
M  daily-note.txt
```

这正是路径级拆分需要的中间状态：`daily-note.txt` 已经 staged，可以先提交；`README.md` 仍留在 working tree，等待下一次提交。

## 3、退回一步

如果把不属于本次提交的路径放进了 index，可以取消暂存：

```shell
git restore --staged <path>
```

它只撤销“准备提交”这个动作，不撤销文件内容。更完整的撤销场景见 [[6、撤销修改和取消暂存|撤销修改和取消暂存]]。

# 五、同文件拆分

两个不相关意图有时会混在同一个文件里，例如一段是修正文案，另一段是改命令示例。这时路径级拆分不够细，可以先知道这个工具：

```shell
git add -p <path>
```

`-p` 是 patch 模式，可以交互式选择一部分 hunk 进入 index。它适合“同一个文件里有多块不相关修改”的场景。

本阶段先把路径级拆分练稳，再逐步使用 `git add -p`。过早依赖交互式暂存，反而容易把重点从“按意图组织提交”转移到命令细节上。

# 六、本地练习

起点：继续使用上一课结束后的本地仓库。上一课完成后，仓库应为 clean，最新提交信息是 `Practice pre-commit checklist`。

先确认当前状态：

```shell
git status -s
git log --oneline --decorate --max-count=3
```

用编辑器打开 `daily-note.txt`，在末尾新增一行：

```text
Small commits are easier to review and recover.
```

再用编辑器打开 `README.md`，在末尾新增一段：

```text
This repository is used for hands-on Git practice.
```

先提交学习笔记这个意图：

```shell
git status -s
git diff
git add daily-note.txt
git diff --staged
git commit -m "Record commit hygiene note"
```

再提交 README 说明这个意图：

```shell
git status -s
git add README.md
git diff --staged
git commit -m "Clarify practice repository purpose"
```

最后检查：

```shell
git log --oneline --decorate --max-count=4
git show --stat HEAD
git status -s
```

检查目标：

| 检查项 | 期待结果 |
|---|---|
| 最新提交 | `Clarify practice repository purpose` |
| 上一个提交 | `Record commit hygiene note` |
| `daily-note.txt` | 新增一句 commit hygiene 笔记 |
| `README.md` | 新增练习用途说明 |
| 最后 `git status -s` | 没有输出 |

本课目标状态：新增两个 commit；每个 commit 只对应一个意图；仓库回到 clean。

# 七、小结

最小可读提交的重点不是最少行数，而是最少理由。能一起解释、一起检查、一起撤销的改动，才适合放在一起。

日常工作里，先按 [[11、提交前检查清单|提交前检查]] 看清楚改动，再用 `git add <path>` 选择本次提交的意图。下一步可以把本单元的本地 Git 动作串成一条日常循环。
