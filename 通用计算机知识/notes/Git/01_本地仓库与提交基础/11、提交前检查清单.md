# 一、提交前检查

提交前检查解决的问题不是“能不能提交”，而是“这次提交里是否只包含我想保存的改动”。很多 Git 事故并不是命令太难，而是提交前少看了一眼：调试文件混进来了、只改了一半就提交了，或者提交信息写完自己也看不懂。

![[assets/pre-commit-checklist-generated.png|600]]

每次提交前只问一个核心问题：

```text
这次 commit 里是否只包含我想保存的改动？
```

最小模型可以压缩成一句话：

```text
status 看范围，diff 看内容，diff --staged 看即将提交，commit 写意图。
```

这套动作把前面几课的命令串成一个固定流程：先观察，再暂存，再确认，最后提交。

# 二、四步清单

## 1、看范围

```shell
git status -s
```

`git status -s` 用来快速回答“有哪些路径变了”。它会把工作区、暂存区、未跟踪文件压缩成简洁状态码。

示例：

```text
 M daily-note.txt
```

左边是空格、右边是 `M`，表示 `daily-note.txt` 在 working tree 中有修改，但还没有进入 index。状态码的读法见 [[4、查看状态、暂存和提交|查看状态、暂存和提交]]。

## 2、看未暂存

```shell
git diff
```

`git diff` 查看 working tree 里还没有进入 index 的内容。它回答的是：“如果现在不再执行 `git add`，这些内容不会进入下一次提交。”

示例：

```diff
diff --git a/daily-note.txt b/daily-note.txt
@@
+Practiced the pre-commit checklist.
```

看到新增行后，先判断它是否属于这次提交。如果属于，再暂存：

```shell
git add daily-note.txt
```

## 3、看已暂存

```shell
git diff --staged
```

这是提交前最关键的一眼。`git commit` 读取的是 index，所以 `git diff --staged` 展示的就是“如果现在提交，commit 里会有什么”。

示例：

```diff
diff --git a/daily-note.txt b/daily-note.txt
@@
+Practiced the pre-commit checklist.
```

如果这里出现了不该进本次提交的内容，要先取消暂存或重新整理，而不是直接提交。

## 4、写意图

```shell
git commit -m "Practice pre-commit checklist"
```

提交信息不是文件清单，而是这次变更的意图。`Practice pre-commit checklist` 比 `Update daily-note.txt` 更好，因为它说明了为什么改，而不只是说哪个文件变了。

# 三、暂存区

## 1、commit 读取 index

`git commit` 默认读取 index，也就是暂存区，而不是直接读取整个 working tree。

| 区域 | 提交前检查命令 | 关注点 |
|---|---|---|
| working tree | `git diff` | 还没暂存的内容 |
| index | `git diff --staged` | 即将进入提交的内容 |
| commit | `git show --stat HEAD` | 最新提交实际保存的内容摘要 |

这也是为什么 `git diff` 为空不代表没有东西要提交。如果所有改动都已经 staged，`git diff` 可能没有输出，但 `git diff --staged` 仍然会显示下一次提交草稿。

## 2、取消误暂存

如果发现不该进入这次提交的路径已经放进 index，可以取消暂存：

```shell
git restore --staged <path>
```

它只把路径从 index 拿出来，不删除 working tree 里的文件内容。

常见场景：

```shell
git restore --staged debug.log
git status -s
```

取消暂存和丢弃修改的区别见 [[6、撤销修改和取消暂存|撤销修改和取消暂存]]。

# 四、输出判断

## 1、未暂存修改

```text
 M daily-note.txt
```

右侧 `M` 表示 working tree 有修改，但 index 里还没有这次修改。此时要用 `git diff` 看具体内容。

## 2、已暂存修改

```text
M  daily-note.txt
```

左侧 `M` 表示修改已经 staged。此时要用 `git diff --staged` 检查下一次提交会包含什么。

## 3、空 diff

`git diff` 没有输出，只能说明 working tree 相对 index 没有额外修改。它不能证明“没有东西要提交”。

提交前要把两个差异都看一遍：

```shell
git diff
git diff --staged
```

查看 diff 输出结构见 [[5、查看修改内容|查看修改内容]]。

# 五、本地练习

起点：继续使用上一课结束后的本地仓库。上一课完成后，仓库应为 clean，最新提交信息是 `Add shared ignore rules`。

先确认当前状态和最近提交：

```shell
git status -s
git log --oneline --decorate --max-count=3
```

用编辑器打开 `daily-note.txt`，在末尾新增一行：

```text
Practiced the pre-commit checklist.
```

然后按提交前检查清单执行：

```shell
git status -s
git diff
git add daily-note.txt
git status -s
git diff --staged
git commit -m "Practice pre-commit checklist"
git show --stat HEAD
git status -s
```

检查目标：

| 检查项 | 期待结果 |
|---|---|
| 最新提交信息 | `Practice pre-commit checklist` |
| 最新提交统计 | `daily-note.txt` 有 1 行新增 |
| 最后 `git status -s` | 没有输出 |

本课目标状态：新增一个 `Practice pre-commit checklist` 提交；`daily-note.txt` 增加一行；仓库回到 clean。

# 六、小结

提交前检查的顺序是：先用 `git status -s` 看范围，再用 `git diff` 看未暂存内容，再用 `git diff --staged` 看即将提交的快照，最后用 `git commit -m` 写下这次提交的意图。

这套流程和 [[10、修改最近一次提交|修改最近一次提交]] 互补：提交前检查做得越稳，后续需要 amend 的次数就越少。下一步可以继续学习怎样把改动切成更小、更清楚的提交。
