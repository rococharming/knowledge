# 一、为什么需要分支

分支（branch）让同一个仓库可以同时保留稳定主线和正在开发的工作线。实际开发中，通常不会直接在 `main` 上完成所有功能、修复和实验，而是从 `main` 创建新分支，完成后再把结果合并回来。

常见流程是：

![[assets/git-branch-workflow-handdrawn.png|600]]

这样做有几个好处：

- **保护主分支稳定性**：`main` 保持相对可运行、可发布的状态。
- **支持并行开发**：多个功能、修复和实验可以放在不同分支上推进。
- **降低实验成本**：实验失败时，可以直接丢弃实验分支。
- **方便整合成果**：分支开发完成后，再通过合并或变基把成果带回主线。

分支并不会复制整个项目目录。它更像是给某个提交起了一个可以移动的名字，因此创建分支非常轻量。

# 二、分支、提交和 HEAD

分支管理的核心心智模型是：提交形成历史链条，分支名指向某个提交，`HEAD` 再指向当前所在分支。

![[assets/git-branch-head-handdrawn.png|600]]

## 1、分支是指向提交的可移动名字

Git 的一次提交可以理解为项目在某个时刻的快照。分支则是一个名字，它指向某个提交，并且会随着新提交向前移动。

假设当前提交历史如下：

```text
A --- B --- C
            ^
            |
           main
```

这里：

- `A`、`B`、`C` 是提交。
- `main` 是分支名，当前指向提交 `C`。
- `main` 后续如果产生新提交，就会移动到新提交上。

从底层看，本地分支通常保存在 `.git/refs/heads/` 下面。这个细节不需要日常手动操作，但有助于理解“删除分支”为什么删除的是引用名，而不是立刻删除提交对象。`.git` 结构见 [[2、创建 Git 仓库|创建 Git 仓库]]。

## 2、HEAD 表示当前所在位置

`HEAD` 表示当前检出位置。在普通分支状态下，它通常指向当前分支，而当前分支再指向某个提交。

如果当前位于 `main`：

```text
HEAD -> main -> C
```

这表示：当前工作位置是 `main` 分支，而 `main` 当前指向提交 `C`。这个模型在理解恢复操作时也很重要，因为 `reset`、`reflog` 等命令经常围绕 `HEAD` 和分支指针移动展开。恢复前的风险判断见 [[通用计算机知识/notes/Git/04_撤销、恢复与历史整理/1、撤销前的三问诊断|撤销前的三问诊断]]。

## 3、提交会推动当前分支向前移动

如果当前在 `main` 上，并创建一次新提交 `D`：

```text
A --- B --- C --- D
                  ^
                  |
                 main
                  ^
                  |
                 HEAD
```

新提交生成后，`main` 会从 `C` 移动到 `D`。这里的关键是：移动的是当前分支指针，而不是所有分支都会自动前进。

# 三、实践中的分支工作流

## 1、从最新主分支创建工作分支

日常开发中，创建功能分支前通常先回到主分支，并确认主分支是自己要基于的起点：

```shell
git switch main
git status
git switch -c feature-login
```

如果项目有远程协作，通常还会先拉取最新主线，再创建分支。本篇先聚焦本地分支；远程分支和同步会在远程协作笔记中展开。

也可以显式指定从哪个提交或分支创建新分支：

```shell
git switch -c feature-login main
git switch -c hotfix-login <commit>
```

这适合在不切回 `main` 的情况下，直接从某个明确起点创建分支。

## 2、分支命名要表达用途

分支名最好让人一眼看出它的用途。常见约定：

| 类型 | 示例 | 适用场景 |
|---|---|---|
| `feature/*` | `feature-login`、`feature/user-profile` | 新功能 |
| `fix/*` | `fix-login-error` | 修复 bug |
| `hotfix/*` | `hotfix/payment-timeout` | 紧急修复 |
| `experiment/*` | `experiment/new-cache` | 实验性方案 |

个人练习仓库可以简单用 `dev`、`test-branch`；真实项目里更推荐使用能描述目的的名字。分支名不是提交信息，细节仍应写进提交记录。提交习惯见 [[通用计算机知识/notes/Git/01_本地仓库与提交基础/4、查看状态、暂存和提交|查看状态、暂存和提交]]。

## 3、一个分支尽量只做一件事

实践中，一个分支最好围绕一个清晰目标展开：一个功能、一个修复、一次实验。这样后续合并、回滚、代码审查都会更简单。

不推荐在同一个分支里混合做太多无关事情，例如同时改登录页、重构目录结构、调整格式化配置。这样的分支即使能合并，也会让历史难以理解。

如果开发过程中发现顺手改了无关内容，可以先停下来用 `git status` 和 `git diff` 看清楚范围，再决定是拆出新分支、拆提交，还是暂时撤销。差异检查见 [[5、查看修改内容|查看修改内容]]。

# 四、查看、创建和切换分支

## 1、查看本地分支

```shell
git branch
```

输出可能类似：

```text
* main
  dev
```

其中 `*` 表示当前所在分支。上面表示当前位于 `main`，仓库里还有一个本地分支 `dev`。

## 2、查看分支指向的提交

```shell
git branch -v
```

`-v` 会显示每个分支当前指向的提交哈希和提交信息摘要，适合快速判断各分支停在哪次提交上。

示例输出：

```text
* main 9f31a2c update README
  dev  42b7c18 add login draft
```

如果想进一步观察分支之间的关系，可以结合 [[9、灵活查看提交历史|提交历史查看]] 中的 `git log` 技巧。

## 3、只创建分支

```shell
git branch <branch-name>
```

例如：

```shell
git branch dev
```

这条命令只创建 `dev` 分支，不会自动切换过去。假设创建前是：

```text
HEAD -> main -> C
```

创建后变成：

```text
HEAD -> main -> C
        dev  -> C
```

此时 `main` 和 `dev` 都指向同一个提交 `C`，但当前仍然在 `main`。

## 4、切换到已有分支

```shell
git switch <branch-name>
```

例如：

```shell
git switch dev
```

切换后：

```text
main -> C
HEAD -> dev -> C
```

切换分支的本质，是让 `HEAD` 指向另一个分支，并把工作区内容切换到该分支对应的提交状态。

> [!warning] 切换前先看工作区状态
> 如果当前工作区有未提交修改，切换分支是否成功取决于这些修改会不会被目标分支覆盖。
>
> - 已跟踪文件的未提交修改：如果目标分支会改动同一路径，Git 通常会拒绝切换；如果不会冲突，修改可能会继续留在工作区。
> - 未跟踪的新文件：如果目标分支没有同名路径，通常可以切换，并且这些未跟踪文件会留在新的工作区；如果目标分支已经有同名文件，Git 会拒绝切换，避免覆盖未跟踪文件。
>
> 切换前建议先用 `git status` 检查。必要时提交、取消暂存、撤销修改，或先保存到临时位置。状态检查见 [[通用计算机知识/notes/Git/01_本地仓库与提交基础/4、查看状态、暂存和提交|查看状态、暂存和提交]]；撤销和取消暂存见 [[6、撤销修改和取消暂存|撤销修改和取消暂存]]。

## 5、创建并立即切换分支

实际使用中，更常见的是创建并立即切换：

```shell
git switch -c <branch-name>
```

例如：

```shell
git switch -c feature-login
```

它相当于连续执行：

```shell
git branch feature-login
git switch feature-login
```

创建功能分支、修复分支、实验分支时，通常优先使用 `git switch -c`。

# 五、在分支上提交与分叉

## 1、分支从同一个提交开始

假设当前在 `dev` 分支上，且 `main` 和 `dev` 都指向 `C`：

```text
main -> C
HEAD -> dev -> C
```

此时两个分支没有分叉，只是两个名字指向同一个提交。

## 2、新提交只推动当前分支

如果在 `dev` 上创建一次提交 `D`：

![[assets/git-dev-branch-commit-d-handdrawn.png|600]]

可以看到：

- `dev` 向前移动到 `D`。
- `main` 仍然停在 `C`。
- 当前 `HEAD` 仍然指向 `dev`。

这就是分支能够独立开发的原因：在一个分支上提交，不会让其他分支自动跟着移动。

## 3、分叉是什么意思

分叉是指两个分支从同一个提交出发，但后续至少有一个分支产生了新的提交，导致它们指向不同的历史位置。

刚创建 `dev` 时，`main` 和 `dev` 仍然指向同一个提交；在 `dev` 上提交 `D` 后，两个分支就指向了不同的历史位置：

![[assets/git-branch-divergence-handdrawn.png|600]]

此时 `main` 和 `dev` 已经分叉。后续需要通过合并、变基等方式再整合历史。

# 六、查看分支图

学习分支时，建议经常使用：

```shell
git log --oneline --graph --decorate --all
```

这个命令会把提交历史、分支指针和 `HEAD` 位置放在一张文本图里展示。

各参数含义：

| 参数 | 作用 |
|---|---|
| `--oneline` | 每次提交显示成一行 |
| `--graph` | 用 ASCII 图显示分支关系 |
| `--decorate` | 显示分支名、标签、`HEAD` 等引用 |
| `--all` | 显示所有分支的历史 |

示例输出：

```text
* 42b7c18 (HEAD -> dev) add login draft
* 9f31a2c (main) update README
* 6d21a77 initial commit
```

从这个输出可以读出：

- 当前位于 `dev` 分支。
- `dev` 指向提交 `42b7c18`。
- `main` 指向提交 `9f31a2c`。
- `dev` 比 `main` 多了一次提交。

实践中可以先用 `git branch -v` 看分支停在哪，再用上面的图形日志看它们如何分叉。若要查看某次提交改了什么，继续用 [[9、灵活查看提交历史|灵活查看提交历史]] 和 [[5、查看修改内容|查看修改内容]]。

# 七、删除分支

## 1、删除前先确认是否已经合并

删除分支前，先确认当前在哪个分支，以及目标分支是否已经合并：

```shell
git branch
git branch --merged
git branch --no-merged
```

常见理解：

| 命令 | 作用 |
|---|---|
| `git branch --merged` | 列出已经合并到当前分支的本地分支 |
| `git branch --no-merged` | 列出还没有合并到当前分支的本地分支 |

执行这两个命令时要注意“当前分支”是谁。比如切到 `main` 后执行，判断的是其他分支是否已经合并进 `main`。

## 2、安全删除本地分支

删除已经不需要的本地分支：

```shell
git branch -d <branch-name>
```

例如：

```shell
git branch -d dev
```

需要注意：

- 不能删除当前正在使用的分支。
- `-d` 是相对安全的删除方式。
- 如果分支包含尚未合并的提交，Git 通常会拒绝删除。

如果要删除 `dev`，应先切换到其他分支：

```shell
git switch main
git branch -d dev
```

## 3、强制删除分支

```shell
git branch -D <branch-name>
```

`-D` 会强制删除分支名。它不会立刻抹掉提交对象本身，但会丢掉这个分支对提交的引用；如果没有其他分支、标签或引用能找到这些提交，后续就更难恢复。

![[assets/git-force-delete-branch-handdrawn.png|600]]

> [!danger] 初学阶段不要随便使用 `-D`
> 强制删除前，先用 `git log --oneline --graph --decorate --all` 看清楚该分支上是否有需要保留的提交。若不确定，可以先不要删除，或者创建一个临时备份分支。

## 4、删除前创建临时备份分支

如果不确定一个分支能不能删，可以先给它当前指向的提交起一个临时名字：

```shell
git branch backup-dev dev
git branch -D dev
```

这样即使 `dev` 被删，`backup-dev` 仍然指向原来的提交。等确认不需要后，再删除备份分支。

找回误删分支通常依赖 `git reflog` 或明确的提交哈希。操作前先按 [[通用计算机知识/notes/Git/04_撤销、恢复与历史整理/1、撤销前的三问诊断|撤销前的三问诊断]] 确认当前分支、工作区状态和共享风险。

## 5、本地删除不等于远程删除

`git branch -d dev` 和 `git branch -D dev` 只删除本地分支。它们不会删除远程仓库上的同名分支，也不会删除其他人电脑里的分支。

本篇只讲本地分支。远程分支、上游分支、推送和删除远程分支属于协作开发内容，应该单独学习。

# 八、实践检查清单

## 1、开始一个新任务前

```shell
git switch main
git status
git switch -c feature-login
```

检查重点：

- 当前是不是基于正确的起点。
- 工作区和暂存区是否干净。
- 分支名是否能表达任务目的。

## 2、切换到别的任务前

```shell
git status
git diff
git diff --staged
```

如果工作区有改动，先判断这些改动属于当前任务，还是应该拆到别的分支。不要把“临时调试”“格式化”“功能改动”混在一个分支和一组提交里。

## 3、删除分支前

```shell
git switch main
git branch --merged
git branch --no-merged
git log --oneline --graph --decorate --all
```

如果目标分支已经合并，优先使用 `git branch -d <branch-name>`。只有明确确认分支内容不需要，才考虑 `-D`。

# 九、命令速查

| 目标 | 命令 |
|---|---|
| 查看本地分支 | `git branch` |
| 查看分支及其提交信息 | `git branch -v` |
| 查看已合并到当前分支的分支 | `git branch --merged` |
| 查看未合并到当前分支的分支 | `git branch --no-merged` |
| 创建分支但不切换 | `git branch <branch-name>` |
| 切换到已有分支 | `git switch <branch-name>` |
| 创建并切换分支 | `git switch -c <branch-name>` |
| 从指定起点创建并切换 | `git switch -c <branch-name> <start-point>` |
| 查看分支图 | `git log --oneline --graph --decorate --all` |
| 安全删除本地分支 | `git branch -d <branch-name>` |
| 强制删除本地分支 | `git branch -D <branch-name>` |

# 十、小结

理解 Git 分支，最重要的是记住三个角色：

- **提交**：一次项目快照。
- **分支**：指向某个提交的可移动名字。
- **`HEAD`**：当前所在位置，通常指向当前分支。

创建分支时，只是新增一个指向某个提交的名字；在分支上提交时，只有当前分支会向前移动；删除分支时，删除的是分支名这个引用，而不是直接删除项目文件。

实践中要养成三类习惯：从明确起点创建分支，切换前先检查工作区，删除前先确认是否已经合并。只要能用分支图看懂 `HEAD` 和各分支指向哪里，后续学习合并、冲突处理和历史整理都会轻松很多。
