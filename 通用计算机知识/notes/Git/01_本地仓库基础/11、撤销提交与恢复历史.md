# 一、先判断撤销发生在哪个阶段

Git 中的“撤销”不是一个命令能覆盖所有情况。先判断修改处于哪个阶段，以及历史是否已经共享。

| 需求 | 常用命令 | 对历史的影响 |
|---|---|---|
| 取消暂存或丢弃未提交修改 | `git restore` | 不影响提交历史 |
| 修正最近一次本地提交 | `git commit --amend` | 替换最近提交 |
| 撤销未共享的本地提交 | `git reset` | 移动分支指针，可能重写历史 |
| 找回本地指针曾经的位置 | `git reflog` | 查看本地引用移动记录 |

未提交修改见 [[6、撤销修改和取消暂存|撤销修改和取消暂存]]；最近一次提交见 [[10、修改最近一次提交|修改最近一次提交]]。本篇重点是本地、未共享历史中的 `reset` 和 `reflog`。已共享提交的撤销见 [[通用计算机知识/notes/Git/03_远程仓库与协作/2、协作中的撤销与历史修复|协作中的撤销与历史修复]]。

# 二、HEAD、分支指针和提交

## 1、三个角色

| 概念 | 可以如何理解 | 特点 |
|---|---|---|
| 提交 | 一次已保存的项目快照 | 通过哈希标识，创建后不会原地修改 |
| 分支 | 指向某个提交的可移动标签 | 例如 `main` |
| `HEAD` | 当前检出位置 | 正常分支状态下指向当前分支 |

假设历史是 `A → B → C`，当前处于 `main`：

```text
HEAD → main → C
```

这表示 `HEAD` 指向 `main`，`main` 指向提交 `C`，所以当前提交是 `C`。

## 2、`reset` 移动的是什么

执行：

```shell
git reset B
```

在正常分支状态下，核心变化是当前分支从 `C` 移回 `B`。提交 `C` 本身没有立即被销毁，只是不再能通过 `main` 这个分支找到。

`--soft`、`--mixed`、`--hard` 的区别，在于移动分支指针后如何处理暂存区和工作区。

> [!note] Detached HEAD
> 如果 `HEAD` 直接指向某个提交，而不是指向分支，就称为 Detached HEAD。本篇默认讨论正常分支状态。

# 三、`git reset --soft`

假设当前历史是：

```text
A → B → C  （main 当前指向 C）
```

现在想让 `main` 回到 `B`。

## 1、命令

```shell
git reset --soft HEAD~1
```

## 2、结果

| 位置 | 执行后的状态 |
|---|---|
| 分支指针 | `main` 从 `C` 移到 `B` |
| 暂存区 | 保持执行前内容 |
| 工作区 | 保持执行前内容 |

可以记成：

> 撤销提交，但保留改动，并让它们继续处于已暂存状态。

适合撤销提交后立刻重新提交，或把几个本地提交重新整理成一次提交。

# 四、`git reset --mixed`

`--mixed` 是 `git reset` 的默认模式。

```shell
git reset --mixed HEAD~1
git reset HEAD~1
```

结果：

| 位置 | 执行后的状态 |
|---|---|
| 分支指针 | `main` 从 `C` 移到 `B` |
| 暂存区 | 重置为 `B` |
| 工作区 | 保持执行前内容 |

可以记成：

> 撤销提交，保留文件内容，但把改动退回未暂存状态。

适合撤销提交后重新挑选哪些内容进入下一次提交。

# 五、`git reset --hard`

```shell
git reset --hard HEAD~1
```

结果：

| 位置 | 执行后的状态 |
|---|---|
| 分支指针 | `main` 从 `C` 移到 `B` |
| 暂存区 | 重置为 `B` |
| 工作区 | 重置为 `B` |

可以记成：

> 把分支、暂存区和工作区一起强制恢复到目标提交。

> [!danger] `git reset --hard` 可能丢失数据
> `reflog` 通常可以找回被分支指针跳过的提交，但不能保证找回从未提交、又被 `--hard` 覆盖的工作区内容。执行前应先运行 `git status` 和 `git diff`，并用提交、备份或 `git stash` 保存重要改动。

# 六、三种 `reset` 模式对比

| 模式 | 分支指向 | 暂存区 | 工作区 | 改动最终在哪里 |
|---|---|---|---|---|
| `--soft` | 目标提交 | 保持执行前内容 | 保持执行前内容 | 暂存区，已暂存 |
| `--mixed` | 目标提交 | 重置为目标提交 | 保持执行前内容 | 工作区，未暂存 |
| `--hard` | 目标提交 | 重置为目标提交 | 重置为目标提交 | 被丢弃 |

选择时只问一个问题：撤销提交后，这些改动应该去哪里？

| 期望结果 | 选择 |
|---|---|
| 保留改动，且仍准备提交 | `--soft` |
| 保留改动，但重新挑选暂存内容 | `--mixed` |
| 确认改动不再需要 | `--hard` |

# 七、使用 `git reflog` 找回历史位置

`reflog` 是 Reference Log，记录 `HEAD`、本地分支等引用何时从哪个提交移动到哪个提交。

```shell
git reflog
git reflog -5
```

误执行 `reset` 后，可能看到：

```text
edba6e9 HEAD@{0}: reset: moving to HEAD~1
64829c9 HEAD@{1}: commit: add config
```

恢复时优先使用明确的提交哈希，而不是会随操作变化的 `HEAD@{n}`。

安全流程：

```shell
git status
git show 64829c9
git branch rescue-before-reset 64829c9
```

先创建临时分支保住目标提交，再决定是否让当前分支回到它：

```shell
git reset --hard 64829c9
```

> [!warning] `reflog` 不是永久档案
> 它是当前本地仓库的记录，不会随普通 `git push` 上传；记录和不可达对象也可能随时间过期并被清理。

# 八、小结

撤销历史前先确认两件事：这个提交是否已经共享、撤销后是否要保留文件内容。

| 场景 | 优先选择 |
|---|---|
| 最近一次本地提交写错 | `git commit --amend` |
| 本地提交想撤回但保留改动 | `git reset --soft` 或 `--mixed` |
| 本地提交和改动都确定不要 | `git reset --hard` |
| 误操作后找回提交位置 | `git reflog` |

如果提交已经推送或可能被他人基于其继续开发，不要在这里用 `reset` 重写共享历史；应转到 [[通用计算机知识/notes/Git/03_远程仓库与协作/2、协作中的撤销与历史修复|协作中的撤销与历史修复]] 使用 `git revert`。
