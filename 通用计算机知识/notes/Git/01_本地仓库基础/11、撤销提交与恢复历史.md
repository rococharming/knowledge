# 一、撤销不同阶段的修改

Git 中的“撤销”不是一个单一操作。应先确认修改位于哪个阶段，以及它是否已经共享：

| 需求 | 常用命令 | 对历史的影响 |
| --- | --- | --- |
| 取消暂存或丢弃未提交修改 | `git restore` | 不影响提交历史 |
| 修正最近一次本地提交 | `git commit --amend` | 替换最近提交 |
| 撤销未共享的本地提交 | `git reset` | 移动分支指针，可能重写历史 |
| 撤销已共享提交的影响 | `git revert` | 保留原历史，新增反向提交 |
| 找回本地指针曾经的位置 | `git reflog` | 只查看本地引用移动记录 |

未提交修改的处理见 [[6、撤销修改和取消暂存]]；最近一次提交的修正见 [[10、修改最近一次提交]]。本篇重点是 `reset`、`revert` 和 `reflog`。

# 二、HEAD、分支指针和提交

理解 `reset`、`reflog` 之前，需要先分清提交、分支指针和 `HEAD` 各自代表什么。

## 1、三个角色

| 概念 | 可以如何理解 | 特点 |
| --- | --- | --- |
| 提交 | 一次已保存的项目快照 | 通过哈希标识，创建后不会被原地修改 |
| 分支 | 指向某个提交的可移动标签 | 例如 `main`；创建新提交后通常会向前移动 |
| `HEAD` | 记录当前检出位置的特殊引用 | 在正常分支状态下，它指向当前分支 |

关键是：分支不是一串独立复制的提交，而是一个有名字的指针。

## 2、HEAD 如何找到当前提交

假设历史中已经有 `A → B → C` 三个提交，当前处于 `main` 分支：

```text
HEAD → main → C
```

这个关系表示：

1. `HEAD` 指向当前分支 `main`。
2. `main` 指向提交 `C`。
3. 因此当前提交是 `C`。

## 3、reset 移动的是什么

![[Git-HEAD分支指针手绘.png|400]]

在图中执行：

```shell
git reset B
```

发生的核心变化是：

1. 当前分支 `main` 从提交 `C` 移回提交 `B`。
2. `HEAD` 仍然指向 `main`，所以它会跟随 `main` 回到 `B`。
3. 提交 `A`、`B`、`C` 本身都没有被修改。
4. `C` 只是不再能通过 `main` 这个分支找到；短期内通常还可以通过 `reflog` 恢复。

因此，在这里讨论的正常分支状态中，`reset` 首先会移动当前分支指针。`--soft`、`--mixed`、`--hard` 的区别，在于移动指针之后如何处理暂存区和工作区。

> [!note] Detached HEAD（分离头指针）
> 在正常分支状态下，`HEAD` 指向分支。如果直接检出某个提交，`HEAD` 可以绕过分支、直接指向该提交，这种状态称为 Detached HEAD。本篇的 `reset` 讨论默认处于正常分支状态。

# 三、git reset --soft

下面三种模式使用同一个场景：

```text
A → B → C  （main 当前指向 C）
```

假设提交 `C` 相对 `B` 新增了一组改动，记为 `Δ`。执行命令前，工作区和暂存区都与 `C` 一致，仓库处于干净状态。现在要让 `main` 回到 `B`。

## 1、命令

```shell
git reset --soft HEAD~1
```

## 2、执行结果

| 位置 | 执行后的状态 |
| --- | --- |
| 分支指针 | `main` 从 `C` 移到 `B` |
| 暂存区 | 保持执行前的内容 |
| 工作区 | 保持执行前的内容 |

因为分支已经回到 `B`，而暂存区仍保留 `C` 对应的内容，所以改动 `Δ` 会显示为已暂存，可以直接重新提交。

可以记成：

> 撤销提交，但保留改动，并且让它们继续处于已暂存状态。

## 3、适合场景

- 刚提交完就想重新整理提交信息或内容
- 将连续几次本地提交重新整理为一次提交
- 希望撤销提交后保持“随时可以再次提交”的状态

# 四、git reset --mixed

`--mixed` 是 `git reset` 的默认模式。

## 1、命令

```shell
git reset --mixed HEAD~1
```

也可以省略 `--mixed`：

```shell
git reset HEAD~1
```

## 2、执行结果

| 位置 | 执行后的状态 |
| --- | --- |
| 分支指针 | `main` 从 `C` 移到 `B` |
| 暂存区 | 重置为 `B` 对应的内容 |
| 工作区 | 保持执行前的内容 |

暂存区已经回到 `B`，但工作区仍保留原来的文件内容，因此改动 `Δ` 会显示为未暂存。你可以重新检查它们，再决定哪些内容执行 `git add`。

可以记成：

> 撤销提交，保留文件内容，但把改动退回未暂存状态。

## 3、适合场景

- 撤销提交后，想重新选择哪些改动进入下一次提交
- 一次提交中混入了不同主题的改动，需要拆分
- 希望保留所有文件内容，先回到提交前的编辑状态

# 五、git reset --hard

## 1、命令

```shell
git reset --hard HEAD~1
```

## 2、执行结果

| 位置 | 执行后的状态 |
| --- | --- |
| 分支指针 | `main` 从 `C` 移到 `B` |
| 暂存区 | 重置为 `B` 对应的内容 |
| 工作区 | 重置为 `B` 对应的内容 |

分支、暂存区和工作区全部回到 `B`，因此改动 `Δ` 不会留在暂存区或工作区中。

可以记成：

> 把分支、暂存区和工作区一起强制恢复到目标提交。

> [!danger] `git reset --hard` 可能丢失数据
> `reflog` 通常可以找回被分支指针跳过的提交 `C`，但不能保证找回从未提交、又被 `--hard` 覆盖的工作区内容。执行前应先运行 `git status` 和 `git diff`，并通过提交、备份或 `git stash` 保存重要改动。

> [!note] 未跟踪文件
> `git reset --hard` 不等于“清空整个项目目录”，它通常不会删除普通的未跟踪文件。但如果未跟踪文件阻碍 Git 恢复目标提交中的路径，它们仍可能被删除。

# 六、三种 reset 模式对比

对于同一个“从 `C` 回到 `B`”的场景，三种模式的区别如下：

![[Git-reset三种模式手绘.png|400]]

| 模式 | 分支指向 | 暂存区 | 工作区 | `Δ` 最终在哪里 |
| --- | --- | --- | --- | --- |
| `--soft` | `B` | 保持执行前内容 | 保持执行前内容 | 暂存区，已暂存 |
| `--mixed` | `B` | 重置为 `B` | 保持执行前内容 | 工作区，未暂存 |
| `--hard` | `B` | 重置为 `B` | 重置为 `B` | 被丢弃 |

选择时可以只问一个问题：撤销提交后，这些改动应该去哪里？

| 期望结果 | 选择 |
| --- | --- |
| 保留改动，且仍然准备提交 | `--soft` |
| 保留改动，但重新挑选暂存内容 | `--mixed` |
| 确认改动不再需要 | `--hard` |

> [!tip] 从保守的模式开始
> 如果不确定改动是否还有价值，优先使用 `--soft` 或 `--mixed`。只有在确认暂存区和工作区中的相关改动都可以放弃时，才使用 `--hard`。

# 七、使用 git reflog 找回历史位置

`reflog` 是 Reference Log（引用日志）的缩写。它记录 `HEAD`、本地分支等引用何时从哪个提交移到了哪个提交。

可以把它理解为：

> Git 在本地保留的“指针移动日记”。

## 1、reflog 能解决什么

执行 `reset`、`amend`、切换分支或变基后，某个提交可能不再出现在当前的 `git log` 中。只要它还没被 Git 清理，通常就能通过 `reflog` 重新找到。

![[Git-reflog恢复手绘.png|800]]

上图中，`reset` 只是让 `main` 从 `C` 移到 `B`，并没有立即销毁提交 `C`。`reflog` 记录了指针曾经在 `C`，因此可以用这条记录定位它。

## 2、查看 reflog

```shell
git reflog
```

只查看最近几条：

```shell
git reflog -5
```

误执行 `reset` 后，可能看到：

```text
edba6e9 HEAD@{0}: reset: moving to HEAD~1
64829c9 HEAD@{1}: commit: add config
```

| 内容 | 含义 |
| --- | --- |
| `64829c9` | 当时所在提交的哈希 |
| `HEAD@{1}` | `HEAD` 的上一个记录位置 |
| `commit: add config` | 导致指针变化的操作说明 |

`HEAD@{1}` 中的数字会随后续操作变化。恢复时使用已确认的提交哈希，通常更清楚。

## 3、安全恢复流程

假设 `64829c9` 是想找回的提交。

先确认当前工作区状态：

```shell
git status
```

再检查目标提交：

```shell
git show 64829c9
```

优先创建一个临时分支保住它：

```shell
git branch rescue-before-reset 64829c9
```

这不会移动当前分支，只是给目标提交增加一个可达引用，是更保守的恢复方式。

如果确实要让当前分支重新指向它，再执行：

```shell
git reset --hard 64829c9
```

> [!warning] 找回提交不等于找回所有未提交内容
> `reflog` 主要记录引用移动。它能帮助找回已经形成的提交，但不能保证找回从未提交、又被覆盖的工作区内容。

## 4、reflog 的边界

- 它是当前本地仓库的记录，不会随普通 `git push` 上传。
- 同一项目在不同电脑上的 `reflog` 通常不同。
- `reflog` 不是永久档案，记录和不可达对象可能随时间过期并被清理。
- 发现误操作后，应尽快定位目标提交并创建恢复分支。

# 八、使用 git revert 安全撤销共享提交

`git revert` 不会删除或改写旧提交。它会计算目标提交引入了哪些改动，再将这些改动反过来应用到当前状态，最后创建一个新提交。

可以记成：

> 不删除错误提交，而是新增一次“反向操作”。

## 1、历史如何变化

![[Git-revert反向提交手绘.png|800]]

假设当前历史是 `A → B → C`，现在要撤销 `B` 引入的改动。执行后，Git 保留 `A`、`B`、`C`，并在末尾新增反向提交 `D`：

```text
A → B → C → D
```

`B` 仍然存在于历史中，`D` 只负责抵消 `B` 引入的改动。

> [!important] revert 不等于回到 B 之前的完整状态
> `C` 中与 `B` 无关的后续改动仍然保留。`revert B` 只尝试反做 `B` 本身引入的改动。

## 2、基本操作流程

先检查当前状态和目标提交：

```shell
git status
git show <commit>
```

然后执行撤销：

```shell
git revert <commit>
```

默认情况下，Git 会打开编辑器编辑新提交的信息。如果希望直接使用 Git 生成的默认信息：

```shell
git revert --no-edit <commit>
```

操作完成后检查新提交：

```shell
git show HEAD
git log --oneline -5
```

## 3、出现冲突时

如果当前代码已经对 `B` 修改过的位置做了后续改动，Git 可能无法自动反做 `B`，此时会暂停并报告冲突。

查看冲突：

```shell
git status
```

手动解决文件冲突后：

```shell
git add <file>
git revert --continue
```

如果不想继续本次撤销：

```shell
git revert --abort
```

`--abort` 会取消当前未完成的 `revert` 流程，尽量恢复到执行 `revert` 之前的状态。

## 4、适合场景

- 错误提交已经推送到远程仓库
- 其他人可能已经基于该提交继续开发
- 需要保留完整的审计历史

# 九、reset 和 revert 的区别

| 对比项 | `git reset` | `git revert` |
| --- | --- | --- |
| 核心动作 | 移动当前分支指针 | 新增反向提交 |
| 原提交是否保留在当前历史中 | 可能不再可见 | 保留 |
| 是否重写历史 | 是 | 否 |
| 主要适用范围 | 本地、未共享历史 | 已共享历史 |
| 对工作区的风险 | 取决于所选模式 | 不直接丢弃未提交内容，但可能冲突 |

![[exec-3028966f-f330-4e64-87c8-43682bd7d8e6.png|400]]

核心原则：

> 本地、未共享的提交可以考虑 `reset`；已共享的提交优先考虑 `revert`。
