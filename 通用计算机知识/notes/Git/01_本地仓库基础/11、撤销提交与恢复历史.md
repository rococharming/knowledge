# 一、撤销不同阶段的修改

Git 中的“撤销”不是一个单一操作。应先确认修改位于哪个阶段，以及它是否已经共享：

| 需求 | 常用命令 | 对历史的影响 |
| --- | --- | --- |
| 取消暂存或丢弃未提交修改 | `git restore` | 不影响提交历史 |
| 修正最近一次本地提交 | `git commit --amend` | 替换最近提交 |
| 撤销未共享的本地提交 | `git reset` | 移动分支指针，可能重写历史 |
| 撤销已共享提交的影响 | `git revert` | 保留原历史，新增反向提交 |
| 找回本地指针曾经的位置 | `git reflog` | 只查看本地引用移动记录 |

未提交修改的处理见 [[6、撤销修改和取消暂存]]；最近一次提交的修正见 [[10、修改最近一次提交]]。本篇重点是 `reset`、`revert` 和 `reflog`。

# 二、HEAD、分支指针和提交

在正常的分支状态下，可以简化理解为：

```text
HEAD ──指向──▶ 当前分支 ──指向──▶ 某个提交
```

例如：

```text
HEAD -> main -> edba6e9
```

这表示 `HEAD` 通过 `main` 分支间接指向提交 `edba6e9`。

执行：

```shell
git reset <commit>
```

会让当前分支指向另一个提交。三种 `reset` 模式的主要区别，是分支指针移动后如何处理暂存区和工作区。

# 三、git reset --soft

```shell
git reset --soft <commit>
```

它会：

- 移动当前分支指针
- 保留暂存区
- 保留工作区

可以理解为：撤销提交，但把撤销出来的改动继续放在暂存区。

```shell
git reset --soft HEAD~1
```

上述命令让当前分支回到上一次提交，但最近一次提交对应的改动仍然处于暂存状态。

适合场景：

- 撤销刚才的提交，保留改动并继续保持暂存
- 将连续几次本地提交重新整理为一次提交

# 四、git reset --mixed

```shell
git reset --mixed <commit>
```

`--mixed` 是 `git reset` 的默认模式，因此也可以写成：

```shell
git reset <commit>
```

它会：

- 移动当前分支指针
- 重置暂存区
- 保留工作区

可以理解为：撤销提交，再把改动放回工作区，变成未暂存状态。

```shell
git reset --mixed HEAD~1
```

执行后，最近一次提交的改动仍然存在于文件中，但不再处于暂存状态。适合需要重新选择提交内容的场景。

# 五、git reset --hard

```shell
git reset --hard <commit>
```

它会：

- 移动当前分支指针
- 重置暂存区
- 重置工作区

可以理解为：强制让分支、暂存区和工作区都回到指定提交对应的状态。

> [!danger] `git reset --hard` 可能丢失数据
> 它会丢弃暂存区和工作区中的相关改动。`reflog` 通常可以帮助找回被移出当前分支历史的提交，但无法保证找回从未提交、又被 `--hard` 覆盖的工作区内容。执行前应先提交、备份或使用 `git stash`保存重要内容。

# 六、三种 reset 模式对比

| 模式 | 移动分支指针 | 重置暂存区 | 重置工作区 | 常见用途 |
| --- | --- | --- | --- | --- |
| `--soft` | 是 | 否 | 否 | 撤销提交，改动保持暂存 |
| `--mixed` | 是 | 是 | 否 | 撤销提交，重新选择暂存内容 |
| `--hard` | 是 | 是 | 是 | 强制回到指定提交 |

记忆方式：

```text
soft  ：只动分支指针
mixed ：再动暂存区
hard  ：连工作区也一起动
```

# 七、使用 git reflog 找回历史位置

`git reflog` 用于查看 `HEAD` 和本地分支引用曾经移动过的位置：

```shell
git reflog
```

例如，误执行 `reset` 后，可以先在 `reflog` 中找到操作前的提交哈希：

```text
edba6e9 HEAD@{0}: reset: moving to HEAD~1
64829c9 HEAD@{1}: commit: add config
```

假设 `64829c9` 是需要找回的提交，可以先检查它：

```shell
git show 64829c9
```

确认无误后，再根据目标选择恢复方式。例如，让当前分支重新指向它：

```shell
git reset --hard 64829c9
```

> [!note] `reflog` 是本地恢复记录
> 它不是远程仓库的共享提交历史，也不会随普通 `git push` 上传。不同仓库副本的 `reflog` 可能不同。

# 八、使用 git revert 安全撤销共享提交

`git revert` 不会删除或改写指定提交，而是创建一个新提交，用反向改动抵消原提交的影响。

```shell
git revert <commit>
```

如果希望直接使用 Git 默认生成的提交信息：

```shell
git revert --no-edit <commit>
```

可以简化理解为：

```text
A -- B -- C
          │
          └─ revert B 后新增 D

A -- B -- C -- D
```

`B` 仍然存在于历史中，`D` 包含用来撤销 `B` 影响的反向改动。

适合场景：

- 错误提交已经推送到远程仓库
- 其他人可能已经基于该提交继续开发
- 需要保留完整的审计历史

`revert` 时如果当前代码和原提交差异较大，也可能出现冲突。解决冲突后，需要按 Git 的提示继续或取消操作。

# 九、reset 和 revert 的区别

| 对比项 | `git reset` | `git revert` |
| --- | --- | --- |
| 核心动作 | 移动当前分支指针 | 新增反向提交 |
| 原提交是否保留在当前历史中 | 可能不再可见 | 保留 |
| 是否重写历史 | 是 | 否 |
| 主要适用范围 | 本地、未共享历史 | 已共享历史 |
| 对工作区的风险 | 取决于所选模式 | 不直接丢弃未提交内容，但可能冲突 |

核心原则：

> 本地、未共享的提交可以考虑 `reset`；已共享的提交优先考虑 `revert`。

# 十、操作前的检查流程

在执行会移动历史或改动文件的命令前，先检查：

```shell
git status
git log --oneline -5
git diff
git diff --staged
```

然后按需求选择：

```text
修改还没有提交？
  └─ restore

只是最近一次本地提交需要修正？
  └─ commit --amend

需要撤销未共享的本地提交？
  └─ reset --soft / --mixed / --hard

提交已经共享，需要撤销它的影响？
  └─ revert

误移动了 HEAD 或分支，需要找回原位置？
  └─ reflog
```

历史检查命令见 [[9、灵活查看提交历史]]。
