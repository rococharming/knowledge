# 一、Git 本地提交模型

Git 本地仓库的核心操作不是把文件直接提交到仓库，而是经过一个中间区域：暂存区。

本地提交流程可以概括为：

```text
工作区
  │  git add
  ▼
暂存区
  │  git commit
  ▼
本地仓库
```

对应到实际操作：

```text
修改文件
  │
  ▼
git add
  │
  ▼
git commit
```

这条流程是理解后续命令和文件状态的基础。

命令概览：

| 命令                  | 作用              |
| ------------------- | --------------- |
| `git add`           | 把工作区中的文件内容加入暂存区 |
| `git commit`        | 把暂存区中的内容保存为一次提交 |
| `git status`        | 查看工作区和暂存区的状态    |

需要注意的是，`git commit` 提交的是暂存区中的内容，不是工作区中的所有内容。

如果后续要把本地提交同步到远程仓库，才会使用：

```shell
git push
```

`git push` 属于远程仓库操作，不属于本地提交的核心流程。

# 二、Git的三个工作区域

在一个Git本地仓库中，最核心的三个区域是：

|区域|英文|作用|
|---|---|---|
|工作区|`Working Tree` / `Working Directory`|实际编辑文件的项目目录|
|暂存区|`Staging Area` / `Index`|保存下一次提交要包含的内容|
|本地仓库|`Local Repository`|保存已经提交的历史记录|

日常开发时，文件修改首先发生在工作区。执行 `git add` 后，修改内容进入暂存区。执行 `git commit` 后，暂存区中的内容会生成一次提交，保存到本地仓库。

## 1、工作区

工作区，也叫 `Working Tree` 或 `Working Directory`，就是平时直接看到和编辑的项目目录。

例如：

```text
learngit/
  ├── .git/
  ├── README.md
  ├── src/
  └── Cargo.toml
```

除了 `.git` 目录以外，项目中的普通文件和目录通常都可以看作工作区内容。

在工作区中可以进行：

- 新建文件
- 修改文件
- 删除文件
- 移动文件
- 重命名文件

这些变化会被 Git 检测到，但不会自动进入版本历史。

例如：

```shell
echo "hello" > a.txt
```

此时 `a.txt` 只是工作区中的一个新文件，还没有被 Git 跟踪。

## 2、暂存区

暂存区，也叫 `Staging Area` 或 `Index`，是 Git 在提交前用来收集变更的区域。

可以把暂存区理解为：下一次 commit 要提交的内容。

执行：

```shell
git add a.txt
```

Git 会把 `a.txt` 当前这一刻的内容加入暂存区。

这里容易误解：`git add` 不是简单记录“这个文件名要提交”，而是记录这个文件在执行 `git add` 时的内容快照。

如果执行 `git add a.txt` 后，又继续修改 `a.txt`，那么暂存区中保存的仍然是之前那一版内容，新的修改还停留在工作区。

暂存区底层主要由 `.git/index` 管理。日常使用中不需要直接修改这个文件。

## 3、本地仓库

本地仓库是 Git 真正保存历史记录的地方。

执行：

```shell
git commit -m "add a.txt"
```

Git 会把暂存区中的内容生成一次提交，并保存到本地仓库。

本地仓库的数据保存在 `.git` 目录中，包括提交历史、分支引用、标签引用、对象数据、仓库配置。

# 三、文件状态流转

## 1、文件状态分类

Git 中文件状态可以分为两大类：

| 状态          | 含义                  |
| ----------- | ------------------- |
| `Untracked` | 未跟踪，文件还没有被 Git 纳入管理 |
| `Tracked`   | 已跟踪，文件已经被 Git 纳入管理  |

已跟踪文件又可以继续分为：

| 状态           | 含义              |
| ------------ | --------------- |
| `Unmodified` | 已跟踪，内容与最近一次提交一致 |
| `Modified`   | 已跟踪，但工作区内容发生了修改 |
| `Staged`     | 修改已经加入暂存区，等待提交  |
基本状态流转如下：

```text
新建文件
  │
  ▼
Untracked
  │  git add
  ▼
Staged
  │  git commit
  ▼
Unmodified
  │  修改文件
  ▼
Modified
  │  git add
  ▼
Staged
```

## 2、未跟踪状态

新建文件后，如果还没有执行过 `git add`，它就是未跟踪文件。

```shell
echo "hello" > a.txt
```

查看状态：

```
git status
```

可以看到：

这说明`a.txt`只存在于工作区，Git 还没有把它纳入版本控制。


## 3、已暂存状态

把文件加入暂存区：

```shell
git add a.txt
```

再次查看状态：

```
git status
```

可以看到：

![[assets/Pasted image 20260607224241.png|400]]

这表示 `a.txt` 已经进入暂存区，等待下一次提交。

此时 `a.txt` 已经是已跟踪文件。即使它还没有被提交，也不再是 `Untracked` 状态。

## 4、已修改状态

如果一个已跟踪文件在工作区中被再次修改，它会进入 `Modified` 状态。

例如，在 `git add a.txt` 之后继续修改：

```shell
echo "new line" >> a.txt
```

查看状态：

```shell
git status
```

可以看到：

![[assets/Pasted image 20260607224543.png|400]]

这表示同一个文件同时存在两份变化：

| 位置                              | 含义                |
| ------------------------------- | ----------------- |
| `Changes to be committed`       | 暂存区中已经有一版 `a.txt` |
| `Changes not staged for commit` | 工作区中又产生了新的修改      |
此时如果直接提交：

```shell
git commit -m "add a.txt"
```

提交进去的是暂存区中那一版内容，不包含工作区后续新增的修改。

如果希望最新修改也进入本次提交，需要再次执行：

```shell
git add a.txt
```

`git add` 可以重复执行。每执行一次，都会把文件当前内容重新写入暂存区。

## 5、未修改内容

当暂存区内容被提交后，如果工作区没有新的修改，文件就是 `Unmodified` 状态。

提交：

```shell
git commit -m "modify a.txt"
```

查看状态：

```shell
git status
```

可以看到：

![[assets/Pasted image 20260607224938.png|400]]

这表示：

| 区域   | 状态        |
| ---- | --------- |
| 工作区  | 没有未暂存修改   |
| 暂存区  | 没有待提交内容   |
| 本地仓库 | 已保存最近一次提交 |
此时 `a.txt` 属于已跟踪且未修改状态。


# 四、状态检查和差异查看

## 1、使用git status查看状态

`git status`用来查看当前仓库状态：

```shell
git status
```

它主要回答两个问题：

- 工作区有哪些变化
- 暂存区有哪些变化

常见输出区域如下：

| 输出区域                                    | 含义               |
| --------------------------------------- | ---------------- |
| `Untracked files`                       | 未跟踪文件            |
| `Changes not staged for commit`         | 工作区中有修改，但还没加入暂存区 |
| `Changes to be committed`               | 暂存区中有内容，等待提交     |
| `nothing to commit, working tree clean` | 工作区和暂存区都干净       |
日常使用 Git 时，`git status` 是最常用的检查命令。

## 2、使用git diff查看工作区修改

```shell
git diff
```

它查看的是**工作区相对于暂存区多了哪些修改**。

也就是说，`git diff`显示是的已经修改，但还没有`git add`的内容。

适合在`git add`前检查自己刚刚改了什么。


## 3、使用git diff --staged查看暂存区修改

```shell
git diff --staged
```

它查看的是**暂存区相对于最近一次提交多了哪些修改**.

也就是说，`git diff --staged`显示的是已经`git add`，准备进入下一次 commit 的内容。

也可以使用等价写法：

```shell
git diff --cached
```

# 五、一次完整状态流转示例

## 1、新建文件并查看状态

创建文件：

```shell
echo "hello" > a.txt
```

查看状态：

```shell
git status
```

此时 `a.txt` 是未跟踪文件：

```text
Untracked files:  
		a.txt
```

## 2、加入暂存区并查看状态

执行：

```shell
git add a.txt
```

查看状态：

```shell
git status
```

此时 `a.txt` 已暂存：

```text
Changes to be committed:  
		new file: a.txt
```

## 3、继续修改并查看差异

继续修改：

```shell
echo "new line" >> a.txt
```

查看状态：

```shell
git status
```

此时可能看到：

```text
Changes to be committed:       
		new file:   a.txt
Changes not staged for commit:        
		modified:   a.txt
```

这表示暂存区中有旧版本，工作区中有新修改。

查看工作区新增修改：

```shell
git diff
```

结果：

如果要把最新修改也放进下一次提交，再次执行：

```shell

```

查看暂存区准备提交的内容：

```shell
git diff --staged
```

结果：

## 4、提交并查看历史

提交：

```shell

```

查看状态：

```shell

```

如果没有新的修改，会看到：

# 六、.git目录中的相关内容

## 1、.git目录和本地仓库数据

`.git`是 Git 仓库的核心目录。工作区中的普通文件是项目文件，`.git`中保存的是 Git 管理这些文件所需的数据。

可以查看`.git`目录：

```shell
ls -l .git
```

常见内容包括：

| 内容         | 作用          |
| ---------- | ----------- |
| `config`   | 当前仓库的本地配置   |
| `HEAD`     | 当前检出位置      |
| `hooks/`   | Git 钩子脚本目录  |
| `info/`    | 当前仓库的本地辅助信息 |
| `objects/` | Git 对象数据库   |
| `refs/`    | 分支、标签等引用    |
| `index`    | 暂存区的底层文件    |

## 2、index与暂存区

`.git/index` 是暂存区的底层表现形式。

执行：

```shell
git add a.txt
```

本质上就是把 `a.txt` 当前内容写入 `index`。

刚执行 `git init` 时，仓库中可能还没有 `.git/index` 文件。首次执行 `git add` 后，`index` 文件才会出现。

## 3、objects/和提交历史

`.git/objects/`是 Git 的对象数据库，用来保存 Git 内部对象。

常见对象包括：

| 对象       | 说明   |
| -------- | ---- |
| `blob`   | 文件内容 |
| `tree`   | 目录结构 |
| `commit` | 提交对象 |
| `tag`    | 标签对象 |
执行 `git commit` 后，Git 会把暂存区内容组织成一次提交，并把相关对象写入 `objects/`。

## 4、HEAD与当前检出位置

`.git/HEAD` 表示当前检出位置。

常见内容类似：

```text
ref: refs/heads/main
```

这表示当前位于 `main` 分支。

如果 `HEAD` 直接指向某个提交哈希，而不是指向某个分支引用，就称为 `detached HEAD`，也就是游离 `HEAD` 状态。


## 5、refs/和引用

`.git/refs/` 用来保存引用。

引用可以理解为用一个名字指向某个提交。

常见目录包括：

| 路径              | 说明     |
| --------------- | ------ |
| `refs/heads/`   | 本地分支   |
| `refs/tags/`    | 标签     |
| `refs/remotes/` | 远程跟踪分支 |

例如：

```text
refs/heads/main
```

表示本地 `main` 分支指向的提交。

## 6、config

`.git/config` 是当前仓库的本地配置文件，只对当前仓库生效。

它不同于全局配置文件：

```text
~/.gitignore
```

例如，在当前仓库中执行：

```shell
git config user.email "work@example.com"
```

配置会写入 `.git/config`，只影响当前仓库。

## 7、hooks/

`.git/hooks/` 用来存放 Git 钩子脚本，例如 `pre-commit`、`commit-msg`、`pre-push`。

默认的 `.sample` 文件只是模板，不会自动生效。要启用钩子，需要去掉 `.sample` 后缀；在 macOS 或 Linux 中，通常还需要添加可执行权限。

## 8、info/exclude

`.git/info/exclude` 的作用类似 `.gitignore`，也可以忽略文件。区别是它只对当前本地仓库生效，通常不会提交到远程仓库。
