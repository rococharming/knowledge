# 一、概述

在 Git 仓库中，删除文件和重命名文件都很常见。

删除文件有两种常见方式：

```shell
rm <file>
git rm <file>
```

重命名文件也有两种常见方式：

```shell
mv <old> <new>
git mv <old> <new>
```

它们的区别可以先简单理解为：

| 命令 | 作用 |
| --- | --- |
| `rm` / `mv` | 只操作工作区，后面还需要`git add` |
| `git rm` / `git mv` | 操作工作区，并且自动把变化加入暂存区 |

# 二、删除文件

## 1、使用 rm 删除文件

`rm`是操作系统命令，不是 Git 命令。

例如，删除一个已经被 Git 跟踪的文件`e.txt`：

```shell
rm e.txt
```

它的作用是从工作区删除`e.txt`。

此时 Git 会发现：原来被跟踪的文件不见了。

执行：

```shell
git status
```

可以看到：

```text
deleted:    e.txt
```

如果使用简洁状态查看：

```shell
git status -s
```

可能看到：

```text
 D e.txt
```

这里的`D`出现在第二列，表示工作区中删除了`e.txt`，但这个删除操作还没有进入暂存区。

如果要把这个删除操作加入下一次提交，还需要执行：

```shell
git add e.txt
```

或者：

```shell
git add .
```

可以理解为：

```text
rm e.txt        ->  只是删除工作区文件
git add e.txt   ->  把删除记录加入暂存区
git commit      ->  提交删除记录
```

暂存之后，再执行：

```shell
git status -s
```

可能看到：

```text
D  e.txt
```

这表示删除记录已经进入暂存区，下一次提交会删除这个文件。

## 2、使用 git rm 删除文件

`git rm`是 Git 提供的删除命令。

例如：

```shell
git rm e.txt
```

它会同时做两件事：

| 区域 | 结果 |
| --- | --- |
| 工作区 | 删除`e.txt`文件 |
| 暂存区 | 把删除记录加入暂存区 |

也就是说，它相当于：

```shell
rm e.txt
git add e.txt
```

执行`git rm e.txt`之后，再查看状态：

```shell
git status -s
```

可能看到：

```text
D  e.txt
```

这表示删除操作已经暂存。

需要注意：

1. `git rm`只能用于删除已经被 Git 跟踪的文件。
2. 如果文件有未提交修改，Git 可能会拒绝删除，防止误删内容。
3. 如果只是想让 Git 不再跟踪某个文件，但保留工作区文件，可以使用`git rm --cached <file>`。

例如：

```shell
git rm --cached e.txt
```

这个命令会把`e.txt`从 Git 跟踪中移出，但不会删除工作区里的`e.txt`文件。

`git rm --cached`后面介绍`.gitignore`时会经常用到。

## 3、恢复误删文件

### （1）恢复 rm 删除的文件

如果使用`rm`删除了一个已跟踪文件，但还没有暂存这个删除操作，可以恢复：

```shell
git restore e.txt
```

例如：

```shell
rm e.txt
git status -s
```

可以看到：

```text
 D e.txt
```

此时执行：

```shell
git restore e.txt
```

`e.txt`就会从最近一次提交或暂存区中恢复回来。

### （2）恢复 git rm 删除的文件

如果执行的是：

```shell
git rm e.txt
```

此时删除操作已经进入暂存区。

查看状态可能是：

```text
D  e.txt
```

这时需要先取消暂存：

```shell
git restore --staged e.txt
```

再恢复工作区文件：

```shell
git restore e.txt
```

可以理解为：

| 步骤 | 命令 | 作用 |
| --- | --- | --- |
| 1 | `git restore --staged e.txt` | 先把删除记录从暂存区拿出来 |
| 2 | `git restore e.txt` | 再把工作区文件恢复回来 |

# 三、重命名文件

## 1、使用 mv 重命名文件

`mv`是操作系统命令，不是 Git 命令。

例如，假设`f.txt`已经纳入版本控制，把`f.txt`重命名为`e.txt`：

```shell
mv f.txt e.txt
```

它的作用是把工作区中的`f.txt`改名为`e.txt`。

此时执行：

```shell
git status
```

Git 会识别为两个操作：

```text
deleted:    f.txt
untracked:  e.txt
```

![[assets/Pasted image 20260612004323.png|400]]

如果使用简洁状态查看：

```shell
git status -s
```

可以看到：

```text
 D f.txt
?? e.txt
```

这表示：

| 状态 | 含义 |
| --- | --- |
| ` D f.txt` | 工作区中删除了原来的`f.txt` |
| `?? e.txt` | 工作区中出现了新的未跟踪文件 |

如果要把这次重命名加入暂存区，可以执行：

```shell
git add f.txt e.txt
```

或者：

```shell
git add .
```

暂存后，Git 会识别为重命名：

```text
renamed:    f.txt -> e.txt
```

简洁状态可能显示为：

```text
R  f.txt -> e.txt
```

这里的`R`表示 rename，也就是重命名。

需要注意，Git 本质上不是专门保存“重命名动作”，而是在比较内容时推断：

> 这个新文件很像是从旧文件改名过来的。

如果文件改名的同时内容也大幅修改，Git 不一定识别成重命名，也可能显示为删除旧文件、增加新文件。

## 2、使用 git mv 重命名文件

`git mv`是 Git 提供的重命名命令。

例如：

```shell
git mv f.txt e.txt
```

它相当于：

```shell
mv f.txt e.txt
git add f.txt e.txt
```

也就是说，它会同时完成：

| 区域 | 结果 |
| --- | --- |
| 工作区 | 把`f.txt`重命名为`e.txt` |
| 暂存区 | 把这个重命名变化加入暂存区 |

执行后查看状态：

```shell
git status -s
```

可能看到：

```text
R  f.txt -> e.txt
```

这表示重命名变化已经暂存，下一次提交会记录这次文件名变化。

## 3、恢复 mv 重命名

如果使用`mv`重命名后还没有暂存，可以直接改回去：

```shell
mv e.txt f.txt
```

如果已经暂存，可以先取消暂存：

```shell
git restore --staged f.txt e.txt
```

然后删除重命名后的文件，再恢复原文件：

```shell
rm e.txt
git restore f.txt
```

这几步的含义是：

| 命令                                 | 作用        |
| ---------------------------------- | --------- |
| `git restore --staged f.txt e.txt` | 取消暂存重命名变化 |
| `rm e.txt`                         | 删除重命名后的文件 |
| `git restore f.txt`                | 恢复原来的文件   |
