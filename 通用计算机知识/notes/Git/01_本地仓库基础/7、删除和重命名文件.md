# 一、删除和重命名的核心区别

在 Git 仓库中，删除和重命名都可以用系统命令完成，也可以用 Git 命令完成。

| 操作 | 系统命令 | Git 命令 | 区别 |
|---|---|---|---|
| 删除文件 | `rm <file>` | `git rm <file>` | `git rm` 会自动暂存删除 |
| 重命名文件 | `mv <old> <new>` | `git mv <old> <new>` | `git mv` 会自动暂存重命名 |

可以先记成：

> `rm` / `mv` 只改工作区；`git rm` / `git mv` 改工作区并同步更新暂存区。

# 二、删除文件

## 1、使用 `rm`

```shell
rm e.txt
```

`rm` 是操作系统命令，只会从工作区删除文件。对于已跟踪文件，Git 会在状态中显示删除：

```text
 D e.txt
```

这里的 `D` 在第二列，表示工作区删除了文件，但删除记录还没有暂存。

如果要把删除操作纳入下一次提交：

```shell
git add e.txt
git commit -m "remove e.txt"
```

## 2、使用 `git rm`

```shell
git rm e.txt
```

它相当于：

```shell
rm e.txt
git add e.txt
```

执行后，简洁状态可能显示：

```text
D  e.txt
```

这里的 `D` 在第一列，表示删除记录已经进入暂存区。

## 3、停止跟踪但保留文件

如果只是想让 Git 不再跟踪某个文件，但保留工作区文件：

```shell
git rm --cached e.txt
```

这常用于“文件已经被提交过，后来才发现应该被 `.gitignore` 忽略”的场景。忽略规则见 [[8、忽略规则文件|忽略规则文件]]。

# 三、恢复误删文件

## 1、恢复未暂存的 `rm`

如果只是执行了：

```shell
rm e.txt
```

且还没暂存删除，可以恢复：

```shell
git restore e.txt
```

## 2、恢复已暂存的 `git rm`

如果执行的是：

```shell
git rm e.txt
```

需要先取消暂存，再恢复工作区文件：

```shell
git restore --staged e.txt
git restore e.txt
```

这与 [[6、撤销修改和取消暂存|取消暂存和恢复工作区]] 的规则一致。

# 四、重命名文件

## 1、使用 `mv`

```shell
mv f.txt e.txt
```

`mv` 只操作工作区。Git 可能先看到：

```text
 D f.txt
?? e.txt
```

表示旧文件被删除，新文件还未跟踪。暂存后：

```shell
git add f.txt e.txt
```

Git 可能识别为：

```text
R  f.txt -> e.txt
```

Git 本质上不是永久保存“重命名动作”，而是在比较内容时推断新文件很像旧文件改名而来。如果改名同时大幅改内容，Git 可能显示为删除旧文件、增加新文件。

## 2、使用 `git mv`

```shell
git mv f.txt e.txt
```

它相当于：

```shell
mv f.txt e.txt
git add f.txt e.txt
```

执行后重命名变化已经暂存，下一次提交会记录这个路径变化。

# 五、恢复重命名

## 1、未暂存的重命名

如果只是执行了 `mv`，可以直接改回：

```shell
mv e.txt f.txt
```

## 2、已暂存的重命名

如果重命名已经暂存，可以先取消暂存，再恢复：

```shell
git restore --staged f.txt e.txt
rm e.txt
git restore f.txt
```

含义是：先撤销暂存区里的重命名记录，再删除新路径，最后从 Git 中恢复旧路径。

# 六、小结

| 场景 | 推荐命令 |
|---|---|
| 删除并立刻纳入下一次提交 | `git rm <file>` |
| 只在工作区删除，稍后再决定 | `rm <file>` |
| 停止跟踪但保留本地文件 | `git rm --cached <file>` |
| 重命名并立刻纳入下一次提交 | `git mv <old> <new>` |
| 重命名后还想继续编辑再暂存 | `mv <old> <new>` 后再 `git add` |

判断命令是否“安全”的关键，是看它是否同时改变暂存区。只改工作区的操作更容易回头检查；已经暂存的操作则要用 `git restore --staged` 先退回。
