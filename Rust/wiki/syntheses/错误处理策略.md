# 错误处理策略

Rust 的错误处理体系围绕 `Result<T, E>` 和 `panic!` 两个核心机制展开。选择正确的处理方式，是编写健壮 Rust 代码的关键决策之一。

## 错误分类

### 可恢复错误

> 错误发生后，程序仍然有机会采取补救措施，或者把错误继续上交给上层处理。

这类错误通常来自外部环境：

- 文件不存在
- 权限不足
- 网络请求失败
- 用户输入非法
- 配置文件格式错误

使用 `Result<T, E>` 处理。

### 不可恢复错误

> 程序已经进入了无法安全、合理继续执行的状态。

这类错误通常意味着程序内部逻辑问题：

- 数组或切片越界访问
- 断言失败
- 在 `Err` 上调用 `unwrap()`
- 程序进入理论上不应该到达的分支

使用 `panic!` 处理。

> 编译通过不等于程序绝对不会出错。Rust 只保证安全 Rust 下的内存安全，但程序逻辑错误、运行时错误、外部环境错误仍然有可能发生。

## 处理策略对照表

| 场景 | 推荐方式 | 说明 |
|---|---|---|
| 可预期、可处理的错误 | `Result<T, E>` | 文件不存在、解析失败、网络失败 |
| 程序逻辑错误 | `panic!` | 越界访问、断言失败、不可能分支 |
| 临时示例或测试代码 | `unwrap()` / `expect()` | 示例程序、单元测试、快速验证 |
| 复杂应用程序错误 | 自定义错误类型 | 命令行工具、库、业务程序 |

## 简单判断流程

1. **调用者有机会处理** → 返回 `Result`
2. **程序已经无法合理继续** → 使用 `panic!`
3. **当前只是示例或测试** → 可以使用 `unwrap()` / `expect()`
4. **错误类型需要表达业务语义** → 定义自定义错误类型

## 统一错误类型的方式对比

| 方式 | 示例 | 适合场景 |
|---|---|---|
| 通用错误类型 | `Box<dyn Error>` | 应用程序、小工具、只需要向外报告错误 |
| 自定义错误类型 | `enum MyError` | 库、业务程序、需要区分错误种类 |
| 第三方错误库 | `anyhow`、`thiserror` | 实际项目中减少样板代码 |

## unwrap/expect 使用原则

- **示例代码**：可以，但要注明"生产代码应做适当错误处理"
- **测试代码**：可以，测试失败本身就是需要修复的信号
- **已知不可能失败**：如硬编码的合法值解析，用 `expect("说明理由")`
- **用户输入/外部数据**：**禁止**直接使用 unwrap

```rust
// 合理：硬编码的合法 IP
let home: IpAddr = "127.0.0.1"
    .parse()
    .expect("硬编码的 IP 地址应该是合法的");

// 不合理：用户输入可能非法
let user_ip: IpAddr = user_input.parse().unwrap();  // 危险！
```

## 自定义错误类型的决策

当以下情况出现 2 项及以上时，考虑自定义错误类型：

- 函数可能产生多种不同来源的错误
- 调用者需要精确区分错误种类
- 错误需要携带业务上下文信息
- 当前 crate 是库，需要稳定 API
- 希望配合 `?` 自动转换底层错误
