# 集成测试

集成测试位于被测试库的外部，像普通用户一样通过公开 API 使用库。

## 核心特点

- 只能访问库的**公开 API**
- 每个测试文件会被编译成一个独立的 **crate**
- 适合测试多个模块协作后的整体行为，更接近真实使用场景

> 单元测试关注"内部某个小单元是否正确"，集成测试关注"这个库作为一个整体是否能被正确使用"。

## tests/ 目录

集成测试放在项目根目录的 `tests/` 目录中：

```text
adder
├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    └── integration_test.rs
```

`tests/` 目录是 Cargo 识别集成测试的特殊目录。该目录中的每个测试文件会被当作一个独立 crate 编译，因此需要像外部使用者一样通过 crate 名称引入公开 API：

```rust
use adder::add_two;

#[test]
fn add_two_and_two() {
    let result = add_two(2);
    assert_eq!(result, 4);
}
```

## 运行指定集成测试

- 只运行某个集成测试函数：

```shell
cargo test add_two_and_two
```

- 只运行某个集成测试文件：

```shell
cargo test --test integration_test
```

如果有多个集成测试文件，可以分别运行：

```shell
cargo test --test user_test
cargo test --test order_test
```

## 共享模块

如果多个集成测试文件需要共享初始化函数，不推荐直接创建 `tests/common.rs`，因为该文件会被当作独立测试 crate 编译。

推荐结构：

```text
tests
├── integration_test.rs
└── common
    └── mod.rs
```

`tests/common/mod.rs`：

```rust
pub fn setup() {
    println!("setup...");
}
```

`tests/integration_test.rs`：

```rust
mod common;
use adder::add_two;

#[test]
fn add_two_and_two() {
    common::setup();
    let result = add_two(2);
    assert_eq!(result, 4);
}
```

## 二进制包的集成测试组织

对于只有 `src/main.rs` 的二进制包，集成测试不能像测试库一样直接 `use` 它的内部函数。

更常见的做法是同时提供 `src/lib.rs` 和 `src/main.rs`：

```text
my_app
├── Cargo.toml
├── src
│   ├── lib.rs
│   └── main.rs
└── tests
    └── integration_test.rs
```

将核心逻辑放入 `src/lib.rs`：

```rust
pub fn run(input: &str) -> String {
    input.to_uppercase()
}
```

`src/main.rs` 只保留入口逻辑：

```rust
use my_app::run;

fn main() {
    let result = run("hello");
    println!("{}", result);
}
```

集成测试测试库逻辑：

```rust
use my_app::run;

#[test]
fn run_converts_input_to_uppercase() {
    let result = run("hello");
    assert_eq!(result, "HELLO");
}
```

这种结构的好处：

- `src/lib.rs` 中的核心逻辑可以被单元测试和集成测试覆盖
- `src/main.rs` 保持很薄，只负责参数读取、调用逻辑、输出结果
- 程序行为更容易测试和复用
