# 一、Rust测试概述

## 1、测试的基本定位

Rust 内置了测试支持，可以通过`cargo test`编译并运行项目中的测试代码。

测试函数通常围绕三个步骤展开：

1. 设置测试所需的数据或状态
2. 运行需要验证的代码
3. 使用断言判断结果是否符合预期

Rust项目中常见的测试类型包括：

|测试类型|常见位置|主要用途|
|---|---|---|
|单元测试|`src` 目录中的源码文件内部|测试某个函数、模块或内部实现|
|集成测试|项目根目录下的 `tests/` 目录|像外部用户一样测试库的公开 API|
|文档测试|文档注释中的 Rust 代码块|保证文档示例可以编译或运行|

执行`cargo test`时，`Cargo`会编译并运行当前包的所有单元测试、集成测试和文档测试。


## 2、测试函数的基本结构

使用`cargo new adder --lib`创建一个库项目时，`/src/lib.rs`中通常会生成一个简单的测试模板：

```rust
pub fn add(left: u64, right: u64) -> u64 {  
    left + right  
}  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[test]  
    fn it_works() {  
        let result = add(2, 2);  
        assert_eq!(result, 4);  
    }  
}
```

其中：

| 代码              | 作用                    |
| --------------- | --------------------- |
| `#[cfg(test)]`  | 只在测试构建时编译该模块          |
| `mod tests`     | 约定俗成的测试模块名            |
| `use super::*;` | 将父模块中的内容引入当前测试模块      |
| `#[test]`       | 标记测试函数，使测试执行器可以发现并运行它 |
| `assert_eq!`    | 断言左右两边的值相等            |

被`#[test]`标记的函数会被测试执行器识别并运行。实际项目里可以像 [[Rust/notes/项目/01_minigrep/4、搜索功能、环境变量与输出流|搜索功能、环境变量与输出流]] 那样，先用测试描述搜索函数的行为。

**除了定义测试函数，测试模块中可以定义普通辅助函数**。这些函数不会被当作测试运行，常用于初始化测试状态或复用测试逻辑。

执行测试：

```shell
cargo test
```

结果：

![[assets/Pasted image 20260601124702.png|400]]

`Running unittests src/lib.rs`表示`Cargo`正在运行`src/lib.rs`中的单元测试。括号中的路径是`Cargo`为测试生成的测试二进制文件。

执行`cargo test`时，`Cargo`会以**测试模式**编译当前包以及测试代码，生成测试二进制文件，然后运行这个测试二进制文件。测试二进制文件会查找并执行被`#[test]`标记的测试函数。

`running 1 test`表示测试执行器发现了 1 个测试函数，这里对应的就是`it_works()`。`test tests::it_works ... ok` 表示正在运行 `tests::it_works` 这个测试函数，并且运行结果是 `ok`。

`test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s` 是单元测试阶段的汇总结果。

| 字段                  | 含义                    |
| ------------------- | --------------------- |
| `1 passed`          | 通过了 1 个测试             |
| `0 failed`          | 没有失败的测试               |
| `0 ignored`         | 没有被 `#[ignore]` 跳过的测试 |
| `0 measured`        | 没有 benchmark 相关测试     |
| `0 filtered out`    | 没有因为名称过滤而被排除的测试       |
`Doc-tests adder`。表示 Cargo 开始运行文档测试。文档测试来自文档注释中的 Rust 代码块，例如写在 `///` 注释中的示例代码。当前例子中没有编写文档测试，所以输出为`running 0 test`。


# 二、断言与测试失败

## 1、常用断言宏

Rust测试中常用的断言宏包括：

| 宏                         | 作用               |
| ------------------------- | ---------------- |
| `assert!(expr)`           | 断言表达式为 `true`    |
| `assert_eq!(left, right)` | 断言两个值相等          |
| `assert_ne!(left, right)` | 断言两个值不相等         |
| `panic!`                  | 主动触发 panic，使测试失败 |
示例：

```rust
pub fn add_two(value: i32) -> i32 {
    value + 2
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_two_and_two() {
        let result = add_two(2);
        assert_eq!(result, 4);
    }

    #[test]
    fn add_three_and_two() {
        let result = add_two(3);
        assert_eq!(result, 5);
    }
}
```

运行测试：

![[assets/Pasted image 20260601130302.png|400]]

也可以指定运行某个测试，例如：

```shell
cargo test add_two_and_two
```

结果：

![[assets/Pasted image 20260601130408.png|400]]

测试是否通过，本质上取决于测试函数是否正常执行结束。只要测试函数执行过程中发生 panic，该测试就会失败。

`assert!`、`assert_eq!`、`assert_ne!` 在断言失败时都会触发 panic，因此它们可以直接用于测试判断。

## 2、测试失败示例

```rust

`test tests::add_two_and_two ... FAILED`表示测试失败。

并给出了失败的原因是`assert_eq!` 断言失败：

```text

**默认情况下，测试执行器会并行运行多个测试函数**。测试函数发生 panic 时，不会让整个测试进程立即崩溃，而是由测试执行器收集结果并汇总输出。

## 3、自定义失败信息

默认断言失败信息有时不够清晰，`assert!`断言宏**可以**添加自定义失败信息。

示例：

```rust
  
pub fn greet(name: &str) -> String {  
    format!("Hello, {}!", name)  
}  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[test]  
    fn greeting_contains_name() {  
        let result = greet("Tom");  
        let target = "John";  
        assert!(result.contains(target),  
                "greeting should contain name: {}, actual greeting: {}",  
                target,  
                result  
        );  
    }  
  
}
```

结果：

![[assets/Pasted image 20260601131738.png|400]]

`assert!` 后面的参数格式类似 `format!`。当断言失败时，这段信息会作为 panic 信息输出。

复杂测试中建议写清楚失败原因，尤其是测试数据较多、断言条件较复杂时。

# 三、should_panic

## 1、测试是否发生panic

有些函数的预期行为就是在非法输入时`panic`。此时可以使用`#[should_panic]`标记测试函数。

示例：

```rust
 
pub struct Number {  
    value: i32  
}  
  
impl Number {  
    pub fn new(value: i32) -> Self {  
        if value < 0 || value > 100 {  
            panic!("Value must be between 0 and 100");  
        }  
        Self { value }  
    }  
}  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[should_panic]  
    #[test]    
    fn greater_than_hundred() {  
       Number::new(101);  
    }  
}
```

测试结果：

![[assets/Pasted image 20260601141550.png|500]]

这个测试只有在 `Number::new(101)` 发生 panic 时才会通过。

如果改成：

```rust
#[test]
#[should_panic]
fn greater_than_hundred() {
    Number::new(50);
}
```

再次运行：

![[assets/Pasted image 20260601141751.png|500]]

提示测试没有按照期望的那样`panic`，这是由于 `Number::new(50)` 不会 panic，测试失败。

## 2、指定期望的`panic`信息

只判断是否发生`panic`不够精确，因为函数可能因为其他原因`panic`，而测试仍然通过。

可以在`#[should_panic]`中通过`expected`指定期望的`panic`信息片段：

```rust
  
  
pub struct Number {  
    value: i32  
}  
  
impl Number {  
    pub fn new(value: i32) -> Self {  
        if value < 0 {  
            panic!("The number must greater than or equal to 0, got {}", value);  
        } else if value > 100 {  
            panic!("The number must less than or equal to 100, got {}", value);  
        }  
        Self { value }  
    }  
}  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[should_panic(expected = "less than or equal to 100")]  
    #[test]    
    fn greater_than_hundred() {  
       Number::new(200);  
    }  
}
```

结果：

![[assets/Pasted image 20260601142342.png|600]]

`expected` 判断的是实际 panic 信息中是否包含指定字符串，不要求完全相等，也不要求必须是字符串前缀。

由于预期的片段是`less than or equal to 100`，这里的200确实满足。

如果改成：

```rust
    #[should_panic(expected = "less than or equal to 100")]  
    #[test]    
    fn greater_than_hundred() {  
       Number::new(-1);  
    } 
```

结果：

![[assets/Pasted image 20260601142638.png|600]]

虽然也发生了 panic，但 panic 信息不包含 `less than or equal to 100`，测试会失败。

# 四、返回Result<T, E>的测试函数

## 1、使用Result表示测试结果

测试函数也可以返回`Result<T, E>`。这种写法适合测试中需要使用 `?` 运算符的场景。

示例：

```rust
pub fn add_two(value: i32) -> i32 {  
    value + 2  
}  
  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[test]  
    fn it_works() -> Result<(), String> {  
  
        let result = add_two(2);  
        if result == 4 {  
            Ok(())  
        } else {  
            Err(String::from("two plus two does not equal four"))  
        }  
    }  
  
}
```

结果：

![[assets/Pasted image 20260601143105.png|500]]

如果故意把`add_two()`函数写错：

```rust
pub fn add_two(value: i32) -> i32 {  
    value + 3  
}  
```

测试失败：

![[assets/Pasted image 20260601143225.png|500]]

因此，返回`Result`的测试函数规则如下：

|返回值|测试结果|
|---|---|
|`Ok(())`|测试通过|
|`Err(e)`|测试失败，并输出错误信息|

## 2、Result测试与错误断言

返回 `Result<T, E>` 的测试函数不适合再使用 `#[should_panic]`。如果要测试某段代码是否返回错误，推荐直接断言 `Result` 的状态。

示例：

```rust
fn parse_number(input: &str) -> Result<i32, std::num::ParseIntError> {
    input.parse::<i32>()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parse_invalid_number_returns_error() {
        let result = parse_number("abc");

        assert!(result.is_err());
    }
}
```

如果要进一步检查错误内容，可以使用`match`：

```rust
pub fn parse_number(input: &str) -> Result<i32, std::num::ParseIntError> {  
    input.parse()  
}  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[test]  
    fn parse_invalid_number_returns_error() {  
        let result = parse_number("abc");  
  
        match result {  
            Ok(value) => panic!("expected error, got {}", value),  
            Err(e) => {  
                assert_eq!(e.kind(), &std::num::IntErrorKind::InvalidDigit)  
            }  
        }  
    }  
  
}
```


# 五、运行测试

## 1、cargo  test的基本作用

执行：

```shell
cargo test
```

会先编译测试代码，生成**测试二进制文件**，然后运行测试二进制文件。

## 2、cargo test参数与测试二进制参数

```shell
cargo test [Cargo 参数] [测试名称过滤] -- [测试二进制参数]
```

执行`cargo test`时，命令行参数分为两类：

- Cargo测试参数
- 测试二进制参数

规则如下：

|位置|传给谁|示例|
|---|---|---|
|`--` 之前|传给 Cargo|`cargo test --no-run`|
|`--` 之后|传给测试二进制文件|`cargo test -- --test-threads=1`|
查看`Cargo`的测试参数：

```shell
cargo test --help
```

查看测试二进制支持的参数：

```shell
cargo test -- --help
```

## 3、控制测试运行方式

### （1）并行与顺序执行

默认情况下，测试执行器会**并行**运行多个测试，以缩短整体测试时间。

**并行测试要求测试之间不要依赖共享状态**，例如：

- 不要让多个测试同时读写同一个文件
- 不要让多个测试依赖同一个全局变量
- 不要让测试依赖执行顺序
- 不要让测试依赖外部环境的可变状态

如果测试之间存在共享资源，可以使用测试二进制的`--test-threads`参数将测试线程数设置为 `1`，使测试顺序执行：

```rust
cargo test -- --test-threads=1
```

示例代码：

```rust
use std::fs;

pub fn write_message(path: &str, message: &str) {
    fs::write(path, message).unwrap();
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn write_first_message() {
        write_message("target/test-output.txt", "first");
        let content = std::fs::read_to_string("target/test-output.txt").unwrap();
        assert_eq!(content, "first");
    }

    #[test]
    fn write_second_message() {
        write_message("target/test-output.txt", "second");
        let content = std::fs::read_to_string("target/test-output.txt").unwrap();
        assert_eq!(content, "second");
    }
}
```

顺序运行：

```shell
cargo test -- --test-threads=1
```

结果：

![[assets/Pasted image 20260601150357.png|600]]

如果尝试并行执行：

![[assets/Pasted image 20260601150452.png|500]]

测试失败，这是由于两个函数同时写同一个文件造成数据污染导致的。

不过，实践中更推荐的做法是让每个测试使用**独立资源**，例如每个测试使用不同的临时目录或文件名，避免测试之间互相影响。


### （2）显示测试输出

默认情况下：

- 测试通过时，测试函数中的`println!`输出不会显示
- 测试失败时，相关输出通常会显示在失败详情中

示例：

```rust
pub fn print_and_return_10(value: i32) -> i32 {
    println!("Got value: {}", value);
    10
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn this_test_will_pass() {
        let value = print_and_return_10(1);
        assert_eq!(value, 10);
    }

    #[test]
    fn this_test_will_fail() {
        let value = print_and_return_10(2);
        assert_eq!(value, 5);
    }
}
```

结果：

![[assets/Pasted image 20260601150943.png|500]]

可以看到，测试成功的标准输出不会打印，但测试失败时的标准输出会显示在错误详情中。

如果希望通过测试的输出也显示出来，可以使用测试二进制参数`--show-output`：

```rust
cargo test -- --show-output
```

结果：

![[assets/Pasted image 20260601151151.png|600]]

可以看到此时还增加了`successes`的详情和汇总，包含测试通过的标准输出打印。

实际调试时也常用`--nocapture`：

```shell
cargo test -- --nocapture
```

`--nocapture` 会禁用输出捕获，让测试中的输出直接打印出来。相比 `--show-output`，它更适合临时调试。

结果：

但很明显，这里的输出有些混乱。这是因为用了 `--nocapture`，测试函数里的 `println!` 不再被测试框架捕获，而是直接打印到终端。而默认情况下，Rust 测试是**并行执行**的，所以多个测试函数的输出、panic 信息、测试结果可能交错出现。

如果想让输出按测试顺序更清楚，可以加上单线程参数：

```shell
cargo test -- --nocapture --test-threads=1
```

### （3）按名称运行部分测试

可以通过测试名称过滤运行部分测试。

示例代码：

```rust
pub fn add_two(value: i32) -> i32 {
    value + 2
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_two_and_two() {
        let result = add_two(2);
        assert_eq!(result, 4);
    }

    #[test]
    fn add_three_and_two() {
        let result = add_two(3);
        assert_eq!(result, 5);
    }

    #[test]
    fn one_hundred() {
        let result = add_two(100);
        assert_eq!(result, 102);
    }
}
```

- 只运行指定测试：

```shell
cargo test add_two_and_two
```

- 运行名称中包含`add`的测试

```shell
cargo test add  
```

- 运行某个模块下的测试

```shell
cargo test tests::add
```

名称过滤不是只能匹配前缀，只要测试完整路径中包含指定字符串，就会匹配。


### （4）忽略部分测试

对于耗时较长、依赖外部服务或暂时不想默认运行的测试，可以使用 `#[ignore]`。

仍然使用前面的例子，将`one_hundred`函数用`#[ignore]`标记。

```rust
#[test]  
#[ignore]  
fn one_hundred() {  
    let result = add_two(100);  
    assert_eq!(result, 102);  
}
```

执行`cargo test`结果如下：

![[assets/Pasted image 20260601153052.png|500]]

如果后面需要运行全部测试，不需要再去把测试函数的`#[ignore]`一个个去掉，只需要增加测试二进制参数`--include-ignored`：

```shell
cargo test -- --include-ignored
```

结果：

![[assets/Pasted image 20260601153317.png|500]]

也可以使用测试二进制参数`--ignored`只运行被`#[ignore]`标记的测试函数：

```shell
cargo test -- --ignored
```

> `--ignored` 表示只运行被 `#[ignore]` 标记的测试，`--include-ignored` 表示普通测试和被忽略的测试都运行。


### （5）只编译测试但不运行

有时只想确认测试能否编译，不想真正运行测试，可以使用`Cargo`测试参数`--no-run`：

```shell
cargo test --no-run
```

该命令会编译测试目标，但不会执行测试。

# 六、开发依赖\[dev-dependencies]

## 1、开发依赖的作用

有些依赖只在测试、示例或benchmark中使用，不应该进入正常依赖构建。此时可以放在 `Cargo.toml` 的 `[dev-dependencies]` 中。

示例：

```rust
[dev-dependencies]
pretty_assertions = "1"
```

`pretty_assertions` 可以提供更清晰的断言差异输出，常用于测试场景。

## 2、在测试中使用开发依赖

示例：

```rust
pub fn add_two(value: i32) -> i32 {
    value + 2
}

#[cfg(test)]
mod tests {
    use super::*;
    use pretty_assertions::assert_eq;

    #[test]
    fn add_two_and_two() {
        let result = add_two(2);
        assert_eq!(result, 3);
    }
}
```

# 七、单元测试

## 1、单元测试的概念

前面的例子都是单元测试。单元测试通常用于测试一个较小的代码单元，例如一个函数、一个模块或某个内部逻辑。

**Rust的单元测试一般与被测试代码放在同一个源码文件**。这样做有两个好处：

- 测试代码靠近被测试代码，便于维护
- 单元测试可以访问当前模块中的私有项

单元测试更适合验证局部逻辑，例如边界条件、私有辅助函数、错误分支和纯函数行为。

## 2、测试模块与#\[cfg(test)]

单元测试的常见写法是在源码文件中定义一个 `tests` 模块：

```rust
pub fn add_two(value: i32) -> i32 {
    internal_add(value, 2)
}

fn internal_add(left: i32, right: i32) -> i32 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_two_adds_two() {
        let result = add_two(2);
        assert_eq!(result, 4);
    }
}
```

`#[cfg(test)]` 的作用：只有在测试构建时才编译这个模块。普通的 `cargo build` 不会编译该测试模块。

`cfg` 是 configuration 的缩写，表示条件编译。`test` 是 Rust 在编译测试时提供的配置选项。

## 3、测试私有函数

因为单元测试模块通常是当前模块的子模块，所以它可以通过 `use super::*;` 访问父模块中的私有项。

示例：

```rust
pub fn add_two(value: i32) -> i32 {
    internal_add(value, 2)
}

fn internal_add(left: i32, right: i32) -> i32 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn internal_add_works() {
        let result = internal_add(2, 2);
        assert_eq!(result, 4);
    }
}
```

`internal_add` 没有使用 `pub`，但单元测试仍然可以调用它。

是否直接测试私有函数需要看场景：

| 场景                   | 建议                  |
| -------------------- | ------------------- |
| 私有函数逻辑复杂，且难以通过公开接口覆盖 | 可以直接测试              |
| 私有函数只是公开函数的简单拆分      | 优先测试公开接口            |
| 私有函数经常变化             | 谨慎直接测试，避免测试过度依赖实现细节 |

# 八、集成测试

## 1、集成测试的概念

集成测试位于被测试库的外部，像普通用户一样通过公开 API 使用库。

它的特点是：

- 只能访问库的公开API
- 每个测试文件会被编译成一个独立的`crate`

集成测试适合测试多个模块协作后的整体行为，更接近真实使用场景。

> 单元测试关注“内部某个小单元是否正确”，集成测试关注“这个库作为一个整体是否能被正确使用”。


## 2、tests/ 目录

集成测试放在项目根目录的 `tests/` 目录中。

目录结构：

```text
adder
├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    └── integration_test.rs
```

`src/lib.rs`：

```rust
pub fn add_two(value: i32) -> i32 {  
    internal_add(value, 2)  
}  
  
fn internal_add(left: i32, right: i32) -> i32 {  
    left + right  
}  
  
  
#[cfg(test)]  
mod tests {  
    use super::*;  
  
    #[test]  
    fn internal_add_test() {  
        let result = internal_add(1,2);  
        assert_eq!(result, 3);  
    }  
  
}
```

`tests/integration_test.rs`：

```rust
use adder::add_two;  
  
#[test]  
fn add_two_and_two() {  
    let result = add_two(2);  
    assert_eq!(result, 4);  
}  
  
#[test]  
fn add_two_and_three() {  
    let result = add_two(3);  
    assert_eq!(result, 5);  
}
```

现在执行`cargo test`：

![[assets/Pasted image 20260601160952.png|600]]

可以看到输出中会出现集成测试文件以及测试结果。

可以只运行某个集成测试函数：

```rust
cargo test add_two_and_two
```

![[assets/Pasted image 20260601161050.png|500]]

可以只运行这个集成测试文件：

```rust
cargo test --test integration_test
```

![[assets/Pasted image 20260601161201.png|400]]

`tests/` 目录是 Cargo 识别集成测试的特殊目录。该目录中的每个测试文件会被当作一个独立 crate 编译，因此需要像外部使用者一样通过 crate 名称引入公开 API：

```rust
use adder::add_two;
```

## 3、运行指定集成测试

如果有多个集成测试文件：

```text
tests
├── user_test.rs
├── order_test.rs
```

可以分别运行：

```shell
cargo test --test user_test
cargo test --test order_test
```

也可以继续使用测试名称过滤：

```shell
cargo test create_user  
cargo test order
```


## 4、集成测试中的共享模块

如果多个集成测试文件需要共享初始化函数，不推荐直接创建：

```text
tests/common.rs
```

因为 `tests/` 目录下的每个 `.rs` 文件都会被当作一个独立的集成测试 crate 编译，可能导致额外的测试输出。

推荐结构是：

```text
tests
├── integration_test.rs
└── common
    └── mod.rs
```

`tests/common/mod.rs`：

```rust
pub fn setup() {
    println!("setup...");
}
```

`tests/integration_test.rs`：

```rust
mod common;  
  
use adder::add_two;  
  
  
#[test]  
fn add_two_and_two() {  
    common::setup();  
    let result = add_two(2);  
    assert_eq!(result, 4);  
}  
  
#[test]  
fn add_two_and_three() {  
    common::setup();  
    let result = add_two(3);  
    assert_eq!(result, 5);  
}
```

## 5、二进制包的集成测试组织

对于只有 `src/main.rs` 的二进制包，集成测试不能像测试库一样直接 `use` 它的内部函数。

更常见的做法是同时提供 `src/lib.rs` 和 `src/main.rs`：

```text
my_app
├── Cargo.toml
├── src
│   ├── lib.rs
│   └── main.rs
└── tests
    └── integration_test.rs
```

将核心逻辑放入 `src/lib.rs`：

```rust
pub fn run(input: &str) -> String {
    input.to_uppercase()
}
```

`src/main.rs` 只保留入口逻辑：

```rust
use my_app::run;

fn main() {
    let result = run("hello");
    println!("{}", result);
}
```

集成测试测试库逻辑：

```rust
use my_app::run;

#[test]
fn run_converts_input_to_uppercase() {
    let result = run("hello");
    assert_eq!(result, "HELLO");
}
```

这种结构的好处是：

- `src/lib.rs` 中的核心逻辑可以被单元测试和集成测试覆盖
- `src/main.rs` 保持很薄，只负责参数读取、调用逻辑、输出结果
- 程序行为更容易测试和复用

# 九、文档测试

## 1、文档测试的作用

Rust 的文档注释不仅可以生成 HTML 文档，还可以包含可测试的代码示例。

常见文档测试有两类：

| 注释    | 作用                    |
| ----- | --------------------- |
| `///` | 为紧随其后的函数、结构体、枚举等项编写文档 |
| `//!` | 为当前模块或 crate 编写整体文档   |

示例：

```rust
//! # My Test Adder  
//!  
//! `adder` 提供了简单的数学工具  
  
/// Add one to the given number  
///  
/// # Examples  
///  
/// ```  
/// let arg = 2;
/// let answer = adder::add_one(arg);
///  
/// assert_eq!(3, answer)
/// ```  
pub fn add_one(value: i32) -> i32 {  
    value + 1  
}
```

生成文档：

```shell
cargo doc
```

生成并打开文档：

```shell
cargo doc --open
```

运行测试：

```shell
cargo test
```

结果：

![[assets/Pasted image 20260601164519.png|400]]

测试输出了文档测试的内容。

如果只想运行文档测试：

```shell
cargo test --doc
```

## 2、文档测试的执行方式

普通文档测试满足两个条件时通过：

- 代码可以编译
- 运行时不发生`panic`

例如，`add_one(2)`返回的不是3，`assert_eq!(3, answer)`会 panic，文档测试失败。

如果代码块没有标注语言，文档测试默认会按 Rust 代码处理。

## 3、隐藏辅助代码

有时文档示例需要一些辅助代码才能编译，但不希望这些代码显示在最终文档中。可以使用 `#` 隐藏行。

示例：

```rust
//! # My Test Adder  
//!  
//! `adder` 提供了简单的数学工具  
  
/// Add one to the given number  
///  
/// # Examples  
///  
/// ```  
/// # use adder::add_one;
/// let arg = 2;
/// let answer = add_one(arg);
///  
/// assert_eq!(3, answer)
/// ```  
pub fn add_one(value: i32) -> i32 {  
    value + 1  
}
```

以 `#` 开头的行会参与编译和测试，但不会显示在生成的文档中。

例如这里的`# use adder::add_one;`会让`use adder::add_one;`不出现在生成的文档中：

![[assets/Pasted image 20260601165314.png|500]]

这种写法适合隐藏 `use`、初始化代码或辅助定义，让文档展示更简洁。

## 4、文档测试代码块标记

文档测试支持一些常用标记：

| 标记                            | 含义                    |
| ----------------------------- | --------------------- |
| `no_run`                      | 只编译，不运行               |
| `should_panic`                | 代码应当编译成功，但运行时应当 panic |
| `compile_fail`                | 代码应当编译失败              |
| `ignore`                      | 忽略该代码块                |
| `edition2021` / `edition2024` | 指定代码块使用的 Rust Edition |
示例：只编译不运行

```rust
/// ```no_run
/// loop {
///     println!("running forever");
/// }
/// ```
pub fn example() {}
```

结果：代码块会参与编译，但不会真正运行无限循环。
