# 一、重构目标

[[Rust/notes/项目/01_minigrep/1、命令行参数与文件读取|命令行参数与文件读取]] 已经让 `minigrep` 能读取命令行参数和文件内容，但代码都集中在 `main` 函数中。

本篇的目标不是增加搜索功能，而是把程序从“能跑”重构成“入口清晰、逻辑可复用、错误能被显式处理”的结构。

最终项目结构是：

```shell
src/
├── main.rs
└── lib.rs
```

职责划分如下：

| 文件 | 职责 |
|---|---|
| `main.rs` | 程序入口、收集命令行参数、处理错误并退出 |
| `lib.rs` | 配置结构、参数解析、程序运行逻辑 |

重构后的核心原则是：

- `main.rs` 尽量短小，只做入口协调。
- `lib.rs` 保存可复用的业务逻辑，后续搜索函数和测试也会放在这里。
- 可预期的运行错误用 `Result` 返回，不用 `panic!` 当作常规控制流。

# 二、提取参数解析逻辑

最开始的代码直接在 `main` 中通过索引取参数：

```rust
let query = &args[1];
let file_path = &args[2];
```

这能运行，但有两个问题：

- 参数解析逻辑和程序入口混在一起。
- `query` 和 `file_path` 只是两个分散变量，没有形成一个明确的“配置”概念。

可以先把参数解析提取成函数：

```rust
fn parse_config(args: &[String]) -> (&str, &str) {
    let query = &args[1];
    let file_path = &args[2];

    (query, file_path)
}
```

`main` 中调用：

```rust
let args = env::args().collect::<Vec<String>>();
let (query, file_path) = parse_config(&args);
```

这一步只是把“参数如何映射到变量”的逻辑从 `main` 中挪出去。返回元组仍然不够清晰，因为 `query` 和 `file_path` 是有业务含义的配置项，不只是两个普通字符串。

# 三、使用 Config 组织配置

更清晰的做法是定义 `Config` 结构体，把运行程序需要的配置集中在一个类型中：

```rust
struct Config {
    query: String,
    file_path: String,
}
```

然后让参数解析函数返回 `Config`：

```rust
fn parse_config(args: &[String]) -> Config {
    let query = args[1].clone();
    let file_path = args[2].clone();

    Config { query, file_path }
}
```

调用方式变成：

```rust
let args = env::args().collect::<Vec<String>>();
let config = parse_config(&args);
```

这样代码表达的含义更明确：

```text
query + file_path = 程序运行所需的配置
```

> 注意：`args[1].clone()` 和 `args[2].clone()` 会克隆命令行参数字符串，因为不能直接从 `Vec<String>` 的索引位置移动出元素。对命令行参数来说，这点开销很小，这个阶段优先保持代码清晰。

# 四、将参数解析改为 Config::new

`parse_config` 的作用是创建 `Config`，因此可以改成 `Config` 的关联函数：

```rust
impl Config {
    fn new(args: Vec<String>) -> Config {
        let query = args[1].clone();
        let file_path = args[2].clone();

        Config { query, file_path }
    }
}
```

调用方式变成：

```rust
let args = env::args().collect::<Vec<String>>();
let config = Config::new(args);
```

这种写法更符合 Rust 中“由类型自己提供构造逻辑”的习惯，例如：

```rust
String::new()
Vec::new()
Config::new(args)
```

当前实际项目中的 `Config::new` 接收的是 `Vec<String>`，也就是取得参数列表的所有权。这样写更简单，但调用后 `args` 就不能再继续使用。另一种常见写法是接收 `&[String]`，由调用者保留参数列表所有权。

# 五、参数不足时返回 Result

如果用户没有传入足够参数：

```shell
cargo run
```

直接访问索引会导致 panic：

```rust
args[1]
args[2]
```

这类 panic 通常会包含线程名、源码位置、回溯提示等信息，对命令行用户并不友好。参数不足属于可预期的用户输入错误，更适合用 `Result` 表达。

实际项目中的写法是：

```rust
impl Config {
    pub fn new(args: Vec<String>) -> Result<Self, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        Ok(Config {
            query,
            file_path,
        })
    }
}
```

返回类型：

```rust
Result<Self, &'static str>
```

含义如下：

| 分支 | 含义 |
|---|---|
| `Ok(Config { ... })` | 参数解析成功，得到配置 |
| `Err("not enough arguments")` | 参数不足，返回静态错误信息 |

这里的 `Self` 等价于 `Config`，在 `impl Config` 内部使用 `Self` 可以减少重复。`&'static str` 是字符串字面量类型，适合表示这种简单、固定的错误信息。

# 六、在 main 中处理参数错误

`main` 中使用 `unwrap_or_else` 处理 `Config::new` 返回的 `Result`：

```rust
use std::env;
use std::process;
use minigrep::Config;

fn main() {
    let args = env::args().collect::<Vec<String>>();

    let config = Config::new(args)
        .unwrap_or_else(|err| {
            println!("Problem parsing arguments: {}", err);
            process::exit(1);
        });
}
```

`unwrap_or_else` 的行为是：

| 情况 | 行为 |
|---|---|
| `Ok(config)` | 取出 `config`，继续运行 |
| `Err(err)` | 执行闭包中的错误处理逻辑 |

这里的闭包是：

```rust
|err| {
    println!("Problem parsing arguments: {}", err);
    process::exit(1);
}
```

`process::exit(1)` 会立即结束程序，并返回非零退出码。在命令行程序中，非零退出码通常表示程序运行失败。

运行：

```shell
cargo run
```

输出：

```text
Problem parsing arguments: not enough arguments
```

这比索引越界 panic 更适合终端用户阅读。当前代码仍然用 `println!` 输出错误，后续可以改成 `eprintln!`，把错误信息写入标准错误流。

# 七、提取 run 函数

完成参数解析后，`main` 中仍然不应该继续承担文件读取和业务逻辑。可以把实际运行逻辑提取到 `run` 函数中：

```rust
fn run(config: Config) {
    let contents = fs::read_to_string(config.file_path)
        .expect("Something went wrong reading the file");

    println!("\nWith text:\n{contents}");
}
```

`main` 只负责调用：

```rust
run(config);
```

提取之后，入口职责变成：

```text
main
├── 收集命令行参数
├── 创建 Config
└── 调用 run
```

这一步还没有解决文件读取错误的处理方式，因为 `run` 中仍然使用 `expect`，文件不存在时程序仍会 panic。

# 八、让 run 返回 Result

文件不存在、路径错误、权限不足都属于可预期的运行错误。更合理的方式是让 `run` 返回 `Result`，把错误交给 `main` 统一处理。

实际项目中的 `run` 是：

```rust
use std::error::Error;
use std::fs;

pub fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;
    println!("\nWith text:\n{contents}");

    Ok(())
}
```

这里有两个关键点。

## 1、`Result<(), Box<dyn Error>>`

```rust
Result<(), Box<dyn Error>>
```

含义如下：

| 部分 | 含义 |
|---|---|
| `()` | 成功时不返回有意义的数据，只表示运行完成 |
| `Box<dyn Error>` | 失败时可以返回任意实现了 `Error` trait 的错误类型 |

`Box<dyn Error>` 适合入门阶段和小型 CLI 程序：它不要求马上设计自定义错误枚举，可以先把不同来源的错误统一装箱返回。

## 2、用 `?` 传播错误

```rust
let contents = fs::read_to_string(config.file_path)?;
```

如果读取成功，`contents` 得到文件内容；如果读取失败，`?` 会提前从 `run` 返回错误，让调用者处理。

这比 `expect` 更适合业务错误处理，因为错误没有在底层直接终止程序，而是沿着调用链返回给入口。

# 九、在 main 中处理 run 的错误

`run` 返回 `Result` 后，`main` 需要检查运行是否失败：

```rust
if let Err(e) = minigrep::run(config) {
    println!("Application error: {}", e);
    process::exit(1);
}
```

这里使用 `if let Err(e)`，因为 `run` 成功时只返回 `()`，没有需要继续使用的值；只有失败时才需要取出错误并打印。

实际项目中的 `main.rs` 是：

```rust
use std::env;
use std::process;
use minigrep::Config;

fn main() {
    let args = env::args().collect::<Vec<String>>();

    let config = Config::new(args)
        .unwrap_or_else(|err| {
            println!("Problem parsing arguments: {}", err);
            process::exit(1);
        });

    if let Err(e) = minigrep::run(config) {
        println!("Application error: {}", e);
        process::exit(1);
    }
}
```

此时 `main` 的职责已经很清楚：入口、错误展示、退出码。真正的配置解析和运行逻辑放在库代码里。

# 十、拆分 main.rs 和 lib.rs

Rust 包可以同时包含二进制 crate 和库 crate。`src/main.rs` 编译成可执行程序，`src/lib.rs` 编译成库；同一个包里的二进制 crate 可以通过包名访问库 crate 暴露的 API。

当前包名是 `minigrep`，所以 `main.rs` 中可以写：

```rust
use minigrep::Config;
```

并调用：

```rust
minigrep::run(config)
```

## 1、`src/lib.rs`

实际项目中的 `lib.rs`：

```rust
use std::error::Error;
use std::fs;

pub struct Config {
    query: String,
    file_path: String,
}

impl Config {
    pub fn new(args: Vec<String>) -> Result<Self, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        Ok(Config {
            query,
            file_path,
        })
    }
}

pub fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;
    println!("\nWith text:\n{contents}");

    Ok(())
}
```

这里需要 `pub` 的项目是：

| 项目 | 为什么需要 `pub` |
|---|---|
| `Config` | `main.rs` 需要使用这个类型 |
| `Config::new` | `main.rs` 需要调用构造逻辑 |
| `run` | `main.rs` 需要调用运行逻辑 |

`Config` 的字段目前没有写 `pub`，所以它们只能在 `lib.rs` 内部访问。这是更好的封装方式：外部代码只需要拿到一个配置对象并交给 `run`，不必直接读写字段。

> 当前阶段 `query` 字段已经被解析并保存，但 `run` 还没有真正搜索文本，所以 `cargo test` 会提示 `field query is never read`。这是阶段性警告，下一篇实现搜索功能后会被消除。

## 2、`src/main.rs`

实际项目中的 `main.rs`：

```rust
use std::env;
use std::process;
use minigrep::Config;

fn main() {
    let args = env::args().collect::<Vec<String>>();

    let config = Config::new(args)
        .unwrap_or_else(|err| {
            println!("Problem parsing arguments: {}", err);
            process::exit(1);
        });

    if let Err(e) = minigrep::run(config) {
        println!("Application error: {}", e);
        process::exit(1);
    }
}
```

`main.rs` 不直接读取文件，也不直接访问 `Config` 字段。它只是把参数交给 `Config::new`，再把配置交给 `minigrep::run`。

# 十一、运行与验证

在项目目录运行：

```shell
cargo run -- frog poem.txt
```

当前阶段还没有实现搜索，因此程序会打印整个文件内容：

```text
With text:
I'm nobody! Who are you?
Are you nobody, too?
Then there's a pair of us - don't tell!
They'd banish us, you know.

How dreary to be somebody!
How public, like a frog
To tell your name the livelong day
To an admiring bog!
```

参数不足时运行：

```shell
cargo run
```

输出：

```text
Problem parsing arguments: not enough arguments
```

文件不存在时运行：

```shell
cargo run -- frog missing.txt
```

输出类似：

```text
Application error: No such file or directory (os error 2)
```

这些错误都不会再表现为索引越界或文件读取 panic，而是由 `main` 统一展示并以非零退出码结束。

# 十二、本篇小结

这一阶段完成了 `minigrep` 的结构重构和基础错误处理。

当前结构是：

```text
main.rs
  ├── 收集命令行参数
  ├── 调用 Config::new
  ├── 处理参数错误
  ├── 调用 minigrep::run
  └── 处理运行错误

lib.rs
  ├── Config
  ├── Config::new
  └── run
```

关键变化如下：

| 重构点 | 作用 |
|---|---|
| `Config` | 把 `query` 和 `file_path` 组织成程序配置 |
| `Config::new` | 解析命令行参数，并用 `Result` 表达参数错误 |
| `unwrap_or_else` | 在入口处自定义参数错误处理 |
| `run` | 提取程序主逻辑，减少 `main` 的职责 |
| `?` | 向调用者传播文件读取错误 |
| `Box<dyn Error>` | 简化运行错误的返回类型 |
| `main.rs` / `lib.rs` | 分离程序入口和业务逻辑 |

下一步可以在 `lib.rs` 中实现真正的搜索函数，并在 [[Rust/notes/项目/01_minigrep/3、搜索功能、环境变量与输出流|搜索功能、环境变量与输出流]] 中补充测试、环境变量和标准错误输出。
