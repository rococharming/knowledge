# 一、阶段目标

[[Rust/notes/项目/02_rlog/2、命令行参数设计|命令行参数设计]] 已经让 `rlog` 能把终端命令解析成结构化的 `Cli`。

当前程序运行后只会打印参数结构：

```rust
fn main() {
    let cli = Cli::parse();

    println!("{cli:#?}");
}
```

这对验证参数设计很有用，但还不是真正的日志工具。本篇进入第 2 阶段：把程序从“只解析参数”推进到“根据参数打开日志文件，并按行读取内容”。

本阶段完成后，下面的命令应该能读取 `full_log.txt` 并输出日志行：

```shell
cargo run -- view full_log.txt
```

本阶段暂时不做：

- 不按 `--level` 过滤。
- 不按 `--contains` 过滤。
- 不统计 `INFO`、`WARN`、`ERROR`。
- 不解析时间和模块。

只做一件事：

> 根据子命令拿到文件路径，打开文件，用 `BufReader` 按行读取。

# 二、为什么要继续拆模块

当前项目已经有两个源码文件：

```shell
src/
├── main.rs
└── cli.rs
```

职责如下：

| 文件 | 当前职责 |
|---|---|
| `main.rs` | 程序入口，调用 `Cli::parse()` |
| `cli.rs` | 定义命令行参数结构 |

如果把文件读取、过滤、统计都继续写进 `main.rs`，`main` 很快会变成一团入口逻辑和业务逻辑混在一起的代码。更好的方式是新增一个运行模块，例如 `app.rs`：

```shell
src/
├── main.rs
├── cli.rs
└── app.rs
```

新的职责划分是：

| 文件        | 职责                          |
| --------- | --------------------------- |
| `main.rs` | 程序入口，只负责解析参数和调用运行逻辑         |
| `cli.rs`  | 定义 `Cli`、`Commands`、`Level` |
| `app.rs`  | 根据子命令执行实际功能，例如读取文件          |

# 三、按行读取文件

读取日志文件时，不建议一开始就用 `std::fs::read_to_string` 把整个文件读进内存。

日志文件通常可能很大，更适合使用：

```rust
File + BufReader + lines()
```

对应导入：

```rust
use std::fs::File;
use std::io::{self, BufRead, BufReader};
use std::path::Path;
```

这几个类型的作用如下：

| 类型或 trait | 用途 |
|---|---|
| `File` | 打开磁盘文件 |
| `BufReader` | 给文件读取增加缓冲，提高逐行读取效率 |
| `BufRead` | 提供 `.lines()` 这种按行读取方法 |
| `Path` | 接收文件路径引用 |
| `io::Result` | 表示文件读取可能失败 |

可以先写一个小函数，只负责打印文件每一行：

```rust
fn print_lines(path: &Path) -> io::Result<()> {
    let file = File::open(path)?;

    let reader = BufReader::new(file);

    for line in reader.lines() {
        let line = line?;
        println!("{}", line);
    }

    Ok(())
}
```

这里有两个 `?`：

| 代码 | 可能的错误 |
|---|---|
| `File::open(path)?` | 文件不存在、没有读取权限 |
| `line?` | 某一行读取失败 |

`?` 的含义是：如果成功，就取出里面的值继续执行；如果失败，就把错误直接返回给调用者。这个写法比 `expect` 更适合 CLI 程序，因为文件不存在属于可预期错误，不应该让程序 panic。

# 四、定义 app.rs

`app.rs` 可以先接收 `Commands`，再根据不同子命令决定怎么运行。

第一版代码如下：

```rust
use std::fs::File;
use std::path::Path;
use std::io::{self, BufRead, BufReader};
use crate::cli::Commands;

pub fn run(command: Commands) -> io::Result<()> {

    match command {

        Commands::View {
            file,
            level: _,
            contains: _
        } => {
            print_lines(&file)?;
        }

        Commands::Stats {
            file,
            level: _,
            contains: _
        } => {
            print_lines(&file)?;
        }

    }

    Ok(())
}


fn print_lines(path: &Path) -> io::Result<()> {
    let file = File::open(path)?;

    let reader = BufReader::new(file);

    for line in reader.lines() {
        let line = line?;
        println!("{}", line);
    }

    Ok(())
}
```

这段代码暂时让 `view` 和 `stats` 都调用 `print_lines`。这不是最终行为，只是为了在本阶段验证两件事：

1. 子命令分发已经连上。
2. 文件读取已经连上。

其中 `level: _` 和 `contains: _` 表示：这两个参数已经被解析出来了，但本阶段暂时不用它们。

> 注意：如果直接写 `level` 和 `contains` 但不用，编译器会给 unused variable warning。写成 `_` 可以明确告诉编译器“这里暂时忽略这个字段”。

# 五、修改 main.rs

有了 `app.rs` 后，`main.rs` 可以从“打印参数”改成“调用运行逻辑”。

推荐写法：

```rust
mod cli;
mod app;

use clap::Parser;
use cli::Cli;
use std::process;

fn main() {
    let cli = Cli::parse();

    if let Err(err) = app::run(cli.command) {
        eprintln!("rlog error: {}", err);
        process::exit(1);
    }
}
```

这里的职责是：

| 代码 | 含义 |
|---|---|
| `mod app;` | 引入 `src/app.rs` |
| `Cli::parse()` | 解析命令行参数 |
| `app::run(cli.command)` | 把子命令交给运行逻辑 |
| `if let Err(err)` | 统一处理运行错误 |
| `eprintln!` | 把错误写到标准错误 |
| `process::exit(1)` | 用非零退出码表示失败 |

这和 `minigrep` 项目里的思路一样：`main` 负责入口协调和错误退出，真正逻辑放在其他模块。

# 七、当前代码的问题

## 1、stats 暂时还不是真的统计

当前 `Stats` 分支仍然调用 `print_lines`，只是为了先验证文件读取链路。

下一阶段应该让 `Stats` 分支进入统计逻辑，而不是输出每一行。

## 2、过滤参数暂时没有使用

`level` 和 `contains` 已经能从 CLI 中解析出来，但本阶段没有使用：

```rust
level: _,
contains: _,
```

下一阶段可以先实现 `contains` 过滤，因为它只需要判断一行文本是否包含关键词：

```rust
line.contains(keyword)
```

然后再实现 `level` 过滤，因为它需要先从日志行中识别 `INFO`、`WARN`、`ERROR`。

## 3、print_lines 直接打印，不方便测试

`print_lines` 现在直接 `println!`，这对入门阶段最直观，但不太方便单元测试。

后续可以把读取、过滤、输出继续拆开：

| 函数 | 职责 |
|---|---|
| `read_lines` | 读取文件行 |
| `matches_filter` | 判断一行是否匹配过滤条件 |
| `print_line` | 输出匹配行 |
| `stats` | 累加级别数量 |

先写直接版本没有问题。项目早期重点是让功能链路跑通，等功能稳定后再根据测试需要继续重构。

# 八、本篇小结

本阶段完成的是：把 `rlog` 从参数解析推进到文件读取。

当前项目结构建议变成：

```shell
src/
├── main.rs
├── cli.rs
└── app.rs
```

本篇涉及的 Rust 知识点：

| 知识点 | 用途 |
|---|---|
| `mod` | 把 `app.rs` 接入项目 |
| `match` | 根据 `view` / `stats` 子命令分发 |
| `File::open` | 打开日志文件 |
| `BufReader` | 高效按行读取 |
| `BufRead::lines` | 得到逐行迭代器 |
| `io::Result` | 表示文件读取可能失败 |
| `?` | 简洁传播错误 |
| `eprintln!` | 把错误输出到标准错误 |

下一步可以进入 [[Rust/notes/项目/02_rlog/4、日志过滤与级别解析|日志过滤与级别解析]]，真正使用 `--contains` 和 `--level`，让 `view` 只输出匹配的日志行。
