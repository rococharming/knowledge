# 一、阶段目标

[[Rust/notes/项目/02_rlog/5、统计功能|统计功能]] 完成后，`rlog` 第一版已经具备 CLI 项目的主干能力：解析命令、读取文件、过滤日志和统计级别数量。

本篇进入第一版收尾阶段，重点不是继续加新功能，而是检查一个命令行工具能不能像“完整小项目”一样交付：

- 错误输出是否清楚。
- `--help` 是否能说明用法。
- 测试是否能跑通。
- release 二进制是否能构建。
- 构建出的二进制是否能直接运行。

这一阶段完成后，项目应该能通过：

```shell
cargo test
cargo build --release
./target/release/rlog view full_log.txt --level error
```

# 二、错误输出

CLI 程序应该把正常结果写到标准输出，把错误信息写到标准错误。当前 `main.rs` 已经使用 `eprintln!` 处理运行错误：

```rust
mod app;
mod cli;
mod filter;
mod stats;

use clap::Parser;
use cli::Cli;
use std::process;

fn main() {
    let cli = Cli::parse();

    if let Err(err) = app::run(cli.command) {
        eprintln!("rlog error: {}", err);
        process::exit(1);
    }
}
```

这里有两个关键点：

| 代码 | 作用 |
|---|---|
| `eprintln!` | 把错误信息写到标准错误 |
| `process::exit(1)` | 用非零退出码表示程序失败 |

可以用不存在的文件验证错误路径：

```shell
cargo run -- view missing.log
```

预期输出类似：

```text
rlog error: No such file or directory (os error 2)
```

这比 `panic` 更适合用户阅读。文件不存在是可预期错误，不是程序内部崩溃。

# 三、帮助信息

`clap` 会根据 `Cli`、`Commands` 和字段上的文档注释生成帮助信息。

当前 `cli.rs` 中的命令结构类似：

```rust
#[derive(Parser, Debug)]
#[command(name = "rlog")]
#[command(version = "0.1.0")]
#[command(about = "A simple log filtering and analysis CLI")]
pub struct Cli {
    #[command(subcommand)]
    pub command: Commands,
}
```

可以先查看顶层帮助以及版本：

```shell
cargo run -- --help
cargo run -- --version
```

重点检查：

| 项目 | 期望 |
|---|---|
| 命令名 | 显示 `rlog` |
| 版本号 | 显示 `0.1.0` |
| 子命令 | 包含 `view` 和 `stats` |
| 帮助选项 | 包含 `--help` |

再检查子命令帮助：

```shell
cargo run -- view --help
cargo run -- stats --help
```

重点确认 `file`、`--level`、`--contains` 都有说明。

> 注意：当前源码注释里 `filtered bu level or keyword` 应该改成 `filtered by level or keyword`。这类拼写会直接出现在 `--help` 中，因此帮助文案也属于 CLI 质量的一部分。

# 四、测试检查

第一版至少应该能跑通：

```shell
cargo test
```

如果前面几篇已经给 `filter.rs` 和 `stats.rs` 补了单元测试，`cargo test` 会一起运行它们。

推荐检查的测试范围：

| 模块 | 测试重点 |
|---|---|
| `filter.rs` | `--contains`、`--level`、组合过滤 |
| `stats.rs` | 无过滤统计、关键词过滤后统计、级别过滤后统计 |
| `app.rs` | 第一版可以暂不测，等输出逻辑稳定后再考虑集成测试 |

对这个阶段来说，测试不是为了追求数量，而是保护最容易写错的规则：过滤条件和统计结果。

# 五、发布构建

开发阶段常用：

```shell
cargo run -- view full_log.txt
```

但真正交付 CLI 工具时，需要生成 release 二进制：

```shell
cargo build --release
```

构建成功后，二进制文件通常在：

```shell
target/release/rlog
```

可以直接运行：

```shell
./target/release/rlog view full_log.txt --contains connection
./target/release/rlog stats full_log.txt
```

`cargo build --release` 和普通 `cargo build` 的区别：

| 命令 | 特点 | 适用场景 |
|---|---|---|
| `cargo build` | 编译快，未开启主要优化 | 日常开发 |
| `cargo build --release` | 编译慢，开启优化 | 发布或真实使用 |

release 二进制通常更小、更快，但编译时间更长。

# 六、第一版验收

第一版可以用一组命令做验收：

```shell
cargo test
cargo run -- --help
cargo run -- view full_log.txt
cargo run -- view full_log.txt --level error
cargo run -- view full_log.txt --contains connection
cargo run -- stats full_log.txt
cargo build --release
./target/release/rlog view full_log.txt --level warn
```

验收时重点看：

| 能力 | 检查方式 |
|---|---|
| 参数解析 | `--help` 和错误参数提示正常 |
| 文件读取 | `view full_log.txt` 输出全部日志 |
| 关键词过滤 | `--contains connection` 只输出相关行 |
| 级别过滤 | `--level error` 只输出错误日志 |
| 统计 | `stats full_log.txt` 输出各级别数量 |
| 测试 | `cargo test` 通过 |
| 发布 | `cargo build --release` 生成二进制 |

如果这些都能通过，`rlog` 第一版就可以认为完成。

# 七、后续方向

第一版完成后，可以进入第二版能力：

| 方向 | 说明 |
|---|---|
| 解析时间 | 从日志头中提取时间字段 |
| 解析模块 | 提取 `rlog::app`、`rlog::network` 等模块名 |
| 时间范围过滤 | 支持 `--since`、`--until` |
| JSON 输出 | 增加 `--json`，输出结构化结果 |
| 集成测试 | 使用测试文件验证完整 CLI 输出 |

这些功能都应该建立在第一版稳定结构之上，而不是一次性塞进 `main.rs`。

# 八、小结

本阶段完成的是第一版收尾：确认错误处理、帮助信息、测试和 release 构建。

本篇涉及的 Rust 和 CLI 知识点：

| 知识点 | 用途 |
|---|---|
| `eprintln!` | 输出错误信息 |
| `process::exit(1)` | 返回失败退出码 |
| `cargo test` | 运行单元测试 |
| `cargo build --release` | 构建发布版二进制 |
| `target/release/rlog` | 最终可执行文件 |
| `--help` | 检查 CLI 用户界面 |

到这里，`rlog` 第一版已经从项目目标、参数设计、模块拆分、文件读取、日志过滤、统计功能走到可构建交付。后续可以在第二版中继续扩展时间、模块和 JSON 输出。
