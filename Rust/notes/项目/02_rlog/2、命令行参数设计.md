# 一、阶段目标

[[Rust/notes/项目/02_rlog/1、日志分析 CLI 项目目标|日志分析 CLI 项目目标]] 已经明确了 `rlog` 的第一版范围。本篇进入第 1 阶段：设计命令行参数。

命令行参数设计要解决的问题是：用户在终端里输入一条命令后，程序如何把这条命令解析成 Rust 中清晰的数据结构。

第一版先支持两类动作：

```shell
rlog view full_log.txt
rlog view full_log.txt --level error
rlog view full_log.txt --contains connection
rlog stats full_log.txt
```

其中：

- `view` 表示查看日志行。
- `stats` 表示统计日志级别数量。
- `full_log.txt` 是日志文件路径。
- `--level` 是可选的级别过滤条件。
- `--contains` 是可选的关键词过滤条件。

本阶段暂时不读取文件、不解析日志、不做统计，只完成一件事：

> 把终端参数解析成结构化的 Rust 值，并先用 `Debug` 格式打印出来。

这样做的好处是，后续实现读取文件、过滤和统计时，可以直接基于已经设计好的参数结构继续写，而不是让参数解析逻辑散落在 `main` 函数中。

# 二、为什么使用 clap

在 [[Rust/notes/项目/01_minigrep/2、命令行参数与文件读取|minigrep]] 中，命令行参数是通过 `std::env::args()` 手动读取的。这个方式适合入门理解参数本质，但当命令变复杂后，手动解析会很快变得难维护。

`rlog` 一开始就有子命令和可选参数，更适合使用 [[Rust/notes/常用crate/2、clap|clap]]。

`clap` 可以自动处理：

| 能力 | 说明 |
|---|---|
| 子命令 | 例如 `view` 和 `stats` |
| 位置参数 | 例如日志文件路径 `full_log.txt` |
| 选项参数 | 例如 `--level error` |
| 布尔标志 | 例如后续可能加入的 `--json` |
| 帮助信息 | 自动生成 `--help` |
| 参数校验 | 对枚举值做限制，例如只允许 `info`、`warn`、`error` |

本项目使用 `derive` 写法，让命令行参数直接映射成结构体和枚举。

# 三、添加依赖

在 `Cargo.toml` 中添加 `clap`：

```toml
[dependencies]
clap = { version = "4", features = ["derive"] }
```

其中：

- `clap` 是命令行参数解析 crate。
- `version = "4"` 表示使用 clap 4.x。
- `features = ["derive"]` 表示启用过程宏，让我们可以用 `#[derive(Parser)]`、`#[derive(Subcommand)]` 和 `#[derive(ValueEnum)]`。

> 注意：本阶段只需要 `clap`。`anyhow`、`regex`、`serde`、`serde_json` 可以等到文件读取、日志解析和 JSON 输出阶段再加入。

# 四、设计命令结构

`rlog` 的命令可以分成三层：

```text
rlog 子命令 文件路径 选项参数
```

对应到第一版命令：

| 命令 | 子命令 | 文件路径 | 选项参数 |
|---|---|---|---|
| `rlog view full_log.txt` | `view` | `full_log.txt` | 无 |
| `rlog view full_log.txt --level error` | `view` | `full_log.txt` | `--level error` |
| `rlog view full_log.txt --contains connection` | `view` | `full_log.txt` | `--contains connection` |
| `rlog stats full_log.txt` | `stats` | `full_log.txt` | 无 |

因此，Rust 中可以设计成：

```text
Cli
└── command: Commands
    ├── View { file, level, contains }
    └── Stats { file, level, contains }
```

这里的关键是：`view` 和 `stats` 虽然行为不同，但它们都需要读取同一个日志文件，也都可以复用过滤条件。

# 五、定义 cli.rs

为了让 `main.rs` 保持简短，可以把命令行参数结构放到 `src/cli.rs`。

第一版推荐代码如下：

```rust
use clap::{Parser, Subcommand, ValueEnum};
use std::path::PathBuf;

#[derive(Parser, Debug)]
#[command(name = "rlog")]
#[command(version = "0.1.0")]
#[command(about = "A simple log filtering and analysis CLI")]
pub struct Cli {
    #[command(subcommand)]
    pub command: Commands,
}

#[derive(Subcommand, Debug)]
pub enum Commands {
    /// Print log lines, optionally filtered bu level or keyword.
    View {
        /// Path to the log file.
        file: PathBuf,

        /// Only show log lines with this level.
        #[arg(long, value_enum)]
        level: Option<Level>,

        /// Only show log lines containing this text.
        #[arg(long)]
        contains: Option<String>,
    },

    /// Count log lines, optionally filtered bu level or keyword.
    Stats {
        /// Path to the log file.
        file: PathBuf,

        /// Only count log lines with this level.
        #[arg(long, value_enum)]
        level: Option<Level>,

        /// Only show log lines containing this text.
        #[arg(long)]
        contains: Option<String>,
    },
}

#[derive(Debug, Clone, ValueEnum)]
pub enum Level {
    Info,
    Warn,
    Error,
}
```

这段代码对应当前 `rlog/src/cli.rs`。这里没有导入 `Args`，因为这一阶段还没有把重复参数抽成公共结构。后续如果希望把 `file`、`level`、`contains` 抽成一个 `FilterArgs`，再引入 `Args` 会更合适。

这段代码里有三个核心类型。

## 1、Cli

`Cli` 表示整个命令行程序的入口参数：

```rust
pub struct Cli {
    #[command(subcommand)]
    pub command: Commands,
}
```

它目前只有一个字段：`command`。这表示用户必须选择一个子命令，例如 `view` 或 `stats`。

`#[derive(Parser)]` 让 `Cli` 获得从终端参数解析自己的能力。后续可以通过：

```rust
let cli = Cli::parse();
```

直接得到一个 `Cli` 值。

## 2、Commands

`Commands` 是一个枚举，用来表达不同子命令：

```rust
pub enum Commands {
    View { ... },
    Stats { ... },
}
```

这比使用字符串判断更清晰。程序后续可以用 `match` 分发逻辑：

```rust
match cli.command {
    Commands::View { .. } => {
        // 查看日志
    }
    Commands::Stats { .. } => {
        // 统计日志
    }
}
```

这里体现了 Rust 枚举的优势：不同命令的参数可以和命令本身绑定在一起。

## 3、Level

`Level` 表示日志级别：

```rust
pub enum Level {
    Info,
    Warn,
    Error,
}
```

加上 `#[derive(ValueEnum)]` 后，`clap` 会把命令行中的字符串转换成枚举值。

例如：

```shell
cargo run -- view full_log.txt --level error
```

会解析成类似：

```text
level: Some(Error)
```

如果用户输入不支持的级别，例如：

```shell
cargo run -- view full_log.txt --level debug
```

`clap` 会自动报错，因为第一版只支持 `info`、`warn`、`error`。

这里还需要注意 `#[arg(long, value_enum)]`：

```rust
#[arg(long, value_enum)]
level: Option<Level>,
```

- `long` 表示命令行参数使用长选项形式，也就是 `--level`。
- `value_enum` 表示这个参数的值要按照 `Level` 枚举解析。

如果只写 `#[arg(long)]`，在很多情况下 `clap` 也能通过 `ValueEnum` 推导出可选值；但显式写上 `value_enum` 更直观，读代码时一眼就知道 `level` 不是任意字符串，而是受枚举约束的参数。

# 六、修改 main.rs

`///` 开头的是 Rust 文档注释。对普通库代码来说，它会进入 `cargo doc` 生成的文档；对 `clap` 来说，它还会被用来生成命令行帮助信息。

例如：

```shell
cargo run -- view --help
```

会显示 `view` 子命令支持的参数，以及 `file`、`--level`、`--contains` 分别代表什么。

如果没有这些文档注释，`--help` 仍然能列出参数名，但用户只能看到参数形状，不知道每个参数的用途。对于 CLI 工具来说，帮助信息也是用户界面的一部分，所以第一阶段就应该把说明写上。

`main.rs` 只负责启动解析，并把解析结果打印出来：

```rust
mod cli;

use clap::Parser;
use cli::Cli;

fn main() {
    let cli = Cli::parse();
    println!("{cli:#?}");
}
```

这里的职责非常清楚：

| 代码 | 含义 |
|---|---|
| `mod cli;` | 引入 `src/cli.rs` 模块 |
| `use clap::Parser;` | 引入 `parse` 方法所在的 trait |
| `use cli::Cli;` | 使用自己定义的 CLI 参数结构 |
| `Cli::parse()` | 从终端参数解析出 `Cli` |
| `println!("{cli:#?}")` | 临时打印解析结果，方便验证 |

> 注意：`println!("{cli:#?}")` 只是本阶段的临时验证方式。后续真正实现业务逻辑后，会改成根据子命令调用不同函数。

# 七、运行与验证

完成 `Cargo.toml`、`src/cli.rs` 和 `src/main.rs` 后，可以先运行：

```shell
cargo check
```

如果编译通过，说明类型和依赖没有问题。

然后验证 `view` 子命令：

```shell
cargo run -- view full_log.txt
```

预期会看到类似输出：

```text
Cli {
    command: View {
        file: "full_log.txt",
        level: None,
        contains: None,
    },
}
```

继续验证级别过滤参数：

```shell
cargo run -- view full_log.txt --level error
```

预期会看到：

```text
Cli {
    command: View {
        file: "full_log.txt",
        level: Some(
            Error,
        ),
        contains: None,
    },
}
```

再验证关键词过滤：

```shell
cargo run -- view full_log.txt --contains connection
```

预期会看到：

```text
Cli {
    command: View {
        file: "full_log.txt",
        level: None,
        contains: Some(
            "connection",
        ),
    },
}
```

最后验证 `stats` 子命令：

```shell
cargo run -- stats full_log.txt
```

预期会看到：

```text
Cli {
    command: Stats {
        file: "full_log.txt",
        level: None,
        contains: None,
    },
}
```

# 八、当前代码的问题

## 1、只解析参数，还没有业务逻辑

当前程序只会打印参数结构，不会读取文件，也不会过滤日志。

这不是问题，而是刻意控制范围。第 1 阶段的验收标准就是：终端命令能被稳定解析成 Rust 数据结构。

## 2、View 和 Stats 参数有重复

`View` 和 `Stats` 都有：

```rust
file: PathBuf,
level: Option<Level>,
contains: Option<String>,
```

这会产生一点重复。第一版先接受这个重复，因为它让每个子命令的参数结构非常直观。等后续逻辑稳定后，如果重复继续增加，再考虑抽出公共结构。

## 3、Level 暂时放在 cli.rs 中

`Level` 现在放在 `cli.rs`，因为它直接服务于命令行参数解析。后续进入日志解析阶段时，可能会把日志级别移动到 `log_entry.rs`，让 CLI 和日志解析共用同一个类型。

这类调整属于正常演进：先让概念清楚地跑起来，再根据真实使用位置移动代码。

# 九、本篇小结

本阶段完成的是 `rlog` 的命令行接口设计。

当前版本应该能够解析：

| 命令 | 解析结果 |
|---|---|
| `rlog view full_log.txt` | 查看全部日志 |
| `rlog view full_log.txt --level error` | 查看 error 级别日志 |
| `rlog view full_log.txt --contains connection` | 查看包含关键词的日志 |
| `rlog stats full_log.txt` | 统计日志级别数量 |

本篇涉及的 Rust 知识点：

| 知识点 | 用途 |
|---|---|
| `struct` | 表示整个 CLI 参数 |
| `enum` | 表示子命令和日志级别 |
| `Option` | 表示可选过滤条件 |
| `PathBuf` | 表示文件路径 |
| `derive` | 通过宏自动生成解析能力 |
| `Debug` | 临时打印结构化参数 |

下一步可以进入 [[Rust/notes/项目/02_rlog/3、模块拆分与文件读取|模块拆分与文件读取]]，让程序真正打开日志文件，并用 `BufReader` 按行读取内容。
