# 一、阶段目标

[[Rust/notes/项目/02_rlog/3、模块拆分与文件读取|模块拆分与文件读取]] 已经让 `rlog` 能根据子命令打开日志文件，并用 `BufReader` 按行输出内容。

上一阶段的 `app.rs` 虽然已经接收了 `level` 和 `contains`，但只是暂时忽略：

```rust
Commands::View {
    file,
    level: _,
    contains: _,
} => {
    print_lines(&file)?;
}
```

本篇进入下一阶段：真正使用 `--contains` 和 `--level`，让 `view` 只输出匹配的日志行。

本阶段完成后，下面几条命令应该有不同输出：

```shell
cargo run -- view full_log.txt
cargo run -- view full_log.txt --contains connection
cargo run -- view full_log.txt --level error
cargo run -- view full_log.txt --level warn --contains connection
```

本阶段暂时只改 `view` 行为，`stats` 先留空。真正的 `TRACE`、`DEBUG`、`INFO`、`WARN`、`ERROR` 数量统计放到下一篇。

# 二、过滤模型

日志过滤的核心问题是：给定一行日志，以及用户传入的可选过滤条件，判断这一行是否应该输出。

命令行中已经有两个过滤条件：

| 参数 | 类型 | 含义 |
|---|---|---|
| `--contains` | `Option<String>` | 只输出包含关键词的行 |
| `--level` | `Option<Level>` | 只输出指定级别的行 |

因为两个参数都是可选的，所以过滤规则可以先定义成：

| 条件 | 行为 |
|---|---|
| 没有 `--contains` | 不按关键词限制 |
| 有 `--contains connection` | 当前行必须包含 `connection` |
| 没有 `--level` | 不按级别限制 |
| 有 `--level error` | 当前行必须是 `ERROR` 级别 |
| 两个条件都有 | 必须同时满足 |

这类逻辑很适合单独拆成 `filter.rs`，避免塞进文件读取循环里。

# 三、先用测试固定过滤规则

`matches_filter` 是纯函数，不读文件、不打印输出，很适合先写红灯测试。先在 `filter.rs` 中写下期望：

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn matches_without_filters() {
        let line = "[2026-07-20T09:30:00Z INFO rlog::app] started";

        assert!(matches_filter(line, None, None))
    }

    #[test]
    fn filters_by_keyword() {
        let line = "[2026-07-20T09:32:45Z ERROR rlog::network] connection failed";

        assert!(matches_filter(line, None, Some("connection")));
        assert!(!matches_filter(line, None, Some("storage")));
    }

    #[test]
    fn filters_by_level() {
        let line = "[2026-07-20T09:32:45Z ERROR rlog::network] connection failed";

        assert!(matches_filter(line, Some(&Level::Error), None));
        assert!(!matches_filter(line, Some(&Level::Warn), None));
    }
}
```

为了让红灯来自行为不满足，而不是函数缺失导致编译失败，可以先补最小骨架：

```rust
use crate::cli::Level;

pub fn matches_filter(line: &str, level: Option<&Level>, contains: Option<&str>) -> bool {
    todo!()
}

fn parse_level(line: &str) -> Option<&Level> {
    todo!()
}
```

这时测试可以编译，但运行会在 `todo!()` 处失败。测试覆盖的行为是：

| 测试                        | 行为              |
| ------------------------- | --------------- |
| `matches_without_filters` | 没有过滤条件时保留日志行    |
| `filters_by_keyword`      | 有关键词时只保留包含关键词的行 |
| `filters_by_level`        | 有级别时只保留对应级别的行   |

# 四、实现 matches_filter

为了让测试变绿，把过滤函数设计成接收一行文本和两个可选条件：

```rust
use crate::cli::Level;

pub fn matches_filter(line: &str, level: Option<&Level>, contains: Option<&str>) -> bool {
    if let Some(keyword) = contains
        && !line.contains(keyword)
    {
        return false;
    }

    if let Some(expected_level) = level
        && parse_level(line) != Some(expected_level)
    {
        return false;
    }

    true
}
```

这个函数按“先排除不匹配，再默认通过”的方式写：

| 返回值 | 含义 |
|---|---|
| `true` | 当前行满足过滤条件，应该输出 |
| `false` | 当前行不满足过滤条件，应该跳过 |

这里使用 `Option<&Level>` 和 `Option<&str>`，是为了借用已有参数，不需要额外克隆 `Level` 或 `String`。

`Level` 需要派生 `PartialEq`，因为过滤函数中会比较解析出的级别和用户传入的级别：

```rust
if let Some(expected_level) = level
    && parse_level(line) != Some(expected_level)
{
    return false;
}
```

当前 `cli.rs` 中的 `Level` 写法是：

```rust
#[derive(ValueEnum, Debug, Clone, PartialEq)]
pub enum Level {
    Trace,
    Debug,
    Info,
    Warn,
    Error,
}
```

当前代码使用的是 let-chain 写法，把“过滤条件存在”和“当前行不满足条件”合并在同一个 `if` 中：

```rust
if let Some(keyword) = contain
    && !line.contains(keyword)
{
    return false;
}
```

这段代码可以读作：如果用户传入了关键词，并且当前行不包含这个关键词，就返回 `false`。它等价于嵌套的 `if`：

```rust
if let Some(keyword) = contain {
    if !line.contains(keyword) {
        return false;
    }
}
```

当前项目使用 `edition = "2024"`，这种写法能让过滤逻辑更紧凑。

两个 `if let Some(...)` 分别处理两个可选条件：

- 如果用户传了关键词，就检查 `line.contains(keyword)`。
- 如果用户传了级别，就检查当前行解析出的级别是否等于目标级别。

只要有一个条件不满足，就提前 `return false`。如果两个条件都没有拦住，最后返回 `true`。

# 五、实现 parse_level

当前测试日志格式类似：

```text
[2026-07-20T09:32:45Z ERROR rlog::network] connection failed
```

第一版可以先用简单字符串包含判断来识别级别：

```rust
fn parse_level(line: &str) -> Option<&Level> {
    if line.contains(" ERROR ") {
        Some(&Level::Error)
    } else if line.contains(" WARN ") {
        Some(&Level::Warn)
    } else if line.contains(" INFO ") {
        Some(&Level::Info)
    } else if line.contains(" DEBUG ") {
        Some(&Level::Debug)
    } else if line.contains(" TRACE ") {
        Some(&Level::Trace)
    } else {
        None
    }
}
```

这里刻意匹配 `" TRACE "`、`" DEBUG "`、`" INFO "`、`" WARN "`、`" ERROR "`，而不是直接匹配 `"INFO"` 或 `"ERROR"`。

原因是日志内容中也可能出现这些单词。例如：

```text
[2026-07-20T09:30:00Z INFO rlog::app] printed ERROR as plain text
```

如果直接用 `line.contains("ERROR")`，这行可能会被误判为 `ERROR` 级别。匹配前后带空格的级别字符串虽然仍然简单，但比直接匹配单词更稳一点。

> 注意：这仍然不是最终解析方案。后续解析时间和模块时，可以用 `regex` 或更明确的切分逻辑解析日志头。

这里有一个 Rust 细节：`parse_level` 返回 `Option<&Level>`，但 `Some(&Level::Info)` 不是返回局部变量引用。`Level::Info` 这类无内部可变性、无析构逻辑的枚举值可以被编译器常量提升，因此这里可以安全返回引用。

如果想让所有权关系更直观，也可以让 `Level` 派生 `Copy`，并让 `parse_level` 返回拥有值：

```rust
#[derive(Debug, Clone, Copy, ValueEnum)]
pub enum Level {
    Trace,
    Debug,
    Info,
    Warn,
    Error,
}

fn parse_level(line: &str) -> Option<Level> {
    if line.contains(" ERROR ") {
        Some(Level::Error)
    } else if line.contains(" WARN ") {
        Some(Level::Warn)
    } else if line.contains(" INFO ") {
        Some(Level::Info)
    } else if line.contains(" DEBUG ") {
        Some(Level::Debug)
    } else if line.contains(" TRACE ") {
        Some(Level::Trace)
    } else {
        None
    }
}
```

对这种小枚举来说，返回 `Option<Level>` 往往更简单；当前源码使用 `Option<&Level>`，因此后面的统计函数也接收 `&Level`。

# 六、接入 app.rs

有了 `matches_filter` 后，`app.rs` 需要从“打印所有行”改成“只打印匹配行”。

先在 `main.rs` 接入新模块：

```rust
mod app;
mod cli;
mod filter;
```

然后在 `app.rs` 中使用过滤函数：

```rust
use crate::cli::{Commands, Level};
use crate::filter::matches_filter;
use std::fs::File;
use std::io::{self, BufRead, BufReader};
use std::path::Path;

pub fn run(command: Commands) -> io::Result<()> {
    match command {
        Commands::View {
            file,
            level,
            contains,
        } => {
            print_matching_lines(&file, level.as_ref(), contains.as_deref())?;
        }

        Commands::Stats {
            file: _,
            level: _,
            contains: _,
        } => {}
    }

    Ok(())
}

fn print_matching_lines(
    path: &Path,
    level: Option<&Level>,
    contain: Option<&str>,
) -> io::Result<()> {
    // 打开日志文件
    let file = File::open(path)?;

    // 包装成行缓冲器
    let reader = BufReader::new(file);

    for line in reader.lines() {
        let line = line?;

        if matches_filter(&line, level, contain) {
            println!("{}", line);
        }
    }

    Ok(())
}
```

`Stats` 分支里写成 `file: _`，表示当前阶段明确忽略这个字段。这样可以避免编译器提示 unused variable warning；等下一阶段实现统计时，再把它改回 `file` 并交给统计函数使用。

这里有两个新写法值得注意。

## 1、as_ref

`level` 的类型是：

```rust
Option<Level>
```

但 `matches_filter` 需要的是：

```rust
Option<&Level>
```

所以使用：

```rust
level.as_ref()
```

它会把 `Option<Level>` 转成 `Option<&Level>`，也就是“保留可选结构，但只借用里面的值”。

## 2、as_deref

`contains` 的类型是：

```rust
Option<String>
```

过滤函数需要的是：

```rust
Option<&str>
```

所以使用：

```rust
contains.as_deref()
```

它会把 `Option<String>` 转成 `Option<&str>`。这比手动写 `contains.as_ref().map(|s| s.as_str())` 更简洁。

# 七、运行验证

本阶段继续使用 `full_log.txt`。

查看全部日志：

```shell
cargo run -- view full_log.txt
```

按关键词过滤：

```shell
cargo run -- view full_log.txt --contains connection
```

预期只输出包含 `connection` 的日志行：

```text
[2026-07-20T09:32:05Z WARN rlog::network] connection is slow
[2026-07-20T09:32:45Z ERROR rlog::network] connection failed
[2026-07-20T09:32:50Z DEBUG rlog::retry] connection retry backoff set to 200ms
[2026-07-20T09:33:10Z INFO rlog::retry] retrying connection
[2026-07-20T09:33:40Z INFO rlog::network] connection established
```

按级别过滤：

```shell
cargo run -- view full_log.txt --level error
```

预期输出：

```text
[2026-07-20T09:32:45Z ERROR rlog::network] connection failed
[2026-07-20T09:35:22Z ERROR rlog::storage] failed to write archive file
```

同时使用两个过滤条件：

```shell
cargo run -- view full_log.txt --level warn --contains connection
```

预期输出：

```text
[2026-07-20T09:32:05Z WARN rlog::network] connection is slow
```

这个结果说明两个过滤条件是“同时满足”的关系，而不是“满足任意一个即可”。

# 八、当前边界

## 1、级别解析仍然粗糙

当前级别解析只是判断日志行是否包含 `" TRACE "`、`" DEBUG "`、`" INFO "`、`" WARN "`、`" ERROR "`。

这对第一版测试日志够用，但它依赖日志格式比较稳定。后续如果要支持更多格式，可以把日志行解析成结构体：

```rust
struct LogEntry {
    level: Level,
    raw: String,
}
```

这样过滤逻辑就不用直接面对原始字符串。

## 2、Stats 还没有统计

本阶段只让 `view` 使用过滤条件。`Stats` 分支暂时留空，下一阶段复用 `matches_filter` 统计过滤后的日志级别数量。

# 九、小结

本阶段完成的是：按红灯测试先固定过滤规则，再实现 `matches_filter` 和 `parse_level`，最后让 `view` 真正使用 `--contains` 和 `--level`。

当前项目结构建议变成：

```shell
src/
├── main.rs
├── cli.rs
├── app.rs
└── filter.rs
```

本篇涉及的 Rust 知识点：

| 知识点 | 用途 |
|---|---|
| `PartialEq` | 让 `Level` 支持 `==` 和 `!=` 比较 |
| `Option<&T>` | 借用可选值，避免克隆 |
| `as_ref` | 把 `Option<T>` 转成 `Option<&T>` |
| `as_deref` | 把 `Option<String>` 转成 `Option<&str>` |
| let-chain | 合并可选值判断和布尔条件 |
| `if let Some` | 只在用户传入过滤条件时检查 |
| 提前返回 | 不满足条件时直接 `return false` |
| 模块拆分 | 把过滤逻辑放到 `filter.rs` |
