# 一、基本分类

## 1、Rust错误处理

Rust 没有传统意义上的异常机制，而是把错误明确分为两类：

- **可恢复错误**：使用`Result<T, E>`表示
- **不可恢复错误**：使用`panic!`表示

这种分类方式的核心思想是：

> 错误应该根据性质决定处理方式，而不是统一交给异常机制。

如果错误发生后，程序仍然有机会处理、补救或交给上层，就使用`Result<T, E>`。

如果程序已经进入无法安全、合理继续执行的状态，就使用`panic!`。


## 2、可恢复错误

可恢复错误是指：

> 错误发生后，程序仍然有机会采取补救措施，或者把错误继续上交给上层处理。

这类错误通常来自外部环境，而不是程序内部逻辑错误。

常见场景包括：

- 文件不存在
- 权限不足
- 网络请求失败
- 用户输入非法
- 配置文件格式错误

例如，打开文件失败不一定说明程序写错了，也可能只是文件暂时不存在。程序可以选择提示用户、创建文件、换一个路径重试，或者把错误继续向上传递。

Rust 通常使用`Result<T,E>`表示这类错误。

## 3、不可恢复错误

不可恢复错误是指：

> 程序已经进入了无法安全、合理继续执行的状态。

这类错误通常意味着程序内部逻辑有问题，或者某个本不应该被破坏的前提条件被破坏了。

常见场景包括：

- 数组或切片越界访问
- 断言失败
- 在`Err`上调用`unwrap()`
- 程序进入理论上不应该到达的分支

例如，访问不存在的数组下标通常说明代码逻辑有问题，此时继续运行可能会掩盖更严重的问题，Rust 会触发 `panic`，让错误尽早暴露。

> 需要注意：编译通过不等于程序绝对不会出错。Rust 只保证安全 Rust 下的内存安全，但程序逻辑错误、运行时错误、外部环境错误仍然有可能发生。

## 4、错误处理方式的选择

| 错误类型       | 推荐方式                    | 典型场景            |
| ---------- | ----------------------- | --------------- |
| 可预期、可处理的错误 | `Result<T, E>`          | 文件不存在、解析失败、网络失败 |
| 程序逻辑错误     | `panic!`                | 越界访问、断言失败、不可能分支 |
| 临时示例或测试代码  | `unwrap()` / `expect()` | 示例程序、单元测试、快速验证  |
| 复杂应用程序错误   | 自定义错误类型                 | 命令行工具、库、业务程序    |

简单判断：

- 调用者有机会处理：返回 `Result`
- 程序已经无法合理继续：使用 `panic!`
- 当前只是示例或测试：可以使用 `unwrap()` / `expect()`
- 错误类型需要表达业务语义：定义自定义错误类型

# 二、panic!与不可恢复错误

## 1、panic基本含义

在 Rust 中，`panic` 是程序遇到不可恢复错误时进入的异常终止流程。`panic!` 是一个宏，用于主动触发 `panic`。

当 `panic` 发生时，当前执行流程不会继续正常运行，而是进入错误终止流程。

示例：

```rust
fn main() {  
	panic!("crash and burn");  
}
```

结果：

![[Pasted image 20260529172733.png|400]]

`panic!`可以像`println!`一样接收格式化参数：

```rust
fn check_age(age: i32) {  
    if age < 0 {  
        panic!("age cannot be negative: {age}");  
    }  
}  
  
fn main() {  
    check_age(-1);  
}
```

`panic!` 适合表达“程序已经进入不应该继续执行的状态”。

普通业务错误、用户输入错误、文件不存在这类可预期问题，通常不应该直接使用`panic!`，而应该使用 `Result`。

## 2、panic的被动触发

有些`panic`是程序运行到非法状态时，由Rust或标准库自动触发的。

例如，向量越界访问：

```rust
fn main() {
    let v = vec![1, 2, 3];

    println!("{}", v[99]);
}
```

这段代码可以通过编译，但运行时会触发 `panic`：

![[Pasted image 20260526161502.png|500]]

因为 `v` 的长度是 `3`，合法下标只有 `0..3`，访问 `99` 明显越界。

可以看到输出了哪个线程panic、panic发生的具体代码位置以及panic发生的原因。

常见的被动触发场景包括：

- 数组、切片、`Vec<T>` 越界访问
- 整数除以零
- `assert!`、`assert_eq!` 等断言失败
- 在 `Err` 上调用 `unwrap()` 或 `expect()`
- 在 `None` 上调用 `unwrap()` 或 `expect()`

这类 `panic` 往往说明程序逻辑存在问题。Rust 选择在运行时立即暴露错误，而不是让程序继续在错误状态下运行。


## 3、panic发生后的默认行为

当`panic`发生时，`Rust`默认使用**栈展开**，也就是`unwind`。

大致流程如下：

1. 输出错误信息，说明`panic`的位置和原因
2. 如果启动了回溯信息（`RUST_BACKTRACE=1`），输出调用栈
3. 从当前函数开始，沿调用栈逐层退出
4. 退出过程中清理局部变量，调用它们的`drop`方法
5. 当前线程结束。如果是主线程`panic`，则整个进程结束。

因此，`panic`不等于瞬间崩溃。默认情况下，它是一个受控制的终止过程。

示例：

```rust
struct Guard;

impl Drop for Guard {
    fn drop(&mut self) {
        println!("Guard dropped");
    }
}

fn main() {
    let _guard = Guard;

    panic!("something went wrong");
}
```

> 有关Drop Trait后续会具体介绍，这里只需要知道它负责一些清理工作。

发生 `panic` 时，`_guard` 在栈展开过程中仍然会被清理，`drop` 方法会被调用。

![[Pasted image 20260526161155.png|500]]

这说明：在安全 Rust 中，`panic` 不会破坏内存安全。它是明确受控的错误终止机制，不是未定义行为。

## 4、backtrace调用栈信息

当程序发生 `panic` 时，Rust 默认会输出简要错误信息。如果需要查看更完整的调用栈，可以设置环境变量 `RUST_BACKTRACE=1`。

示例：

```rust
fn main() {
    let v = vec![1, 2, 3];

    println!("{}", v[99]);
}
```

macOS / Linux：

```rust
RUST_BACKTRACE=1 cargo run
```

结果：

![[Pasted image 20260526162447.png|800]]

调用栈信息会显示函数调用路径。**通常越靠上，越接近错误发生的位置；越靠下，越接近程序入口或运行时调用**。

例如 `main` 函数一般是最早调用的函数，所以排在接近最下面。从下往上看：

- 最底层的 `core::ops::function::FnOnce::call_once` 是运行时调用 `main` 的入口包装层，简单理解为Rust将 `main` 当作一个函数对象执行。
- `hello_cargo::main at ./src/main.rs:5:6` 这一层就是我们写的代码，说明当前 `panic` 是从 `hello_cargo` 这个crate的 `main` 函数里触发的，具体位置在`./src/main.rs:5:6` 。 **这通常是排查问题时最该关注的一层，因为这是用户层代码，而不是标准库内部。**
- `<alloc::vec::Vec<T,A> as core::ops::index::Index<I>>::index` 这一层说明对 `Vec` 执行了索引操作，对应代码里就是 `v[99]` 。
- `core::slice::index::<impl core::ops::index::Index<I> for [T]>::index` ， `Vec` 的底层可以看作一个切片 `slice` ，所以继续往下转到切片的索引实现。
- `<usize as core::slice::index::SliceIndex<[T]>>::index` 说明传入的索引类型是 `usize` ，这是更底层的按某个下标访问切片的实现。
- `core::panicking::panic_bounds_check` 这一层非常关键，它表示标准库在**进行边界检查时发现越界** ，于是决定触发`panic` 。也就是说，真正检测出错误的地方在这里：索引超出了合法的范围。
- `core::panicking::panic_fmt` 这一层可以理解为Rust将 `panic` 信息格式化，准备输出错误内容。例如 `index out of bounds: the len is 3 but the index is 99` 就是这一阶段构造的。
- `__rustc::rust_begin_unwind` 这是panic处理流程的更底层入口，它表示程序正式进入了**unwind** （栈展开）阶段。也就是打印panic信息、沿调用栈逐层输出、清理局部变量，最终结束当前线程。

调用栈信息可以帮助定位错误发生的路径。通常重点关注自己项目中的函数。排查问题时，不必逐行理解所有标准库栈帧，先找自己代码中的位置。

> 调用栈信息会受操作系统、Rust 版本、构建模式、优化等级影响，不同环境下输出可能不同。


## 5、abort直接终止

除了默认栈展开，Rust还支持另一种`panic`处理方式：直接终止，也就是 `abort`。

可以在`Cargo.toml`中配置：

```toml
[profile.release]
panic = 'abort'
```

这样在 `release` 构建中，一旦发生 `panic`，程序会直接终止，不再进行栈展开，也不会执行沿途局部变量的清理逻辑。

这种方式的优点是：可执行文件可能更小，运行时不需要保留栈展开相关支持代码。

但代价是：失去栈展开过程中的清理机会，也不能通过常规方式捕获这种 `panic`。

## 6、双重panic

如果程序正在处理第一次 `panic`，并且在栈展开过程中又发生第二次 `panic`，Rust 通常会直接终止进程。这种情况叫双重 `panic`。

例如，在某个类型的 `drop` 方法中再次触发 `panic`，就可能造成双重 `panic`。

示例：

```rust
struct BadDrop;

impl Drop for BadDrop {
    fn drop(&mut self) {
        panic!("panic in drop");
    }
}

fn main() {
    let _x = BadDrop;

    panic!("first panic");
}
```

这类情况通常属于严重错误。实际开发中应避免在 `drop` 中触发 `panic`。

## 7、线程中的panic

`panic` 是线程级别的。

如果子线程发生 `panic`，默认只会终止这个子线程，其他线程仍然可以继续运行。

如果发生 `panic` 的是主线程，那么整个进程通常会退出。

有关线程`panic`的内容，可以放到[[1、多线程编程基础|线程]]笔记中继续展开。

# 三、Result与可恢复错误

## 1、Result的基本含义

对于可能失败、但程序仍然有机会处理的操作，Rust 通常使用 `Result<T, E>`。

`Result` 是标准库中的枚举，简化定义如下：

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

其中：

- `Ok(T)` 表示操作成功，并携带成功值。

- `Err(E)` 表示操作失败，并携带错误值。

例如，打开文件可能成功，也可能失败：

```rust
use std::fs::File;

fn main() {
    let result = File::open("hello.txt");

    println!("{result:?}");
}
```

结果：

```text
Err(Os { code: 2, kind: NotFound, message: "No such file or directory" })
```

`File::open("hello.txt")` 的返回类型是：

```rust
Result<File, std::io::Error>
```

- 如果打开成功，返回 `Ok(File)`

- 如果打开失败，返回 `Err(std::io::Error)`

这类错误通常来自外部环境，例如文件不存在、权限不足、路径错误等，因此属于可恢复错误。

## 2、使用 match 处理Result

处理 `Result` 最完整的方式是使用 `match`。

```rust
use std::fs::File;

fn main() {
    let file = match File::open("hello.txt") {
        Ok(file) => file,
        Err(error) => {
            panic!("打开文件失败：{error}");
        }
    };

    println!("{file:?}");
}
```

这里提前在当前项目目录新建一个`hello.txt`。

结果：

```text
File { fd: 3, path: "/Users/11185032/projects/hello_cargo/hello.txt", read: true, write: false }
```

这种写法虽然完整，但如果所有错误都只是 `panic`，就不算是真正的可恢复处理。

更典型的做法是根据错误类型采取不同措施。例如，如果是文件不存在的错误，可以先创建文件；如果是其他错误再触发 `panic` ：

```rust
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let file = match File::open("hello.txt") {
        Ok(file) => file,
        Err(error) => match error.kind() {
            ErrorKind::NotFound => match File::create("hello.txt") {
                Ok(created_file) => created_file,
                Err(create_error) => {
                    panic!("创建文件失败：{create_error}");
                }
            },
            other_error => {
                panic!("打开文件失败：{other_error:?}");
            }
        },
    };

    println!("{file:?}");
}
```

这里的关键点是：错误不是一律终止，而是先判断是否有补救方案。

- 如果是 `NotFound`，程序尝试创建文件。
- 如果是权限不足、路径非法等其他错误，再选择终止。

这就是 `Result` 的意义：让错误成为普通值，由代码显式处理。


## 3、match的适用场景

`match`适合完整分支处理。

示例：

```rust
fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        Err(String::from("除数不能为 0"))
    } else {
        Ok(a / b)
    }
}

fn main() {
    match divide(10, 2) {
        Ok(value) => println!("结果：{value}"),
        Err(error) => println!("错误：{error}"),
    }
}
```

适合使用`match`的场景包括：

- 成功和失败都要明确处理
- 不同错误要走不同的逻辑
- 需要写清楚控制流
- 错误处理本身就是当前函数的重要逻辑


## 4、unwrap和expect

`unwrap()` 的行为很直接：

- 如果是 `Ok(v)` ，返回内部的成功值

- 如果是 `Err(e)` ，触发 `panic`

示例：

```rust
use std::fs::File;

fn main() {
    let file = File::open("hello.txt").unwrap();

    println!("{file:?}");
}
```

如果文件不存在，这段代码会触发 `panic`。

`unwrap()` 很方便，但不能滥用。它适合示例代码、测试代码，或者错误发生时直接终止程序确实合理的场景。

`expect()` 和 `unwrap()` 类似，但可以自定义错误信息。

示例：

```rust
use std::fs::File;

fn main() {
    let file = File::open("hello.txt").expect("无法打开 hello.txt");

    println!("{file:?}");
}
```

如果发生错误，`expect()` 的信息会和底层错误一起输出。

结果：

![[Pasted image 20260526170746.png|600]]

相比 `unwrap()`，`expect()` 更适合表达“这里为什么可以假设成功”。

例如：

```rust
use std::net::IpAddr;

fn main() {
    let home: IpAddr = "127.0.0.1"
        .parse()
        .expect("硬编码的 IP 地址应该是合法的");

    println!("{home:?}");
}
```

这里字符串是写死的合法 IP 地址，使用 `expect()` 是合理的。

但如果 IP 地址来自用户输入，就不应该直接 `expect()`，而应该正常处理错误。

## 5、unwrap_or和unwrap_or_else

如果失败不想`panic`，可以使用`unwrap_or`或`unwrap_or_else`提供默认值。

例如：

```rust
fn main() {
    let result: Result<i32, &str> = Err("error");

    let number = result.unwrap_or(0);

    println!("{number}");
}
```

`unwrap_or(0)` 表示：

- 成功时返回 `Ok` 内部的值
- 失败时返回默认值 `0`

如果默认值需要通过计算得到，可以用`unwrap_or_else`：

```rust
fn main() {
    let result: Result<i32, &str> = Err("error");

    let number = result.unwrap_or_else(|error| {
        println!("error: {error}");
        0
    });

    println!("{number}");
}
```

`unwrap_or_else()` 接收一个闭包，只有在 `Err` 时才会执行。有关闭包知识详见[[19、闭包|闭包]]，当前只需要知道它可以延迟生成默认值。

## 6、is_ok 和 is_err 

如果只想判断成功或失败，可以使用 `is_ok()` 和 `is_err()`：

```rust
fn main() {
    let result: Result<i32, &str> = Ok(10);

    println!("{}", result.is_ok());
    println!("{}", result.is_err());
}
```

它们只返回布尔值，不会取出内部数据。

## 7、ok 和 err 

`ok()`和`err()`会把`Result`转换为`Option`。

`ok()`会把`Result<T,E>`转换成`Option<T>`：

- 如果是`Ok(v)`，转换为`Some(v)`
- 如果是`Err(e)`，转换为`None`

示例：

```rust
fn main() {
    let result: Result<i32, &str> = Ok(10);

    let option = result.ok();

    println!("{option:?}");
}
```

输出：

```text
Some(10)
```

`err()` 则相反，将`Result<T, E>`转换为`Option<E>`：

- `Ok(v)` 变成 `None`
- `Err(e)` 变成 `Some(e)`

```rust
fn main() {
    let result: Result<i32, &str> = Err("error");

    let option = result.err();

    println!("{option:?}");
}
```

输出：

```text
Some("error")
```

这两个方法会丢弃另一侧的信息，所以只适合确实不关心其中一侧的场景。

## 8、as_ref和as_mut

很多`Result`方法会按值接收`self`，也就是说会消耗原来的`Result`。

如果不想消耗它，可使用`as_ref`或`as_mut()`。

`as_ref`会把`Result<T,E>`转换为`Result<&T,&E>`。

示例：

```rust
fn main() {
    let result: Result<String, String> = Ok(String::from("hello"));

    let option = result.as_ref().ok();

    println!("{option:?}");
    println!("{result:?}");
}
```

这里 `result.as_ref().ok()` 得到的是 `Option<&String>`，不会移动原来的 `String`。

`as_mut()` 类似，但它把`Result<T,E>`转换为`Result<&mut T,&mut E>`。它适合在不移动 `Result` 的前提下修改内部值。

## 9、忽略Result

`Result<T, E>`类型本身带有`#[must_use]`属性，所以只要一个表达式返回`Result`，而你完全不处理它，编译器就会警告。

例如：

```rust
fn hello() -> Result<i32, String> {
    Ok(0)
}

fn main() {
    hello();
}
```

![[Pasted image 20260530211324.png|400]]

正常情况下需要`match`等显式处理。如果确实要忽略这个结果，可以显式写成：

```rust
fn main() {
    let _ = hello();
}
```

这表示：我知道这里返回了一个 `Result`，但我明确选择忽略它。

不过，忽略 `Result` 要谨慎。多数情况下，至少应该记录日志、提示用户，或者说明为什么可以忽略。

补充一点：`#[must_use]` 不只可以标在类型上，也可以标在函数上。

例如：

```rust
#[must_use]
fn build_number() -> i32 {
    100
}

fn main() {
    build_number();
}
```

结果：

![[Pasted image 20260530211637.png|400]]


这里即使返回值是普通 `i32`，也会警告。因为函数本身被标记为 `#[must_use]`。


# 四、传播错误

## 1、手动传播错误

很多时候，当前函数不想处理错误，而是把错误交给调用者处理。

不使用`?`时，可以使用`match`手动传播错误：

```rust
use std::fs::File;  
use std::io::Read; 

fn read_username_from_file() -> Result<String, std::io::Error> {  
    let mut file = match File::open("username.txt") {  
        Ok(f) => f,  
        Err(e) => return Err(e),  
    };  
      
    let mut username = String::new();  
      
    match file.read_to_string(&mut username) {  
       Ok(_) => Ok(username),  
        Err(e) => Err(e),  
    }  
}
```

这段代码逻辑很清楚，但写起来比较啰嗦。

## 2、使用?传播Result

`?`是错误传播的快捷写法，其行为是：

- 如果结果是`Ok(value)`，取出`value`，程序继续执行
- 如果结果是`Err(error)`，立即从当前函数返回 `Err(error)`

因此：

```rust
let mut file = File::open("username.txt")?;
```

可以理解为：

```rust
let mut file = match File::open("hello.txt") {
    Ok(f) => f,
    Err(e) => return Err(e),
};
```

使用 `?` 改写前面的示例：

```rust
use std::fs::File;  
use std::io::Read;  
  
fn read_username_from_file() -> Result<String, std::io::Error> {  
      
    let mut file = File::open("username.txt")?;  
  
    let mut username = String::new();  
  
    file.read_to_string(&mut username)?;  
      
    Ok(username)  
}
```


## 3、?的链式写法

`?` 可以连续使用：

```rust
use std::fs::File;  
use std::io::Read;  
  
fn read_username_from_file() -> Result<String, std::io::Error> {  
    let mut username = String::new();  
    File::open("username.txt")?.read_to_string(&mut username)?;  
    Ok(username)  
}
```


## 4、?与错误类型转换

`?`不只是提前返回错误。**如果满足条件，它还会把当前错误类型转换为当前函数返回的错误类型**。

这个转换依赖 `From` Trait，`From` Trait 后续会详细介绍，这里只需要如果一个类型实现了`From`，那么就可以将另一种类型转换为当前类型。

例如，如果当前函数返回`Result<T, MyError>`，而某个表达式返回 `Result<T, std::io::Error>`，那么只要存在：

```rust
impl From<std::io::Error> for MyError
```

就可以使用 `?` 自动把 `std::io::Error` 转换成 `MyError`。

这也是自定义错误类型中经常实现 `From` 的原因。


## 5、?也可以用于 Option

`?` 不只用于 `Result`，也可以用于 `Option`。

对 `Option` 来说：

- 如果是 `Some(v)`，取出 `v`，继续执行
- 如果是 `None`，立即返回 `None`

示例：

```rust
fn first_elem(values: &[i32]) -> Option<&i32> {
    let value = values.get(0)?;

    Some(value)
}
```

再看一个从文本中取出第一行的最后一个字符的例子：

```rust
fn last_char_of_first_line(text: &str) -> Option<char> {
	text.lines().next()?.chars().last()
}
```

这里的逻辑是：

1. `text.lines().next()?` 获取第一行。
2. 如果没有第一行，直接返回 `None`。
3. 如果有第一行，就继续取这一行的最后一个字符。


# 五、Box\<dyn Error\>

## 1、多种错误类型的问题

实际开发中，一个函数可能遇到多种错误。

例如，从输入中读取多行数字时，可能发生两类错误：

- 读取文本时发生`std::io::Error`
- 解析整数时发生`std::num::ParseIntError`

示例：

```rust
use std::io::BufRead;  
  
fn read_numbers(reader: &mut dyn BufRead) -> Result<Vec<i64>, std::io::Error> {  
  
    let mut numbers: Vec<i64> = Vec::new();  
  
    for line_result in reader.lines() {  
        let line = line_result?;  
        let number = line.parse()?;  
        numbers.push(number);  
    }  
    Ok(numbers)  
}
```

编译报错：

![[Image 65.png|600]]

原因是：

`line_result?` 的错误类型是 `std::io::Error`。`line.parse()?` 的错误类型是 `std::num::ParseIntError`。

但函数返回类型是`Result<Vec<i64>, std::io::Error>`。因此`?` 可以传播 `io::Error`，却不能直接把 `ParseIntError` 当作 `std::io::Error`，因为 `std::io::Error` 没有实现`From<ParseIntError>`。


## 2、统一错误类型的基本思路

当一个函数可能产生多种错误时，需要把这些错误统一到一个返回类型中。

常见方式有三种：

| 方式      | 示例                   | 适合场景               |
| ------- | -------------------- | ------------------ |
| 通用错误类型  | `Box<dyn Error>`     | 应用程序、小工具、只需要向外报告错误 |
| 自定义错误类型 | `enum MyError`       | 库、业务程序、需要区分错误种类    |
| 第三方错误库  | `anyhow`、`thiserror` | 实际项目中减少样板代码        |

当前笔记重点理解标准库方式。

## 3、std::error::Error

在介绍 `Box<dyn Error>` 之前，需要先理解 `std::error::Error`。

**`std::error::Error`是标准库提供的错误公共接口，许多标准库错误类型都实现了这个Trait**。

例如：

- `std::io::Error`
- `std::num::ParseIntError`
- `std::str::Utf8Error`
- `std::fmt::Error`

一个类型实现了`std::error::Error`，通常表示它可以作为“错误类型”被统一处理。

`Error`Trait的作用主要有两个：

- 作为错误类型的公共接口，让不同错误类型可以被统一对待
- 支持错误链，通过`source()`表示当前错误背后的底层原因



## 4、使用Box\<dyn Error\>统一错误

`Box<dyn std::error::Error>`是[[13、特征对象|特征对象]]的一种形式，它表示：把某个实现了`Error`的具体错误类型放在堆上，然后通过`dyn Error`这个公共接口来使用它。

它常用来统一一个函数中可能出现的多种错误。

例如，改写前面的`read_numbers()`函数：

```rust
use std::io::BufRead;  
  
fn read_numbers(reader: &mut dyn BufRead) -> Result<Vec<i64>, Box<dyn Error>> {  
  
    let mut numbers: Vec<i64> = Vec::new();  
  
    for line_result in reader.lines() {  
        let line = line_result?;  
        let number = line.parse()?;  
        numbers.push(number);  
    }  
    Ok(numbers)  
}
```

此时，函数返回`Result<Vec<i64>, Box<dyn Error>>`，含义是：

- 成功时返回`Vec<i64>`
- 失败时返回某个实现`Error`的错误类型

使用 `Box<dyn Error>` 时，`?` 可以自动把很多具体错误转换成 `Box<dyn Error>`。这背后的关键仍然是 `From` 转换。只要具体错误类型实现了 `Error`，并满足必要的生命周期要求，就可以被装箱成 `Box<dyn Error>`。

可以简化理解为标准库提供了类似能力：

```rust
use std::error::Error;

impl<E> From<E> for Box <dyn Error>
where
	E: Error 
{
	fn from(error: E) -> Self {
		Box::new(error)
	}
}
```

# 六、自定义错误处理

## 1、自定义错误处理的适用场景

`Box<dyn Error>`可以快速统一处理多种错误类型，但它的缺点是错误语义不够明确。调用者只知道函数可能返回某种错误，但不容易从函数签名中看出具体可能失败在哪里。

如果希望错误类型更清晰、更容易匹配，就可以定义自己的错误类型。

自定义错误类型适合以下场景：

- 一个函数可能产生多种错误
- 调用者需要区分错误种类
- 错误需要携带业务上下文
- 当前 crate 是库，需要提供清晰稳定的错误 API
- 希望配合 `?` 自动转换底层错误


## 2、自定义错误枚举

Rust 中最常见的自定义错误形式是枚举。例如，读取数字时可能发生读取错误和解析错误，可以使用枚举将它们统一起来：

```rust
 enum ReadNumberError {  
	Io(std::io::Error),  
	Parse(std::num::ParseIntError),  
}
```

每个枚举变体表示一种错误来源：

| 变体                       | 表示的错误     |
| ------------------------ | --------- |
| `ReadNumberError::Io`    | 读取输入时发生错误 |
| `ReadNumberError::Parse` | 解析整数时发生错误 |
错误枚举的好处是：调用者可以用`match`精确处理不同错误。

```rust
match error {
	ReadNumberError::Io(error) => {
		eprintln!("读取失败：{error}");
	},
	ReadNumberError::Parse(error) => {
		eprintln!("数字格式失败：{error}");
	}
}
```

## 3、实现Debug

错误类型通常需要实现 `Debug`，通过`#[derive(Debug)]`派生宏自动实现。

```rust
#[derive(Debug)]
enum ReadNumberError {
    Io(std::io::Error),
    Parse(std::num::ParseIntError),
}
```

`Debug` 主要面向开发者，用于调试输出。

例如：

```rust
println!("{:?}", error);
```

实现 `std::error::Error` 时，错误类型也需要实现 `Debug`。

因此，自定义错误类型一般会先写`#[derive(Debug)]`。

## 4、实现Display

`Display`用于定义错误面向用户时如何显示。

```rust
use std::fmt::{Display, Formatter};  
#[derive(Debug)]  
enum ReadNumberError {  
    Io(std::io::Error),  
    Parse(std::num::ParseIntError),  
}  
  
impl Display for ReadNumberError {  
    fn fmt(&self, f: &mut Formatter<'_>) -> std::fmt::Result {  
        match self {  
            ReadNumberError::Io(error) => write!(f, "读取输入失败：{}", error),  
            ReadNumberError::Parse(error) => write!(f, "解析数字失败：{}", error),  
        }  
    }  
}
```

`Display` 的作用是控制：

```rust
println!("{}", error);
```


## 5、实现std::error::Error

自定义错误类型如果要接入 Rust 标准错误处理体系，还需要实现`std::error::Error`。

`Error` Trait 是标准库中的错误公共接口。它的简化定义可以理解为：

```rust
pub trait Error: Debug + Display {
	fn source(&self) -> Option<&dyn Error> {
		None
	}
}
```

这个简化定义说明了两点：

- 实现`Error`的类型，也需要实现`Debug`和`Display`
- `source()`默认返回`None`，表示当前错误没有更底层的错误来源

所以前面先实现 `Debug` 和 `Display`，不是偶然的。一个标准错误类型既要能给开发者调试，也要能给用户或上层代码显示错误信息。

`source()`是默认实现，因此一个类型实现`Error`，往往实现`Debug`和`Display`是必须的。

示例：

```rust
use std::fmt::{Display, Formatter};  
use std::error::Error;  
#[derive(Debug)]  
enum ReadNumberError {  
    Io(std::io::Error),  
    Parse(std::num::ParseIntError),  
}  
  
impl Display for ReadNumberError {  
    fn fmt(&self, f: &mut Formatter<'_>) -> std::fmt::Result {  
        match self {  
            ReadNumberError::Io(error) => write!(f, "读取输入失败：{}", error),  
            ReadNumberError::Parse(error) => write!(f, "解析数字失败：{}", error),  
        }  
    }  
}  
  
impl Error for ReadNumberError {}
```

这里的空实现是合法的，因为 `source()` 有默认实现。也就是说，如果不重写 `source()`，这个错误类型仍然是一个标准错误类型，只是它不会向外暴露底层错误来源。

实现 `Error` 后，`ReadNumberError` 就可以更好地融入 Rust 标准错误处理体系。例如，它可以被进一步转换成 `Box<dyn Error>`，也可以被上层代码通过 `dyn Error` 统一处理。

不过，当前这个实现还没有保留底层错误链。由于 `ReadNumberError::Io` 和 `ReadNumberError::Parse` 本身都包装了底层错误，更完整的写法通常会继续实现 `source()`。

## 6、实现source()保留底层错误

`std::error::Error`提供了`source()`方法，用于返回当前错误背后的底层原因。

例如`ReadNumberError::Io(io_error)`，当前错误是`ReadNumberError::Io`，底层原因是里面保存的`std::io::Error`。

如果希望上层代码能够继续访问这个底层错误，可以实现`source()`：

```rust
impl Error for ReadNumberError {  
    fn source(&self) -> Option<&(dyn Error + 'static)> {  
        match self {  
            ReadNumberError::Io(error) => Some(error),  
            ReadNumberError::Parse(error) => Some(error),  
        }  
    }  
}
```

`source()` 的返回类型是`Option<&(dyn Error + 'static)>`：

- `Some(error)`：当前错误有底层原因
- `None`：当前错误没有更底层的错误来源

有了`source()`，上层代码就可以逐层打印错误原因：

```rust
use std::error::Error;

fn print_error(mut error: &dyn Error) {
	eprintln!("error: {error}");
	
	while let Some(source) = error.source() {
		eprintln!("caused by: {source}");
		error = source;
	}
}
```

需要注意，`Display` 负责当前错误怎么显示，`source()` 负责保留底层错误来源。两者作用不同。

例如下面这种写法：

```rust
impl Display for ReadNumberError {
    fn fmt(&self, f: &mut Formatter<'_>) -> fmt::Result {
        match self {
            ReadNumberError::Io(_) => write!(f, "读取输入失败"),
            ReadNumberError::Parse(_) => write!(f, "解析数字失败"),
        }
    }
}
```

当前错误信息只显示“读取输入失败”或“解析数字失败”，底层的 `io::Error` 或 `ParseIntError` 交给 `source()` 保存。这样错误信息更有层次。

## 7、实现From支持?自动转换

自定义错误类型如果要配合`?`使用，通常还需要实现`From`。

前面的 `read_numbers()` 函数中有两处 `?`：

```rust
let line = line_result?;
let number = line.parse()?;
```

其中：

- `line_result?` 可能产生 `std::io::Error`
- `line.parse()?` 可能产生 `std::num::ParseIntError`

如果函数返回类型是：

```rust
Result<Vec<i64>, ReadNumberError>
```

那么 `?` 需要知道如何把 `std::io::Error` 和 `std::num::ParseIntError` 转换成 `ReadNumberError`。

这就需要实现 `From`。

让 `std::io::Error` 转换成 `ReadNumberError`：

```rust
impl From<std::io::Error> for ReadNumberError {
    fn from(error: std::io::Error) -> Self {
        Self::Io(error)
    }
}
```

让 `std::num::ParseIntError` 转换成 `ReadNumberError`：

```rust
impl From<std::num::ParseIntError> for ReadNumberError {
    fn from(error: std::num::ParseIntError) -> Self {
        Self::Parse(error)
    }
}
```

实现之后，下面的代码就可以正常使用`?`：

```rust
use std::io::BufRead;

fn read_numbers(reader: &mut dyn BufRead) -> Result<Vec<i64>, ReadNumberError> {
    let mut numbers = Vec::new();

    for line_result in reader.lines() {
        let line = line_result?;
        let number: i64 = line.parse()?;
        numbers.push(number);
    }

    Ok(numbers)
}
```

当 `line_result?` 遇到 `std::io::Error` 时，会自动调用：

```
ReadNumberError::from(error)
```

当 `line.parse()?` 遇到 `std::num::ParseIntError` 时，也会自动调用对应的 `from()`。

所以 `From` 的作用不是单独为了转换而转换，而是为了让 `?` 能把底层错误统一转换成当前函数声明的错误类型。


## 8、自定义错误类型的完整示例

```rust
use std::fmt::{Display, Formatter};  
use std::error::Error;  
use std::io::BufRead;  
#[derive(Debug)]  
enum ReadNumberError {  
    Io(std::io::Error),  
    Parse(std::num::ParseIntError),  
}  
  
impl Display for ReadNumberError {  
    fn fmt(&self, f: &mut Formatter<'_>) -> std::fmt::Result {  
        match self {  
            ReadNumberError::Io(_) => write!(f, "读取输入失败"),  
            ReadNumberError::Parse(_) => write!(f, "解析数字失败"),  
        }  
    }  
}  
  
impl Error for ReadNumberError {  
    fn source(&self) -> Option<&(dyn Error + 'static)> {  
        match self {  
            ReadNumberError::Io(error) => Some(error),  
            ReadNumberError::Parse(error) => Some(error),  
        }  
    }  
}  
  
impl From<std::io::Error> for ReadNumberError {  
    fn from(value: std::io::Error) -> Self {  
        Self::Io(value)  
    }  
}  
  
impl From<std::num::ParseIntError> for ReadNumberError {  
    fn from(value: std::num::ParseIntError) -> Self {  
        Self::Parse(value)  
    }  
}  
  
  
fn print_error(mut error: &dyn Error) {  
    eprintln!("{}", error);  
    while let Some(source) = error.source() {  
        eprintln!("caused by: {}", source);  
        error = source;  
    }  
}  
  
  
fn read_numbers(reader: &mut dyn BufRead) -> Result<Vec<i64>, ReadNumberError> {  
    let mut numbers = Vec::new();  
  
    for line_result in reader.lines() {  
        let line = line_result?;  
        let number = line.parse::<i64>()?;  
        numbers.push(number);  
    }  
  
    Ok(numbers)  
}  
  
fn main() {  
      
    let stdin = std::io::stdin();  
    let mut reader = stdin.lock();  
  
    match read_numbers(&mut reader) {  
        Ok(numbers) => println!("{numbers:?}"),  
        Err(error ) => {  
            print_error(&error);  
        }  
    }  
}
```

# 七、Result类型别名

在标准库和实际项目中，常常会给`Result`定义类型别名，避免重复书写错误类型。

例如，标准库的`std::io`模块中有类似定义：

```rust
pub type Result<T> = std::result::Result<T, std::io::Error>;
```

因此，`std::io::Result<String>`等价于`Result<String, std::io::Error`。

使用时，常见写法如下：

```rust
use std::fs::File;
use std::io;

fn open_file() -> io::Result<File> {
	File::open("hello.txt")
}
```

这里的 `io::Result<File>` 表示`Result<File, io::Error>`。

项目中也可以为自己的错误类型定义别名。

例如：

```rust
type AppResult<T> = Result<T, AppError>;
```

然后函数可以写成：

```rust
fn load_config() -> AppResult<T> {
	// ...
}
```


# 八、main函数中的错误处理

## 1、在main中使用`expect`

小程序或示例代码中，可以直接使用`expect()`：


```rust
use std::fs;

fn main() {
    let content = fs::read_to_string("hello.txt").expect("读取 hello.txt 失败");

    println!("{content}");
}
```

这种写法简单，但错误发生时会直接 `panic`。

适合示例、测试、临时脚本，不适合需要精细错误处理的程序。

## 2、让main返回Result

`main` 是程序入口。它既可以直接处理错误，也可以返回 `Result`。

更常见的方式是让 `main` 返回 `Result`，这样就可以在 `main` 中使用 `?`。

```rust
use std::error::Error;
use std::fs;

fn main() -> Result<(), Box<dyn Error>> {
    let content = fs::read_to_string("hello.txt")?;

    println!("{content}");

    Ok(())
}
```

这种写法比到处写 `expect()` 更整洁，适合稍复杂的程序。

如果 `main` 返回 `Err`，Rust 会打印错误并以失败状态退出

这里使用 `Box<dyn Error>`，表示 `main` 可以返回多种实现了 `Error` 的错误类型


## 3、使用 `run()` 函数组织程序

命令行程序中常见结构是：真正逻辑写在 `run()` 中，`main()` 只负责统一处理错误和退出码。

```rust
use std::io;  
use std::fs;  
use std::process;  
  
fn main() {  
    if let Err(error) = run() {  
        eprintln!("{}", error);  
        process::exit(1);  
    }  
}  
  
fn run() -> io::Result<()> {  
  
    let content = fs::read_to_string("hello.txt")?;  
  
    println!("{content}");  
  
    Ok(())  
}
```

这种结构有几个好处：

- 核心逻辑可以使用 `?`
- `main` 统一打印错误
- 可以明确控制退出码
- 程序结构更清楚

`run()` 的返回类型可以根据程序复杂度选择。如果程序只涉及 I/O 错误，可以返回 `io::Result<()>`；如果可能产生多种错误，可以返回 `Result<(), Box<dyn Error>>` 或自定义错误类型。

```rust
fn run() -> Result<(), Box<dyn Error>> {  
	// ...  
	Ok(())  
}
```

对于更复杂的程序，也可以定义自己的应用错误类型：

```rust
fn run() -> Result<(), AppError> {
    // ...
    Ok(())
}
```

这种结构能让核心逻辑保持清晰，让入口函数统一处理最终错误。
