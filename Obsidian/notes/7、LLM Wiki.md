# 一、LLM Wiki 的基本概念

LLM Wiki 是一种用大语言模型维护个人知识库的模式：人负责收集材料、提出问题和判断方向，LLM 负责把材料整理成持续演化的 Markdown Wiki。

它解决的不是“如何临时问一堆文件一个问题”，而是“如何让知识在每次阅读、提问和整理之后都沉淀下来”。在这个模式里，Wiki 不是聊天记录的附属品，而是一个长期存在、可复利增长的知识工件。

简单来说，[[Obsidian/notes/1、Obsidian入门|Obsidian]] 是阅读和浏览层，LLM 是维护者，Markdown 文件系统是知识库本体。人和 AI 的协作关系更接近“产品负责人 + 工程师”：

- **人**：决定读什么、问什么、保留什么、如何判断价值。
- **LLM**：总结、归类、补链接、更新旧页面、发现矛盾和维护索引。
- **Wiki**：承载已经整理过的知识，而不是每次查询时重新拼装的临时答案。

> 关键转变：从“查询时临时检索”转向“平时持续编译”。前者每次都从原始材料重新开始，后者把每次处理结果沉淀为下一次可复用的知识层。

# 二、和传统 RAG 的区别

## 1、传统 RAG 的工作方式

传统 RAG 通常把文档切块、建立索引，然后在用户提问时检索相关片段，再交给 LLM 生成答案。这种方式适合快速问答，但它有一个明显限制：知识主要存在于原始文档和索引里，不会自动形成一套稳定的中间层。

当一个问题需要综合多篇文章、多次查询和长期积累时，RAG 往往会反复做同一件事：搜索、读取、拼接、总结。答案可能当下可用，但如果没有写回知识库，下次仍然要重新来过。

![[assets/llm-wiki-traditional-rag-handdrawn.png|600]]

## 2、LLM Wiki 的工作方式

LLM Wiki 会在原始材料和最终问答之间增加一层“编译后的 Wiki”。每次加入新材料时，LLM 不只是把它放进索引，而是把它吸收到已有知识结构里：

- 新文章会生成摘要页。
- 新概念会补充到概念页。
- 新人物、工具、组织会进入实体页。
- 与旧说法冲突的内容会被标记或修正。
- ...

此外，用户提问时，高价值的查询结果还可以反向沉淀为新的分析页。

这样，Wiki 会随着材料和问题逐步变厚，而不是只在聊天窗口里短暂出现答案。

![[assets/llm-wiki-workflow-handdrawn.png|600]]

## 3、两者的核心差异

| 维度   | 传统 RAG      | LLM Wiki            |
| ---- | ----------- | ------------------- |
| 知识形态 | 原始文档 + 检索索引 | 原始文档 + 持久 Wiki      |
| 处理时机 | 查询时临时拼装     | 摄取时持续整理             |
| 结果沉淀 | 通常停留在聊天中    | 写回 Markdown 页面      |
| 维护重点 | 检索相关片段      | 维护页面、链接、矛盾和索引       |
| 适合场景 | 快速问答、大量文件检索 | 长期研究、个人知识积累、主题 Wiki |

需要注意的是，LLM Wiki 并不排斥搜索或 RAG。随着 Wiki 规模变大，仍然可以使用全文搜索、BM25、向量检索或本地搜索工具。区别在于：检索对象不再是原始材料，而是已经被整理过的 Wiki 页面。

# 三、三层架构

LLM Wiki 的基础架构可以拆成三层：原始资料、Wiki 和 Schema。三层分离之后，知识库的边界会清楚很多。

![[assets/llm-wiki-three-layer-architecture-handdrawn.png|600]]

## 1、Raw Sources：原始资料层

原始资料层保存文章、论文、网页剪藏、视频字幕、图片和数据文件。它是知识库的**来源层**，通常只读，不在整理时直接改写。

这层的重点是“保留证据”。例如网页可以通过 [[Obsidian/notes/4、Obsidian Web Clipper|Obsidian Web Clipper]] 保存为 Markdown，B 站视频可以通过 [[Obsidian/notes/5、Bilibili Obsidian Clipper|Bilibili Obsidian Clipper]] 保存字幕、简介和链接。后续即使 Wiki 页面被更新，也能回到原始材料检查依据。

## 2、Wiki：编译输出层

Wiki 是 LLM 负责生成和维护的 Markdown 页面集合。它不是原始资料的堆放区，而是经过提炼后的知识层。

常见页面类型包括：

- **summary**：单篇来源材料的摘要。
- **entity**：人物、组织、产品、框架等实体页。
- **concept**：概念、方法、理论页。
- **comparison**：对比分析页。
- **overview**：领域总览页。
- **synthesis**：综合判断或阶段性结论。
- **recipe**：可复用流程和操作配方。

Wiki 层适合大量使用 [[Obsidian/notes/2、Obsidian 扩展语法|Obsidian 扩展语法]]，尤其是维基链接、属性、标签、嵌入和 Callout。链接越稳定，LLM 后续维护时越容易理解知识之间的关系。

## 3、Schema：维护规则层

Schema 是写给 LLM 的操作规则，可以是 `AGENTS.md`、`CLAUDE.md` 或其他项目说明文件。它规定目录结构、页面格式、命名规范、摄取流程、查询流程和维护边界。

Schema 的价值在于把 LLM 从“泛泛聊天助手”约束成“这个知识库的维护者”。没有 Schema 时，LLM 容易每次按自己的习惯整理；有 Schema 后，它会按同一套文件结构、标题格式和日志规则持续工作。

一个最小结构可以长这样：

```text
my-llm-wiki/
├── schema.md
├── raw/
│   ├── articles/
│   ├── papers/
│   └── videos/
└── wiki/
    ├── index.md
    ├── log.md
    ├── summaries/
    ├── entities/
    ├── concepts/
    └── syntheses/
```

这里的 `schema.md` 负责单个主题知识库的维护规则，`raw/` 保存不可变的原始材料。`wiki/`沉淀提炼的知识。

# 四、三类核心操作

## 1、Ingest：摄取新材料

Ingest 是把新材料从 raw 层吸收到 wiki 层的过程。它不是简单总结，而是一次结构化维护。

![[assets/llm-wiki-ingest-operation-handdrawn.png|600]]

一次完整摄取通常包括：

1. 读取原始材料。
2. 提炼关键观点、事实和方法。
3. 创建或更新摘要页。
4. 更新相关概念页、实体页和综合页。
5. 补充交叉引用。
6. 更新 `index.md`。
7. 追加 `log.md`。

单篇材料可能会影响多个页面。例如一篇关于 LLM Wiki 的文章，既会生成来源摘要，也可能更新“知识库架构”“Obsidian 工作流”“AI Agent 协作方式”等页面。

> 注意：Ingest 的目标不是把来源全文改写一遍，而是把新增知识放到已有结构中。真正有价值的是“整合进网络”，不是“多一篇摘要”。

## 2、Query：基于 Wiki 查询

Query 是向已经整理过的 Wiki 提问。LLM 应先读索引，再定位相关页面，最后综合回答，并在回答里带上引用。

高质量 Query 的关键是：好答案不要只留在聊天里。如果一次查询产出了有长期价值的对比表、判断框架、路线图或问题清单，就应该写回 Wiki，成为新的页面或更新到已有页面。

这样，问题本身也会推动知识库成长。读材料带来增长，提问题同样带来增长。

![[assets/llm-wiki-query-operation-handdrawn.png|600]]

## 3、Lint：健康检查

Lint 是对 Wiki 做维护体检。随着页面变多，知识库会出现一些自然损耗：

![[assets/llm-wiki-lint-operation-handdrawn.png|600]]

- 页面之间说法不一致。
- 旧结论被新材料推翻但没有更新。
- 某些页面没有入链，变成孤立页。
- 重要概念反复出现，却没有自己的页面。
- 索引漏掉新页面。
- 标签和属性命名不统一。

定期 Lint 可以让知识库保持可导航、可追溯和可增长。它相当于给 Wiki 做一次代码审查，只不过审查对象是知识结构。

# 五、索引和日志

## 1、index.md：内容导航

`index.md` 是面向内容的目录。它列出 Wiki 里的页面、分类和一句话摘要，帮助人和 LLM 快速定位相关知识。

在小到中等规模的知识库里，一个维护良好的索引常常比复杂检索系统更好用。LLM 可以先读索引，判断该看哪些页面，而不是一上来就全库搜索。

一个实用的索引条目通常包含：

- 页面链接。
- 页面类型。
- 一句话摘要。
- 可选的来源数、更新时间或状态。

## 2、log.md：演化时间线

`log.md` 是按时间追加的操作记录，记录每次 ingest、query 和 lint 做了什么。它不是内容目录，而是知识库的演化时间线。

日志的价值有三点：

- **追踪变化**：知道最近处理过哪些材料和问题。
- **恢复上下文**：LLM 可以快速了解近期工作，而不用重新读完整仓库。
- **形成审计线索**：当页面发生变化时，可以追溯它来自哪次操作。

日志条目最好使用稳定格式，例如：

```markdown
## [2026-07-13] ingest | LLM Wiki

- 创建: `[[Rust 基础语法]]`, `[[变量与可变性]]`, `[[常量与静态变量]]`, `[[数据类型]]`, `[[控制流]]`, `[[函数]]`, `[[注释]]`
- 类型: articles
- 来源: `raw/articles/Rust基础语法.md`
```

# 六、工具链与实践方式

## 1、Obsidian 适合做阅读层

Obsidian 的优势在于它直接读写本地 Markdown，又提供图谱、反向链接、属性、搜索和插件系统。LLM Wiki 可以把 Obsidian 当作知识库 IDE：LLM 在文件层维护内容，人用 Obsidian 阅读、检查和导航。

这也是为什么 [[Obsidian/notes/3、Obsidian 插件|Obsidian 插件]] 很重要。Web Clipper、搜索、图谱、属性、Bases、Dataview、Canvas、Marp 等能力，都可以围绕 Wiki 工作流扩展出来。

## 2、CLI 适合做 Agent 操作入口

当 AI Agent 要和 Obsidian 仓库协作时，[[Obsidian/notes/6、Obsidian CLI|Obsidian CLI]] 可以提供比普通文件读写更语义化的操作入口，例如读取笔记、搜索仓库、查看反向链接、管理属性和调用模板。

普通 shell 更适合处理纯文本层面的批量操作；Obsidian CLI 更适合承接“这是一个 Obsidian 仓库”的应用语义。两者可以配合使用，但要清楚谁负责什么。

## 3、CLI 搜索工具适合处理中大型 Wiki

在小规模知识库里，`wiki/index.md` 往往已经够用：LLM 先读索引，再进入相关页面。但当 Wiki 页面越来越多，单靠索引会逐渐变慢，也容易漏掉正文里细碎但重要的线索。

这时可以为 Wiki 增加本地搜索工具。一个典型选择是 [qmd](https://github.com/tobi/qmd)：它面向 Markdown 文件，支持本地搜索、混合 BM25/向量检索和 LLM 重排序。它既可以作为 CLI 被 LLM 调用，也可以通过 MCP 服务器变成更原生的工具入口。

这个思路的重点不是必须使用某个固定工具，而是让 LLM 拥有更稳定的“查找相关页面”能力：

- **小规模**：优先读 `index.md`，成本低、上下文清楚。
- **中大型规模**：使用搜索 CLI 或 MCP，从标题、正文、标签和目录里找候选页面。
- **特殊需求**：可以让 LLM 临时写一个朴素搜索脚本，例如按关键词、路径、frontmatter 或最近更新时间过滤。

> 注意：搜索工具只是导航增强，不应该替代 Wiki 层本身。LLM Wiki 的核心仍然是把知识整理成可复用页面，而不是把所有问题都退回到原始材料检索。

## 4、Git 适合做版本历史

LLM Wiki 本质上是一组 Markdown 文件，所以天然适合放进 Git。Git 可以记录每次摄取、查询归档和健康检查带来的变化，也方便回滚或比较不同阶段的知识结构。

对长期知识库来说，版本历史非常重要。它让“知识如何变成现在这样”这件事可以被追溯，而不是只看到最终页面。

# 七、适用场景与边界

## 1、适用场景

LLM Wiki 适合任何需要长期积累、反复更新和跨材料综合的主题：

- **个人成长**：健康、心理、自我观察、习惯和目标复盘。
- **深度研究**：围绕一个主题持续读论文、报告和文章。
- **读书笔记**：为一本书建立人物、地点、主题和情节关系 Wiki。
- **团队知识库**：会议记录、客户访谈、项目文档和内部决策沉淀。
- **竞品分析**：持续跟踪产品、公司、功能和市场变化。
- **课程学习**：把课程、作业、案例和延伸资料组织成可复习网络。

这些场景的共同点是：单次总结不够，知识会持续增长，而且新材料经常需要改写旧理解。

## 2、不适合的场景

LLM Wiki 不是所有知识管理问题的默认答案。下面几类场景可能不值得搭完整 Wiki：

- 只需要临时问答，不打算长期沉淀。
- 资料量很少，普通笔记已经够用。
- 来源高度敏感，无法接受 LLM 读取。
- 主题变化太快，但没有时间维护来源和规则。
- 只想保存原文，不需要提炼、关联和综合。

如果目标只是快速剪藏网页，先用 [[Obsidian/notes/4、Obsidian Web Clipper|Web Clipper]] 保存来源就足够。只有当材料开始积累，并且需要长期整理、对比和追踪时，LLM Wiki 的价值才会明显。

# 八、实践建议

## 1、先小规模跑通

不要一开始就设计复杂系统。可以先选一个主题，准备十几篇材料，建立最小目录结构，然后让 LLM 按三类操作工作：

- 新材料进入 raw。
- 整理结果写入 wiki。
- 每次操作记录到 log。

等流程跑顺之后，再决定是否加入搜索工具、Dataview、Bases、Canvas 或自动化脚本。

## 2、把规则写进 Schema

凡是希望 LLM 稳定遵守的规则，都应该写入 Schema，而不是只在聊天里临时说明。包括：

- 文件夹结构。
- 页面分类。
- frontmatter 字段。
- 命名规则。
- 链接规则。
- ingest、query、lint 的步骤。
- 哪些目录只读，哪些目录可以修改。

Schema 会随着使用不断演化。好的 Schema 不是一次写完的，而是在真实维护中逐步变得具体。

## 3、人要保留判断权

LLM 可以做大量整理工作，但不应该替代人的判断。人仍然要决定哪些来源重要、哪些结论可信、哪些问题值得继续追。

更稳妥的协作方式是：让 LLM 承担繁琐维护，让人负责方向和判断。这样既能降低维护成本，也能避免知识库变成自动生成但无人真正理解的文本堆。

# 九、小结

LLM Wiki 的核心是把知识管理从“存文件 + 临时问答”升级为“持续编译的个人 Wiki”。原始材料保留证据，Wiki 承载整理后的知识，Schema 约束 LLM 的维护方式，index 和 log 则让知识库可导航、可追踪。

它特别适合与 Obsidian 配合：[[Obsidian/notes/2、Obsidian 扩展语法|扩展语法]] 提供链接和属性，[[Obsidian/notes/4、Obsidian Web Clipper|Web Clipper]] 和 [[Obsidian/notes/5、Bilibili Obsidian Clipper|Bilibili Clipper]] 负责收集材料，[[Obsidian/notes/6、Obsidian CLI|Obsidian CLI]] 帮助 AI Agent 操作仓库。组合起来，就形成了一套“人负责思考，AI 负责维护”的长期知识工作流。
