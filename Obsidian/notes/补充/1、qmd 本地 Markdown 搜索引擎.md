# 一、qmd 解决什么问题

qmd（Query Markup Documents）是面向 Markdown 文档的本地搜索引擎。它把一个或多个文档目录组织为 collection，然后提供关键词搜索、向量语义搜索、混合检索和文档回读能力。索引、向量和模型推理都可以留在本机，适合个人笔记、技术文档和 LLM 维护的 wiki。

[[llm-wiki-zh-CN|LLM Wiki 中文规范]] 并没有把 qmd 当成知识库的必选基础设施，而是把它放在“wiki 增长后的可选 CLI 工具”这个位置：

- 中小规模时，先读 `index.md` 定位页面，通常已经足够。
- 页面数量增长、人工扫描索引开始低效时，再用 qmd 缩小候选集。
- qmd 只负责“找到可能相关的文档”，最终回答仍要回读原页面、综合内容并标注引用。

> qmd 是检索层，不是知识库本身，也不是替代 `index.md` 的自动问答系统。

# 二、基本心智模型

## 1、从目录到候选文档

qmd 的流程要分成两个阶段看：**检索前的入库准备**和**针对问题的实际检索**。前者是对文档集合建立和维护索引，后者才会在用户提出问题时发生。

![[qmd-本地检索工作流手绘.png|600]]

### （1）检索前：收集与入库

1. **收集（collection）**：把目录注册为有名 collection，并指定匹配规则。它只定义“哪些文件属于这个可搜索集合”，不会回答任何问题，也不会立即建立可搜索内容。
2. **文本索引（`qmd update`）**：扫描 collection 中的文件和增量变更，建立 BM25 全文索引。这是“让关键词可搜”的入库步骤，文档新增、删除或修改后需要再运行。
3. **向量索引（`qmd embed`）**：将文档切成文本块并计算 embedding。这是“让语义可搜”的入库步骤；它可选但是 `vsearch` 和完整混合 `query` 的前提。

### （2）实际检索：根据问题产生候选

4. **检索（`search` / `vsearch` / `query`）**：这一步才是针对用户问题的实际检索。
   - `qmd search`：查 BM25 文本索引，为关键词和精确短语找候选文档。
   - `qmd vsearch`：查向量索引，为自然语言概念找语义接近的文本块。
   - `qmd query`：同时使用 BM25 和向量候选，经 RRF 融合与本地模型重排后给出结果。
5. **回读（`get` / `multi-get`）**：它不负责排名或发现新候选。它是在检索结果已经出来后，按 docid 或路径取回 1–5 篇高相关原文（或定位行区间），供 LLM 核对、综合和引用。

> 一句话记忆：`collection` 定义语料范围，`update` 和 `embed` 是建立可检索索引，`search` / `vsearch` / `query` 是实际搜索，`get` / `multi-get` 是为答案回取证据。

### （3）为什么要分开

如果文档修改后没有运行 `qmd update`，`search` 可能查不到新内容；如果只运行了 `update` 而没有运行 `embed`，BM25 仍可用，但基于向量的语义召回不完整。两者都就绪后，`query` 才能发挥它的混合检索能力。

## 2、三种检索方式

| 命令            | 基本原理                          | 适用问题                | 主要代价                  |
| ------------- | ----------------------------- | ------------------- | --------------------- |
| `qmd search`  | BM25 关键词全文检索                  | 页面标题、专有名词、代码符号、确切短语 | 不擅长跨表述方式的语义匹配         |
| `qmd vsearch` | 查询扩展 + 文本块向量相似度                | 自然语言描述的概念、同义改写      | qmd 2.5.3 需 generation 模型扩展问题、embedding 模型向量化问题与文档；不需 reranker |
| `qmd query`   | BM25 + 向量候选 + RRF 融合 + LLM 重排 | 语义复杂、需要高质量排序的问题     | 需 embedding 模型 + reranker；裸自然语言 query 通常还需查询扩展模型 |

BM25 关心“查询词是否出现在文档中，以及这些词的区分度”；向量搜索关心“查询与文本块的语义是否接近”。`qmd query` 把多路候选用 Reciprocal Rank Fusion（RRF）融合，再用重排模型优化最终顺序。

## 3、结构化 query 比“把问题原样丢进去”更稳定

`qmd query "用户的原始问题"` 属于裸 query，会调用本地查询扩展模型，自动生成多路查询。这种写法简单，但 Agent 通常掌握更多上下文，更好的做法是自己编写结构化查询：

- `intent:`：说明要找什么、应排除什么，仅用于消歧和排序。
- `lex:`：填写标题、别名、罕见词和精确短语，走 BM25。
- `vec:`：用接近原页面的自然语言表达目标概念。
- `hyde:`：写一小段“理想文档或答案可能怎么说”，再用这段文本去找语义相近的内容。

```zsh
qmd query -c knowledge-rust -n 10 --json --explain $'intent: 查找 Rust 中共享可变状态的安全设计，排除只讲普通所有权移动的页面\nlex: Arc Mutex RwLock 共享可变状态\nvec: 如何在多线程间安全共享并修改同一份数据\nhyde: 通过 Arc 共享所有权，并用 Mutex 或 RwLock 保证同一时刻的可变访问受到同步约束。'
```

`--explain` 适合调试为什么某些结果排在前面；稳定后可去掉它。精确标题或罕见词检索则不必启动整套混合流水线，直接使用 `qmd search` 通常更快。


# 三、常用决策和命令配方

## 1、如何选择搜索模式

| 已知信息               | 首选方式                        | 原因                          |
| ------------------ | --------------------------- | --------------------------- |
| 知道页面标题或罕见专有名词      | `qmd search`                | BM25 更快，精确匹配不需要 LLM         |
| 只知道“意思”，不知道原文用词    | `qmd vsearch`                 | 语义候选召回，不启动 BM25 融合与 reranker      |
| 同时掌握精确术语与概念描述，并需消歧 | 结构化 `qmd query`             | 结合词汇锚点、语义召回、融合与重排            |
| 希望优先速度、本地模型不可用     | `qmd search`                | 不依赖 embedding 与重排模型         |
| 多个 collection 同时搜索 | 分 collection 检索后合并，或提高 `-n` | 全局 Top-K 可能被大 collection 占满 |
| 需要回答事实、引用原文        | 搜索后 `get` / `multi-get`     | 摘要片段只是线索，不足以支撑细节结论          |

## 2、提高查准率

- 用 `-c` 限定 collection，不要无条件搜全库。
- 在 `lex:` 中放标题、别名、代码符号和罕见词。
- 精确短语可用引号，不想要的词可用负号排除，例如 `lex: "machine learning" -"deep learning"`。
- 有歧义时添加 `intent:`，同时写明目标与排除项。
- 调试时使用 `--json --explain`，观察各检索路径与重排得分。
- 结果过多时可使用 `--min-score`，但阈值应通过实际查询校准，不应盲目固定。

## 3、提高召回率

- 在 `lex:` 中补充中英文同义词、缩写、旧名与新名。
- 在 `vec:` 中改写问题，尽量接近知识页面会使用的陈述方式。
- 难以用短句表达时增加 `hyde:`，但要把它当成“检索假设”，不能当成已被知识库验证的事实。
- 多领域查询时，先分别检索每个 collection，避免大 collection 将小 collection 的结果挤出 Top-K。
- 首轮失败后改写查询，并用该领域 `wiki/index.md` 兜底，不要只是不断增大 `-n`。
