
## 启动什么——以macOS平台为例

hello 不是一个能自己弹出窗口的桌面程序。它被构建成了`libapp.dylib`，本质上是一块“可被其他程序加载的应用代码”。真正运行的是桌面宿主`uipreviewer`。

![[assets/Pasted image 20260728151046.png|600]]

> **最重要的边界：** previewer 是“运行应用的壳”，hello dylib 是“被装进壳里的内容”。因此看到 previewer 窗口，不等于 hello 已经成功启动。


## 三个入口，各管一层

`main()`  进程入口：

操作系统启动 `uipreviewer` 后，首先进入 `src/main.rs`。它不负责创建 hello UI，只根据当前编译平台 选择 macOS、Windows 或 Linux 实现。

`platform_mac::run()` 平台入口：

它负责 macOS 上的启动总流程：识别 `--native`、准备运行环境、启动 UI 线程和服务、创建事件循环，并进入 macOS 窗口生命周期。

`app_start_main()` 应用入口：

它在 hello 的 `libapp.dylib` 里面。previewer 加载 dylib、找到这个符号并在 UI 线程调用它之后，hello 才开始创建和挂载自己的页面。

> **启动责任链：**`main()` 选平台 → `platform_mac::run()` 搭好舞台 → `app_start_main()` 把 hello UI 放到舞台上。


## 五个必要概念

### `--native` 启动模式开关

告诉 previewer：“这次不要走系统 launcher 路径，要加载一个 Rust 应用动态库。”

### `UIPREVIEWER_DYLIB_APP_APTH`应用地址

要加载的 app dylib 位置。macOS hello 通常指向 dist/libs/local/libapp.dylib

### `UI thread`操作 UI 的专用线程

hello 的响应式状态和  UI runtime 归这个线程管理。所以 previewer 不能在任意后台线程直接调用 `app_start_main`， 而要把任务投递到 UI 线程。

### `event loop`窗口值班循环

窗口创建后，程序不能立即退出。事件循环持续等待鼠标、键盘、窗口缩放和 redraw 请求，并把这些事件交给对应处理逻辑。


### `render surface`真正承接像素的画布

只有操作系统窗口还不够，还要准备可绘制的图形表面。 hello 挂载的是 UI 内容，render surface 负责让这些内容最后变成屏幕像素。

## 为什么 native app 还会启动 PMS/AMS/IMS

这是 previewer 在桌面上模拟的 BlueOS 基础服务：

- PMS：包管理服务，参与当前 previewer 的统一环境初始化和 ready 条件
- AMS：应用管理服务，提供显示配置，并与 PMS 一起形成“系统已准备好”的门槛
- IMS：输入管理服务，把鼠标、触摸和按键转换成应用可接收的输入事件

> **不要误解为 native app 由 AMS 启动。** `--native` 跳过了 AMS 的 `startApp` 路径， 由 previewer 直接加载 dylib；但当前 macOS 实现仍启动这些共享服务， 并等待 AMS/PMS ready 后才投递 `app_start_main`。


现在更像是一个临时过渡方案启动：

环境变量给出 dylib 路径

 ->  previewer 直接 dlopen
 -> 查找 app_start_main
 -> 在 UI 线程中调用

它绕过了应用安装、包查询和生命周期管理，更像 previewer bring-up 阶段的直接加载通道，而不是完整的 BlueOS 原生应用管理方案。

> 当前 PMS/AMS 不是 Rust app 的启动管理者，而是从原 JS 应用启动框架继承下来的启动脚手架。

但它们现在还不是完全“零作用”：

- PMS/AMS ready 被当成系统初始化完成的门槛。
- AMS 还接收显示尺寸和折叠状态配置。
- 当前代码必须等两者 ready，才会投递 `app_start_main`。
- IMS 仍然真正负责鼠标、触摸和按键输入。

所以 PMS 最接近“形式上存在”；AMS还承担少量环境配置，但两者都没有发挥原本的应用管理核心职责。
