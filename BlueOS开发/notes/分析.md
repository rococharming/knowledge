## native 应用工程

```
examples/hello
├── build.config.js
├── Cargo.toml         
└── src
    ├── App.rs
    ├── CMakeLists.txt
    ├── manifest.json
    └── pages
        └── home
            └── index.ux
```

目录分为三层：

- jax 构建入口
- Rust cdylib 入口
- 页面/manifest 资源

- `Cargo.toml`：定义 Rust 产物。关键：

```toml
[lib]
name = "app"
crate-type = ["cdylib"]
path = "src/App.rs"
```

意思是把 `src/App.rs` 编译成动态库，最终类似 macOS 上的 `libapp.dylib`。它自己不直接声明 `system_framework` 依赖，而是交给 jax/CMake 注入，避免和 ui-previewer 链接出的 `system_framework.dylib` hash 不一致。

`build.config.js`：jax 的构建配置。它告诉 jax：native 构建入口在 `./src/CMakeLists.txt`，ABI 默认用 `local`。所以执行 `jax buildndk` 时，会从这里找到 CMake 工程。

`src/CMakeLists.txt`：native 动态库的 CMake 描述。核心作用是：

```
blueos_add_library(app SHARED)
blueos_link_rustdylib(app PRIVATE system_framework)
```

也就是构建一个名叫 `app` 的 shared library，并声明它依赖 `system_framework`。jax 会据此给 rustc 注入 `--extern system_framework=...`、`-Lnative` 等参数。

`src/App.rs`：真正的 native 应用入口。

```rust
#[unsafe(no_mangle)]
pub extern "C" fn app_start_main() -> i32
```

`ui-previewer --native` 加载 `libapp.dylib` 后，就会找这个符号并调用它。然后 `App.rs` 里会用：

```rust
ux!("src/pages/home/index.ux")
```

把 `.ux` 页面编译成组件树，再 `mount_with_resolver`，最后 `attach_to_app_window` 挂到 ui-previewer 当前窗口里。

`src/manifest.json`：应用清单。里面有包名、版本、router、display 等信息：

```
"package": "com.application.hello",
"isNativeApp": true,
"router": {
  "entry": "home"
}
```

但在当前 `--native` 路径里，它不是像普通 `--app` 那样被 PMS 注册后由 AMS 启动；它更多是保留应用元信息和页面结构约定。

`examples/hello` 里的作用主要是：

1. 读取 `build.config.js`
2. 找到 `src/CMakeLists.txt`
3. 调 CMake/Ninja 和 Rust 工具链
4. 编译 `src/App.rs`
5. 链接 `system_framework.dylib`
6. 产出 `dist/libs/local/libapp.dylib`
