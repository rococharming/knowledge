# 一、HTTP基础概述

## 1、HTTP基本概念

`HTTP`，全称 Hyper Text Transfer Protocol，即超文本传输协议。

它是一个**应用层协议**，用于客户端与服务器之间传输资源。

`HTTP`最初服务于万维网，浏览器向 Web 服务器请求网页资源，服务器返回 HTML 页面、图片、CSS、JavaScript 等内容。

资源类型包括：

- 网页资源：HTML、CSS、JavaScript
- 媒体资源：图片，音频、视频
- 数据资源：JSON、XML、API接口返回结果
- 文件资源：文档、压缩包、下载文件

现代应用中，HTTP的使用范围已经远远不止网页浏览，常见场景包括：

- 前后端接口通信
- 移动端与服务端通信
- 第三方API调用
- 微服务间通信
- 爬虫抓取网页
- AI服务接口调用

`HTTP`是现代Web开发的最基础、最常用的网络通信协议之一。


## 2、HTTP核心作用

**HTTP的核心作用，是让客户端与服务器能够按照统一格式交换数据**

典型交互：

```text
浏览器 / 客户端                         Web 服务器
     │                                      │
     │  发送 HTTP 请求                      │
     │ ───────────────────────────────────▶ │
     │                                      │
     │  返回 HTTP 响应                      │
     │ ◀─────────────────────────────────── │
     │                                      │
     │  浏览器解析响应内容并展示页面              │
```

HTTP规范定义：

- 请求应该长什么样
- 响应应该长什么样
- 用什么方法表达操作意图
- 用什么状态码表达处理结果
- 如何通过 Header 携带附加信息
- 如何通过 Body 传输具体数据

> HTTP 本质上是一套客户端和服务器之间交换信息的约定。


## 3、HTTP 应用场景

`HTTP`在前端、后端、移动端、云服务和 AI 服务中都很常见。

前端常见场景：

- 页面加载
- 接口请求
- Cookie 管理
- 跨域处理
- 缓存控制
- DevTools Network分析

后端常见场景：

- 编写API接口
- 处理请求参数
- 返回JSON数据
- 设置状态码
- 做登录认证
- 部署到 Nginx、网关、负载均衡器后面

其他常见场景；

- 移动端App请求后端接口
- 爬虫抓取网页内容
- 第三方平台开放API
- 微服务之间通过 HTTP 协议通信
- AI服务通过HTTP API接收请求并返回结果


# 二、HTTP基本模型

## 1、客户端-服务器模型

HTTP 基于**客户端-服务器模型**。

客户端负责发起请求，服务器负责处理请求并返回响应。

示意图如下：

![[assets/Pasted image 20260512210519.png|300]]

**常见客户端**：浏览器、curl、Postman、移动端App、前端JavaScript程序、后端服务、爬虫、自动化脚本。

**服务器负责提供资源或执行业务逻辑**：例如提供HTML、CSS、JavaScript、图片等资源，数据库查询返回JSON等。


## 2、请求-响应模型

HTTP核心交互模式就是**请求-响应模型**，也就是说：

> 客户端先发送请求，服务器再返回响应。

![[assets/Pasted image 20260512214119.png|300]]

客户端请求示例：

```http
GET /index.html HTTP/1.1
Host: example.com
```

服务器响应示例：

```http
HTTP/1.1 200 OK
Content-Type: text/html

<html>
  <body>Hello HTTP</body>
</html>
```

其中：

- `GET /index.html HTTP/1.1` 表示客户端想获取 `/index.html` 这个资源；
- `Host: example.com` 表示请求的目标主机；
- `HTTP/1.1 200 OK` 表示服务器成功处理请求；
- `Content-Type: text/html` 表示响应体是 HTML 文档；
- 空行后面的内容就是响应体。

HTTP 通信不是客户端和服务器之间随意发送数据，而是通过一个个结构化的消息完成。

客户端发送的消息叫做**HTTP请求**。

服务器发送的消息叫做**HTTP响应**。


## 3、面向资源思想

HTTP围绕**资源**设计，资源通过`URL`标识。

例如：

- `/index.html`：一个HTML网页
- `/images/logo.png`：一张图片
- `/users/1`：一个用户
- `/articles/100`：一篇文章
- `/orders/abc123`：一个订单

在HTTP请求中，通过请求方法来表示对资源做何种操作，例如：

| 方法     | 操作   | 说明     |
| ------ | ---- | ------ |
| GET    | 获取   | 读取资源   |
| POST   | 创建   | 提交新数据  |
| PUT    | 更新   | 完整更新资源 |
| PATCH  | 局部更新 | 部分更新资源 |
| DELETE | 删除   | 删除资源   |
例如：

```html
GET /users/1 HTTP/1.1
Host: api.example.com
```

表示读取ID为1的用户资源。

```html
DELETE /users/1 HTTP/1.1
Host: api.example.com
```

表示删除ID为1的用户资源。

> URL标识资源，请求方法表达操作意图


## 4、应用层协议定位

HTTP 位于网络分层模型中的**应用层**，它建立在更底层的传输能力之上。

经典五层网络模型如下图所示：

![[assets/Pasted image 20260512214427.png|200]]

HTTP不直接负责底层数据如何传输，它关注的是请求、响应、资源、状态码、Header、Body。

底层协议则关注传输、分片、可靠性和连接建立。

## 5、HTTP 与 TCP/TLS/QUIC的关系

不同版本的 HTTP，底层依赖的传输方式不同。

- HTTP/1.1 和 HTTP/2.  ——  基于 TCP
- HTTPS  ——  HTTP 与传输层之间加入 TLS，用于加密、完整性校验和身份认证
- HTTP/3 ——  基于QUIC，QUIC 使用 UDP 作为底层协议，但它自己实现了可靠传输、TLS 1.3 加密、拥塞控制等能力


# 三、HTTP系统组成

## 1、客户端

发起 HTTP 请求的一方。典型客户端：浏览器、curl、Postman、移动端App、前端 JS、后端服务。

示例：

- 使用 `curl` 命令请求一个网页：

```shell
curl https://example.com
```

这里的 `curl` 就是 HTTP 客户端。

- 前端代码中使用 `fetch` 请求接口：

```JavaScript
fetch('/api/users')
  .then(res => res.json())
  .then(data => console.log(data));
```

这里运行 JavaScript 的浏览器就是客户端。

- 在后端服务之间调用接口时，发起请求的后端服务也可以看作是 HTTP 客户端。

例如，订单服务向用户服务发送 HTTP 请求，用户服务返回 HTTP 响应，这里的订单服务就是 HTTP 客户端。


## 2、用户代理（User Agent）

用户代理（User Agent）是指**代表用户发起 HTTP 请求的客户端程序**。

常见用户代理包括：浏览器、搜索引擎爬虫、curl、Postman、移动端APP、自动化测试工具。

用户代理可以携带客户端信息到服务器，以便服务器进行统计、兼容或调试处理。

HTTP 请求中可以通过 `User-Agent` 请求头标识用户代理信息。

例如：

```text
User-Agent: Mozilla/5.0
```

服务器可以根据 User-Agent 大致判断请求来源类型，例如桌面浏览器、移动浏览器或脚本工具。但 User-Agent 可以伪造，因此不适合作为严格安全凭证，仅用于统计、兼容和日志。

## 3、服务器

服务器是接收请求并返回响应的一方。**服务器提供资源或执行业务逻辑**。

在实际系统里，**服务器可能是一台机器，也可能是多台机器组成的集群**。如下图所示：

![[assets/Pasted image 20260512222206.png|500]]

基本过程如下：

1. 用户发起请求：用户通过浏览器或App访问同一个网站或接口地址
2. 负载均衡器分发：所有的请求先到负载均衡器，由它统一入口并分发给不同后端服务器
3. 后端服务器处理请求：收到请求的后端服务器返回资源会执行业务逻辑
4. 访问共享资源：后端可能读写数据库、缓存或发送消息到消息队列完成任务
5. 响应返回用户：处理结果经过负载均衡器返回给用户

## 4、Web服务器和应用服务器

### （1）Web服务器

Web 服务器是指**专门处理HTTP请求并返回网页内容的服务器软件**。它更偏向于处理 HTTP 接入层的事情。

常见职责包括：

- 接收客户端HTTP请求
- 返回静态资源，例如 HTML、CSS、JS、图片；
- 反向代理，把请求转发给后端服务
- 负载均衡：把请求分发给多个后端实例
- HTTPS终止，也就是处理TLS证书和HTTPS加密连接
- 压缩、缓存、限流、访问控制等。

常见的 Web 服务器有`Apache`、`Nginx`、`Caddy`等。

特点：

- 主要处理静态内容
- 性能优化侧重于高并发请求和静态资源缓存
- 一般不直接处理负责业务逻辑

### （2）应用服务器

应用服务器是指**专门处理业务逻辑和动态请求的服务器软件**。它更偏向于处理业务代码。

常见职责包括：

- 接收来自 Web 服务器或客户端的请求
- 执行业务处理逻辑（如用户登录、订单处理等）
- 与数据库、缓存、消息队列等后端资源交互
- 返回处理结果，通常是动态生成的内容（如JSON、HTML页面等）

常见的应用服务器有Node.js（JavaScript）、Tomcat（Java）、Spring Boot（Java）、Django/Flask（Python）。

**特点**：

- 处理动态内容和业务逻辑
- 可以集成数据库、缓存和消息队列等
- 性能优化侧重于业务逻辑处理能力和事务管理


### （3）Web 服务器与应用服务器的协作流程

在实际生产环境中，Web服务器和应用服务器经常配合使用。客户端请求通常先到Web服务器，例如Nginx。Nginx负责接收请求、处理HTTPS、返回静态资源，或者把动态接口请求转发给后端应用服务。后端应用服务负责业务逻辑，必要时访问数据库，并把处理结果返回给 Nginx，再由 Nginx 返回给客户端。

## 5、代理

在客户端和服务器之间，可能还会经过一些中间实体，这些实体叫做**代理**。

![[assets/Pasted image 20260512233510.png|500]]


代理本质上位于通信中间，负责转发、处理或控制 HTTP 消息。

CDN 就是一种常见的缓存代理。如果用户请求了一个图片资源，而 CDN 节点已经缓存了该图片，那么 CDN 就可以直接返回资源，不必每次都回源到真实服务器。

企业内部网络也可能使用代理控制员工访问外部网络的行为。

在后端系统中，API网关、负载均衡器、Nginx反向代理，也都可以看作HTTP 通信链路中的中间层。

## 6、正向代理和反向代理

代理可以分为很多类型，其中最常见的就是**正向代理**和**反向代理**。

正向代理是站在客户端一侧的代理。

# 四、HTTP基本性质

1. 简单易读

HTTP 的设计相对简单，尤其是 HTTP/1.1 以及更早版本中，请求和响应报文都具有较强的文本可读性。

请求示例：

```http
GET / HTTP/1.1  
Host: example.com  
Accept: text/html
```

响应示例：

```http
HTTP/1.1 200 OK
Content-Type: text/html

<html>Hello HTTP</html>
```

虽然 HTTP/2 和 HTTP/3 的底层传输格式已经不再是简单文本报文，但 HTTP 的核心语义没有变化，仍然有请求、响应、方法、状态码等。

2. 灵活

HTTP 可以传输各种类型的数据。具体数据类型通过 `Content-Type` 表示：

- `text/html`：响应体是HTML
- `application/json`：响应体是JSON
- `image/png`：响应体是PNG图片
- `multipart/form-data`：响应体是表单和文件上传数据

3. 可扩展

HTTP是一种可扩展协议，它可以通过 Header 扩展很多能力。

```http
Cache-Control: max-age=3600
```

可以控制缓存。

```http
Authorization: Bearer token123
```

可以携带认证信息。

```http
Set-Cookie: session_id=abc123
```

可以让浏览器保存 Cookie。

4. 无状态

HTTP是无状态协议。所谓无状态是指，HTTP本身不会自动记住前一次请求的信息。

服务器收到两个请求：

```text
请求 1：POST /login
请求 2：GET /profile
```

HTTP 协议本身不会自动知道这两个请求是不是同一个用户发来的。

这会带来一些问题：

- 用户登录后，服务器怎么知道后续请求还是这个用户？
- 用户把商品加入购物车后，服务器怎么知道购物车属于谁？
- 用户切换页面时，网站怎么保持登录状态？

不过，虽然HTTP本身无状态，但Web应用可以借助 Cookie / Session /Token建立有状态的会话。

5. 依赖可靠传输

传统 HTTP 主要依赖 TCP，因为 TCP 提供可靠传输能力。HTTP/3 则依赖 QUIC。QUIC 虽然基于 UDP，但它自己提供可靠传输、安全加密、拥塞控制等能力。

因此，HTTP 对底层传输的核心要求不是“必须是 TCP”，而是：

> 底层传输应该能够可靠地交付 HTTP 消息，或者在失败时明确报告错误。

# 五、一次完整的HTTP访问过程

## 1、URL解析

以访问这个地址为例：

```text
https://www.example.com/articles/1
```

浏览器首先会解析URL：

- 协议：https
- 主机：www.example.com
- 端口：443
- 路径：/articles/1

如果 URL 中没有显式写端口，则使用协议默认端口。

- HTTP 默认为 80
- HTTPS 默认为 443

**URL 是客户端定位资源的重要方式**。其中，协议决定使用 HTTP 还是 HTTPS，主机决定访问哪台服务器，端口决定连接服务器上的哪个服务，路径决定请求服务器上的哪个资源。

## 2、DNS解析

浏览器需要把域名解析成 IP 地址：

```text
www.example.com → 93.184.216.34
```

因为真实网络通信需要依靠 IP 地址找到目标服务器。

域名是给人看的地址，IP 是给网络通信用的地址。

如果浏览器或系统缓存中已经有对应解析结果，就可以直接使用缓存；否则就需要向 DNS 服务器查询。

## 3、连接建立

浏览器拿到服务器IP地址之后，需要和服务器建立连接。

如果是 HTTP/1.1 或 HTTP/2，通常需要建立 TCP 连接。如果是 HTTPS，还需要进行 TLS 握手。

![[assets/Pasted image 20260513003914.png]]

如果是 HTTP/3，则底层使用 QUIC。

连接建立完成后，客户端和服务器之间才可以正式传输 HTTP 请求和响应。


## 4、HTTP请求发送

连接建立之后，浏览器构造 HTTP 请求并发送给服务器。


```http
GET /articles/1 HTTP/1.1
Host: www.example.com
Accept: text/html
User-Agent: Mozilla/5.0
```



## 5、服务器处理请求

服务器收到请求后，会根据请求内容进行处理。如请求 `/articles/1`，服务器可能会去数据库中查询 ID 为 1 的文章，然后生成 HTML 页面或 JSON 数据返回给客户端。

如果请求的是静态资源，如 `/logo.png`、`style.css`，服务器会直接从文件系统或缓存读取资源并返回。

如果请求的是动态接口，如 `/api/users/1`，服务器通常会执行业务代码，查询数据库，然后返回 JSON 响应。

## 6、HTTP响应返回

服务器处理完成后，会返回 HTTP 响应：

```http
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: max-age=600

<html>
  <body>文章内容</body>
</html>
```

## 7、客户端解析响应

浏览器收到 HTTP 响应后，解析响应内容。如果响应体是 HTML，浏览器会解析页面。如果 HTML 中引用了其他资源，则继续发送更多 HTTP 请求。

HTML 示例：

```html
<link rel="stylesheet" href="/style.css">
<script src="/main.js"></script>
<img src="/logo.png">
```

浏览器会继续发起请求：

```text
浏览器 / 客户端                         Web 服务器
     │                                      │
     │  GET /style.css                      │
     │ ───────────────────────────────────▶ │
     │  返回 CSS 文件                       │
     │ ◀─────────────────────────────────── │
     │                                      │
     │  GET /main.js                        │
     │ ───────────────────────────────────▶ │
     │  返回 JavaScript 文件                │
     │ ◀─────────────────────────────────── │
     │                                      │
     │  GET /logo.png                       │
     │ ───────────────────────────────────▶ │
     │  返回图片资源                        │
     │ ◀─────────────────────────────────── │
     │                                      │
```

所以，打开一个网页通常不是一次 HTTP 请求完成的，而是很多个 HTTP 请求共同完成的。

这也是为什么浏览器 DevTools 的 Network 面板中，经常能看到几十个甚至上百个请求。
