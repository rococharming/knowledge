# 一、HTTP 缓存

HTTP 缓存是浏览器和中间代理保存服务器响应副本的机制，目的是减少重复请求、降低延迟和服务器压力。

当浏览器再次请求同一个资源时，如果缓存仍然有效，就可以直接用本地副本，不必再向服务器发请求。这大幅提升了页面加载速度，也减少了网络带宽消耗。

HTTP 缓存的核心是"如何判断缓存是否仍然有效"，这通过一组请求/响应头来协商。

# 二、强缓存

## 1、什么是强缓存

强缓存是指：在缓存未过期的时间内，浏览器直接使用本地副本，**完全不与服务器通信**。

强缓存命中时，浏览器返回的状态是 200，但实际没有发起网络请求（开发者工具里会标注 from disk cache 或 from memory cache）。

强缓存由两个字段控制：`Cache-Control` 和 `Expires`。

## 2、Cache-Control

`Cache-Control` 是 HTTP/1.1 的头，优先级高于 `Expires`。常用指令：

- `max-age=3600`：缓存有效期为 3600 秒。
- `no-cache`：不强缓存，每次都要向服务器验证。
- `no-store`：完全不缓存。
- `public` / `private`：是否允许中间代理缓存。

示例响应头：

```http
HTTP/1.1 200 OK
Cache-Control: max-age=3600
Content-Type: text/html
```

这里的 `max-age=3600` 表示浏览器在 3600 秒内可以直接用这份缓存。

## 3、Expires

`Expires` 是 HTTP/1.0 的头，指定一个绝对过期时间：

```http
Expires: Wed, 10 Jul 2026 16:00:00 GMT
```

由于绝对时间依赖客户端时钟，且优先级低于 `Cache-Control`，现代实践通常以 `Cache-Control` 为主，`Expires` 作为兜底。

> 注意：同时存在时，`Cache-Control` 的 `max-age` 会覆盖 `Expires`。

# 三、协商缓存

## 1、什么是协商缓存

强缓存过期后，浏览器不会直接丢弃缓存，而是带着标识去问服务器"这份缓存还能用吗"。如果服务器说能用，返回 304，浏览器继续用本地副本；如果不能用，返回 200 和新内容。

协商缓存虽然发了一次请求，但省掉了传输响应体的开销。

## 2、两种验证机制

| 机制 | 请求头 | 响应头 | 特点 |
|---|---|---|---|
| Last-Modified | If-Modified-Since | Last-Modified | 基于时间，精度到秒 |
| ETag | If-None-Match | ETag | 基于内容哈希，更精确 |

`ETag` 优先级高于 `Last-Modified`，因为内容可能没变但修改时间变了（比如重新部署但文件内容相同）。

## 3、完整流程

示例请求（协商缓存）：

```http
GET /style.css HTTP/1.1
If-None-Match: "abc123"
```

若内容未变，服务器响应：

```http
HTTP/1.1 304 Not Modified
ETag: "abc123"
```

浏览器收到 304，直接用本地缓存。注意 304 响应没有响应体，所以很轻量。

# 四、缓存策略选择

## 1、按资源类型选

- **带哈希的静态资源**（如 `app.a3f9.css`）：强缓存 `max-age` 设很长（如一年），文件内容变了哈希就变，URL 也变，自然不会用旧缓存。
- **HTML 文档**：用 `no-cache`，每次协商验证，保证用户拿到最新入口。
- **用户数据**：通常 `no-store`，不缓存敏感内容。

## 2、常见陷阱

> 注意：强缓存 `max-age` 期间，即使服务器更新了资源，用户也看不到新版本。这就是为什么带哈希的文件名是最佳实践——通过换文件名强制更新。

# 五、延伸

强缓存与协商缓存配合使用，能覆盖大多数场景。后续可了解 [[Service Worker|Service Worker]] 提供的可编程缓存层，以及 [[CDN 缓存|CDN 缓存]] 在边缘节点的缓存策略。
