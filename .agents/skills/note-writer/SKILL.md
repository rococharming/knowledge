# 技术笔记生成

把来源材料（或一个主题）整理成一篇结构清晰、风格统一的技术笔记，保存到用户指定路径。

## 触发与边界

本技能生成**单篇笔记**，写到用户调用时指定的路径。它不维护领域索引、不写操作日志、不归档来源文件——那些是 `ingest` 的职责。如果用户要整合 raw 素材进领域 wiki/ 并更新 index/log，应改用 `ingest`。两者的区别在于目标：note-writer 产出单篇笔记，ingest 维护整个领域知识库。

笔记风格遵循 `references/style-guide.md`，章节模板见 `references/template.md`。生成前必须读取这两个文件。

## 工作流

### 1. 解析输入

识别用户给的输入属于哪一类，解析成"源材料"：

| 输入类型 | 识别 | 处理 |
|---|---|---|
| **URL** | 以 `http` 开头 | 调用 `defuddle` skill 提取干净 Markdown |
| **本地文件** | 是已存在的文件路径 | 直接 Read（含浏览器插件抓取的字幕稿 .md） |
| **文本片段** | 内联文本 | 直接作为源材料 |
| **主题** | 简短主题词、无文件/URL | 标记为无外部源，凭知识生成 |

字幕稿按普通本地文件读取，但生成长期笔记时要做“归档化”处理：去掉时间戳、口语填充、弹幕/评论语境和来源现场感。除非用户要求保留来源评论，否则不要写“视频中提到”“作者演示”“评论中有人提醒”等表述；应改写成可长期复用的事实、步骤、限制或注意事项。

### 2. 确定输出路径与文件名

- **路径**：用户调用时指定。未指定时询问，不要自行假设。
- **文件名**：扫描目标目录下已有笔记，识别序号约定。
  - 若目录使用序号约定（如 `3、所有权.md`、`10、泛型.md`），先算出候选序号 = 文件名序号最大值 + 1。
  - 若目录无序号约定，用主题名作文件名，如 `深入理解 epoll.md`。
  - 序号识别要看文件名开头的"数字、"模式，主题部分用本次笔记的核心主题。
  - **正文预留序号检查**：候选序号确定后，再扫描同目录已有笔记的正文，看是否有 `[[N、某主题]]` 形式的维基链接**指向尚未创建的笔记**（即该序号 N 被某篇笔记"预留给将来的下一篇"，但对应文件还不存在）。若候选序号恰好落在这样的预留上，不要擅自抢占、也不要盲目跳到下一个——停下来告诉用户："序号 N 已被 `[[某篇笔记]]` 预留给主题 X，但文件尚未创建。本次主题是 Y。是用 N（可能与预留意图不符）、跳到下一个可用序号、还是别的？" 由用户决定。这是为了尊重作者已有的写作规划，而不是机械地取最大值+1。

### 3. 加载风格范本

读取 `references/style-guide.md`（风格规范与可调维度）和 `references/template.md`（章节模板与完整范例）。

### 4. 生成笔记

按风格范本写：

1. **frontmatter**：包含 `title`、`date`、`tags`、`aliases` 四个字段。`date` 使用当前日期（`YYYY-MM-DD`）。`tags` 必须符合 Obsidian 标签规则：只能包含字母、数字（不能作为首字符）、下划线 `_`、连字符 `-` 和斜杠 `/`，不能包含空格；多词标签用连字符、下划线或层级斜杠表示，例如 `git-revert`、`Git协作`。命令、术语或自然语言短语若原名包含空格（如 `git revert`、`React Server Components`），不要放入 `tags`，应放入 `aliases`。`aliases` 写 1-3 个便于 Obsidian 搜索和链接补全的常用别名。
2. **正文**：按 `一、` → `1、` → `（1）` 序数组织标题，概念先行，示例驱动。标题优先短而准：一级标题一般用 2-6 个字或一个专有名词，二级标题用 2-8 个字概括一个概念块。不要照搬来源材料的讲稿顺序，应按"概念 / 职责 / 组成 / 示例 / 区别 / 配置 / 自测 / 后续"等稳定块重组。
3. **标题成组**：一级标题下如果使用二级标题，二级标题必须至少有两个；如果只有一个二级主题，就取消二级标题，把内容直接并入一级标题正文。不要出现孤立的 `## 1、...`。
4. **来源去语境化**：笔记面向未来阅读，而不是复述来源材料。把“视频里说/作者说/评论说”的材料转写为直接陈述；只在需要追溯证据、评价可信度或保留争议时才显式提来源。

生成时根据内容性质**自动判断**风格强度（纯概念少代码、语法教程多示例、对比多用表格），用户也可在调用时用参数覆盖：
- `--style=教程|概念|对比|参考`：笔记侧重
- `--with-code=yes|no|auto`：是否配代码示例，默认 auto
- `--depth=浅|中|深`：详略程度，默认中

### 5. 自动交叉引用

扫描目标目录下已有笔记，识别与本篇主题相关的概念，在正文中用 `[[笔记名|显示名]]` 维基链接关联。关联要相关且准确——只链接真正同主题或互补的笔记，不要为了凑链接而硬连。链接显示名用该笔记的简短主题。

### 6. 自检

写完后快速复查（聚焦真正容易出错、且不易在写作中即时保证的几项，不必逐条长篇检查）：

- **尖括号转义**：正文和标题中不在代码块/行内代码里的 `<` 已转义为 `\<`（如泛型 `Vec\<T>`）。代码围栏和反引号内的 `<` 不转义。这是 Obsidian 渲染的硬约束，漏一处会让该行之后的内容消失，必须查。
- **标签有效**：frontmatter 的 `tags` 不含空格，且只使用 Obsidian 允许的字符；包含空格的命令名、专有名词和短语应保留在 `aliases`，不要作为标签。
- **链接有效**：`[[维基链接]]` 指向的笔记真实存在，或是有意预留的（与第 2 步的预留检查一致）。
- **标题序数连续**：`一、/1、/（1）` 无跳级、无重复。
- **无孤立子标题**：任一一级标题下若出现二级标题，则同一一级标题下至少有两个二级标题；否则删除该唯一二级标题并把内容并回一级标题正文。
- **标题短而准**：一级标题避免"某某的基本概念 / 当前连接的某某"这类长讲稿式标题，优先写成 `Node.js`、`npm`、`包与依赖`、`环境检查`、`配置与帮助` 等短概念块。
- **归档口吻**：长期笔记中不保留无必要的来源现场话术，如“视频中提到”“作者说”“评论中有人提醒”。这些内容应改写为稳定的操作说明、限制条件或注意事项。

frontmatter 的字段完整性和文件名序号在第 2、4 步已确定，无需重复检查；加粗空格等格式问题交给写作时的常规注意，不单列。

### 7. 输出确认

告知用户：笔记保存路径、序号、关联了哪些已有笔记、自检结果。

## 与其他技能协作

- 提取 URL 内容时，调用 `defuddle`。
- 笔记中的 Obsidian 语法（维基链接、嵌入、标注）遵循 `obsidian-markdown` skill 规范。
- 笔记写入哪个领域、是否进 wiki 层，由用户决定；本技能只负责生成单篇笔记。
