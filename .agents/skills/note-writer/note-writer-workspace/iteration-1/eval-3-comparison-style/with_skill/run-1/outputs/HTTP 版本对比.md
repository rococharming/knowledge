# 一、HTTP 版本演进概览

HTTP 是 Web 上交换数据的应用层协议。从 1997 年的 HTTP/1.1 到如今的 HTTP/3，每次版本升级都针对前一代的瓶颈：连接利用率低、队头阻塞、头部冗余、握手延迟。理解三个版本的差异，本质是理解 **它们各自解决了什么问题、又引入了什么代价** 。

## 1、为什么会有多个版本

- **HTTP/1.1** 解决的是"如何让连接可复用、如何规范缓存与主机"，奠定了现代 Web 的语义基础。
- **HTTP/2** 解决的是"如何在单个连接上并行多个请求"，应对页面资源爆炸式增长。
- **HTTP/3** 解决的是"传输层的队头阻塞与握手慢"，把传输层从 TCP 换成基于 UDP 的 QUIC。

> 关键线索：每一次升级都在消除上一代留下的队头阻塞（Head-of-Line Blocking），但消除的层级不同——HTTP/2 消除应用层的，HTTP/3 连传输层一起消除。

## 2、版本时间线

| 版本 | 年份 | 传输层 | 核心改进 | RFC |
|---|---|---|---|---|
| HTTP/1.1 | 1997（2007 定稿） | TCP | 持久连接、管道化、Host 头、缓存协商 | RFC 7230-7235 |
| HTTP/2 | 2015 | TCP | 二进制分帧、多路复用、头部压缩 HPACK、服务器推送 | RFC 7540 / 9113 |
| HTTP/3 | 2022 | QUIC（UDP） | QUIC 传输、0-RTT 握手、连接迁移、无传输层队头阻塞 | RFC 9114 |

# 二、核心维度对比

对比三个版本，最直观的方式是按维度并排看。下面四张表分别覆盖传输层、多路复用、头部、安全。

## 1、传输层与连接管理

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 底层传输 | TCP | TCP | QUIC（UDP） |
| 加密 | 可选（HTTPS 需 TLS） | 实际强制 TLS（浏览器只支持 h2 over TLS） | 强制 TLS 1.3（QUIC 内置） |
| 握手次数 | TCP 1-RTT + TLS 1-2 RTT | TCP 1-RTT + TLS 1-2 RTT | QUIC 1-RTT（首次）/ 0-RTT（恢复） |
| 连接复用 | 持久连接 keep-alive | 单连接多路复用 | 单连接多路复用 |
| 连接迁移 | 不支持（IP 变即断） | 不支持 | 支持（基于连接 ID，切 Wi-Fi/4G 不断） |

## 2、多路复用与队头阻塞

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 并发请求 | 多个 TCP 连接（浏览器限 6 个/域） | 单连接多流并行 | 单连接多流并行 |
| 应用层队头阻塞 | 有（管道化几乎废弃） | 无（流间独立） | 无 |
| 传输层队头阻塞 | 有（TCP 丢包阻塞所有连接内数据） | 有（一个 TCP 包丢失阻塞所有流） | 无（QUIC 流间独立） |
| 队头阻塞根因 | 单连接串行 + TCP 顺序 | TCP 字节流语义绑定所有流 | QUIC 在 UDP 上按流分帧 |

> 注意：HTTP/2 虽然在应用层解决了队头阻塞，但由于所有流共享一条 TCP 连接，TCP 层一个包丢失会让所有流停下来等重传——这是 HTTP/3 改用 QUIC 的根本动机。

## 3、头部格式

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 格式 | 文本（ASCII） | 二进制分帧 | 二进制分帧 |
| 头部压缩 | 无（重复头部每次都传） | HPACK | QPACK |
| 压缩效率 | 低 | 高（静态表 + 动态表 + 哈夫曼） | 高（类似 HPACK，适配乱序） |
| 服务器推送 | 无 | 有（Server Push，实践中已弱化） | 有（但同样逐步弃用） |

## 4、安全性

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 明文支持 | 支持 | 仅 h2c（浏览器不用） | 不支持 |
| 默认加密 | 否 | 是 | 是 |
| TLS 版本 | TLS 任意 | TLS 1.2+ | TLS 1.3 |
| 前向保密 | 取决于配置 | 通常具备 | 强制具备 |

# 三、各版本关键特性

## 1、HTTP/1.1

HTTP/1.1 是最长寿的版本，定义了现代 HTTP 的语义（方法、状态码、缓存、Host 头）。它的核心改进是 **持久连接（keep-alive）** ，让一个 TCP 连接可以连续发多个请求，避免每次都重新握手。

但 HTTP/1.1 的并行能力有限：

- 浏览器对同一域名限制约 6 个并发连接。
- 管道化（pipelining）理论上能串行发请求，但响应必须按序返回，一旦前面的慢就阻塞后面，且中间代理支持差，实际几乎没人用。
- 为了绕开 6 连接限制，站点常做 **域名分片（domain sharding）** ，把资源分散到多个子域名——这又增加了连接和 DNS 开销。

> 典型优化手段：资源合并（sprite、concat）、内联小资源、减少请求数。这些在 HTTP/2 之后大多不再必要。

## 2、HTTP/2

HTTP/2 把连接从"文本+串行"变成"二进制分帧+并行"。单个 TCP 连接上可以同时跑多个流（stream），每个流承载一个请求/响应，帧可以交错到达再按流重组。

核心特性：

- **二进制分帧** — 数据切成帧传输，帧带流 ID，可交错。
- **多路复用** — 一个连接并行多个请求，彻底告别 6 连接限制。
- **头部压缩（HPACK）** — 用静态表/动态表/哈夫曼消除重复头部，对 Cookie 重的场景收益明显。
- **服务器推送** — 服务器可主动把资源推给客户端（如随 HTML 推 CSS），但实践中常与缓存冲突，主流浏览器已逐步弃用。

```http
# HTTP/2 的连接前言（magic + SETTINGS 帧）
PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n
# 之后是二进制帧，每帧含 length/type/flags/streamID
```

HTTP/2 的代价是 **队头阻塞下沉到 TCP 层** ：所有流共享一个 TCP 连接，一个包丢失会卡住所有流的重传与交付。在丢包率高的网络（如移动端）上，HTTP/2 有时反而比 HTTP/1.1 的多连接还慢。

## 3、HTTP/3

HTTP/3 不再跑在 TCP 上，而是跑在 QUIC 上。QUIC 是 Google 设计、IETF 标准化的传输协议，跑在 UDP 之上，把 TLS 1.3 握手和传输握手合并。

核心特性：

- **QUIC 传输** — 在 UDP 上自己实现可靠传输、拥塞控制、加密。
- **流级独立** — 每个流有自己的丢包重传范围，一个流丢包不阻塞其他流。
- **0-RTT 握手** — 首次连接 1-RTT，恢复连接可 0-RTT 直接带数据。
- **连接迁移** — 连接以连接 ID 标识，IP 变了（切网络）连接不断。
- **QPACK** — HPACK 的演进版，适配 QUIC 的乱序交付。

```http
# HTTP/3 不再是 TCP 连接前言，而是 QUIC 握手
# 客户端发 Initial 包（含 TLS ClientHello），1-RTT 后即可发请求
# 恢复连接时 0-RTT 带上早期数据
```

HTTP/3 的代价是 **UDP 在部分网络被限速或阻断** ：一些企业防火墙、中间盒只优化 TCP 流量，对 UDP 不友好或直接丢弃，导致 QUIC 退化为 TCP。部署 HTTP/3 通常需要回退到 HTTP/2。

# 四、性能权衡与选型

## 1、典型场景权衡

| 场景 | 推荐版本 | 理由 |
|---|---|---|
| 高丢包移动网络 | HTTP/3 | 无传输层队头阻塞，连接迁移不断线 |
| 内网低延迟 API | HTTP/2 或 1.1 | 丢包少，HTTP/2 多路复用收益稳定 |
| 大量小资源页面 | HTTP/2+ | 多路复用消除连接瓶颈，头部压缩省带宽 |
| 需要兼容老客户端/中间盒 | HTTP/1.1 | 兼容性最好，UDP 可能被阻 |
| 强实时、频繁切网络 | HTTP/3 | 0-RTT + 连接迁移体验最好 |
| 受限网络（UDP 被封） | HTTP/2 | QUIC 无法建立，需回退 |

## 2、各版本权衡列举

- **HTTP/1.1** — 兼容性最好、调试最简单（明文可抓包），但并发弱、头部冗余、连接开销大。
- **HTTP/2** — 多路复用显著提升资源密集页面，单连接省握手；但 TCP 层队头阻塞在高丢包下拖累所有流，且二进制帧调试需专门工具。
- **HTTP/3** — 彻底解决队头阻塞、握手最快、支持连接迁移；但 UDP 兼容性是硬伤，部署复杂度高，QPACK 在乱序下压缩率略低于 HPACK。

## 3、迁移成本权衡

| 维度 | 1.1 → 2 | 2 → 3 |
|---|---|---|
| 服务端改造 | 中（需支持 h2、TLS、HPACK） | 高（需支持 QUIC/UDP、证书配置） |
| 客户端 | 浏览器原生支持 | 浏览器原生支持 |
| 中间盒兼容 | 好（仍是 TCP+TLS） | 差（UDP 可能被丢弃） |
| 调试工具 | 需支持 h2 的抓包工具 | 需支持 QUIC 的工具（较新） |
| 实际收益 | 高（多路复用） | 视网络而定（弱网收益大） |

> 注意：HTTP/3 通常不单独部署，而是与 HTTP/2 并存——通过 Alt-Svc 头宣告 QUIC 可用，客户端先走 HTTP/2，再尝试升级到 HTTP/3，失败则回退。这是应对 UDP 兼容性问题的标准做法。

# 五、小结

三个版本不是替代关系，而是 **分层优化** ：HTTP/1.1 定义语义，HTTP/2 优化应用层并发，HTTP/3 优化传输层。选型时抓住两个关键问题——网络丢包率高不高、UDP 通不通——基本就能定方向。

核心权衡一句话： **HTTP/2 用单连接换并发，HTTP/3 用 UDP 换无队头阻塞** ，各自都付出了新的代价。
