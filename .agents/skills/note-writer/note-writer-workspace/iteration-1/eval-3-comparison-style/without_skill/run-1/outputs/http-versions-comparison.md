# HTTP/1.1 vs HTTP/2 vs HTTP/3 对比笔记

三个 HTTP 大版本的核心区别，几乎都集中在"传输层"和"并发模型"上。本文按维度逐项对比，先给一张总表，再展开细节。

## 一、总表速览

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 标准化年份 | 1997 | 2015 | 2022（RFC 9114） |
| 传输层 | TCP | TCP | **QUIC（基于 UDP）** |
| 加密 | 可选（HTTPS 叠加 TLS） | 事实标准需 TLS（RFC 8441 允许明文，但浏览器不支持） | **强制 TLS 1.3 内嵌** |
| 报文格式 | 文本（ASCII） | 二进制分帧 | 二进制分帧 |
| 多路复用 | 无（每连接单请求） | 有（单 TCP 连接多流） | 有（单 QUIC 连接多流） |
| 队头阻塞（HOL） | **应用层 + TCP 层都有** | 应用层解决，**TCP 层仍存在** | **应用层与传输层都解决** |
| 头部压缩 | 无（重复明文头） | HPACK | **QPACK（适配乱序）** |
| 服务器推送 | 无（仅 pipelining，实际很少用） | 有（Server Push，已逐步弃用） | 有（但生态同样在弱化） |
| 连接建立往返 | 1 RTT（TCP）+ 1~2 RTT（TLS） | 同 1.1 | **1 RTT（甚至 0-RTT 恢复）** |
| 连接迁移 | 不支持（IP 变动断连） | 不支持 | **支持（连接 ID 解耦 IP）** |

## 二、传输层：从 TCP 到 QUIC

这是三代之间最根本的分水岭。

**HTTP/1.1 与 HTTP/2 共用 TCP**。TCP 是可靠、有序的流协议,所有上层 HTTP 流复用同一条 TCP 连接时,只要某一个包丢失,TCP 必须停下等重传完成,才能把后续已到达的数据交给应用层。这就是 TCP 层的队头阻塞。

**HTTP/3 放弃 TCP,改用 QUIC**。QUIC 跑在 UDP 之上,自己实现了可靠传输、拥塞控制、加密,并把多个流做成相互独立的传输单元。一个流丢包,只会阻塞该流,其它流照常推进。

> 选择 UDP 不是为了"快",而是为了"绕开操作系统内核里那套写死的 TCP 栈",在用户态快速迭代传输协议。

## 三、多路复用与队头阻塞

三代在这条线上是递进关系。

**HTTP/1.1**：一条 TCP 连接同一时刻只能处理一个请求。提升并发的办法是开多条连接（浏览器通常限 6 个/域名）或用 keep-alive 复用连接但仍是串行。pipelining 理论上允许"管道式"连续发送,但响应必须按序返回,实际几乎无人启用。

**HTTP/2**：在单条 TCP 连接上引入"流"(stream)概念,多个请求/响应以二进制帧交错传输,真正并发。但所有流共享一条 TCP 连接 → 丢一个包,所有流都被 TCP 卡住。即应用层 HOL 解决了,TCP 层 HOL 没解决。

**HTTP/3**：QUIC 中每个流独立可靠传输。丢包只影响相关流,其它流不受牵连。这是相对 HTTP/2 最实质的改进。

| HOL 类型 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 应用层（请求间） | 存在 | 解决 | 解决 |
| 传输层（包间） | 存在 | 存在 | 解决 |

## 四、报文格式与头部压缩

**文本 vs 二进制**。HTTP/1.1 是行文本协议,可读但冗长、解析易错;HTTP/2 起改为二进制分帧,帧是最小传输单元,多个帧拼成消息,多个消息复用流。

**头部压缩演进**：

- HTTP/1.1：每个请求都带完整明文头部,重复字段（如 Cookie、User-Agent）反复传输。
- HTTP/2：引入 **HPACK**,用静态表 + 动态表 + 哈夫曼编码压缩重复头部。
- HTTP/3：引入 **QPACK**。因为 QUIC 流之间可能乱序到达,QPACK 不能像 HPACK 那样依赖严格顺序,必须用显式确认机制更新动态表,复杂度更高,但设计目标一致。

## 五、安全性

| 项 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 明文可用 | 是 | RFC 允许,浏览器不支持 | 否 |
| 默认加密 | 否 | 是（事实） | 是（强制 TLS 1.3） |
| TLS 版本 | 任意 | TLS 1.2+ | **TLS 1.3** |

HTTP/3 把 TLS 1.3 直接揉进 QUIC 握手中,不再像前两代那样 TLS 叠在 TCP 之上。好处是握手与传输合并,坏处是中间盒（防火墙、代理）更难做明文检测,部署阻力也由此而来。

## 六、连接建立与迁移

**握手开销**。HTTP/1.1/2 over TLS 需要先 TCP 握手(1 RTT),再 TLS 握手(1~2 RTT),合计 2~3 RTT 才能发第一个请求。HTTP/3 把传输握手与加密握手合并,首包 1 RTT;对曾连过的服务器,可用 0-RTT 恢复,首请求甚至能随握手包一起发。

**连接迁移**。TCP 连接由四元组(源 IP、源端口、目的 IP、目的端口)标识,手机切 Wi-Fi/5G 时 IP 变了,TCP 连接必断,得重建。QUIC 用**连接 ID** 标识连接,与 IP 解耦,网络切换后连接可平滑延续。

| 能力 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 首包 RTT | 2~3 | 2~3 | 1(0-RTT 恢复) |
| 网络切换不断连 | 否 | 否 | 是 |

## 七、服务器推送

HTTP/2 的 Server Push 允许服务器在客户端请求 HTML 时,主动把 CSS/JS 一起推过去。听起来美好,实践中却难用:服务器难以准确判断客户端缓存状态,容易推冗余资源。Chrome 已于 2022 年移除对 HTTP/2 Server Push 的支持。

HTTP/3 保留了推送能力,但生态同样冷淡。当下主流替代方案是 `<link rel="preload">`、103 Early Hints 等更可控的方式。

## 八、部署与成熟度

- **HTTP/1.1**：最成熟,任何环境都能跑,代理/中间盒/调试工具全套支持。
- **HTTP/2**：广泛部署,主流 CDN、Nginx、浏览器默认支持,通常 over TLS 部署。
- **HTTP/3**：部署持续增长,主流浏览器与 CDN 已支持,但 UDP 在部分企业网络/防火墙被限速或阻断,需 fallback 到 HTTP/2。

## 九、选型建议

- **大多数 Web 服务**:HTTP/2 已是稳妥默认,收益大、风险低。
- **弱网/移动端为主**:HTTP/3 的连接迁移与抗丢包收益明显,值得在 CDN 层开启并保留 fallback。
- **受严格中间盒审计的环境**(金融、内网合规):HTTP/2 over TLS 更可控,HTTP/3 的 UDP 与内嵌加密可能被策略拒绝。
- **遗留系统/简单脚本**:HTTP/1.1 仍够用,不必强行升级。

## 十、一句话总结

HTTP/1.1 解决了"能通信",HTTP/2 解决了"应用层并发",HTTP/3 解决了"传输层并发与移动性"。每一代都补上一代的队头阻塞,但每代也都带来新的部署成本。
