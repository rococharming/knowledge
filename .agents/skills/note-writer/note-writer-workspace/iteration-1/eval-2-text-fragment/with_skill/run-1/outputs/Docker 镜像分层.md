# 一、镜像分层的基本概念

Docker 镜像是由多层只读层（layer）叠加而成的。每一层都是文件系统的一部分变更记录，从下到上依次叠加，构成镜像的完整文件系统视图。

这种分层不是实现细节，而是 Docker 设计的核心。它带来两个关键能力：层复用与写时复制。理解分层，才能理解镜像为什么这样构建、容器为什么这样运行、镜像体积为什么有时超出预期。

# 二、分层与 Dockerfile 指令的对应

镜像的每一层对应 Dockerfile 里的一条指令。构建时，每条会修改文件系统的指令都会产生一个新层。

常见的产层指令：

- `FROM`：引入基础镜像，产生一层。
- `RUN`：执行命令并提交结果，产生一层。
- `COPY`：把文件复制进镜像，产生一层。

示例：

```dockerfile
FROM alpine:3.18        # 基础层
RUN apk add curl        # 新增一层：安装 curl
COPY app.sh /app/       # 新增一层：放入脚本
```

这个 Dockerfile 会产生三个层（不含基础镜像内部已有的层）：`FROM` 带来基础镜像层，`RUN` 新增一层包含 curl，`COPY` 新增一层包含 app.sh。最终镜像就是这些层从下到上依次叠加的结果。

> 注意：并非所有指令都产层。`ENV`、`LABEL`、`WORKDIR` 等指令只修改镜像元数据，不产生新的文件系统层。

# 三、分层的复用价值

分层最大的好处是复用。如果多个镜像共享相同的基础层，磁盘上只存一份；构建时也能命中缓存，不必重复执行相同指令。

## 1、存储复用

同一台机器上拉取多个基于 `alpine` 的镜像时，`alpine` 那一层只在磁盘存一份，各镜像共享。镜像越多、共享的基础层越多，节省的磁盘空间越显著。

## 2、构建缓存

Dockerfile 前面的指令如果没变，构建时直接复用已有层，跳过执行。这也是为什么把变化少的指令放前面、变化多的放后面——能最大化缓存命中，加快构建速度。

# 四、容器可写层与写时复制

容器启动时，Docker 会在镜像层之上再加一层可写层。容器运行中所有对文件系统的修改都写在这层，镜像本身保持不变。

这就是写时复制（Copy-on-Write）：容器读取文件时，从上往下在各层查找，命中即返回；修改文件时，先把文件从下层复制到可写层，再在可写层修改。

写时复制的意义在于：同一个镜像可以同时启动成百上千个容器，它们共享只读的镜像层，各自只维护自己那份很小的可写层，互不干扰。

# 五、删除文件与镜像体积

分层也带来一个容易踩的坑：在某一层删除文件，底层对应的文件其实还在。

## 1、为什么删不干净

层是只读的，`RUN rm /some/file` 这条指令产生的新层只是"标记删除"——在上层用一个 whiteout 记录遮挡住底层文件。底层那一层里的文件依然存在，占用空间。

这意味着：即使后续层删掉了基础镜像里的大文件，镜像体积也不会变小，最终镜像可能比预期大很多。

## 2、应对思路

- **在同一层清理**：在同一 `RUN` 中安装并清理临时文件，避免临时文件被写进某个中间层。
- **多阶段构建**：用多阶段构建（multi-stage build），只把最终需要的产物复制到目标镜像，丢弃中间产物所在的所有层。

示例：

```dockerfile
# 不推荐：留下含构建产物的中间层
RUN wget big-file.tar.gz
RUN tar xzf big-file.tar.gz
RUN rm big-file.tar.gz   # 删了也没用，big-file 仍在前面那层

# 推荐：在同一层完成下载和清理
RUN wget big-file.tar.gz \
    && tar xzf big-file.tar.gz \
    && rm big-file.tar.gz
```

右侧写法把下载、解压、清理放进同一条 `RUN`，临时文件不会遗留到任何层，镜像更小。

# 六、小结

Docker 镜像的分层机制把文件系统变更拆成只读层，带来了存储复用与构建缓存的价值，配合容器可写层实现写时复制，让同一镜像能高效支撑大量容器。代价是层一旦产生即不可变，删除文件只能遮挡不能真正清除，需要在编写 Dockerfile 时注意在同一层内清理临时文件。
