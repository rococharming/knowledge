# Docker 镜像分层原理

Docker 镜像并非一个整体文件，而是由多层只读层叠加而成。理解分层机制是看懂镜像体积、构建缓存和容器文件行为的基础。

## 一、镜像的分层结构

Docker 镜像由多层 **只读层** 叠加构成，每一层对应 Dockerfile 里的一条指令：

- `FROM` 产生一层（基础镜像层）
- `RUN` 产生一层（执行命令产生的文件变更）
- `COPY` 产生一层（拷入文件产生的变更）

每条指令在构建时生成一个新的只读层，记录相对于上一层的文件系统差异。最终镜像就是这些层自下而上堆叠的结果。

## 二、分层的复用与缓存

分层结构的核心好处是 **复用**：

- **磁盘存储**：多个镜像若共享相同的基础层，磁盘上只存一份，不会重复占用空间。
- **构建缓存**：构建时若某层及其上层未发生变化，可命中缓存直接复用，无需重新执行对应指令。

这也是 Dockerfile 中把变化频率低的指令（如安装依赖）放在前面、变化频率高的（如拷贝业务代码）放在后面的原因——前层稳定，缓存命中率更高。

## 三、容器可写层与写时复制

容器启动时，Docker 会在镜像的只读层之上 **再加一层可写层**：

- 所有对容器的修改（写文件、改文件、删文件）都发生在这一可写层。
- 镜像本身保持 **只读不变**，多个容器可共享同一镜像而互不干扰。

这种机制就是 **写时复制（Copy-on-Write）**：只有当容器真正修改某个文件时，才把该文件从只读层复制到可写层再修改，未修改的文件继续共享只读层。

## 四、删除文件的陷阱

分层结构带来一个容易忽略的副作用——删除文件并非真正删除：

- 在新层中"删除"文件，实际只是在可写层做了一个 **删除标记**，隐藏了下层文件。
- 底层只读层里的原文件 **依然存在**，仍占据镜像空间。

因此镜像实际体积可能比预期更大。常见对策是把会产生大文件再删除的操作（如下载、解压、清理）合并到 **同一条 `RUN` 指令** 中，避免中间层残留无用文件。
