# 一、rebase 的基本概念

`git rebase` 是 Git 中用于"整理提交历史"的命令，它把一系列提交挪到一个新的起点（base）上，从而让提交线变成一条直线。

简单来说，当你在分支上开发时，主线（如 `main`）可能已经往前走了。`rebase` 会把你分支上的提交逐个"摘下来"，放到主线最新提交的后面重新接上，效果像是"我的分支一直基于最新的主线开发"。它解决的核心问题是： **保持提交历史线性、整洁，避免大量分叉与合并的噪音。**

> 注意：rebase 会重写提交历史，被挪动的提交会获得新的 commit hash。这一点决定了它在协作场景下的使用边界（见后文）。

理解 rebase 前，建议先熟悉 [[1、Git基础|Git 基础]] 中的提交与分支概念。

# 二、rebase 的工作原理

## 1、提交是怎么被"挪"的

假设当前状态：

- `main` 上有提交 `A → B → C`
- 你从 `B` 拉出分支 `feature`，在其上提交了 `X → Y`

此时的历史是：

```
A → B → C        (main)
     \
      X → Y      (feature)
```

执行 `git rebase main`（在 `feature` 分支上）后，Git 会：

1. 找到 `feature` 与 `main` 的共同祖先（这里是 `B`）。
2. 把 `feature` 上自共同祖先以来的提交（`X`、`Y`）暂存起来。
3. 把 `feature` 指针移到 `main` 的最新提交（`C`）。
4. 把暂存的提交按顺序重新应用到 `C` 之后，得到新的 `X'`、`Y'`。

结果变成：

```
A → B → C → X' → Y'   (main, feature)
```

分支不再有分叉，提交历史成一条直线。这里的关键是：`X'`、`Y'` 是 **重新生成的新提交**，内容相同但 hash 不同。

## 2、与 merge 的区别

| 方面 | `git merge` | `git rebase` |
|---|---|---|
| 历史 | 保留分叉，产生合并提交 | 重写为线性历史 |
| 提交 hash | 原提交不变 | 被挪动的提交 hash 改变 |
| 冲突处理 | 一次性解决 | 可能逐个提交解决 |
| 适用场景 | 想保留真实分支拓扑 | 想要干净线性历史 |

> 注意：merge 保留"发生了什么"，rebase 让历史读起来像"一开始就是这样设计的"。

# 三、基本用法

## 1、把当前分支 rebase 到目标分支

示例：

```bash
git switch feature
git rebase main
```

这条命令把 `feature` 分支上的提交重新接到 `main` 最新提交之后。执行前确保当前在要 rebase 的分支上。

## 2、解决冲突

rebase 逐个重放提交时，如果某个提交与目标分支冲突，会暂停并提示。此时：

```bash
# 1. 手动编辑冲突文件，解决冲突
# 2. 标记已解决
git add <冲突文件>

# 3. 继续 rebase
git rebase --continue

# 如果想跳过当前提交
git rebase --skip

# 如果想放弃整个 rebase，回到开始前状态
git rebase --abort
```

与 merge 不同，rebase 的冲突可能 **逐个提交出现**，因为每个提交是单独重放的。这也是 rebase 有时比 merge 繁琐的原因。

> 注意：解决冲突后用 `git add` 暂存，但 **不要** `git commit`，而是直接 `git rebase --continue`，rebase 会自动完成该提交。

# 四、交互式 rebase

## 1、什么是交互式 rebase

交互式 rebase（`git rebase -i`）允许你在重放提交前，对每一个提交进行编辑：调整顺序、合并、改写提交信息，甚至删除。它是 **整理本地提交历史的最强工具**。

## 2、常用操作

```bash
# 整理最近 3 个提交
git rebase -i HEAD~3
```

执行后打开编辑器，列出待处理的提交：

```
pick 1a2b3c4 添加登录页
pick 5d6e7f8 修复 typo
pick 9a0b1c2 重构登录逻辑
```

把 `pick` 改成相应动作即可：

| 动作 | 含义 |
|---|---|
| `pick` | 保留该提交 |
| `reword` | 保留提交，但改提交信息 |
| `squash` | 把该提交合并到前一个提交，并合并提交信息 |
| `fixup` | 同 squash，但丢弃该提交的提交信息 |
| `drop` | 删除该提交 |

例如把"修复 typo"改成 `fixup`，它就会无声并入前一个提交，历史更干净。

> 注意：交互式 rebase 会重写历史，已推送到共享分支的提交不要随便 rebase。

# 五、黄金法则与常见陷阱

## 1、不要 rebase 已推送的公共提交

> 注意： **永远不要对已经推送到共享分支、且他人可能基于它工作的提交执行 rebase。** 因为 rebase 会生成新 hash，其他人本地仍是旧提交，再次拉取时会出现重复提交和混乱冲突。

rebase 的安全场景是：对 **只有自己用的本地分支** 整理历史，整理好后再推送。

## 2、rebase 后推送

rebase 重写了历史，本地与远程的提交已不同。直接 `git push` 会被拒绝，需要强制推送：

```bash
git push --force-with-lease
```

> 注意：优先用 `--force-with-lease` 而非 `--force`。前者会在远程被他人更新时拒绝推送，避免覆盖别人的工作。

## 3、rebase 与已合并分支

如果分支已经被 merge 进主线，再对它 rebase 会让那些提交"复活"成新提交，造成重复。rebase 适用于尚未合并的分支整理。

# 六、小结

rebase 的价值是把杂乱的分支历史整理成清晰的线性叙事。核心要记住两点： **它能重写历史** （因此整理本地提交很安全、整理公共提交很危险），且交互式 rebase 是打磨提交序列的利器。

掌握 rebase 后，下一步可以学习 [[1、Git基础|Git 基础]] 中的分支与提交流程，理解它们如何配合。后续整理 Git 分支策略、`git cherry-pick` 等笔记时，也会反复用到 rebase 的"重放提交"思想。
