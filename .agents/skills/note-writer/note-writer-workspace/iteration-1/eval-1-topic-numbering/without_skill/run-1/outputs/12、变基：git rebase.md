# 一、什么是 rebase

`rebase` 字面意思是“变基”，即 **更换分支的基底提交**。它会取出当前分支自分叉点以来的一系列提交，逐个重新应用到指定的目标提交之上。

理解 rebase 的关键，是分清 **基底（base）** 和 **待重放的提交**：

- 基底：分支当前所依赖的起点提交，通常是它与目标分支的分叉点。
- 待重放的提交：当前分支上自分叉点之后产生的一系列提交。

执行 rebase 后，这些提交会基于新的基底被重新创建，看起来就像是从目标提交直接“长出来”的一样。

> [!note] rebase 属于重写历史
> rebase 会重新创建提交对象。新提交与原提交内容可能相同，但提交哈希不同。这与 [[11、撤销提交与恢复历史]] 中 `reset` 移动分支指针的做法不同——rebase 改变的是提交序列本身的连接关系。

# 二、为什么需要 rebase

合并分支有两种典型做法：

| 做法 | 命令 | 历史形态 |
| --- | --- | --- |
| 普通合并 | `git merge` | 保留分叉与合并提交，历史是“真实发生过的” |
| 变基后再合并 | `git rebase` + `git merge` | 历史变成一条直线，看起来像“从未分叉过” |

假设有如下分叉：

```text
      C --- D       (feature)
     /
A --- B             (main)
```

- 用 `git merge` 合并，历史保留分叉，最终出现一个合并提交：

```text
      C --- D
     /       \
A --- B ------ M   (main)
```

- 用 `git rebase` 后再合并，feature 的提交被“搬到” main 末端，历史变成直线：

```text
A --- B --- C' --- D'   (main)
```

`C'`、`D'` 是重新应用后生成的新提交，内容与 `C`、`D` 对应，但哈希不同。

rebase 的核心价值是 **保持线性的、易读的提交历史**。这在以下场景特别有用：

- 个人开发分支同步主干最新改动后，希望历史干净
- 开源项目中，维护者要求贡献者在 PR 中保持线性历史
- 审查代码时，希望看到一组连续的、逻辑清晰的提交

# 三、基本用法：把分支变基到目标提交

## 1、命令

```shell
git rebase <目标提交或分支>
```

例如在 `feature` 分支上，想把它变基到 `main` 的最新提交：

```shell
git checkout feature
git rebase main
```

## 2、执行过程

执行前：

```text
      C --- D       (feature, HEAD)
     /
A --- B --- E       (main)
```

`main` 在分叉后新增了 `E`。`git rebase main` 会：

1. 找到 `feature` 与 `main` 的分叉点 `B`。
2. 收集 `feature` 上自 `B` 之后的提交：`C`、`D`。
3. 把 `feature` 的基底“换”成 `main` 的最新提交 `E`。
4. 依次重新应用 `C`、`D`，生成新提交 `C'`、`D'`。

执行后：

```text
A --- B --- E               (main)
             \
              C' --- D'      (feature, HEAD)
```

`C`、`D` 在当前分支视图中不再可见，但短期内通常仍能通过 `reflog` 找回，见 [[11、撤销提交与恢复历史]]。

# 四、处理冲突

rebase 逐个重放提交。如果某个提交与目标基底在新基底上的对应改动有重叠，Git 会暂停并报告冲突。

## 1、查看冲突

```shell
git status
```

冲突文件中会包含冲突标记，解决方式与普通合并冲突一致。

## 2、解决并继续

手动编辑冲突文件后：

```shell
git add <file>
git rebase --continue
```

Git 会继续重放下一个提交。如果继续过程中又有冲突，重复上述步骤。

## 3、跳过当前提交

如果某个提交重放后产生的冲突难以处理，且该提交可以放弃，可以跳过它：

```shell
git rebase --skip
```

## 4、中止整个 rebase

如果希望完全放弃本次变基、回到 rebase 之前的状态：

```shell
git rebase --abort
```

`--abort` 会取消当前未完成的 rebase 流程，恢复分支到执行 rebase 前的位置。

> [!tip] rebase 前保持工作区干净
> rebase 期间 Git 需要切换工作区内容。如果工作区有未提交改动，可能无法开始或继续 rebase。开始前先运行 `git status` 确认干净，必要时用 `git stash` 暂存改动。

# 五、交互式 rebase

交互式 rebase 允许在重放过程中 **修改提交序列**，是整理历史最常用的工具。

## 1、命令

```shell
git rebase -i <目标提交>
```

例如整理 `feature` 分支上最近 3 个提交：

```shell
git rebase -i HEAD~3
```

Git 会打开编辑器，列出待重放的提交：

```text
pick e3a1b2c 添加登录表单
pick 7f9d4a1 修复登录校验
pick 2b8c5e0 补充注释
```

每一行开头的命令决定了如何处理该提交。

## 2、常用动作

| 动作 | 含义 |
| --- | --- |
| `pick` | 保留该提交（默认） |
| `reword` | 保留提交内容，但修改提交信息 |
| `edit` | 暂停在该提交，可修改其内容后再继续 |
| `squash` | 把该提交合并到前一个提交，并合并提交信息 |
| `fixup` | 与 `squash` 类似，但丢弃该提交的提交信息 |
| `drop` | 丢弃该提交 |

## 3、典型场景：合并多个小提交

把零碎提交合并成一个清晰的提交：

```text
pick e3a1b2c 添加登录表单
fixup 7f9d4a1 修复登录校验
fixup 2b8c5e0 补充注释
```

完成后，三个提交会合并成一个，提交信息沿用第一个。

## 4、典型场景：调整提交顺序

直接调整编辑器中各行的顺序，保存退出后，Git 会按新顺序重放提交。注意调换顺序可能引发冲突。

# 六、rebase 与 merge 的取舍

| 对比项 | `git merge` | `git rebase` |
| --- | --- | --- |
| 历史形态 | 保留分叉与合并提交 | 重放为线性序列 |
| 是否重写历史 | 否 | 是，提交哈希变化 |
| 冲突处理 | 一次性解决 | 逐个提交重放，可能多次冲突 |
| 适用场景 | 整合已共享分支、保留真实分叉 | 整理本地分支、保持线性历史 |

两种做法并不互斥。常见工作流是：

> 在本地开发分支上用 rebase 同步主干、整理提交；最终合并到主干时用 merge（或快进合并）。

# 七、黄金法则：不要 rebase 已共享的提交

rebase 会重写历史。如果某个提交已经被推送到远程、且其他人可能基于它开发，对它执行 rebase 会造成历史分叉，带来难以处理的冲突。

> [!danger] 不要对已推送的公共分支执行 rebase
> 对已经共享的提交执行 rebase，会让其他协作者的本地历史与你的新历史不一致，后续合并会出现重复提交和混乱冲突。公共分支应使用 `git merge` 或 `git revert`。

回顾 [[10、修改最近一次提交]] 中的 `amend`：它同样会替换提交、改变哈希，因此也只适用于本地未共享的提交。rebase 是同一原则的更一般形式——只重写 **自己独占** 的提交。

# 八、安全地 abort 与恢复

## 1、rebase 期间的状态

rebase 进行中时，Git 会在 `.git/` 下记录 rebase 的进度。此时：

- `git status` 会提示当前正在 rebase，并显示已重放到哪个提交。
- `git rebase --abort` 可以随时回到 rebase 开始前的状态。

## 2、用 reflog 找回 rebase 前的提交

如果 rebase 已经完成，但事后想回到 rebase 之前的状态，可以用 `reflog` 定位原提交：

```shell
git reflog
```

找到 rebase 开始前 `HEAD` 所在的位置（通常标注 `rebase: ...` 或 `rebase (start)`），然后：

```shell
git reset --hard <rebase前的提交哈希>
```

`reflog` 的使用细节见 [[11、撤销提交与恢复历史]]。

> [!warning] reset --hard 会丢弃工作区改动
> 这里使用 `--hard` 是因为目标是将分支完整回到 rebase 前的状态。执行前同样应确认工作区中没有未保存的有价值改动。

# 九、操作流程

```text
需要整理或同步本地分支历史
  │
  ├─ 同步主干最新改动
  │    └─ git fetch
  │       git rebase <主干分支>
  │          ├─ 无冲突：自动完成
  │          └─ 有冲突：解决 → git add → git rebase --continue
  │
  ├─ 整理本地提交序列
  │    └─ git rebase -i HEAD~N
  │       ├─ 合并：squash / fixup
  │       ├─ 改信息：reword
  │       └─ 调顺序：调整行顺序
  │
  └─ 出错时
       ├─ 放弃本次 rebase：git rebase --abort
       └─ 找回 rebase 前状态：git reflog → git reset --hard <哈希>
```

提交前的暂存与检查流程见 [[4、查看状态、暂存和提交]]；查看整理后的提交历史见 [[9、灵活查看提交历史]]；撤销与恢复的完整机制见 [[11、撤销提交与恢复历史]]。
