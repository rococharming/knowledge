# 一、Docker 镜像分层的基本概念

Docker 镜像是由多层只读层叠加而成的。每一层都是一组文件系统变更，叠在一起就构成了镜像最终的文件视图。

理解分层是理解 Docker 的关键：它解释了镜像为什么能复用、构建为什么能加速、容器为什么能"随手改而不破坏镜像"，也解释了镜像为什么常常比预期大。

# 二、分层与 Dockerfile 指令的对应

镜像里的每一层对应 Dockerfile 里的一条指令。构建镜像时，Docker 会按顺序执行每条指令，每条产生变更的指令都会生成一个新层。

常见指令与层的对应：

| Dockerfile 指令 | 是否产生新层 | 说明 |
|---|---|---|
| `FROM` | 是 | 引入基础镜像的层 |
| `RUN` | 是 | 执行命令并保存文件系统变更 |
| `COPY` / `ADD` | 是 | 把文件加入镜像 |
| `ENV` / `LABEL` | 通常是 | 记录元数据（现代版本会优化） |
| `WORKDIR` | 否 | 只影响后续指令的工作目录 |

示例：

```dockerfile
FROM node:20
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
```

这里的 `FROM`、`COPY package.json .`、`RUN npm install`、`COPY . .` 各产生一个新层；`WORKDIR /app` 不产生层，只切换工作目录。

> 注意：`RUN` 指令写成一条还是多条，直接影响层的数量和镜像大小。常见做法是把相关的 `apt-get install` 和清理命令用 `&&` 串成一条 `RUN`，避免清理掉的文件仍残留在前一层里。

# 三、分层带来的复用

分层结构最大的好处是复用，体现在两个地方：

- **磁盘存储**：如果多个镜像共享相同的基础层，磁盘上只存一份。比如十个镜像都基于 `node:20`，这个基础层只占一份磁盘空间。
- **构建缓存**：构建时，Docker 会按指令顺序逐层检查缓存。如果某层的输入（指令文本、被复制的文件内容）没变，就直接复用旧层，跳过实际执行。

这种机制让"改一行代码重新构建"变得很快——前面没变的层都命中缓存，只有变化点之后的层需要重建。

> 注意：Dockerfile 中把变化频繁的部分放在后面，能最大化缓存命中。比如先 `COPY package.json` + `RUN npm install`，最后再 `COPY . .`，这样改业务代码时不会让依赖安装层失效。

# 四、容器与写时复制

容器启动时，Docker 并不是把整个镜像复制一份，而是在镜像层之上再加一层 **可写层**。

- 所有对容器的修改（写文件、删除文件、改配置）都写在这层可写层里。
- 镜像层本身完全只读、保持不变。
- 多个容器基于同一个镜像启动时，共享只读的镜像层，各自有独立的可写层。

这就是 **写时复制（Copy-on-Write）**：读取时直接从镜像层读，只有要修改时才把对应文件复制到可写层再改。镜像本身始终不被触碰，所以同一个镜像可以同时跑很多容器。

> 注意：容器删除后，它的可写层随之消失。需要持久化的数据应放到 **卷（volume）** 或绑定挂载中，不要写进可写层。

# 五、分层的陷阱：删除并不真正删除

分层是只读层叠加，这意味着 **删除文件其实只是在新层里标记删除**，底层里那个文件还在。

典型场景：在一个基于大镜像的 Dockerfile 里，先 `COPY` 了一个大文件，后面又 `RUN rm` 删掉它。可写层记录了"删除"这个动作，但大文件所在的那一层依然存在、依然占空间。结果就是镜像比预期大很多。

应对方式：

- **合并到同一层**：把"下载→使用→清理"用一条 `RUN` 串起来，让清理和产生在同一层发生。
- **多阶段构建**：用一个临时镜像构建产物，再 `COPY` 到精简的基础镜像里，把构建期的中间文件彻底留在构建镜像中，不进入最终镜像。
- **选小基础镜像**：如 `alpine`、`distroless`，从源头减少不必要的层和文件。

# 六、小结

Docker 镜像 = 多个只读层叠加；每层对应一条 Dockerfile 指令。分层带来存储复用和构建缓存，容器通过可写层 + 写时复制实现"改而不破镜像"。代价是删除不真正回收空间，需要靠合并 `RUN`、多阶段构建来控制镜像体积。
