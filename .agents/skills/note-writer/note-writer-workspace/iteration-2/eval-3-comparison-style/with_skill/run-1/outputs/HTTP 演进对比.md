# 一、HTTP 演进概览

HTTP 是 Web 通信的基础协议，从 1997 年的 HTTP/1.1 到今天的 HTTP/3，每一代都在解决上一代的性能瓶颈。理解三者的差异，本质上是理解"如何在不可靠、有延迟的网络上传得更快"。

三代的演进动机可以浓缩成一句话：

- **HTTP/1.1**：确立了持久连接和管线化的标准，但队头阻塞严重，连接利用率低。
- **HTTP/2**：在 TCP 之上引入二进制分帧和多路复用，一个连接就能并发多个请求。
- **HTTP/3**：抛弃 TCP，改用基于 UDP 的 QUIC，把多路复用做到传输层，彻底消除队头阻塞。

这里的关键是：演进不是推翻重来，而是**层层下探**——HTTP/2 优化了应用层，HTTP/3 则动了传输层。每一代都保持了对上一代的语义兼容（方法、状态码、头部含义不变），变得只是传输方式和帧格式。

# 二、核心机制对比

## 1、传输层与连接模型

三代最根本的差异在传输层。HTTP/1.1 和 HTTP/2 跑在 TCP 上，HTTP/3 跑在 QUIC（UDP）上。

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | QUIC（UDP） |
| 加密 | 可选（HTTPS） | 实践中强制 TLS 1.2+ | 强制 TLS 1.3（内建于 QUIC） |
| 连接复用 | keep-alive 复用 TCP 连接 | 单 TCP 连接多路复用 | 单 QUIC 连接多路复用 |
| 建连握手 | TCP + TLS（多次 RTT） | TCP + TLS（2-3 RTT） | QUIC 合并握手（1 RTT，甚至 0 RTT） |

> 注意：HTTP/2 规范本身不强制 TLS，但所有主流浏览器只在 HTTPS 上实现 HTTP/2（h2 over TLS），所以实践中它和 TLS 绑定。HTTP/3 则把 TLS 1.3 直接嵌进 QUIC，加密是协议的硬性组成部分。

## 2、多路复用与并发

这是三代差异最直观的地方，也是性能差距的主要来源。

- **HTTP/1.1**：一个 TCP 连接同一时刻只能处理一个请求。浏览器靠"开多个连接"（通常 6 个/域名）来并发，但每个连接仍要排队。
- **HTTP/2**：一个连接上可以同时跑多个请求/响应，各自拆成帧交错传输，互不阻塞。
- **HTTP/3**：同样多路复用，但因为跑在 QUIC 上，**单个流丢包不会阻塞其他流**——这是相对 HTTP/2 的关键改进。

HTTP/2 的多路复用解决了应用层的队头阻塞（HOL），但 TCP 层的队头阻塞仍在：一旦某个包丢失，TCP 要等重传，整个连接上所有流都被卡住。HTTP/3 把流做到 QUIC 层，每个流独立有序，丢包只影响那一个流。

## 3、头部与压缩

HTTP/1.1 的头部是纯文本，且每次请求几乎重复发送一堆相同的头（Cookie、User-Agent 等），带宽浪费明显。

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 头部格式 | 纯文本 | 二进制帧 | 二进制帧 |
| 压缩 | 无 | HPACK | QPACK（HPACK 的 QUIC 版） |
| 重复头部 | 每次全量发送 | 维护静态/动态表，只发差量 | 同 HPACK 思路，适配乱序传输 |

HPACK 用哈夫曼编码 + 静态/动态表，大幅压缩重复头部。QPACK 是它的 QUIC 适配版，因为 QUIC 的流可以乱序到达，QPACK 在处理表更新时比 HPACK 更谨慎，以避免压缩上下文错乱。

# 三、关键特性详解

## 1、HTTP/1.1：keep-alive 与管线化

HTTP/1.1 默认开启 `Connection: keep-alive`，一个 TCP 连接可以串行发多个请求，省去了反复建连的开销。

```http
GET /a.css HTTP/1.1
Host: example.com

GET /b.js HTTP/1.1
Host: example.com
```

两个请求复用一条连接，但**必须按顺序**：a.css 的响应回来后才能发 b.js。这就是 HTTP/1.1 的队头阻塞——前面的请求慢了，后面全排队。

管线化（pipelining）允许一次性发出多个请求，但响应仍须按序返回，且实践中代理和服务器支持差，基本被弃用。浏览器普遍改用"多连接并发"来绕过这个限制。

## 2、HTTP/2：二进制分帧与多路复用

HTTP/2 把请求/响应拆成带流 ID 的二进制帧，多个流的帧在同一 TCP 连接上交错传输。

```
客户端                       服务器
  |--- DATA(stream=1) ------->|
  |--- HEADERS(stream=3) ---->|
  |<-- DATA(stream=1) ---------|
  |--- DATA(stream=3) ------->|
  |<-- HEADERS(stream=3) ------|
```

每个流独立，互不阻塞（在应用层）。引入的特性：

- **多路复用**：单连接并发无数请求。
- **头部压缩**：HPACK。
- **服务端推送**：服务器可主动推送资源（如 CSS/JS），减少往返。实践中推送难用准、易浪费，HTTP/3 已弱化，主流趋势是用 `preload` 链接代替。
- **流优先级**：标记哪些流更重要，优先调度。

> 注意：HTTP/2 没有消除 TCP 层队头阻塞。丢一个包，整个 TCP 连接所有流都被卡到重传完成。

## 3、HTTP/3：QUIC 与 UDP

QUIC 是 Google 设计、IETF 标准化的传输协议，跑在 UDP 上，把 TCP 的可靠传输 + TLS 1.3 的加密 + HTTP/2 的多路复用融合成一层。

- **连接迁移**：连接用一组 Connection ID 标识，不绑定 IP+端口。手机从 Wi-Fi 切到 4G，IP 变了，QUIC 连接不断，TCP 做不到。
- **0-RTT 建连**：对已连过的服务器，首个请求可以和握手一起发出去，几乎零等待。
- **流级独立重传**：丢包只阻塞丢包的那个流。
- **握手合并**：TLS 握手嵌进 QUIC 握手，比 TCP+TLS 少一个 RTT。

示例：用 curl 测试 HTTP/3（需支持 QUIC 的版本）。

```bash
curl --http3 -I https://www.cloudflare.com
```

如果服务器支持，响应会走 QUIC/HTTP/3；不支持时自动回退到 HTTP/2 或 1.1。

# 四、对比总表与权衡

## 1、特性对比总表

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 发布年份 | 1997 | 2015 | 2022（RFC 9114） |
| 传输层 | TCP | TCP | QUIC（UDP） |
| 多路复用 | 否（靠多连接） | 是（应用层） | 是（传输层） |
| 应用层队头阻塞 | 有 | 无 | 无 |
| 传输层队头阻塞 | 有 | 有 | 无 |
| 头部压缩 | 无 | HPACK | QPACK |
| 二进制格式 | 否（文本） | 是 | 是 |
| 加密 | 可选 | 实践强制 | 强制 |
| 建连 RTT | 2-3 | 2-3 | 1（首连）/ 0（复连） |
| 连接迁移 | 不支持 | 不支持 | 支持 |
| 服务端推送 | 无 | 有 | 有（弱化） |

## 2、迁移与兼容性权衡

升级不是无代价的，要权衡收益和成本。

- **HTTP/1.1 → HTTP/2**：成本低。服务器开启 h2（通常配合 TLS 和 ALPN 协商），浏览器自动升级，应用代码几乎不用改。收益主要在高并发小请求场景。
- **HTTP/2 → HTTP/3**：成本高。QUIC 跑 UDP，许多防火墙、负载均衡器、中间盒只优化了 TCP，对 UDP 放行差或限速；运维监控工具对 QUIC 的支持也较新。需要服务端、CDN、负载均衡全链路支持。
- **回退机制**：HTTP/3 的发现通过 `Alt-Svc` 头声明，客户端先用 HTTP/2 连上，再尝试升级到 HTTP/3，失败就留在 h2。这保证了平滑过渡，不破坏现有可用性。

> 注意：UDP 在部分企业网络和云环境中被限制或丢包率较高。部署 HTTP/3 前要确认网络路径对 UDP 的支持，否则可能适得其反。

## 3、选型建议

- **新项目 / 静态资源为主的站点**：优先上 HTTP/2，收益大、成本低。CDN 基本默认支持。
- **弱网、移动端、连接切换频繁的场景**：HTTP/3 价值最大，连接迁移和 0-RTT 对移动体验提升明显。前提是 CDN 和基础设施支持。
- **企业内网 / 受限网络**：HTTP/2 更稳妥，UDP 可能被防火墙拦截，HTTP/3 未必能跑通。
- **遗留系统**：HTTP/1.1 仍广泛可用，短期内不会淘汰，但并发性能差，新接口建议至少走 h2。

# 五、延伸

三代的演进主线是"把多路复用层层下推"：HTTP/2 在应用层多路复用，HTTP/3 在传输层多路复用。语义层（方法、状态码、头、缓存）保持稳定，这也是为什么上层应用几乎无感升级。
