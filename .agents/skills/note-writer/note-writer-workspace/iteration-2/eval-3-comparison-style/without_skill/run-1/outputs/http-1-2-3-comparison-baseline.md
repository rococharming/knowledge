# HTTP/1.1、HTTP/2、HTTP/3 对比笔记

HTTP 协议经历了三代演进，每一代都针对上一代的瓶颈做了改进。三代的核心差异集中在 **传输层**、**多路复用能力** 和 **队头阻塞** 三个维度。本文以对比视角梳理三者差异，并给出选型建议。

## 一、核心维度对比

先看一张总览表，后续各节展开关键差异。

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 发布年份 | 1997（RFC 2068） | 2015（RFC 7540） | 2022（RFC 9114） |
| 传输层 | TCP | TCP | **QUIC（基于 UDP）** |
| 加密 | 可选（HTTPS 叠 TLS） | 基本必配 TLS 1.2+ | **强制 TLS 1.3**（内建于 QUIC） |
| 多路复用 | 否 | 是（二进制帧） | 是（独立流） |
| 队头阻塞 | 有（应用层 + TCP 层） | 解决应用层，**仍存在 TCP 层** | **彻底解决**（流之间独立） |
| 头部压缩 | 无 | HPACK | QPACK |
| 服务端推送 | 无 | 支持（实践中逐渐弃用） | 不支持（转向 103 Early Hints） |
| 连接迁移 | 不支持 | 不支持 | **支持** |
| 0-RTT | 不支持 | 不支持 | **支持** |

## 二、传输层：从 TCP 到 QUIC

这是三代之间最根本的分界线。

### HTTP/1.1 与 HTTP/2：共用 TCP

两者都跑在 TCP 之上，需要先完成 TCP 三次握手。若启用 HTTPS，还要叠加 TLS 握手，首次请求的延迟成本较高。

```
HTTP/1.1 + HTTPS:  TCP 握手（1 RTT） + TLS 握手（1~2 RTT） + 请求（1 RTT）
HTTP/2   + HTTPS:  TCP 握手（1 RTT） + TLS 握手（1~2 RTT） + 请求（1 RTT）
```

从传输层看，HTTP/2 并没有比 HTTP/1.1 省握手。

### HTTP/3：基于 QUIC

QUIC 是 Google 设计、IETF 标准化的传输协议，跑在 **UDP** 之上，把 TLS 1.3 直接内建进去。这意味着：

- 握手与加密合并，首次连接只需 **1 RTT**。
- 重连场景下可做到 **0-RTT**，即第一个数据包就能携带业务请求。

```
HTTP/3 首次:   QUIC 握手（含 TLS 1.3，1 RTT） + 请求（合并）
HTTP/3 重连:   0-RTT，请求随握手包一起发出
```

代价是 UDP 在部分网络（企业防火墙、运营商）会被限速或阻断，部署 HTTP/3 时需考虑回退。

## 三、多路复用与队头阻塞

这是理解三代演进的主线。

### HTTP/1.1：每个请求一条连接

HTTP/1.1 默认使用 **持久连接**（keep-alive），但一个 TCP 连接在同一时刻只能处理一个请求-响应。客户端要并发只能开多条连接（浏览器通常限制同域 6 条）。

**队头阻塞（应用层）**：前一个响应没回来，后续请求只能排队。

常见的缓解手段：

- **管线化（pipelining）**：理论上允许连续发送请求，但响应必须按序返回，且中间代理支持差，实际几乎没人用。
- **域名分片（domain sharding）**：开多个子域名绕过连接数限制。
- **合并资源**：雪碧图、打包 JS/CSS，减少请求数。

### HTTP/2：二进制帧多路复用

HTTP/2 把请求/响应拆成 **二进制帧**，多个流的帧可以在同一条 TCP 连接上交错传输。

- 一个域名只需一条连接。
- 浏览器不再需要域名分片。
- 应用层的队头阻塞被消除。

但 **TCP 层的队头阻塞依然存在**：TCP 保证有序交付，一旦某个包丢失，后面已到达的包也会被 TCP 持住，等丢的包重传完成。所有 HTTP/2 流都被卡住，哪怕它们逻辑上互不相关。

```
丢包影响范围:
HTTP/2:  一个 TCP 包丢失 → 整条连接所有流等待重传
HTTP/3:  一个 QUIC 包丢失 → 只影响该包内的流，其他流继续
```

### HTTP/3：流级独立

QUIC 在传输层就把流设计成独立的，每个流有自己的序号空间。丢包只阻塞那一个流，彻底消除了传输层队头阻塞。

## 四、头部压缩

请求头在 HTTP/1.1 里是明文重复传输的纯文本开销。三代压缩方案对比：

| 方案 | 用于 | 压缩算法 | 静态表 | 动态表 | 跨流共享 |
|---|---|---|---|---|---|
| 无 | HTTP/1.1 | 不压缩 | — | — | — |
| HPACK | HTTP/2 | Huffman + 静态/动态表 | 61 项 | 是 | 是（同连接） |
| QPACK | HTTP/3 | HPACK 的改造版 | 静态表 99 项 | 是 | 是（同连接） |

QPACK 之所以改造，是因为 QUIC 的流独立，头部压缩的动态表更新本身也可能乱序，需要额外的编码指令来保证一致性。因此 QPACK 在弱网下相比 HPACK 略有额外开销，但换来了流独立的优势。

## 五、连接迁移

TCP 连接由 **四元组**（源 IP、源端口、目标 IP、目标端口）标识。手机从 Wi-Fi 切到 4G/5G 时，源 IP 变了，TCP 连接必然断开，需要重新握手。

QUIC 用一个 **连接 ID（Connection ID）** 标识连接，与底层 IP 解耦。网络切换后只要连接 ID 不变，连接就能无缝延续，业务无感知。这是移动场景下 HTTP/3 的关键优势。

## 六、服务端推送

| 版本 | 推送机制 | 现状 |
|---|---|---|
| HTTP/1.1 | 无 | — |
| HTTP/2 | Server Push（PUSH_PROMISE 帧） | 浏览器逐渐移除支持，实践中收益有限、易误推送 |
| HTTP/3 | 不支持 Server Push | 改用 **103 Early Hints**，让客户端预加载 |

Server Push 的核心问题是：服务端难以准确预测客户端是否真的需要某个资源（可能已缓存），推送反而浪费带宽。

## 七、典型场景下的表现差异

### 场景 1：弱网/高丢包

- HTTP/1.1：连接多、握手成本高，丢包影响单个请求。
- HTTP/2：握手省了，但 TCP 队头阻塞让所有流一起卡。
- HTTP/3：流独立，丢包影响最小，且 0-RTT 重连恢复快。**最优**。

### 场景 2：移动端网络切换

- HTTP/1.1 / HTTP/2：连接断开，需重新握手。
- HTTP/3：连接迁移，业务不断。**最优**。

### 场景 3：高并发小请求（如 API 网关）

- HTTP/1.1：受连接数限制，需连接池。
- HTTP/2：多路复用优势明显。
- HTTP/3：与 HTTP/2 接近，但握手更快；若网络稳定，差距不大。

### 场景 4：大文件下载

- 三者差异不明显，瓶颈在带宽而非协议开销。
- HTTP/2 的单连接在极端高带宽下可能因 TCP 窗口管理反而不如多条 HTTP/1.1 连接，但这种情况较少见。

## 八、部署与兼容性

### 协商机制

HTTP/3 无法在 TCP 上协商，需要先通过 HTTP/1.1 或 HTTP/2 的响应头 **`Alt-Svc`** 告诉客户端：本站也支持 HTTP/3，地址在 UDP 某端口。客户端后续请求可切换到 QUIC。

```
Alt-Svc: h3=":443"; ma=86400
```

### 现状

- **HTTP/1.1**：仍是兜底协议，所有客户端必支持。
- **HTTP/2**：主流网站广泛部署，CDN 默认开启。
- **HTTP/3**：主流浏览器（Chrome、Edge、Firefox、Safari）和 CDN（Cloudflare、Akamai、AWS CloudFront）已支持，但 UDP 在部分企业网络受限。

## 九、选型建议

| 需求 | 推荐 |
|---|---|
| 兼容性优先、老客户端 | HTTP/1.1 |
| 通用 Web 服务、API 网关 | HTTP/2 |
| 移动端为主、弱网、全球用户 | HTTP/3（配合 HTTP/2 回退） |
| 内网服务、稳定高带宽 | HTTP/2 足够，HTTP/3 收益有限 |

实践中的稳妥做法是 **同时支持 HTTP/2 和 HTTP/3**：默认走 HTTP/2，通过 `Alt-Svc` 暴露 HTTP/3，让客户端自行升级。纯 HTTP/1.1 仅作为最后兜底。

## 十、演进脉络总结

三代演进可以归纳为三条主线：

1. **传输层换血**：TCP → QUIC（UDP），握手与加密融合。
2. **并发模型升级**：串行连接 → 二进制多路复用 → 流级独立。
3. **队头阻塞逐层消除**：应用层 → TCP 层 → 传输层彻底解决。

每一代都不是推翻重来，而是在上一代基础上针对性修复瓶颈。HTTP/3 的 QUIC 本质上是把 TCP + TLS 的职责重新拆解重组，换来了移动与弱网场景下的实质性提升，但代价是部署复杂度和 UDP 兼容性。
