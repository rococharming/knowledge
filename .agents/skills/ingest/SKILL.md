# Ingest Skill

## 概述

将 `<domain>/raw/` 下的 Markdown 素材阅读、提取、整合到 `<domain>/wiki/`，执行必要的级联更新，并更新索引、日志和 qmd 搜索索引。

**核心职责边界**：ingest 只处理"新素材 vs 现有页面"的矛盾、补充与直接级联影响。全站性的陈旧扫描、孤立页面检测、跨页面矛盾排查由 `lint` 负责。

## 触发条件（必须使用的场景）

- "ingest 这篇文章"
- "处理 raw/ 里的新素材"
- "把 xxx.md 整合到知识库"
- "提炼 raw/articles/ 下的内容"
- "归档 raw/ 中的文件"
- "更新 wiki 内容"
- "补充 [[某页面]] 的内容"
- 任何涉及将 raw 素材转化为 wiki 页面的请求
- 用户要求"处理"、"整理"、"提炼" raw/ 目录下文件的场景

## 输入判断

### 用户指定了具体文件

解析用户提供的文件路径，确认文件存在于 `<domain>/raw/`（或子目录）下。

**单个文件：**
1. 读取文件内容
2. 询问用户是否需要**交互式提炼**：
   - "这篇文章需要我逐轮和你确认提炼角度、分类、重点吗？"
   - 需要（yes/y/是/需要）→ 进入交互式模式
   - 不需要（no/n/否/不用）或未明确回复 → 进入自动处理模式
3. 交互式模式下，向用户展示素材的核心观点、结构和识别出的知识点清单，同时标注聚合建议和匹配结果，确认后再写入 wiki

**多个文件（2个及以上）：**
- 默认自动批量处理，不逐轮交互
- 处理完所有文件后，统一报告结果（创建/更新/归档清单）

### 用户未指定具体文件

1. 扫描 `<domain>/raw/`（不包括 `archive/`），列出所有 `.md` 文件
2. 询问用户要处理哪些文件
3. 根据用户选择的数量，按上述逻辑处理

## 核心处理流程

### 步骤 0：读取领域规则

根据 raw 文件路径确认领域，先读取 `<domain>/domain.md`，明确该领域的分类体系、标签体系、qmd collection 和特殊约定。

### 步骤 1：读取素材

读取用户指定的 raw Markdown 文件。注意：raw/ 内容只读，处理过程中绝不修改原文件。

### 步骤 2：分析拆解

**核心原则：按需拆分，而非强制合并；但同级细粒度概念应优先聚合为上层主题页。**

#### 2.1 识别知识点

通读全文，识别可独立成页的知识点：

| 类型 | 说明 | 示例 |
|---|---|---|
| **实体（entities）** | 工具、产品、框架、组织 | rustup、Cargo、VS Code |
| **概念（concepts）** | 方法论、技术概念、机制 | 所有权、生命周期、Edition |
| **操作指南（recipes）** | 配置步骤、安装流程 | 镜像源配置、IDE 环境搭建 |
| **摘要（summaries）** | 整篇文章的高层次摘要 | 某篇文章的系统梳理 |

#### 2.2 概念聚合判断

多个同级细粒度概念若**满足 2 项及以上**即应聚合为上层主题页：

| 标准 | 说明 | 示例 |
|---|---|---|
| **内容量不足** | 单个概念核心内容少于 3-4 个关键要点 | 整型只有类型表和字面量写法 |
| **检索价值有限** | 用户通常以更大主题查询 | 搜"Rust 数据类型"而非"Rust 整型" |
| **概念层级较低** | 属于某上层主题的同级细分 | 整型/浮点型/布尔型都属于"标量类型" |
| **来源连续性** | 同一素材中连续介绍的同类概念 | 一篇文章连续介绍所有基础类型 |

**聚合示例**：
- ✅ 连续介绍整型、浮点型、布尔型、字符型 → 聚合为 `concepts/数据类型`
- ✅ 连续介绍数组、元组、切片 → 聚合为 `concepts/复合类型` 或归入 `数据类型`
- ❌ 详细介绍所有权系统 → 保持独立 `concepts/所有权`
- ❌ 深入解释生命周期 → 保持独立 `concepts/生命周期`

聚合页面使用清晰的内部标题组织各子概念，每个子概念保留足够的细节。

#### 2.3 独立成页判断

经过聚合判断后，剩余知识点按以下标准决定是否独立成页：

- 有**实质性描述**（不仅是名字提及，有功能说明、原理解释或使用方法）
- 有**独立检索价值**（用户单独搜索时，页面能提供完整信息）
- **不重复**：内容不与其他页面重复

**决策输出**：列出计划创建的所有页面，包括分类、标题、内容范围。对于聚合页面，注明聚合了哪些子概念。

**分类决策**：根据内容特征决定页面分类：

| 素材内容特征 | 目标分类 |
|---|---|
| 单篇文章/论文/视频的整体摘要 | `summaries/` |
| 人、组织、产品、框架 | `entities/` |
| 方法论、技术、理论 | `concepts/` |
| 工具对比、方法对比 | `comparisons/` |
| 子领域全景梳理 | `overviews/` |
| 最佳实践、决策建议 | `syntheses/` |
| 具体问题的操作步骤 | `recipes/` |

同一篇 raw 素材可以同时满足多个条件，产生多个不同分类的页面。例如一篇安装指南可同时产生 summaries、entities 和 recipes。

#### 2.4 每篇 raw 素材必须产出 summaries 页面（强制）

**无论素材内容以何种分类为主，每篇 raw 素材都必须在 `summaries/` 下产出至少一个页面。**

该页面是对整篇素材的高层次摘要，应覆盖素材的全部核心内容、结构和关键知识点，而非仅提炼其中某个分类的部分。它作为该素材的入口页，帮助后续快速回溯原始内容的全貌。

**创建规则**：
- 素材标题（或文件名）作为 summaries 页面标题的基础，必要时补充更精确的描述
- **命名规范**：summaries 页面标题和文件名不得添加"笔记"、"摘要"、"总结"等冗余后缀。标题应直接反映素材主题，如`所有权`、`引用和切片`，而非`所有权笔记`或`引用和切片摘要`
- 内容应结构化：涵盖素材的主题、核心论点、涉及的主要知识点清单、以及各知识点的简要说明
- 若素材同时产生多个分类页面，summaries 页面应作为它们的聚合入口，通过 `[[页面名]]` 链接指向各子页面
- summaries 页面的 `source_count` 固定为 1（每篇素材仅对应一个 summaries 页面）

**不创建 summaries 的例外情况**：
- 素材仅为一段代码片段、一条命令、或一张图表，没有可概括的论述内容
- 素材是另一篇素材的附录或补充说明，且已在主素材的 summaries 中完整覆盖

若不确定是否属于例外，**默认创建 summaries 页面**。

#### 2.5 拆分 vs 不拆分的判断

- 文章同时介绍 rustup、rustc、Cargo → 拆分为 3 个 entities + 1 个 summaries
- 文章只简单提到"使用 cargo build" → 在 summaries 或对应实体页面中提及，不单独创建 Cargo 页面
- 文章详细介绍 Edition 和语义化版本 → 分别创建两个 concepts 页面
- 文章包含 RsProxy 镜像源配置步骤 → 创建 recipes 页面

### 步骤 3：匹配现有页面与矛盾验证

#### 3.1 匹配现有页面

1. 读取 `<domain>/wiki/index.md`，获取所有现有页面标题与分类
2. 标题预筛：
   - **强匹配**：标题相同或语义等价 → 进入矛盾验证
   - **弱匹配**：部分重叠、同义词、同一上层主题 → 进入矛盾验证，标记"可能聚合/并入"
   - **无匹配**：全新主题 → 直接创建
3. **qmd 辅助匹配**（可选）：若标题未直接匹配但概念较复杂，可从知识库根目录执行 `qmd search -c <collection> "<关键词>"` 辅助发现相关页面；`<collection>` 必须从该领域 `domain.md` 读取

**分类隔离原则**：即使主题相同，不同分类的页面也应分别维护。如 `entities/Cargo` 与 `recipes/Cargo 安装配置` 是两个独立页面。

#### 3.2 矛盾验证与修正

**职责边界**：只处理"新素材 vs 现有页面"的矛盾。全站性的陈旧扫描、现有页面之间的相互矛盾由 `lint` 负责。

1. 读取现有页面内容
2. **主张比对**：提取新素材中的关键事实、数据、定义、版本信息，与现有页面逐条比对
3. **矛盾处理**（若发现不一致）：
   - **立即启用联网搜索**，验证双方主张（优先官方文档、权威来源、最新 release note）
   - **以验证结果为准，只写入正确版本**：新素材正确 → 覆盖；现有页面正确 → 保留；双方均不准 → 采用搜索验证后的最准确表述
   - **wiki 页面中不呈现矛盾过程、判断逻辑或"某来源认为"的并列句式**
4. **内容互补判断**（若无矛盾）：
   - 新素材覆盖方面与现有页面不重叠 → 作为新章节补充
   - 高度重叠（>70%）→ 仅增量更新（补充细节、更新 source_count）
   - 新素材是现有页面的子主题，且内容量 ≥ 3-4 个核心要点、有独立检索价值 → 创建子页面，在现有页面添加 `[[子页面]]` 链接

### 步骤 4：提炼内容

**交互式模式（单个文件 + 用户选择交互）：**
1. 向用户展示素材的核心观点、结构和知识点清单，标注聚合建议和匹配结果
2. 询问：知识点确认、聚合确认、匹配确认、提炼角度、重点标注、关联页面
3. 根据反馈生成 wiki 页面草稿，展示给用户确认后再写入

**自动模式（单个文件用户不交互，或多个文件批量）：**
1. 自主分析素材内容，提取关键信息
2. 自主识别知识点、决定分类、匹配现有页面、验证矛盾
3. 自主决定关联页面，直接生成所有 wiki 页面并写入

### 步骤 5：创建/更新 wiki 页面

创建或更新 `<domain>/wiki/` 下的页面。

**frontmatter 格式（必须遵守）：**

```markdown
---
title: 页面标题
date: YYYY-MM-DD
tags: [tag1, tag2]
source_count: N
---
```

- `title`：页面标题，简洁明了
- `date`：创建或最后更新日期
- `tags`：标签数组，使用英文小写，遵循各领域 `domain.md` 中的标签体系
- `source_count`：整数，该页面基于多少个 raw 素材（新建为 1，更新则递增）
- **普通 ingest 页面禁止**添加任何其他 frontmatter 字段（如 `source`、`author`、`url` 等）
- 例外：`type: query_archive` 只用于 Query 归档页，由 `query` skill 创建；ingest 不创建该类型页面，也不把 raw 素材并入 Query 归档页

**页面内容规范：**
- 内容必须提炼而非照搬原文，突出结构化和可检索性
- 使用 `[[维基链接]]` 语法创建交叉引用
- wiki 页面中的 `[[维基链接]]` **必须仅指向同一领域 `wiki/` 目录内的页面**，禁止链接到 `raw/`、`notes/` 或其他目录中的文件
- 新页面应至少引用 1-2 个现有页面
- **同一素材产生的多个页面之间应互相引用**，形成知识网络
- **素材不等于事实**：raw 素材中的主张需经交叉验证后方可写入 wiki。关键事实、版本信息、数据应做快速验证
- **图片处理**：raw 素材中的图片已统一存放于仓库顶层 `assets/` 目录。提炼时原样保留与知识点直接相关的图片（`![[xxx.png]]`），不要修改文件名、不要添加路径前缀；纯装饰性图片可丢弃；图片位置贴合语义

**来源章节（必须）：**

每个 wiki 页面底部必须包含 `## 来源` 章节，列出该页面所基于的原始材料，使用 Obsidian wiki 链接格式：

```markdown
## 来源

- [[<文件名>]]
```

**规范：**
- 放在页面最底部，在所有内容之后
- 使用 `[[<文件名>]]` 格式的 Obsidian 链接（**不含路径前缀和 `.md` 后缀**，Obsidian 会全局解析）
- 新建页面时，列出当前 ingest 的 raw 文件名（不含路径和扩展名）
- 更新已有页面时，读取现有来源章节，在列表末尾追加新来源（不重复已有的）
- 示例：`[[Rust基础语法]]`、`[[HTTP基础概述]]`
- `## 来源` 中的链接**只表示原始材料**，必须保持 raw 文件名语义，不得改写成 wiki 页面名、别名或路径形式
- 即使 raw 文件名与某个 wiki 页面同名，`## 来源` 仍必须保留原始材料名；这类冲突应通过重命名 wiki 页面解决，而不是改来源链接

**命名冲突规避**：wiki 页面文件名（不含路径）不得与原始素材文件名相同。若素材标题恰好是某个核心概念名称（如 `所有权.md`），wiki 页面应使用更精确的命名（如 `所有权系统.md`、`所有权规则.md`），避免 `[[<文件名>]]` 来源链接在 Obsidian 中产生歧义、无法跳转。

**判定顺序：**
- 先固定来源链接为 raw 文件名
- 再为 wiki 页面选择不会与 raw 冲突的文件名
- 不要反过来修改来源链接去适配 wiki 命名

### 步骤 6：级联更新（Cascade Updates）

主页面写入后、索引和日志更新前，检查同领域直接受影响页面。扫描半径只包括：本轮显式引用页面、同分类相近页面、同一素材产出的页面、直接父级 overview/synthesis/recipe/entity 页面，必要时用本领域 qmd 取最多 5 个候选。

允许自动做小改动：补交叉引用、补“相关页面”、更新直接受影响的概览/综合/配方局部段落、修正经验证的新旧事实冲突。禁止跨领域级联、全库陈旧扫描、修改 `notes/`/`raw/`、修改 `type: query_archive` 正文。

日志中固定写 `级联更新:`，按 `更新 / 跳过 / 候选未改` 记录结果；Query 归档页可能过期时只报告给用户或交给 lint。

### 步骤 7：收尾

1. 更新 `<domain>/wiki/index.md`：按分类小写标题组织，使用 `[[页面名]]`，无重复项。
2. 更新顶层 `index.md` 页面计数，排除 `wiki/index.md` 和 `wiki/log.md`。
3. 在 `<domain>/wiki/log.md` 尾部追加一条 Ingest 日志；每个 raw 文件一条，包含创建、更新、级联更新、修正、类型、来源。
4. 移动 raw 文件到 `<domain>/raw/archive/<类型>/`。
5. 从知识库根目录执行 `qmd update -c <collection>`；collection 和 root 必须从 `domain.md` 读取。缺 collection 时先创建：

```bash
qmd collection add <collection-root> --name <collection> --mask "**/*.md"
qmd context add qmd://<collection>/ "<领域描述>"
qmd update -c <collection>
```

6. 建议运行确定性 lint：

```bash
python .agents/skills/lint/scripts/wiki_lint.py --root /Users/songpengfei/knowledge --fix
```

## 完成检查清单

- [ ] 新/更新页面 frontmatter 正确，普通 ingest 页没有 `type: query_archive`
- [ ] 每篇有效 raw 产出 `summaries/` 页面，除非明确说明例外
- [ ] 同素材页面互链，并与现有页面建立合理交叉引用
- [ ] 已做同领域有限半径级联检查并记录
- [ ] 每个页面底部有 `## 来源`，来源链接保留 raw 文件名语义
- [ ] `wiki/index.md`、顶层 `index.md`、`wiki/log.md` 已更新
- [ ] raw 已归档，qmd 已更新

## 关键原则

- 不修改 `notes/`。
- `raw/` 内容只读，完成后移动到 `archive/`。
- 素材属于其所在领域，不自动跨领域 ingest。
- 内容丰富的素材可拆页；同级细碎概念优先聚合，避免 wiki 碎片化。
- 素材不等于事实；冲突主张要验证后再写入。
- wiki 页面文件名不得与 raw 文件名冲突，避免 Obsidian 来源链接歧义。
