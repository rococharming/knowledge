# 从 RAG 到 LLM Wiki 演示稿

> 用 Obsidian + LLM 构建会生长的个人知识库

## 第 1 页：从 RAG 到 LLM Wiki

大家好，我今天想要分享的主题是从 RAG 到 LLM Wiki，用 Obsidian + LLM 构建会生长的个人知识库。它不是单纯的 Obsidian 使用教程，而是使用 AI 进行的个人知识管理范式。

当我们手里有越来越多的文章、论文、视频、网页、笔记，并且这些资料还可能具有时效性时，将这些资料保存下来已经远远不够，而是希望沉淀为可复用、可演进的知识。

过去我们经常使用 AI 进行文件问答，或者通过 RAG 为大模型补充资料，这些方式很多时候都像第一次接触这些资料一样，需要重新检索和重新理解。

LLM Wiki 要解决的问题是：如何让 LLM 像一个长期知识库维护者一样，把资料逐步编译成一套结构化、相互链接、会持续生长的 Wiki。

今天的分享将围绕 RAG 的局限、LLM Wiki 的核心思想、以及如何在 Obsidian 落地的路线展开。

## 第 2 页：传统 RAG 的工作原理

首先我们进入传统 RAG 的工作原理。
大模型的知识主要固化在模型参数中，它不仅受训练数据截止时间限制，也无法直接覆盖企业文档、个人资料等私有领域数据。

所以一提到构建 AI 知识库，我们一开始想到的通常就是 RAG。RAG 是一种通过在模型生成答案之前引入外部知识，使得大模型能够基于最新资料或私有文档回答问题的方法。

传统 RAG 通常包含两个阶段。第一个阶段是知识库构建：先把原始文档切分为多个文本片段，再用嵌入模型把文本片段转换为向量，最后把向量和相关元数据存入向量数据库。

第二个阶段是查询：用户提出问题后，系统把问题也转换成查询向量，从向量数据库中检索语义最相关的文本片段，再把检索结果和用户问题一起写入提示词，最后由大模型根据这些上下文生成答案。

所以 RAG 的关键价值，是让模型在回答之前临时拿到一批外部资料。但它本质上还是一种“查询时检索”的机制，这一点会引出后面我们要讨论的局限。

## 第 3 页：GraphRAG：让知识片段之间有关系

后来，为了增强跨文档关联能力，GraphRAG 在传统 RAG 的基础上引入了知识图谱。就像属性图一样，仅仅通过向量之间的相似度来比较语义还远远不够，节点之间还有各种各样的关系。

GraphRAG 不再把文档保存为相互独立的文本块，而是通过信息抽取模型，从文档中识别实体、属性和关系，再将这些知识组织成图结构。

例如，多篇文档可能分别描述某项技术的提出者、核心方法、应用场景和局限。传统 RAG 只能分别检索这些文本片段，而 GraphRAG 可以通过实体和关系将它们连接起来，形成相对完整的知识网络。

相较于传统 RAG，GraphRAG 的主要改进在于：检索对象不再只是孤立的文本片段，还可以是实体、关系、图社区及其摘要。因此，GraphRAG 主要解决的是知识之间如何建立关联的问题，但没有完全改变查询阶段动态检索和生成的基本模式。

## 第 4 页：Agentic RAG：让 Agent 自主规划检索

Agentic RAG 则由 Agent 自主规划检索，将向量检索、关键词搜索、图查询、网页搜索和数据库查询等能力封装为工具，由 Agent 根据任务需要自主调用。

在 Agentic RAG 中，Agent 不必依赖单次检索，而是可以根据中间结果不断调整策略。这种方式将固定的检索流水线转变为动态决策过程，使系统能够处理更复杂、更开放的任务。

但 Agentic RAG 并没有改变知识使用的基本范式。因此，Agentic RAG 主要解决的是如何更加智能地获取知识，而不是如何持续积累和演化知识。

## 第 5 页：RAG 优化了访问能力，但缺少知识积累

因此，现有 RAG 技术主要围绕检索质量、知识关联和检索策略进行优化，但缺少持续演化的知识沉淀机制。

即使文档数量不断增加、查询次数不断累积，知识库的内部结构也可能没有发生实质变化。原始知识依然主要以文本块、向量、实体或关系的形式存在，直到用户提问时才被临时检索和组织。

这意味着 RAG 系统通常具备的是知识访问能力，而不是完整的知识积累能力。Karpathy 指出 RAG 的三个痛点问题：没有知识积累、跨文档推理弱、工程链路过重。

LLM Wiki 关注的正是这一方向：将大模型从查询阶段的临时知识使用者，进一步转变为知识体系的持续构建者和维护者。

## 第 6 页：Obsidian：人和 LLM 共同使用的知识 IDE

LLM Wiki 的核心是 Agent 加 Markdown 文件目录。因此理论上，我们完全可以让 Agent 直接操作一个本地文件夹。

但普通文件夹更像存储层，它适合 Agent 读写，却不适合人长期浏览和审阅。所以这里使用 Obsidian 来管理本地知识库。

它主要有三大优势：第一，更好浏览，Agent 写出的双向链接在 Obsidian 里可以直接点击跳转；第二，更好审阅，可以查看反向链接、关系图谱和孤立页面；第三，不锁数据，Obsidian 的底层仍然是本地 Markdown 文件，Agent 可以直接改，Git 可以直接管，也可以随时迁移。

此外，Obsidian 还推出了 Obsidian CLI，使得 Agent 更方便、更规范地操作 Obsidian 仓库。用 Karpathy 的话来说：Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

## 第 7 页：LLM Wiki 的三层架构

LLM Wiki 可以分为三层。第一层是原始资料，也就是 raw 目录。它保存来源文档集合，可以是文章、技术博客、论文、图片、视频等。这一层是不可变的，LLM 从中读取，但不修改它们。

第二层是 Wiki 页面，也就是 wiki 目录。它是由 LLM 生成的 Markdown 文件目录，可以再细分为 summaries 摘要、entities 实体、concepts 概念、comparisons 比较、overviews 概览、syntheses 综合结论等等。

第三层是 schema，例如 Claude Code 的 CLAUDE.md，或者 Codex 的 AGENTS.md。它是 Wiki 的维护规范文档，用来告诉 LLM 这个 Wiki 的构建方式、命名约定，以及在摄入素材、回答问题、维护 Wiki 时应该遵循什么工作流。

这是非常关键的配置文件，因为它让 LLM 成为有纪律的 Wiki 维护者，而不是普通的聊天机器人。

## 第 8 页：LLM Wiki 的核心操作

管理 LLM Wiki 知识库主要有三个操作，分别是 Ingest、Query 和 Lint。

Ingest 是摄取，也就是将新的素材放入 raw 原始资料集合，并告诉 LLM 处理它。一个典型流程是：LLM 阅读素材，生成摘要页面，更新 index，更新相关的实体页面和概念页面，并在 log 中追加条目。

Query 是查询。你向 Wiki 提问，LLM 搜索相关页面，阅读它们，并综合出一个带引用的答案。这里有一个重要洞察：好的答案可以作为新页面归档回 Wiki。你要求的一次对比、一次分析、一个你发现的关联，都不应该消失在聊天记录里。

Lint 是校验。定期让 LLM 对 Wiki 做健康检查，查找页面矛盾、陈旧说法、孤立页面、缺失交叉引用，以及可以通过网络搜索填补的数据空白。

## 第 9 页：index.md 与 log.md：导航和时间线

在 LLM Wiki 中，有两个特殊文件会帮助 LLM 和你在 Wiki 增长时进行导航，它们是 index.md 和 log.md。

index.md 是内容导向的。它是 Wiki 中所有内容的目录，每个页面都列出链接、一句话摘要，以及可选的元数据，比如日期或素材数量。LLM 在每次 ingest 时会更新它。回答 query 时，LLM 会先阅读 index.md，找到相关页面，然后再深入阅读。

log.md 则是时间导向的。它是按时间顺序、仅追加的记录，用来记录发生了什么、什么时候发生，例如 ingest、query、lint。log 提供了 Wiki 演进的时间线，也帮助 LLM 理解最近做过什么。

## 第 10 页：Obsidian Web Clipper：把网页变成 raw 素材

接下来是 Obsidian Web Clipper。它是 Obsidian 官方推出的浏览器插件，可以把网页内容以 Markdown 形式直接保存到 Obsidian Vault，方便离线阅读、标注和整理。

对 LLM Wiki 来说，Web Clipper 的位置非常重要，它更像是 raw 素材层的入口。当我们看到一篇网页文章时，不只是把链接收藏起来，而是把正文、标题、作者、发布日期、URL 等元数据一起保存成 Markdown。

它还支持网页高亮和选择保存，也有类似阅读器模式的干净视图，可以去掉广告、侧边栏等干扰。这样，当我们后续让 LLM 进行 Ingest 时，它面对的是一个相对干净、结构化、可追溯的原始素材。

## 第 11 页：模板与变量：让剪藏内容更规范

Web Clipper 的另一个关键能力是模板与变量。模板决定了剪藏内容以什么格式保存到 Obsidian。它不是一段固定文本，而是一套可以复用的保存规则。

模板中的变量会在剪藏网页时被替换为当前页面中的实际数据。比如 title 会变成页面标题，url 会变成当前页面 URL，author 会变成作者，content 会变成正文内容。

不同网站提供的数据并不完全相同，所以 Web Clipper 支持多类变量来源。预设变量比较简单通用，Meta 变量适合提取网页 head 中的描述和封面信息，Schema.org 变量来自 JSON-LD 结构化数据，选择器变量可以通过 CSS 选择器精确提取页面元素，提示变量则可以调用语言模型分析页面。

这件事对 LLM Wiki 很重要。因为原始素材越规范，后续 Ingest 时 LLM 就越容易理解来源、正文、日期、作者和上下文。

## 第 12 页：解释器：剪藏前先让模型处理网页

Web Clipper 还有一个很有用的能力，叫解释器。普通 Web Clipper 的工作方式是读取网页内容，根据模板整理格式，然后保存到 Obsidian。

普通模板变量直接读取网页中的现成数据，比如 title、url、content。这些变量不会让 AI 处理内容，只是提取网页已有的信息。

启用解释器后，流程会多一步：Web Clipper 会把网页内容和提示词发送给模型，模型根据提示词返回摘要、翻译、提取结果或改写结果，再把这些结果填入模板，最后保存到 Obsidian。

解释器提示变量的语法是双大括号里面写一段自然语言提示词，例如“用三句话总结这篇文章”。它的价值在于，剪藏进入 raw 层之前，已经可以完成一次轻量的 AI 处理。

不过它也有边界：解释器需要配置提供商、模型和 API 密钥，运行速度会更慢，也会消耗 Token 和费用。

## 第 13 页：每日工作流：让知识持续进入 Wiki

如果把前面这些概念落到日常实践中，LLM Wiki 可以变成一个很轻量的工作流。

第一步是网页剪藏。看到有价值的文章、博客、资料，就用 Obsidian Web Clipper 把正文、元数据和高亮保存到 raw 目录。

第二步是执行编译，也就是让 LLM 进行 Ingest。它会阅读素材，生成摘要，更新 index，补充相关的概念页面、实体页面和交叉引用。

第三步是直接从 Wiki 提问。这个时候，LLM 不再只是面对原始网页，而是先读已经整理过的 Wiki 页面，再给出综合回答。

第四步是归档答案。如果某个回答质量很高，比如一次对比、一次分析、一个新的关联发现，就可以把它整理成新的 Wiki 页面。

第五步是定期 Lint，自建修复。让 LLM 检查死链、矛盾、孤立页面、陈旧说法和缺失的交叉引用。

## 第 14 页：从检索拼凑，到知识编译

信息增长的速度，早已超过了人类手动整理信息的速度。单纯的“检索-拼凑”模式，可以让你瞬间找到一百篇论文的相关片段，却很难帮你从中提炼出一个真正连贯的知识框架。快速翻书和深度理解之间，始终隔着一道鸿沟。

而 LLM Wiki 所代表的“编译”思路，正在被越来越多的项目和产品采纳。它的本质，是把 LLM 的理解能力前置：将理解成本从每次查询的时刻，转移到内容摄入的那一刻。

每多摄入一份材料，知识不是被塞进数据库，而是被编织进一张不断生长的网。这正是知识积累的复利效应。

## 第 15 页：技术融合方向：不是替代，而是组合

最后看一下技术融合方向。第一点，LLM Wiki 并不是 RAG 的替代品，两者可以结合。

RAG 依然适合处理海量文档、快速检索和低延迟访问；而 LLM Wiki 更适合把高价值材料沉淀为结构化知识网络。所以一个更合理的组合是：RAG 作为外围检索通道，LLM Wiki 作为核心知识沉淀层。

第二个方向是多模态 LLM Wiki。也就是从纯文本走向多模态知识的统一编译。未来不只是文章和 Markdown，图片、视频字幕、音频转写、会议记录、产品截图，都可以进入同一个知识编译流程。

最终的目标，是让不同模态的信息都能被整理为可查询、可链接、可演化的知识结构。

## 第 16 页：总结：从知识访问，到知识积累

最后我们简单总结一下。RAG 解决的是知识访问问题。它让模型可以在回答之前拿到外部资料，适合快速检索最新信息、企业文档和个人资料。

LLM Wiki 关注的是知识积累问题。它不是只在查询时临时拼接片段，而是把资料逐步编译成结构化、相互链接、可演化的 Markdown Wiki。

Obsidian 则提供了一个合适的承载层。它底层是本地 Markdown，适合 LLM 读写；同时又有双向链接、图谱、属性和插件，适合人浏览和审阅。

所以真正的目标不是保存更多资料，而是让资料变成可复用、可演进的知识。
